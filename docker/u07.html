OverlayFS、挂载与容器文件视图

容器看到的根目录是几层只读层加一层可写层合起来的，挂载会盖在上面。

先想一想

镜像的 /app/config.yml 里有默认配置，你用 -v 挂了一个目录到 /app，结果容器里原来的代码全不见了。文件去哪了？

原理图解推演迁移面试小结
01原理

原理

一个目录，几层来源

overlay2 把镜像的只读层作为 lowerdir，把容器的可写层作为 upperdir，合成一个 merged 目录，这就是容器的根文件系统。读文件时从上往下找，第一个找到的就是你看到的。

镜像层被所有基于它的容器共享，所以启动很快，也不占额外空间。

写的时候才复制

修改一个来自镜像的文件时，内核先把整个文件复制到可写层再改，这叫写时复制。大文件改一个字节，也要先复制整个文件，这是数据库不该把数据放在可写层的原因之一。

删除来自镜像的文件时，可写层里会放一个 whiteout 标记把它遮住，下面那层的原文件其实还在。

挂载会遮住原来的目录

绑定挂载和卷都是挂在 merged 视图之上的。挂到 /app，容器看到的就是挂载源的内容，镜像里 /app 的文件被盖住了，并没有被删掉。

有个例外：一个空的命名卷第一次挂到容器里有内容的目录时，Docker 会把镜像里的内容复制进卷。绑定挂载不会这样做。

03推演

先猜，再看结果

镜像的 /app 下有代码。分别执行 docker run -v appdata:/app（新的空命名卷）和 docker run -v $PWD/empty:/app（空的宿主目录），容器里的 /app 各是什么？

空命名卷第一次挂载时，Docker 会把挂载点原有内容复制进卷，所以能看到代码；之后卷就有了自己的生命周期，镜像更新不会再同步进来。绑定挂载直接显示宿主目录，空目录就是空的。

示例输出 · 只读
$ docker run --rm -v appdata:/app app ls /app
app.py  requirements.txt
$ docker run --rm -v $PWD/empty:/app app ls /app
$
04迁移

换个场景

开发时把源码绑定挂载到 /app，结果容器报找不到 node_modules，而镜像构建时明明装过。怎么解释，怎么修？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

node_modules 装在镜像的 /app/node_modules 里，整个 /app 被宿主目录遮住了，宿主机上又没有这个目录。

常见做法是再给 /app/node_modules 单独挂一个卷，让它盖回去；或者把依赖装到 /app 以外的路径。关键是理解挂载会遮蔽，而不是合并。

05面试

讲给面试官听

容器的可写层和卷有什么区别？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

可写层是 overlay 的 upperdir，跟着容器的生命周期，删容器就没了，写入还要经过写时复制，性能不适合重 IO。卷由 Docker 管理，生命周期独立于容器，直接挂进容器、绕开 overlay，适合数据库和需要保留的数据。

追问：删除镜像里的文件为什么不省空间？

可写层只是放一个 whiteout 标记遮住它，底下的只读层没变。镜像层里的文件也一样，要在构建阶段就不放进去。

追问：挂载会删掉镜像里的文件吗？

不会，只是遮住。卸载或换个容器不挂这个目录，原内容就又能看到了。

06小结

带走这几句

  1. 容器根目录是镜像层与可写层的合并视图。
  2. 修改镜像文件会触发整文件复制，删除只是遮住。
  3. 挂载覆盖而非合并；只有空命名卷首次挂载会复制原内容。
