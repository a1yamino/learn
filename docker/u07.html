OverlayFS、挂载与容器文件视图

用新增、删除和挂载遮蔽三个观察，分清镜像层、容器可写层与外部存储。

建议 55 分钟，含实验；按观察结果调整进度。

先想一想

容器里删除 /app/version.txt 后文件消失了；同一镜像启动的新容器却仍能读到它。删除到底发生在哪里？把卷挂到 /app 又为什么看不见原文件？

  • 解释 lower 只读层、upper 可写层与合并文件视图，并说出删除的逻辑含义。
  • 用 docker diff 验证容器文件修改没有写回镜像。
  • 解释卷或 tmpfs 挂载为何会遮住原路径内容，以及它们的寿命边界。
实验前提

需要 Linux 容器 Docker Engine 和可拉取的基础镜像；从仓库根目录开始。先查看 Docker 当前存储驱动：可能是 overlay2，也可能使用 containerd snapshotter；本课不假定宿主目录路径或 /var/lib/docker 内部布局。Desktop 存储位于 Linux VM。本实验只用 Docker API，不直接修改宿主存储。

01 · MODEL

建立因果模型

联合视图把只读镜像与单容器写入叠起来

在使用 OverlayFS 的实现中，镜像层构成 lower，容器可写层是 upper，进程看到合并后的目录。读取优先得到上层版本，首次修改 lower 文件时可能发生 copy-up；新文件只进入该容器的 upper。具体层路径与 snapshotter 实现由 Engine 版本决定，不应写死为某个宿主目录。

即使当前驱动不是 overlay2，Docker 仍给出镜像内容与容器写入分离的用户可见语义。先探测 docker info，再决定是否继续讨论内核 OverlayFS 细节；docker diff 证明文件视图变化，不单独证明底层实现是 OverlayFS。

删除下层文件需要上层记录“不可见”

镜像中的文件不能因为一个容器执行 rm 就被改写。OverlayFS 在上层记录 whiteout，让合并视图隐藏 lower 的对应文件；docker diff 的 D 表示该容器视图中删除。删掉容器可写层后，新容器从原镜像看到原文件。

镜像层不可变不是说运行时文件系统绝对只读。只有 read_only: true 或等效配置才禁止写入根文件系统；即便根文件系统只读，单独挂载的卷和 tmpfs 仍可能可写。

挂载在合并视图之上覆盖目标路径

volume、bind mount 与 tmpfs 都是在目标路径呈现另一个文件系统视图。挂到已有 /app 时，原镜像 /app 内容会暂时被遮蔽，不是被删除。卸掉挂载或换一个没有该挂载的容器仍可读原内容。

Docker 命名卷首次挂载到非空镜像目录时可能复制已有内容，tmpfs 则从空视图开始；本课用 tmpfs 做清晰对照，不把它误解成删除 upper 文件的 whiteout。

存储驱动、挂载和数据库持久化要分别选

可写层随容器对象删除；volume 生命周期由卷管理命令和 Compose 的 down -v 等决定；tmpfs 只存在于运行期，停止即丢失。bind mount 直接指向宿主路径，其权限、路径和备份责任另算。

数据库应放在明确管理的卷中，并通过一致性备份与恢复验证，而不是依赖保留某个容器可写层。选择持久位置前先写清楚需要跨 stop、rm、重建还是跨主机迁移。

03 · EXPERIMENT

用文件差异和 tmpfs 遮蔽验证三层边界

从仓库根目录执行；使用本课镜像 learn-u07:lab 与独立容器 learn-u07-layer。为了写入镜像中的 /app，本课对照容器显式 --user 0；共用应用仍以 UID 10001 运行。容器创建后默认根文件系统可写；不使用 Compose 的 read_only 配置。

运行之前，先预测

在容器中删除镜像自带的 version.txt 后，docker diff 会报告什么？从同一镜像新建容器还能看到原文件吗？tmpfs 挂到 /app 是删除文件还是遮蔽目录？

01 · 先探测当前实际存储后端

docker info --format 'Driver={{.Driver}} DriverStatus={{json .DriverStatus}}'
cd docker/labs
docker build -t learn-u07:lab .

观察：记录实际 Driver/DriverStatus；若后端不是 overlay2，应查当前 Engine 的 containerd snapshotter 信息，不直接推断宿主 overlay2 目录。

解释：讲解 OverlayFS 机制前先确定环境，避免把某个存储路径当作普遍 API。

02 · 确认镜像原文件确实存在

docker run --rm --entrypoint cat learn-u07:lab /app/version.txt
docker image inspect learn-u07:lab --format 'Id={{.Id}} Layers={{len .RootFS.Layers}}'

观察：从新容器可读版本内容；记录本机镜像 ID，不要求固定层数。

解释：建立 lower 文件的基线，否则后续 D 事件无法解释。

03 · 在独立容器里新增并删除文件

docker create --name learn-u07-layer --user 0 --entrypoint python learn-u07:lab -c 'from pathlib import Path; old=Path("/app/version.txt"); print("ORIGINAL",old.read_text().strip()); old.unlink(); Path("/app/u07-added.txt").write_text("from this container\n")'
docker start -a learn-u07-layer
docker diff learn-u07-layer

观察：docker diff 应报告 /app/version.txt 的 D 与 /app/u07-added.txt 的 A；路径前缀可能另有目录修改记录。

解释：逻辑删除由当前容器上层隐藏 lower；新增只属于当前容器。

04 · 用新容器验证原镜像未被改写

docker run --rm --entrypoint cat learn-u07:lab /app/version.txt
docker inspect -f 'ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} Image={{.Image}}' learn-u07-layer

观察：新容器仍能读取版本；旧容器的根文件系统非只读，但其写入没有改变镜像。

解释：区分镜像层不可变与容器根文件系统可写。

05 · 挂载空 tmpfs，观察路径遮蔽

docker run --rm --mount type=tmpfs,destination=/app --entrypoint sh learn-u07:lab -c 'if test -e /app/version.txt; then echo UNEXPECTED_VISIBLE; exit 1; else echo HIDDEN_BY_TMPFS; fi; ls -la /app'
docker run --rm --entrypoint cat learn-u07:lab /app/version.txt

观察：挂载 tmpfs 的容器中原文件暂不可见，未挂载的新容器仍能读到；不要把暂时遮蔽误认成镜像文件删除。

解释：挂载目标路径决定进程的文件视图，其语义独立于 lower/upper 的写入差异。

本实验的清理范围与命令
docker rm -f learn-u07-layer
docker image rm learn-u07:lab
# 只删除本课容器与本课镜像标签；不运行 prune 或改宿主存储。
04 · TRANSFER

换一个条件，还能解释吗

订单应用在默认 Compose 中尝试写 /app/cache.json 失败，但写 /tmp/cache.json 成功。重建后 /tmp 内容消失，/data/orders.db 仍在。你会如何解释三个路径？

提交这些证据

  • 检查容器 HostConfig.ReadonlyRootfs、Mounts 的类型与目标路径。
  • 记录 /app、/tmp、/data 的写入错误或成功，以及重建前后数据。
  • 区分容器对象 stop/start、rm、Compose down 与 down -v 的操作。
对照参考推理

/app 位于只读根文件系统，故写入失败；/tmp 在当前 Compose 被单独挂为 tmpfs，可写但运行期结束会消失。

/data 是命名卷，独立于可写层与 tmpfs；普通重建保留卷时数据可留下，down -v 才会删除该项目的卷。

若缓存需要跨重建，应改用专门卷或可再生策略；若需要持久订单数据，必须另做一致性备份与恢复演练。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 解释容器里删除镜像文件、写入新文件和挂载卷时文件视图分别怎样变化。

查看参考回答与递进追问

在 OverlayFS 路径中，镜像层是 lower，单容器写入进入 upper，合并视图让应用看到结果。新增进 upper；删除 lower 文件由上层 whiteout 隐藏，不改镜像，所以新容器仍能读原文件。把卷或 tmpfs 挂到某路径会遮蔽那里原有视图，挂载消失后原内容仍在。先查存储后端，再用 docker diff、inspect Mounts 与新容器对照；不把后端宿主路径当稳定 API。

追问 1：read_only: true 时 /tmp 还能写吗？

若 /tmp 单独挂为可写 tmpfs，可以；根文件系统只读与挂载点权限是两层设置。

追问 2：docker diff 的 D 是否表示镜像层字节被擦掉？

不表示。它报告容器文件视图相对镜像的删除，OverlayFS 可用 upper whiteout 隐藏 lower。

追问 3：为什么不把数据库直接存容器可写层？

rm 或重建会丢失该对象的可写层，难独立备份和迁移；应使用明确管理的卷并验证恢复。

容易混淆：“镜像层不可变，所以容器里不能写文件。”容器通常有可写层；只读根文件系统需单独配置。

06 · EVIDENCE

用证据判断是否掌握

  1. 镜像层与每个容器的可写层分离；当前容器删除不改原镜像。
  2. docker diff 描述容器视图变化，不承诺具体存储后端。
  3. 挂载会遮蔽目标路径，tmpfs、卷和可写层寿命不同。
  4. 先探测存储驱动，再谈具体 OverlayFS 实现路径。
