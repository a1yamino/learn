NAT、防火墙与回程：一个包的完整路径

端口发布靠目的地址改写，出站靠源地址伪装，两边都依赖连接跟踪。

先想一想

用 ufw 只放行了 22 端口，可 -p 8080:80 发布的服务依然能从外网访问。防火墙为什么没拦住？

01原理

原理

入站：改写目的地址

-p 8080:80 会在 nat 表的 DOCKER 链里加一条 DNAT 规则：发往宿主机 8080 的包，目的地址改成容器 IP 的 80。改写发生在 PREROUTING，早于 INPUT 链。

改写之后，这个包对内核来说是要转发给另一个网络空间的，走的是 FORWARD 链，而不是 INPUT。ufw 默认管的是 INPUT，所以拦不住。

出站：伪装源地址

容器访问外网时，源地址是网桥内的私有 IP，外面的服务器回不了包。POSTROUTING 里的 MASQUERADE 把源地址换成宿主机出口网卡的地址。

连接跟踪记住了每一次改写，回包回来时自动改回去，送到正确的容器。

控制暴露面的正确位置

Docker 留出了 DOCKER-USER 链，在 FORWARD 里先于 Docker 自己的规则执行，用来限制谁能访问发布的端口。

更简单的办法是只绑定到需要的地址：-p 127.0.0.1:8080:80 只让本机访问。服务只给其他容器用，就干脆不发布端口。

同一台机器访问自己发布的端口

从宿主机本身访问 localhost:8080，包不经过 PREROUTING，而是走 OUTPUT 链，Docker 在那里也装了 DNAT 规则。另外，默认还有 docker-proxy 这个用户态进程监听着发布的端口，用来处理一些内核规则覆盖不到的情况，比如回环地址。

所以“外部访问不了，本机能访问”或者反过来，往往是因为两条路径走的规则不同。排查时先分清请求从哪里来。

连接跟踪表也会满

每一个经过 NAT 的连接都要在 conntrack 表里占一条记录。高并发短连接的服务，表可能被占满，新连接直接被丢弃，内核日志里出现 nf_conntrack: table full, dropping packet。

处理方法是调大 nf_conntrack_max、缩短超时，或者让客户端复用长连接，减少新建连接的数量。

走一遍：外部请求的往返

  1. 客户端 203.0.113.9 访问宿主机 10.0.0.5:8080。PREROUTING 中的 DNAT 把目的地址改成 172.17.0.2:80，conntrack 记下这次改写。
  2. 包进入 FORWARD 链，先过 DOCKER-USER，再过 Docker 自己的规则，被放行到网桥，送进容器。
  3. 容器回复给 203.0.113.9。回包经过 conntrack 时，源地址被自动改回 10.0.0.5:8080，客户端看到的是一次普通的回应。

常见误区

ufw 默认拒绝入站，就能挡住发布的端口
发布端口的流量经过 DNAT 后走 FORWARD 链，ufw 默认管理的 INPUT 链看不到它。需要在 DOCKER-USER 里写规则，或只绑定到特定地址。
容器出站不经过 NAT
默认 bridge 网络的出站流量都会被 MASQUERADE，外部看到的源地址是宿主机。要给容器固定出口地址，需要额外配置。

放到生产里

默认把开发和内部服务绑定到 127.0.0.1，确实需要对外再显式绑定到对外网卡地址。

改动 iptables 或防火墙规则时要了解 Docker 也在管理同一套规则，重启 dockerd 会重新写入它自己的链。

03推演

先猜，再看结果

服务以 -p 127.0.0.1:8080:80 发布。另一台机器访问这台主机的 8080，会怎样？

DNAT 规则只匹配目的地址为 127.0.0.1 的包，从外部网卡进来的流量不匹配，也就不会转给容器。这是限制暴露面最直接的方式。

示例输出 · 只读
$ docker port web
80/tcp -> 127.0.0.1:8080
# 另一台机器
$ curl -m 3 http://10.0.0.5:8080
curl: (7) Failed to connect to 10.0.0.5 port 8080
04迁移

换个场景

容器能 ping 通 8.8.8.8，但 curl https://example.com 卡住不返回。宿主机访问一切正常。你怎么拆解？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

能 ping 通 IP，说明出站路由和伪装基本正常。卡住更像是 DNS 或者 MTU 问题：先用 getent hosts example.com 看解析，再看是不是大包被丢。

如果宿主机在 VPN 或隧道上，网桥的 MTU 1500 大于实际路径，TLS 握手的大包会被丢弃，表现正是“小包通、大包卡”。可以调小网络的 MTU 来验证。

05面试

讲给面试官听

为什么 Docker 发布的端口会绕过 ufw？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

端口发布用的是 nat 表的 DNAT，在 PREROUTING 阶段就把目的地址改成了容器 IP。这之后包要转发到另一个网络空间，走 FORWARD 链，而 ufw 默认规则在 INPUT 链。要限制访问，应该在 DOCKER-USER 链里写规则，或者发布时只绑定到需要的地址。

追问：MASQUERADE 和 SNAT 有什么区别？

都是改源地址。SNAT 指定固定地址；MASQUERADE 自动用出口网卡的当前地址，适合动态 IP。

追问：回包是怎么找到容器的？

conntrack 记录了每个连接的原始地址和改写后的地址，回包到达时按记录反向改写，再路由给容器。

06小结

带走这几句

  1. 端口发布是 DNAT，过滤要在 FORWARD/DOCKER-USER 做。
  2. 出站靠 MASQUERADE，回程靠连接跟踪。
  3. 绑定到 127.0.0.1 或不发布，是缩小暴露面的首选。
