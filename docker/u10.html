NAT、防火墙与回程：一个包的完整路径

解释端口发布的目的地址改写、转发过滤、出站伪装与连接跟踪，并辨认本机请求和外部请求的路径差异。

建议 55 分钟，含实验；按观察结果调整进度。

先想一想

为什么关闭宿主机 INPUT 的 8080 仍可能挡不住发布端口，而绑定 127.0.0.1 后外部又访问不到？本机 curl 能否证明外部流量经过了相同路径？

  • 画出入站 DNAT 与回包反向改写的五元组变化。
  • 解释为什么发布端口不一定经过 INPUT 规则。
  • 先识别后端与访问来源，再选择能证明过滤生效的观察。
实验前提

原理适用于常见 bridge 网络；实机实验限定独立原生 Linux、rootful Docker、iptables 防火墙后端，已安装 curl、iptables、conntrack，且有 sudo。Desktop 或 nftables 用户可阅读模型并按本机后端另取证，不能套用下面链名。

01 · MODEL

建立因果模型

发布端口先改目的地址，再决定转发

对常见 iptables bridge 发布路径，外部包进入宿主机后在 nat PREROUTING 相关规则中匹配发布端口，DNAT 将宿主地址:发布端口改为容器地址:目标端口。随后路由决定把它转发给网桥，过滤发生在 FORWARD 相关链，而不是当作发往宿主进程的 INPUT 流量。

因此仅检查 INPUT 的端口拒绝规则不足以证明容器入口被限制。iptables 后端可在 DOCKER-USER 等受支持位置过滤；进入该链时目的地址通常已经 DNAT，若需按原始发布端口匹配，要用连接跟踪的原始目的信息。不要随意清空 Docker 自动创建的规则。

conntrack 保存原始与回复方向

连接跟踪记录协议及原始/回复方向的地址与端口关系。外部客户端看到自己连接宿主发布端口，容器收到的是发往容器端口的请求；回包经过反向转换，客户端仍看到同一对端。NAT 并不是在每次响应中重新猜测它属于哪个客户端。

容器访问外网时，常见 bridge 出站 MASQUERADE 把容器源地址换成宿主出口地址。对外服务看到的通常是宿主地址；返回流量通过连接跟踪回到容器。直连路由、host 网络、IPv6 等配置可能有不同路径，不能把 MASQUERADE 当成所有 Docker 网络的定义。

访问位置与防火墙后端是模型前提

本机产生的请求经过本机 OUTPUT 路径，外部到达网卡的包走 PREROUTING；localhost 发布还可能涉及用户态代理。观察本机成功只能证明本机入口可用，不能替代来自另一台机器的准入测试。

绑定 127.0.0.1 限定宿主发布入口的绑定范围，但并不等于连 Docker 主机本身也无法访问容器 IP。iptables 与 nftables 后端的表、链及用户过滤接入点不同。先记录 Docker 版本、后端、网络与来源，再解释规则；不要把固定链名或 UFW 的表现背成跨环境保证。

03 · EXPERIMENT

在限定后端上只读观察一次本机端口发布

仅在满足本课环境前提的 Linux 实验机执行。Docker 主机无其他名为 learn-u10-web 的容器，本机 18080 空闲。本实验不修改系统防火墙，只读查询 Docker 为实验容器创建的规则。

运行之前，先预测

本机访问 127.0.0.1:18080 与直接访问容器 IP:80 都可能成功；前者是否经过 PREROUTING？先写出你的路径预测。

01 · 记录环境并创建限定入口

docker version --format "{{.Server.Version}}"
docker info --format "{{.Driver}} {{json .SecurityOptions}}"
sudo iptables -t nat -S DOCKER
docker run -d --name learn-u10-web -p 127.0.0.1:18080:80 nginx:stable-alpine

观察：版本、存储信息与现有 DOCKER 链可记录；若 DOCKER 链不存在，先确认是否为 nftables 后端，不继续猜测。新容器应运行。

解释：先确认观察工具对应实际后端；只创建本课专属资源。

02 · 核对绑定地址和目标端口

docker port learn-u10-web
docker inspect learn-u10-web --format "{{json .NetworkSettings.Networks}}"
curl -fsS -o /dev/null -w "%{http_code}
" http://127.0.0.1:18080

观察：发布结果应显示 127.0.0.1:18080；HTTP 返回成功状态。记录实际容器地址。

解释：将声明、实际绑定与应用响应关联，避免把 EXPOSE 当端口发布。

03 · 分别观察本机与入站规则入口

sudo iptables -t nat -S OUTPUT
sudo iptables -t nat -S PREROUTING
sudo iptables -t nat -S DOCKER | grep 18080
sudo iptables -S DOCKER-USER

观察：记录发布规则的目标地址、端口和跳转；具体规则顺序由本机版本决定。DOCKER-USER 的空或放行规则也要记录。

解释：本机 curl 不能单独证明 PREROUTING 行为；规则路径与访问来源必须一致。

04 · 寻找原始与回复方向的证据

curl -fsS http://127.0.0.1:18080 >/dev/null
sudo conntrack -L -p tcp 2>/dev/null | grep 18080

观察：如命中连接条目，比较原始方向与回复方向两组地址；若 localhost 由用户态代理处理，可能看到两段连接，或没有对应 NAT 条目。记录实际结果，不把没有单一条目当失败。

解释：这一步用观测判断代理/内核路径，不能为了符合图示而伪造一条 conntrack 输出。

05 · 区分发布入口限制与主机直连

CIP=$(docker inspect learn-u10-web --format "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}")
curl -fsS -o /dev/null -w "%{http_code}
" "http://$CIP:80"
docker inspect learn-u10-web --format "{{json .HostConfig.PortBindings}}"

观察：原生 rootful Linux 的主机通常可直接访问容器 IP；成功说明“只绑定回环”不等于防住 Docker 主机。若本机额外路由或防火墙阻止，保存规则与错误作为差异证据。

解释：发布规则限制的是一个入口，网络隔离需要根据威胁来源定义。

04 · TRANSFER

换一个条件，还能解释吗

另一台机器请求宿主:18080 超时，本机 curl 正常。有人建议关闭 Docker 防火墙或使用 --network host。请设计最小诊断方案，先不修改规则。

提交这些证据

  • 实际 PortBindings、客户端目标 IP 与本机监听/发布地址。
  • 客户端请求时宿主入站接口是否见包，以及适用后端的 NAT/转发计数或抓包。
  • 容器端服务是否可达，以及回程路由或连接跟踪证据。
对照参考推理

先看是否只绑定 127.0.0.1：若是，外部不能通过宿主非回环地址命中同样的发布入口，这是配置边界而非 Docker 故障。

若确实发布到预期外部地址，按客户端→宿主入站→NAT/过滤→容器→回程逐段取证；安全组、主机防火墙、路由与监听各有独立证据。

只有定位到错误前提后才最小修改，验证授权来源可连接、非授权来源仍失败。host 网络会改变隔离模型，不能作为跳过根因分析的通用修复。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 解释 -p 18080:80 的入站和回程；为什么 ufw deny 18080 不一定能保护容器？

查看参考回答与递进追问

在常见 iptables bridge 后端中，外部包在 PREROUTING 相关规则被 DNAT 到容器 IP:80，路由后经 FORWARD 过滤和网桥/veth进入容器。conntrack 记住原始与回复方向，回包反向转换，因此客户端仍看到宿主:18080。仅配置宿主 INPUT 拒绝规则可能覆盖不到这条转发路径。应识别后端并在受支持的转发过滤位置验证准入，或按需求只绑定回环。localhost 请求与外部请求路径不同，必须分别验证。

追问 1：DOCKER-USER 中看到的目的端口一定是 18080 吗？

通常已经 DNAT 成容器端口80；按原始发布目的匹配时需要连接跟踪的原始目标信息，并考虑入口接口和方向。

追问 2：把 userland-proxy 关闭会让 NAT 不再需要吗？

不会。代理与内核 NAT 是不同实现路径或补充，关闭代理不撤销发布、路由、过滤与连接跟踪模型。

追问 3：换 nftables 后端还能照抄 DOCKER-USER 吗？

不能。Docker nftables 后端没有同样的 DOCKER-USER 结构，应按其受支持表/链和优先级接入，先读取本机配置。

容易混淆：NAT 只改地址，不等于访问控制；绑定回环、容器网络隔离和抵御宿主机访问也不是同一种保证。

06 · EVIDENCE

用证据判断是否掌握

  1. 先写来源与后端，再画 NAT 和过滤路径。
  2. 外部 PREROUTING 与本机 OUTPUT 请求不可混为一次验证。
  3. conntrack 解释双向地址转换；防火墙决定允许哪些连接。
  4. 入口绑定不替代完整网络访问策略。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
