04 🕵️ 0.0.0.0 之谜：容器跑着，却访问不了？


容器有自己的网络命名空间，里面的 127.0.0.1 是容器自己的回环地址，不是你电脑的。端口转发进来的流量从容器的“外部网卡”（如 172.17.0.2）进入。切换监听地址看看：






很多框架默认只监听 localhost：Flask app.run()、uvicorn main:app、Vite dev server、Rails 等。容器里一定要显式写 --host 0.0.0.0。


05 HEALTHCHECK：让 Docker 知道服务“真的活着”


进程在跑 ≠ 服务可用（可能卡死、数据库连不上）。HEALTHCHECK 让 Docker 定期探测：


HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD node -e "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"


⬜⬜⬜⬜⬜⬜⬜⬜
状态：starting




连续失败 retries 次 → unhealthy。docker ps 的 STATUS 会显示 (healthy)/(unhealthy)；Compose（第 8 课）可以“等数据库 healthy 再启动 API”。slim 镜像里没有 curl，所以这里用 node 自己发请求。


06 读懂构建失败


⚠️ 新手常见坑


监听 127.0.0.1：容器 Up，但 curl 返回 Connection reset / Empty reply。改成 0.0.0.0。


-p 写反：-p 宿主机端口:容器端口。-p 3000:8080 和 -p 8080:3000 完全不同。


用 npm start 作为 CMD：npm 会成为 PID 1，可能不转发 SIGTERM。直接 CMD ["node","server.js"]。


改了代码但容器里还是旧的：镜像是构建那一刻的快照。改代码 → 重新 build → 删旧容器 → run 新容器。（开发时热重载用 bind mount，第 6 课。）


Apple Silicon 构建的镜像在服务器上报 exec format error：架构不同（arm64 vs amd64）。用 docker build --platform linux/amd64（第 10 课讲 buildx 多架构）。


✅ 自测 4 题


📝 本课小结
  • 流程：写代码 → Dockerfile → docker build -t → docker run -d -p → curl 验证。
  • 服务在容器里必须监听 0.0.0.0，端口用环境变量配置。
  • HEALTHCHECK 区分“进程在跑”和“服务可用”。
  • 构建报错看 哪一步 [n/m] 失败 + 最后几行错误。
  • 代码改了要重新 build + 重新 run。
