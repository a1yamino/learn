构建上下文、依赖图与缓存正确性

从构建输入和依赖关系预测哪些步骤会重建，区分镜像层缓存、缓存挂载与真正的发布测试。

建议 60 分钟，含实验；按观察结果调整进度。

先想一想

改 README 后镜像重建了，改远端软件包后反而仍显示 CACHED；Dockerfile 明明有 test 阶段，发布镜像时测试却没执行。这些都可能符合缓存规则吗？

  • 根据 COPY 范围与 DAG 预测缓存失效传播。
  • 解释 BuildKit 为什么跳过独立 test 阶段。
  • 用修改单个输入的实验区分层缓存与运行时内容。
实验前提

Docker Engine 或 Desktop，启用 BuildKit，Docker Compose v2；在仓库根目录执行。实验复用 docker/labs 的标准库应用，不需要安装 Python 第三方依赖。

01 · MODEL

建立因果模型

构建上下文是可访问输入边界

构建器只能读取所选上下文、显式命名上下文和挂载等授权输入。COPY 的源相对于上下文根，不是 Dockerfile 所在目录；-f 只选择 Dockerfile，不会自动改变上下文。把仓库根作为上下文又 COPY . .，会把与应用无关的文件变化引入缓存键，也可能送入敏感文件。

文件是否参与某步缓存取决于该步读取的输入。COPY app.py version.txt 比 COPY . . 的输入范围更窄。.dockerignore 在发送上下文前排除内容，不能用它代替运行时保密。单纯修改文件 mtime 不必导致 COPY 缓存失效，文件内容和相关元数据才是要分析的输入。

多阶段是依赖图，不是待办清单

BuildKit 从目标阶段向前寻找依赖。FROM 某阶段、COPY --from=某阶段建立依赖关系；独立 test 阶段不在 final 的依赖路径上时，构建 final 可以跳过 test。这是按图裁剪，不是漏执行。

因此“Dockerfile 里存在测试”不等于“每次发布都测试”。CI 应显式构建 test 目标并执行最终运行时验证，或设计可审计的依赖/门禁。为了把 pytest 装进镜像而让发布产物依赖整个测试阶段，会扩大运行时镜像；测试环境与运行环境应各自明确。

缓存复用的是已知输入的结果

层缓存命中意味着本步已知输入与之前匹配，不意味着互联网上的所有依赖都没变化。RUN apt-get update 或访问网络的命令不会因为远端仓库更新而自动失效；固定依赖输入、主动更新与 --no-cache/--pull 解决的是不同问题。

RUN --mount=type=cache 提供可丢弃的加速目录，层重建时仍可复用下载或编译缓存。正确构建不应依赖缓存里恰巧存在的私有文件；清缓存后也应得到功能正确的结果。secret 的内容不参与缓存失效，换 token 不保证该 RUN 重执行；不应把 token 本身作为 ARG 来“解决”缓存问题。

03 · EXPERIMENT

用共用应用观察DAG裁剪与单输入变化

在仓库根目录开始，临时目录使用 mktemp；以下所有步骤在同一终端。只复制共用应用文件，不修改 docker/labs 原文件。

运行之前，先预测

final 与 test 都 FROM runtime。预测构建 final 时是否执行 test，修改 README 与 version.txt 时分别会影响哪些步骤。

01 · 固定一个很小的上下文

U11_DIR=$(mktemp -d)
cp docker/labs/app.py docker/labs/version.txt docker/labs/verify.py "$U11_DIR/"
cat > "$U11_DIR/Dockerfile" <<'EOF'
# syntax=docker/dockerfile:1
FROM python:3.12-slim AS runtime
WORKDIR /app
COPY app.py verify.py version.txt ./
RUN mkdir -p /data && chown 10001:10001 /data
USER 10001:10001
ENV DATA_DIR=/data BIND_HOST=0.0.0.0 PORT=8000
CMD ["python","app.py","serve"]
FROM runtime AS test
RUN PYTHONPYCACHEPREFIX=/tmp/pycache python -m py_compile app.py verify.py
FROM runtime AS final
EOF

观察：临时目录内包含明确的三个 COPY 输入和一个 Dockerfile；test 只做语法检查，不能当业务验收。

解释：此例专门验证依赖图与输入边界，运行应用和数据接口与共用实验一致。

02 · 构建 final 并保存可检查日志

docker build --progress=plain --target final -t learn-u11:final "$U11_DIR" > "$U11_DIR/final.log" 2>&1
cat "$U11_DIR/final.log"

观察：runtime 构建，test 中 py_compile 不应执行。实际下载耗时不作评分依据。

解释：final 不依赖 test，图裁剪解释了测试为何被跳过。

03 · 显式执行 test，再复用未变输入

docker build --progress=plain --target test -t learn-u11:test "$U11_DIR" > "$U11_DIR/test.log" 2>&1
cat "$U11_DIR/test.log"
printf "只改变未被 COPY 的说明文件
" > "$U11_DIR/README.txt"
docker build --progress=plain --target final -t learn-u11:final "$U11_DIR" > "$U11_DIR/readme.log" 2>&1
cat "$U11_DIR/readme.log"

观察：test 的 py_compile 应执行；README 不在 COPY 列表中，runtime 应可复用。

解释：显式目标与最小输入范围是两种独立设计。

04 · 改变真正的构建输入

printf "11.0.1
" > "$U11_DIR/version.txt"
docker build --progress=plain --target final -t learn-u11:final "$U11_DIR" > "$U11_DIR/version.log" 2>&1
cat "$U11_DIR/version.log"
docker run --rm learn-u11:final python -c "from pathlib import Path; print(Path('/app/version.txt').read_text().strip())"

观察：COPY 与其后的依赖重建；容器读到 11.0.1。不要只看日志耗时推断成功。

解释：把缓存失效和实际运行文件联系，避免仅以“构建变慢”判断产物正确。

05 · 禁用层缓存验证结果不依赖旧缓存

docker build --no-cache --target final -t learn-u11:cold "$U11_DIR"
docker run --rm learn-u11:cold python -c "from pathlib import Path; assert Path('/app/version.txt').read_text().strip()=='11.0.1'; print('version assertion passed')"

观察：干净重建后的版本断言也通过；本实验没有声称两次 image ID 必然相同。

解释：功能正确性、缓存命中和字节级可复现是不同验收，本课只验证前两者。

本实验的清理范围与命令
docker image rm learn-u11:final learn-u11:test learn-u11:cold
rm -rf "$U11_DIR"
04 · TRANSFER

换一个条件，还能解释吗

团队把 Dockerfile 移到 deploy/，仍以仓库根为上下文；每次提交文档都重跑 pip install，token 轮换后私有依赖下载步骤却没执行。请解释两个现象，并提出不会把 token 写进镜像或 ARG 的修复。

提交这些证据

  • 实际 build 命令的 -f 与上下文参数，以及 COPY/.dockerignore。
  • 一份只改文档、一份只改依赖清单的步骤缓存日志。
  • secret 挂载与显式非敏感失效标记的设计，以及冷缓存成功证据。
对照参考推理

先查看是否 COPY . . 放在安装依赖之前；上下文仍是仓库根，文档变化会让该 COPY 及后续依赖步骤失效。按变化频率拆 COPY，并缩小上下文或忽略无关文件。

secret 的内容不参加缓存键，轮换 token 本身不强制重跑。若业务确需重新下载，应变更明确的依赖版本/锁文件或非敏感 CACHE_REV 标记，而不是把 token 放进 ARG。

用文档变化、依赖变化和冷构建分别验证加速与正确性；缓存目录应当可以丢弃，不成为隐藏依赖。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 解释 BuildKit 的构建缓存、多阶段依赖图和 cache mount；如何证明一个优化不会改变构建正确性？

查看参考回答与递进追问

BuildKit 按目标依赖图调度并裁剪无关阶段，阶段中的操作依据指令及已声明输入匹配缓存。层缓存直接复用步骤结果；cache mount 则在步骤重跑时提供临时加速目录，不属于最终层。优化应先限定上下文与 COPY 输入，再把依赖清单放在经常变化的源码之前。以只改文档、改依赖、冷构建等单变量实验观察步骤和运行产物，证明既减少无关失效，又不依赖缓存残留。网络资源和 secret 值不会自动成为所有缓存输入，必须管理版本与更新策略。

追问 1：--target final 会运行在它前面的所有 test 阶段吗？

不会，只执行final的依赖。独立test需要显式构建与门禁，不能靠书写顺序。

追问 2：--no-cache 是否等同于 --pull？

不是。前者禁用构建层缓存，后者请求刷新基础镜像；两者也不替代依赖锁和可控更新。

追问 3：缓存挂载被删掉后构建失败，说明什么？

构建可能把缓存当必需输入或只存在的产物来源；应补明确的下载/构建路径，保证空缓存也能成功，再用缓存加速。

容易混淆：CACHED 只代表已声明输入匹配，不代表依赖最新、安全或发布测试已经执行。

06 · EVIDENCE

用证据判断是否掌握

  1. -f 选择 Dockerfile，上下文参数决定 COPY 的输入边界。
  2. 多阶段是依赖图，存在 test 阶段不代表发布时执行。
  3. 层缓存与 cache mount 加速不同阶段，空缓存也应正确。
  4. 通过单变量输入变化和运行断言验证优化。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
