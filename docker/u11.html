构建上下文、依赖图与缓存正确性

从输入推断哪些步骤会重建，让缓存既快又不出错。

先想一想

只改了一行业务代码，重新构建却把依赖全部重新安装了一遍，花了五分钟。怎么改，才能只重建变化的部分？

原理图解推演迁移面试小结
01原理

原理

缓存是按输入判断的

每条指令的缓存键由它的输入决定：父层、指令文本，以及 COPY/ADD 涉及的文件内容。任何一项变化，这一步和之后的所有步骤都要重新执行。

所以顺序很重要。先复制依赖清单、安装依赖，再复制源码。改代码时，依赖那一层的输入没变，可以直接命中缓存。

构建上下文是发给构建器的全部材料

docker build . 里的点就是上下文。没有 .dockerignore 时，.git、node_modules、本地日志都会被送过去，既拖慢构建，又可能让 COPY . . 的缓存频繁失效，甚至把密钥打进镜像。

BuildKit 只传输用得到的文件，但 COPY . . 会用到全部，所以 .dockerignore 仍然必要。

缓存命中不等于结果正确

RUN apt-get update 的指令文本不变就会命中缓存，即使软件源早已更新。需要新软件包时，要显式改变输入，比如固定版本号，或者用 --no-cache 构建发布版本。

RUN --mount=type=cache 把包管理器的下载缓存放在镜像之外，层失效时也能少下载一些，同时不会把缓存打进镜像。

BuildKit 把 Dockerfile 变成一张图

BuildKit 先把 Dockerfile 解析成依赖图，而不是从上到下逐条执行。多阶段构建里互不依赖的阶段会并行执行，最终目标用不到的阶段直接跳过。

所以多阶段构建不只是为了减小镜像。把测试、编译、打包拆成阶段，还能让无关阶段的修改不触发其他阶段重建。

缓存可以导出和共享

CI 的构建机每次都是新的，本地缓存为空。--cache-to 和 --cache-from 可以把缓存导出到镜像仓库或 CI 的缓存服务，下次构建再导入。

mode=max 会导出所有中间阶段的缓存，命中率更高，但占用空间更大。要按构建频率和仓库容量权衡。

走一遍：把一个慢构建改快

  1. 原始写法：COPY . . 之后执行 npm ci 和 npm run build。每次改代码都要重装依赖，耗时四分钟。
  2. 第一步：先 COPY package.json package-lock.json，执行 npm ci，再 COPY 其余代码。改代码时依赖层命中缓存。
  3. 第二步：给 npm ci 加 --mount=type=cache,target=/root/.npm，依赖变化时也只下载新增的包。
  4. 第三步：用多阶段构建，最终镜像只拷贝构建产物和运行时依赖。改代码后的构建时间降到几十秒。

常见误区

ARG 传入的密码不会留在镜像里
ARG 的值会出现在镜像历史和构建缓存的键里。凭据应该用 --mount=type=secret。
.dockerignore 只影响构建速度
它还决定哪些文件可能被 COPY 进镜像。没有忽略 .env、.git，就可能把密钥和历史打包发布出去。

放到生产里

CI 中配置远程缓存，并对发布分支定期做一次无缓存构建，提前发现依赖漂移。

构建日志里 CACHED 的步骤要心里有数：哪些该命中、哪些不该命中。

03推演

先猜，再看结果

Dockerfile 是 COPY . . 然后 RUN pip install -r requirements.txt。你只改了 app.py。pip install 会重新执行吗？

COPY . . 把 app.py 也算进了输入，它一变这一步就失效，后面的 pip install 跟着重来。先 COPY requirements.txt、安装，再 COPY 其余代码。

示例输出 · 只读
$ docker build -t api .
 => CACHED [2/4] WORKDIR /app
 => [3/4] COPY . .
 => [4/4] RUN pip install -r requirements.txt   38.2s
04迁移

换个场景

CI 用缓存构建，测试一直通过。某天手动用 --no-cache 构建同一个提交，测试失败了。为什么会这样？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

缓存层里装的依赖是很久以前解析的，而 --no-cache 重新解析时，某个没锁版本的依赖升级了，带来了不兼容的变化。

这说明构建并不可复现。解决办法是锁定依赖版本（lock 文件、固定基础镜像摘要），并定期做一次无缓存构建，把这种漂移尽早暴露出来。

05面试

讲给面试官听

怎么写 Dockerfile 才能让缓存有效？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

把变化少的放前面、变化多的放后面：先固定基础镜像，再复制依赖清单并安装，最后复制源码。用 .dockerignore 排除无关文件。依赖的下载缓存用 RUN --mount=type=cache。同时要记得缓存只看输入，不看外部世界，发布版本需要锁定依赖并定期无缓存构建。

追问：ADD 和 COPY 怎么选？

默认用 COPY，语义简单。ADD 会自动解压本地 tar 并支持远程 URL，行为更隐晦，只在确实需要这些功能时使用。

追问：构建时需要私有仓库的令牌怎么办？

用 RUN --mount=type=secret 在这一步临时提供，不要用 ARG 或 ENV，它们会留在镜像历史里。

06小结

带走这几句

  1. 缓存键由输入决定，失效会向下传递。
  2. 先依赖后源码，并用 .dockerignore 控制上下文。
  3. 命中缓存不代表结果新鲜，发布构建要锁版本。
