先想一想

01原理

原理

镜像是一份文件系统加启动说明

镜像里装着应用运行所需的文件：解释器、依赖库、你的代码，再加上一段元数据，写明默认用哪个用户、从哪个目录、执行哪条命令。它不包含内核，也不包含正在运行的进程。

所以“在我机器上能跑”的问题，Docker 解决的是用户态文件和启动方式的差异。内核仍然是宿主机的那一个，内核版本或特性不同，照样会有差别。

容器是按镜像启动的一组普通进程

docker run 会以镜像为底，叠一层可写层，再在隔离的视图里启动镜像指定的命令。这个命令的进程就是容器的主进程，它退出，容器就停止。

隔离靠的是内核的 namespace 和 cgroup，后面几课会拆开讲。现在只需要记住：容器不是小型虚拟机，在宿主机上用 ps 能看到它的进程。

端口发布是把宿主机的一个口转给容器

服务在容器里监听 8000，宿主机默认访问不到，因为容器有自己的网络栈。-p 8080:8000 让宿主机的 8080 把流量转给容器的 8000。

常见的坑是服务只监听了 127.0.0.1。那是容器自己的回环地址，从宿主机转进来的流量到不了它，要监听 0.0.0.0。

03推演

先猜，再看结果

服务在容器内监听 127.0.0.1:8000，你用 -p 8080:8000 启动。在宿主机执行 curl localhost:8080，会发生什么？

发布的端口把流量转到容器的网卡地址，而不是容器内部的 127.0.0.1。服务只听回环地址，转进来的连接没人接。改成监听 0.0.0.0 就好。

示例输出 · 只读
$ curl -sS localhost:8080/health
curl: (56) Recv failure: Connection reset by peer

# 改为监听 0.0.0.0 后
$ curl -sS localhost:8080/health
{"status": "ok"}
04迁移

换个场景

同事说镜像在他的 Mac 上能跑，推到一台 ARM 服务器上直接报 exec format error。镜像不是“到处都能跑”吗？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

镜像打包的是文件，文件里的可执行程序是针对某个 CPU 架构编译的。在 amd64 上构建的镜像，默认只包含 amd64 的二进制。

排查时先看镜像的平台：docker image inspect 里的 Architecture。解决办法是构建对应平台的镜像，或者用多平台构建发布一个索引，让各架构各取所需。第 12 课会细讲。

05面试

讲给面试官听

用一两分钟说清楚：镜像和容器是什么关系？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

镜像是只读的模板，包含文件层和启动配置；容器是用这个模板创建出来的运行实例，多了一层可写层和一个正在运行的主进程。一个镜像可以启动很多容器，它们共享底层只读层，各自写自己的可写层。删掉容器，可写层跟着消失，镜像不受影响。

追问：容器和虚拟机最根本的区别是什么？

虚拟机有自己的内核，靠虚拟化硬件隔离；容器共享宿主机内核，靠 namespace 隔离视图、cgroup 限制资源。所以容器启动快、开销小，但隔离强度也弱一些。

追问：容器停了，里面写的文件还在吗？

停止不等于删除。只要容器对象还在，可写层就在，再 start 能看到之前写的文件。docker rm 之后才没了。要长期保存的数据应该放在卷里。

06小结

带走这几句

  1. 镜像打包的是用户态文件和启动配置，不含内核。
  2. 容器就是宿主机上被隔离的普通进程，主进程退出容器就停止。
  3. 端口发布把宿主机端口转给容器网卡，服务要监听 0.0.0.0。
