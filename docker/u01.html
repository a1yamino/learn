快速上手：交付一个 API

先完成一次最小闭环，再带着真实现象学习进程、存储、网络和构建原理。

建议 60 分钟，含实验；按观察结果调整进度。

先想一想

同一份应用代码已经提供。怎样证明它能运行、能访问，并且删除容器后仍保留业务数据？

  • 能用提供的应用完成构建、启动、访问和读取日志。
  • 能区分镜像、容器和数据卷，并验证重建后数据仍然存在。
  • 能说出下一步应查进程、网络、文件还是构建，而不是盲目重启。
实验前提

需要 Git、Python 3、Docker Engine 或 Docker Desktop，以及支持 up --wait 的 Docker Compose v2。命令使用 Bash；Windows 可在 WSL 运行。先克隆或下载本仓库，从仓库根目录开始。8080 端口应空闲；本课的 learn-docker 项目是独立实验环境。

01 · MODEL

建立因果模型

镜像是输入，容器是被管理的运行实例

Dockerfile 描述如何产生镜像。镜像保存用户态文件和默认启动配置；docker run 或 Compose 用它创建容器，建立文件视图、网络和资源约束，再启动进程。

容器可以处于运行或停止状态；停止不等于删除。重建创建新的容器实例，镜像里的文件相同，也不意味着挂载、环境变量、内核和外部依赖相同。后续课程会逐项验证这些边界。

这份应用的三种职责

api 是 Python 标准库 HTTP 服务，用 SQLite 保存订单。gateway 是 Nginx，只负责接收 HTTP 并转发给 api；orders 是命名数据卷，挂载在 api 的 /data。业务代码已提供，可以直接阅读 docker/labs/app.py。

浏览器访问的是本机 8080，Docker 将它映射到 gateway 的 80；gateway 通过 back 网络中的服务名 api 访问 8000。api 没有直接发布到宿主机。每一段连接都有自己的地址与端口。

运行、就绪与业务正确是不同证据

容器 running 表示主进程还活着；/health 检查 HTTP 服务存活；/ready 会连接 SQLite 并查询订单表。Compose 等 api 健康后再启动 gateway，这能帮助初次启动。

健康检查不会替应用处理所有运行中故障。verify.py 会真正创建订单并查回内容，检验完整业务路径；它的 JSON 结果可以作为后续对比的证据。

数据的身份属于卷

本课把数据库放在命名卷 orders 中，而不是依赖容器的可写层。Compose 项目名参与卷的实际名称；同一项目重建容器，仍会挂载同一个卷。换项目名可能得到另一个新卷。

docker compose down 删除本项目容器和网络，默认保留命名卷。down -v 还会删除卷中的实验数据。清理前先明确你要结束进程，还是要丢弃数据。

03 · EXPERIMENT

构建、访问，再重建

从仓库根目录开始。所有命令在同一个 Bash 终端运行；默认使用 learn-docker 项目。若已有同名项目，先换独立项目名并在后续命令保持一致。

运行之前，先预测

up、stop、down、重建、down -v 分别会改变哪些对象？先写出一次重建后订单是否还在，以及依据是什么。

01 · 确认客户端与执行环境

cd docker/labs
docker version
docker compose version
docker info --format '{{.OSType}} {{.Architecture}} {{.Driver}}'

观察：客户端与服务端都能连接，记录操作系统、架构和存储后端；Desktop 的 Linux 服务端位于虚拟机。

解释：CLI 能运行不代表 Engine 已启动。记录环境能解释后续宿主路径或镜像平台差异。

02 · 构建并等到服务就绪

docker compose up -d --build --wait
docker compose ps

观察：api 健康、gateway 运行；首次可能需要下载镜像。若失败，先查看具体服务日志。

解释：--build 根据当前源码构建，--wait 等待运行或健康条件。命令成功仍需业务验收。

03 · 验证完整业务路径

python3 verify.py http://127.0.0.1:8080 --output evidence/u01.json
curl -fsS http://127.0.0.1:8080/orders
docker compose logs --tail=20 api gateway

观察：JSON 验收 passed 为 true，创建的 verify- 订单能查回；日志有订单创建和 HTTP 访问记录。

解释：这同时验证发布端口、代理、服务名解析、应用与数据库。脚本创建的订单只属于本实验。

04 · 记录容器身份，再重建

docker compose ps -q api
docker compose up -d --force-recreate --wait
docker compose ps -q api
curl -fsS http://127.0.0.1:8080/orders

观察：容器 ID 改变，订单仍在。若数据不同，核对项目名、卷挂载与 DATA_DIR。

解释：实例身份与数据身份分离。重建没有把旧容器可写层带过来，保留数据依赖同一卷。

05 · 观察运行身份和挂载

docker compose exec api id
docker compose exec api python -c "import os; print(os.environ['DATA_DIR'])"
docker volume inspect learn-docker_orders

观察：应用身份为 10001:10001，数据目录为 /data；卷名含项目名前缀。Desktop 的卷路径属于虚拟机。

解释：运行成功只是起点。身份、目录和挂载证据能帮助解释权限与数据问题。

04 · TRANSFER

换一个条件，还能解释吗

你改了 version.txt，执行 docker compose restart 后，/version 仍显示旧版本。先不用任何清理命令，解释哪一层还没有改变，并给出最小修复。

提交这些证据

  • 修改后的文件内容、当前镜像 ID 与容器 ID。
  • restart 前后的 /version，修复后的 /version。
  • 说明为什么不用删除数据卷。
对照参考推理

version.txt 在构建时 COPY 进镜像。修改主机源码并不会改变镜像；restart 只重启已有容器的进程。

先用 docker compose config 确认构建上下文，再执行 docker compose up -d --build --wait，让新镜像对应新的容器。核对 /version 与订单仍保留。

此故障发生在源码→镜像→实例的更新链中。数据卷不需要改变，删除它不能修复镜像版本，反而会丢数据。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 请用一个请求解释镜像、容器、网络和数据卷各自负责什么。

查看参考回答与递进追问

镜像提供用户态文件和启动配置，容器提供隔离与约束下的运行实例，网络把客户端请求送到应用，数据卷保存独立于容器实例的数据。在本项目中，请求从本机8080进入Nginx，再访问api:8000，SQLite写入/data对应的orders卷。每一层都需要不同证据验证。

追问 1：为什么同一个镜像在两台机器上还可能表现不同？

镜像没有封装任意宿主内核、CPU架构、运行时配置、挂载和外部服务。先核对平台与内核环境，再比较环境变量、网络、数据和资源约束；不能只根据tag相同就认定环境相同。

追问 2：容器重启与重建有什么区别？

重启保留容器对象、可写层和配置；重建用选定镜像创建新对象，旧可写层不会作为数据自动继承。显式挂载同一卷可以继续使用数据。

追问 3：running 和健康检查通过能证明业务正确吗？

running只证明主进程存活，健康检查只覆盖其配置的断言。必须沿真实入口做一次订单写入和查询，并核对错误路径与恢复结果，才能支持对应的业务保证。

容易混淆：把Docker当成“环境完全一致”的保证。正确的表达是固定镜像内容，同时显式描述和验证运行环境的边界。

06 · EVIDENCE

用证据判断是否掌握

  1. 构建产生镜像，创建产生容器，重启不会自动换镜像。
  2. 一次成功请求跨越发布端口、代理、网络、应用与数据。
  3. 容器身份与卷身份不同，数据保留依赖明确的挂载。
  4. 先记录可观察事实，再选择与根因对应的最小动作。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
