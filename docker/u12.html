多平台与可复现构建：固定的究竟是什么

区分平台索引和单平台清单，弄清“可移植”“可重部署”“可复现”各自要固定什么。

先想一想

同一个提交构建两次，得到两个不同的摘要。这算不算构建出了问题？

原理图解推演迁移面试小结
01原理

原理

一个名字，多份清单

多平台镜像的顶层是一个索引，里面列出 linux/amd64、linux/arm64 等平台各自的清单。Mac 的 Apple 芯片和 x86 服务器拉同一个标签，会拿到不同的清单。

docker buildx build --platform linux/amd64,linux/arm64 可以一次构建并推送多个平台。跨架构构建可以用 QEMU 模拟，也可以交叉编译，后者通常快得多。

三种“固定”

可移植：同一个名字在不同架构上都能运行，靠多平台索引。可重部署：今天和半年后部署的是同一份内容，靠记录并按摘要拉取。可复现：从同样的源码重新构建，得到逐字节相同的结果，这是最难的一种。

大多数团队真正需要的是可重部署。可复现要求连时间戳、文件顺序、依赖版本都固定。

为什么两次构建摘要不同

层里的文件修改时间、镜像配置中的创建时间、没有锁定的依赖版本，都会让内容不同。BuildKit 支持 SOURCE_DATE_EPOCH 来固定时间戳，基础镜像要按摘要引用，依赖要用 lock 文件。

所以摘要不同不一定是错误，但它说明有输入没固定。要找出是哪一项。

03推演

先猜，再看结果

在 M 系列 Mac 上直接 docker build 并推送，然后在 x86 Linux 服务器上运行。最可能看到什么？

默认按构建机的平台构建，产物只有 arm64。x86 服务器上运行会报平台不匹配，执行时出现 exec format error。需要 --platform 指定，或者构建多平台索引。

示例输出 · 只读
$ docker run api:dev
WARNING: The requested image's platform (linux/arm64) does not
match the detected host platform (linux/amd64)
exec /usr/local/bin/python: exec format error
04迁移

换个场景

安全团队要求“每个线上镜像都能由源码重新构建并核对一致”。你会先固定哪些输入？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

基础镜像按摘要引用；所有依赖用 lock 文件锁定版本和哈希；构建时设置 SOURCE_DATE_EPOCH，让时间戳稳定；避免在构建中下载“最新”的东西。

然后在两台干净的构建机上各构建一次，比较摘要。若不同，用 diffoci 之类的工具逐层比较，找出剩下的变量。

05面试

讲给面试官听

多平台镜像是怎么工作的？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

镜像名指向一个索引，索引里每个条目是一个平台的清单，带着 os、architecture、variant。客户端拉取时按本机平台选择匹配的清单，再下载它引用的配置和层。构建时用 buildx 指定多个平台，可以借助 QEMU 模拟或交叉编译。

追问：可复现和可重部署有什么不同？

可重部署是再次部署时拿到同一份内容，按摘要拉取就能做到。可复现是重新构建得到相同的摘要，需要固定所有输入，包括时间戳。

追问：QEMU 模拟构建有什么代价？

慢，编译型任务可能慢一个数量级；某些系统调用也可能表现不一致。能交叉编译时优先交叉编译。

06小结

带走这几句

  1. 名字指向索引，索引按平台分发清单。
  2. 可移植、可重部署、可复现是三个不同目标。
  3. 摘要不同说明有输入没固定：时间戳、依赖、基础镜像。
