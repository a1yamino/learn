项目：一步步完成

这是开放式综合项目，命令中的目录、镜像和数据库对象需先按要求实现。第 4 课仅有 /health，并未提供订单、数据库访问、缓存、迁移或测试代码。先完成下方功能契约，再进入部署步骤；输出为验收示例，不是运行空目录即可得到的结果。
01

1. 应用和仓库。在第 4 课 API 上实现：订单写入 PostgreSQL 的 shop 数据库、查询订单及 Redis Cache-Aside 缓存、/health 就绪检查。迁移任务创建 orders 表；测试至少断言创建后可查询、更新后缓存失效、缓存不可用时按约定回源。前端通过 /api 访问服务。配置数据库名 POSTGRES_DB=shop，记录初始化数据的实际行数，不要假定预期一定是 42。目录结构如下。

mkdir shop && cd shop && git init
# api/  (Dockerfile, app, tests)
# web/  (Dockerfile, 静态文件, nginx.conf)
# compose.yaml  compose.override.yaml  compose.prod.yaml
# .github/workflows/ci.yml  .dockerignore  .env.example
（.env 加入 .gitignore，只提交 .env.example）
02

2. 镜像。api 用多阶段构建、test 阶段、非 root、缓存挂载；web 用 nginx-unprivileged。检查大小和用户。

docker build -t shop-api ./api && docker build -t shop-web ./web
docker image ls shop-* --format "{{.Repository}} {{.Size}}"
docker run --rm shop-api id -u
shop-api 78MB
shop-web 52MB
10001
03

3. Compose。db 和 redis 带健康检查；migrate 一次性任务；api 依赖 db healthy 和 migrate 成功；只有 web 发布端口。

docker compose up -d --wait && docker compose ps --format "{{.Service}} {{.Status}}"
api Up 20 seconds (healthy)
db Up 31 seconds (healthy)
redis Up 31 seconds (healthy)
web Up 9 seconds (healthy)
04

4. 确认网络隔离。数据库未发布到宿主机 localhost:5432，web 也不能按服务名直连数据库。这个检查不证明对 Docker 主机本身的隔离：Linux 主机通常仍能访问容器 IP。

nc -zv -w2 localhost 5432; docker compose exec web nc -zv -w2 db 5432
nc: connect to localhost port 5432 (tcp) failed: Connection refused
nc: bad address 'db'
05

5. 生产加固（compose.prod.yaml）：资源限制、cap_drop、read_only、no-new-privileges、restart、日志轮转。用 config 检查合并结果。

docker compose -f compose.yaml -f compose.prod.yaml config | grep -E "cap_drop|read_only|memory" | sort | uniq -c
      4     cap_drop:
      4     memory: "…"
      3     read_only: true
06

6. CI：第 23 课的 workflow，构建两个镜像、test 阶段、Trivy 门禁、推送、签名，输出两个 digest。

git push && gh run watch
✓ build (api)  ✓ build (web)  ✓ deploy
07

7. 部署：服务器上通过环境变量传入 digest。

API_IMAGE=ghcr.io/you/shop-api@sha256:… WEB_IMAGE=ghcr.io/you/shop-web@sha256:… \
  docker compose -f compose.yaml -f compose.prod.yaml up -d --wait
✔ Container shop-api-1  Healthy
✔ Container shop-web-1  Healthy
08

8. 备份与恢复演练。备份数据库，删除卷，恢复，确认数据还在。

# 在 Bash 中执行，管道任一步失败均返回失败
set -o pipefail
docker compose exec -T db pg_dump -U postgres shop | gzip > backup.sql.gz || { echo "备份失败，停止恢复演练" >&2; exit 1; }
# 在测试环境：
docker compose down -v && docker compose up -d --wait db
gunzip -c backup.sql.gz | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres shop >/dev/null
docker compose exec db psql -U postgres shop -tc "select count(*) from orders"
  42
09

回滚演练。在测试环境部署健康检查失败的版本，再换回上一个 digest。镜像回滚不回滚数据库或卷：迁移必须与旧应用兼容，破坏性迁移需另行制定数据恢复方案。验证健康状态、订单读写和恢复前后数据行数。

API_IMAGE=…@sha256:<坏版本> docker compose … up -d --wait; echo exit=$?
API_IMAGE=…@sha256:<上一版本> docker compose … up -d --wait; echo exit=$?
container shop-api-1 is unhealthy
exit=1
exit=0

参考结构：

# Shop 运维手册
## 部署
1. 从 CI 最近一次成功运行复制两个 digest
2. API_IMAGE=… WEB_IMAGE=… docker compose -f compose.yaml -f compose.prod.yaml up -d --wait
3. curl -fsS https://shop.example.com/healthz
## 回滚
- deploys.log 里记录每次部署的 digest；用上一行的值重复“部署”第 2 步
## 备份与恢复
- 每天 03:00 cron：pg_dump | gzip，保留 14 天，复制到另一台机器/对象存储
- 每月恢复演练一次（命令见项目第 8 步）
## 排障（第 22 课顺序）
- api 反复重启：docker inspect … OOMKilled → 调整 memory
- 502：docker compose logs web；api 是否 healthy；监听地址
- 磁盘满：docker system df；du -sh /var/lib/docker/containers/*

手册的价值在于被验证过：没有在新机器上照做成功过的步骤，到真正出事时往往行不通。备份同理：没有恢复过的备份，不能算备份。

小结

记住这几点

  1. 镜像：多阶段构建、非 root、固定基础镜像版本、.dockerignore、缓存挂载（第 3、5、17 课）。
  2. 编排：Compose 健康检查 + 依赖条件 + 迁移任务；开发和生产分文件（第 8、18 课）。
  3. 网络：只有反向代理发布端口，数据库和缓存只在内部网络（第 7、15 课）。
  4. 数据：命名卷 + 定期备份并验证能恢复（第 6、16 课）。
  5. 安全与资源：cap-drop、只读文件系统、no-new-privileges、内存和 CPU 限制、日志轮转；镜像扫描、SBOM、签名（第 19–21 课）。
  6. 交付：CI 构建一次、测试、扫描、推送、签名，按 digest 部署，回滚就是换回上一个 digest（第 23 课）。出问题按第 22 课的顺序排查。
