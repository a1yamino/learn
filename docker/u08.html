数据生命周期、权限与可验证恢复

让数据活得比容器久，并且能证明备份真的能恢复。

先想一想

团队每天备份数据库卷，从没出过问题。直到第一次真正需要恢复，才发现备份文件打不开。备份这件事到底该怎么验收？

原理图解推演迁移面试小结
01原理

原理

三种存放位置

可写层随容器删除；命名卷由 Docker 管理，删容器不受影响，要显式删除；绑定挂载直接用宿主机目录，路径和权限都由宿主机决定。生产数据一般放卷里。

docker compose down 默认保留卷，加 -v 才会删除。这个参数很容易在清理时顺手带上。

权限看的是数字 UID

容器里的进程以某个 UID 访问卷里的文件，内核只比较数字，不认用户名。镜像里 app 用户是 10001，卷里文件属于 1000，就会出现权限拒绝。

修复的方式是让数字对上：构建时固定 UID，或者首次初始化时调整卷的属主。不要用 chmod 777 绕过去。

一致的备份，加上真实的恢复

直接复制正在写入的数据库文件，可能拿到写到一半的状态。应该使用数据库自己的备份工具，比如 pg_dump、SQLite 的 backup API，或者先停写再复制。

备份只有恢复过才算数。定期把备份恢复到一个新卷，启动应用，检查数据条数和一条最近的记录。这一步做了，备份才可信。

03推演

先猜，再看结果

镜像以 USER 10001 运行。你把宿主机上属于 UID 1000 的目录绑定挂载到 /data，应用尝试写入。结果是？

内核按数字 UID 判断权限，10001 对属于 1000、权限为 755 的目录没有写权限。Docker 不会自动修改绑定挂载的属主。

示例输出 · 只读
$ docker run --rm -v $PWD/data:/data app touch /data/x
touch: cannot touch '/data/x': Permission denied
$ stat -c '%u %a' data
1000 755
04迁移

换个场景

有人用 docker cp 把运行中 PostgreSQL 容器的数据目录拷了出来当备份。这份备份可靠吗？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

不可靠。拷贝过程中数据库还在写，文件之间可能处于不同时刻，恢复时可能需要大量 WAL 修复，甚至无法启动。

应该用 pg_dump 或 pg_basebackup，或者在停机窗口里停库后再复制。然后按上面的流程恢复到新卷并验证，才能把它当作备份。

05面试

讲给面试官听

容器化的数据库怎么做备份，怎么证明备份可用？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

数据放在命名卷里，备份用数据库自身的一致性机制，比如 pg_dump 或物理备份工具，不直接复制正在写入的文件。备份带时间戳和校验和存到异地。可用性靠定期恢复演练证明：在新卷上恢复、启动一个临时实例、核对行数和最近的记录。

追问：为什么不用 chmod 777 解决卷的权限问题？

它把访问权给了所有人，掩盖了 UID 不一致的真正原因，也扩大了被利用的面。应该让文件属主和进程 UID 一致。

追问：compose down -v 会删除什么？

Compose 文件里声明的命名卷和匿名卷都会被删除，数据就没了。外部卷（external）不会被删。

06小结

带走这几句

  1. 可写层随容器走，卷要显式删除，down -v 会删卷。
  2. 权限比较的是数字 UID。
  3. 备份要一致，并且只有恢复过才算数。
