数据生命周期、权限与可验证恢复

从订单写入到卷备份、删除与恢复，证明数据能跨容器重建且应用仍有正确权限。

建议 60 分钟，含实验；按观察结果调整进度。

先想一想

容器重建后订单还在，所以有人断言“数据库已经安全持久化”。如果误执行 down -v、恢复文件属主为 root，订单服务还能恢复吗？

  • 按 stop、rm、down、down -v 说明容器可写层、tmpfs 和命名卷分别保留多久。
  • 用 SQLite backup API 导出一致快照并在空卷中恢复。
  • 检查 UID 10001 对数据目录的权限，并用 /ready 与订单读取验证恢复。
实验前提

需要 Linux 容器 Docker Engine 或 Docker Desktop、Compose v2、curl、Python 3 和可写本机临时目录；从仓库根目录执行。项目 learn-u08、端口 18008 与卷 learn-u08_orders 只供本课使用。实验会在先导出一致备份后删除该独立项目的卷；不要用已有业务项目替换名称。

01 · MODEL

建立因果模型

数据的寿命取决于它落在哪个对象

共用应用的 /data 是 Compose 命名卷，/tmp 是 tmpfs，根文件系统只读。stop/start 或普通 down/up 不等于删除命名卷；down -v 会删除本项目命名卷。若使用普通容器可写层，它随该容器对象 rm 而消失，不能作为跨重建备份。

本课故意使用独立项目：先导出到宿主临时目录，再删除实验卷，然后重建空卷并恢复。备份文件与被删卷必须位于不同生命周期域；把唯一备份也放在同一个卷中没有恢复意义。

一致快照比直接复制活数据库可靠

SQLite 数据库可能存在进行中的事务和旁路日志文件。应用提供 python app.py backup 通过 SQLite backup API 创建一致快照；直接 docker cp 正在写的 orders.db 可能得到无法反映完整事务的文件。

先在容器内用 backup API 生成 /data/backup.db，再把该快照导出到宿主临时目录。导出后检查备份可读与订单内容，避免把“命令返回 0”当作可恢复证明。生产环境还需考虑备份加密、异地存储和保留策略，本课只验证本地流程。

恢复同时需要内容与访问权限

镜像以 UID/GID 10001 运行。恢复到空命名卷时，文件和目录必须允许该身份读写，SQLite 还可能需要在目录创建临时或日志文件。docker cp 或 root 辅助容器复制可能产生 root 属主，导致 /ready 查询失败或写订单失败。

恢复阶段只在本课独立卷中用 root 辅助容器复制并 chown 到 10001:10001；正常应用仍保持非 root。权限问题要读容器实际 UID、目录属主与错误日志，而不是长期把服务改为 root。

完成恢复要验证业务契约

/health 只证明进程 HTTP 存活；/ready 每次新建数据库连接并查询，可发现数据库不可访问；GET /orders 再证明目标订单存在。恢复后还应写入一笔新订单，验证文件与目录权限可用于持续写入。

备份文件存在、容器 running 或 ready 单独都不足以证明业务恢复。要保留备份路径、原订单、恢复后读写结果和实际卷名，才能让别人复现判断。

03 · EXPERIMENT

备份、删除独立卷并恢复真实订单

所有命令在同一终端，从仓库根目录开始；确保端口 18008 空闲且 learn-u08 项目未被使用。实验只删除 learn-u08_orders，并在卷外 mktemp 临时目录保留备份。每一步失败应停下查看日志，不继续执行删除卷步骤。

运行之前，先预测

普通 down/up 后订单是否仍在？down -v 后卷是否仍在？把快照复制到新卷并把目录、文件属主设为 10001 后，/ready 和新订单写入应如何变化？

01 · 启动独立应用并等待数据库就绪

cd docker/labs
U08_DIR=$(mktemp -d)
LAB_PORT=18008 docker compose -p learn-u08 up -d --build
u08_ready() { n=0; until curl -fsS http://127.0.0.1:18008/ready; do n=$((n+1)); [ "$n" -lt 40 ] || return 1; sleep 0.5; done; }
u08_ready
U08_API=$(docker compose -p learn-u08 ps -q api)
docker inspect -f 'User={{.Config.User}} Mounts={{json .Mounts}}' "$U08_API"

观察：ready 成功；记录 api 容器 UID 与 /data 的命名卷挂载。等待失败先看日志，不继续删除步骤。

解释：确认数据实际落在独立卷中，且服务在操作前可用。

02 · 写订单并导出一致备份到卷外

curl -fsS -H 'Content-Type: application/json' -d '{"item":"u08-book","quantity":2}' http://127.0.0.1:18008/orders
docker compose -p learn-u08 exec -T api python app.py backup /data/backup.db
docker cp "$U08_API":/data/backup.db "$U08_DIR/backup.db"
python3 - "$U08_DIR/backup.db" <<'CHECK'
import sqlite3,sys
with sqlite3.connect(sys.argv[1]) as db:
    assert db.execute("SELECT count(*) FROM orders WHERE item=? AND quantity=?", ("u08-book",2)).fetchone()[0] >= 1
print("BACKUP_HAS_ORDER")
CHECK

观察：POST 成功，宿主备份可独立打开且含目标订单；如果断言失败，不能进入 down -v。

解释：一致快照与卷外副本共同形成可恢复输入，SQLite 内容检查比文件存在更有力。

03 · 普通 down/up，检验卷的独立寿命

docker compose -p learn-u08 down
LAB_PORT=18008 docker compose -p learn-u08 up -d
u08_ready
curl -fsS http://127.0.0.1:18008/orders | python3 -c 'import json,sys; d=json.load(sys.stdin); assert any(x["item"]=="u08-book" and x["quantity"]==2 for x in d["orders"]); print("ORDER_SURVIVED_DOWN")'

观察：普通 down/up 后原订单仍可读；这里没有 -v。

解释：容器对象重建不等于命名卷删除。

04 · 只删除实验项目的卷

docker compose -p learn-u08 down -v
if docker volume inspect learn-u08_orders >/dev/null 2>&1; then echo "volume still exists; stop and investigate"; exit 1; else echo "EXPERIMENT_VOLUME_REMOVED"; fi
test -s "$U08_DIR/backup.db"

观察：只删除 learn-u08 项目卷；卷外备份仍存在且非空。若卷仍在，先排查名称与占用，不推进恢复。

解释：区分删除运行卷和保留独立备份。

05 · 建新卷、复制快照并修正权限

docker volume create learn-u08_orders
docker run --rm --user 0 --mount type=volume,source=learn-u08_orders,target=/data --mount type=bind,source="$U08_DIR/backup.db",target=/backup.db,readonly python:3.12-slim sh -c 'cp /backup.db /data/orders.db && chown -R 10001:10001 /data && ls -ldn /data && ls -ln /data/orders.db'

观察：新卷中 orders.db 与 /data 目录属主为 10001:10001；没有把 root 用作常态应用身份。

解释：目录和文件都需允许 SQLite 运行身份访问及后续写入。

06 · 启动并验证旧订单与新写入

LAB_PORT=18008 docker compose -p learn-u08 up -d
u08_ready
curl -fsS http://127.0.0.1:18008/orders | python3 -c 'import json,sys; d=json.load(sys.stdin); assert any(x["item"]=="u08-book" and x["quantity"]==2 for x in d["orders"]); print("RESTORED_ORDER_FOUND")'
curl -fsS -H 'Content-Type: application/json' -d '{"item":"u08-after-restore","quantity":1}' http://127.0.0.1:18008/orders
curl -fsS http://127.0.0.1:18008/orders | python3 -c 'import json,sys; d=json.load(sys.stdin); assert any(x["item"]=="u08-after-restore" for x in d["orders"]); print("NEW_WRITE_OK")'

观察：ready 成功，旧订单仍可读，新订单可写可读。若 ready 失败，检查卷属主、SQLite 错误与容器日志。

解释：恢复验收覆盖数据库可读和继续写入，避免只看 running 或备份文件存在。

本实验的清理范围与命令
docker compose -p learn-u08 down -v
[ -z "${U08_DIR:-}" ] || rm -rf "$U08_DIR"
unset U08_DIR U08_API
# 仅删除 learn-u08 项目卷与本实验 mktemp 目录；确认已保存所需备份证据后执行。
04 · TRANSFER

换一个条件，还能解释吗

迁移时把备份文件 docker cp 进新容器后，/health 返回 200，/ready 返回 503，日志提示 unable to open database file。原镜像使用 UID 10001。你如何定位并修复，而不是把服务永久改成 root？

提交这些证据

  • 提供容器 inspect 的 Config.User、ReadonlyRootfs 与 /data Mounts，确认数据库实际路径。
  • 在卷内查看 /data 目录与 orders.db 的数字 UID/GID、模式，并检查 /ready 日志。
  • 修正后提交 /ready、旧订单读取、新订单 POST 和再次读取的结果。
对照参考推理

health 只证明 HTTP 进程活着；ready 新连接数据库失败，先核对恢复文件是否在实际 /data 卷、目录是否可遍历和可写、文件是否可读写。

root 复制常把文件留为 root 属主；在隔离的恢复步骤对卷内目录和文件设为应用 UID/GID 10001，正常应用维持非 root。

重新测试读与写；若仍失败，再检查 SQLite 文件完整性、挂载只读标志和磁盘容量，不能仅凭一个 503 断定权限。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 如何设计并验收一个 Docker 命名卷中 SQLite 数据的恢复演练？

查看参考回答与递进追问

先确定数据在 /data 命名卷而非可写层或 tmpfs；写入可识别订单，使用 SQLite backup API 做一致快照，导出到卷外并验证快照含目标记录。只对独立实验项目执行 down -v，建空卷后复制备份并把目录、文件权限交给 UID 10001。重启后用 /ready、旧订单读取和新订单写入三类证据验收。生产还需异地存储、保留和定期恢复，但本演练以真实恢复行为为准。

追问 1：为什么直接 docker cp 正在写的 orders.db 不够？

SQLite 可能正处理事务或有日志文件；逐文件复制不保证事务一致。backup API 提供一致快照。

追问 2：普通 down 和 down -v 分别影响什么？

普通 down 移除该 Compose 项目容器与网络，保留命名卷；down -v 还会删除项目声明的命名卷，本课先导出卷外备份。

追问 3：ready 为 200 就算恢复完成吗？

不够。ready 只确认数据库可查询；还需确认目标旧订单存在和新订单可写，以验证内容与权限。

容易混淆：“持久化等于有卷。”卷可被误删、损坏或带错误权限；可恢复性要由独立备份和演练证明。

06 · EVIDENCE

用证据判断是否掌握

  1. 可写层、tmpfs、命名卷有不同生命周期，删除命令必须与数据对象对应。
  2. 备份必须独立于待删除卷，且 SQLite 快照要保证一致性。
  3. 恢复文件和目录权限必须匹配应用 UID 10001。
  4. 用 ready、旧订单和新写入验证恢复，不以 health 或 running 代替。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
