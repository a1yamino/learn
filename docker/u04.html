cgroups 与资源诊断

从预算、使用量和内核事件区分 CPU 节流、内存回收与 OOM，把调参建立在可验证证据上。

建议 55 分钟，含实验；按观察结果调整进度。

先想一想

API 响应变慢但没崩溃，与容器突然退出且代码为 137，可能来自同一个“资源不够”原因吗？应先读哪些证据再增加配额？

  • 读懂 memory.max、cpu.max、pids.max 与对应事件，解释它们不是同一种限制。
  • 用可控 CPU 负载观察节流，避免把 --cpus 0.5 解释成专属半个核心。
  • 用 OOM 与显式 SIGKILL 的对照证明退出码不能单独定位根因。
实验前提

Linux 容器，要求 cgroup v2 且 Engine 能执行 CPU、memory、pids 控制；先检查 docker info 的相关警告。Docker Desktop 的限制发生在 Linux VM 内，VM 总预算还会构成上层限制。rootless 需要相应控制器委派；不满足时先记录环境限制，不把缺失文件误判成资源未受限。本课无需修改宿主机 cgroup 或使用 sudo。

01 · MODEL

建立因果模型

namespace 给视图，cgroup 给层级预算

cgroup 把进程组织在层级中，控制 CPU、内存、进程数等资源。容器主进程及后续子进程通常处于容器的 cgroup 子树；线程也会影响 pids 计数。cgroup namespace 可以改变看到的路径，但不会取消祖先组施加的限制。

cgroup v2 采用统一层级；/sys/fs/cgroup 下可读 memory.current、memory.max、cpu.max、cpu.stat、pids.current 等文件。路径和可用字段取决于版本与控制器。原生 Linux 的 systemd scope 路径、rootless 用户层级与 Desktop VM 不应硬编码成同一个 /sys/fs/cgroup/system.slice/docker-固定ID.scope。

CPU 配额限制时间，亲和性限制可用核心集合

--cpus 0.5 通常映射为每个调度周期允许约半个 CPU 的执行时间总额。多线程可以在多个核心上同时消耗预算，然后在本周期剩余时间被节流。它不承诺响应时间，也不为容器独占一个物理核心的一半。--cpuset-cpus 限定可运行的 CPU 集合，是不同维度。

cpu.stat 的 nr_throttled、throttled_usec 等反映配额节流；较高 CPU 使用率可能是正常负载，低吞吐也可能是锁、网络或磁盘等待。比较工作负载相同时间窗口的计数增量，才能判断配额是否参与瓶颈。docker stats 是取样展示，不能替代延迟分布和事件证据。

内存上限与 OOM 之间还有回收、swap 和受害者选择

内存计费包含进程匿名页、页缓存及部分内核内存，并不等于应用堆。接近硬上限时内核可能回收缓存，允许时还可能换出匿名页；无法满足分配才可能触发 cgroup OOM。--memory-swap 与 --memory 相等用于禁止额外 swap，但要先确认内核与 Engine 支持该控制。

memory.events 中 max、oom、oom_kill 记录不同事件；OOM 不保证永远杀最大进程，也不保证容器主进程是受害者。若主进程被 SIGKILL，容器常以 137 退出；只杀子进程时对象可能仍 running。应用堆应给非堆内存、线程栈、缓存与临时请求留余量，不能把整个容器预算都给堆。

诊断要把症状、限制和对照放到一起

先看 inspect 中退出码、OOMKilled、Error 与资源配置，再看日志和 cgroup 计数；仍运行时用 stats、CPU 事件、应用请求指标区分节流、内存压力和 I/O 等待。Desktop 还要检查 VM 总内存与其他容器竞争，上层约束可比容器自己的限制更紧。

pids.max 达到上限通常导致创建进程或线程失败，不是自动给更多内存；磁盘空间耗尽也不会因调高 CPU 配额消失。只有在相同负载下改变一个预算并观察收益，才有证据认为调参解决了该瓶颈。本课只做受限负载，不关闭 OOM 保护，也不运行 fork bomb。

03 · EXPERIMENT

CPU 节流与两种 137 的受控对照

独立容器 learn-u04-cpu、learn-u04-mem，使用 python:3.12-slim。实验在 96 MiB/64 MiB 内存边界内运行；需保证 cgroup v2 控制有效。所有步骤同一终端执行；不需要启动共用订单应用。

运行之前，先预测

CPU 忙循环会被限制速度还是被直接杀死？随后显式 kill 与内存超额的 ExitCode 相同时，还能用什么区分？

01 · 确认控制器环境

docker info --format 'CgroupVersion={{.CgroupVersion}} CgroupDriver={{.CgroupDriver}}'
docker run --rm python:3.12-slim python -c 'from pathlib import Path; p=Path("/sys/fs/cgroup/cgroup.controllers"); print(p.read_text() if p.exists() else "本课需要 cgroup v2，请先核对运行环境")'

观察：cgroup v2 可用；同时检查 docker info 警告，特别是 memory/swap 控制支持。若不是 v2，不继续套用本课文件名。

解释：先确认控制有效，避免把环境不支持或 rootless 未委派误当作容器行为。

02 · 以半个 CPU 配额运行有界忙循环

docker run -d --name learn-u04-cpu --cpus=0.5 --memory=96m --memory-swap=96m --pids-limit=32 python:3.12-slim python -u -c 'from pathlib import Path; import time; p=Path("/sys/fs/cgroup"); print({f:(p/f).read_text() for f in ("cpu.max","memory.max","pids.max")},flush=True); print("CPU_BEFORE",(p/"cpu.stat").read_text(),flush=True); start=time.monotonic(); cpu=time.process_time(); x=1;
while time.monotonic()-start < 8:
 x=(x*17+3)%1000003
print("CPU_SECONDS",time.process_time()-cpu,"WALL_SECONDS",time.monotonic()-start,flush=True); print("CPU_AFTER",(p/"cpu.stat").read_text(),flush=True); print("MEASURED",flush=True); time.sleep(300)'

观察：日志打印实际预算与前后 CPU 计数，完成测量后容器暂时继续运行。CPU 时间与墙钟时间由调度和机器负载决定，不要求固定比例。

解释：明确预算后，用同一次任务的事件增量验证 CPU 时间限制，而不是凭机器快慢猜测。

03 · 读取计数增量和取样，确认没有把节流当退出

u04_measured() { n=0; until docker logs learn-u04-cpu 2>&1 | grep -q MEASURED; do n=$((n+1)); [ "$n" -lt 40 ] || return 1; sleep 0.5; done; }
u04_measured
docker logs learn-u04-cpu
docker stats --no-stream learn-u04-cpu
docker inspect -f 'Status={{.State.Status}} OOMKilled={{.State.OOMKilled}} NanoCpus={{.HostConfig.NanoCpus}}' learn-u04-cpu

观察：比较 CPU_BEFORE/AFTER 中 nr_throttled 等的增量，容器应仍 running；stats 可能采到测量结束后的空闲期，不能据此否定前面的节流。

解释：累计计数与即时采样回答不同问题，需要对齐观察时间窗口。

04 · 在禁止额外 swap 的边界内触发内存压力

docker run -d --name learn-u04-mem --memory=64m --memory-swap=64m --pids-limit=32 python:3.12-slim python -u -c 'from pathlib import Path; import time; p=Path("/sys/fs/cgroup"); print("memory.max",(p/"memory.max").read_text(),flush=True); blocks=[];
for i in range(32):
 b=bytearray(4*1024*1024)
 for j in range(0,len(b),4096): b[j]=1
 blocks.append(b); print("ALLOCATED_BLOCKS",len(blocks),flush=True); time.sleep(0.1)
print("UNEXPECTED_COMPLETION: 核对内存限制是否生效",flush=True)'
docker wait learn-u04-mem
docker logs learn-u04-mem
docker inspect -f 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}} Memory={{.HostConfig.Memory}} MemorySwap={{.HostConfig.MemorySwap}}' learn-u04-mem

观察：在控制生效时，持续触碰匿名页会超过内存预算，通常出现 OOMKilled=true 与 SIGKILL 对应退出码。若应用先抛 MemoryError 或其他错误，保留真实日志并解释，不能把不同结果改写成预期。

解释：不只是申请虚拟地址，而是实际触碰页；检查配置与 OOM 状态后才归因。

05 · 制造同退出码的非 OOM 对照

docker kill --signal=SIGKILL learn-u04-cpu
docker inspect -f 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' learn-u04-cpu
docker inspect -f 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' learn-u04-mem

观察：显式 kill 的 CPU 容器也常为 137，但没有本次内存 OOM 标记；与前一容器对照并写出根因差别。

解释：相同症状可以来自不同机制，退出码只是线索，不能单独完成诊断。

04 · TRANSFER

换一个条件，还能解释吗

订单 API 一直 running，P99 延迟突然升高。监控显示内存远低于上限，CPU 使用率看似不高；同事建议直接加内存。你有哪些最小证据能判断这个建议是否相关？

提交这些证据

  • 同一负载窗口中 cpu.max 与 cpu.stat 的前后值，特别是节流计数增量。
  • memory.current/max、memory.events 与业务请求时序。
  • Desktop VM 或祖先预算信息，以及一次只改一个变量的前后对照。
对照参考推理

先核对监控分母和采样窗口。一个被限制到 0.5 CPU 的容器即使在宿主机总核心数分母下占比低，也可能持续触发自己的 CPU 配额。

如果节流与高延迟同窗口增长，可在保留相同请求负载下小幅调整 CPU 配额，比较延迟与节流；没有内存压力证据时，加内存缺乏因果依据。

如果没有节流，要继续查 I/O、锁、依赖服务与上层 VM 竞争。用一次改动验证假设，不把“资源”当作单一旋钮。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · cgroups 怎样限制资源？请用 CPU 与内存说明“资源不足”的不同后果以及诊断方法。

查看参考回答与递进追问

cgroups 将进程组织到有祖先约束的层级中，并由控制器分别计费和限制。CPU 配额通常消耗完周期预算后节流；内存硬上限下会先尝试回收，允许时使用 swap，仍不能满足分配时才可能 OOM。pids 控制进程和线程创建。诊断时我先读实际配置，再对齐 cpu.stat、memory.events、应用日志和请求指标；137 还可能来自显式 kill 或停止超时。Desktop 的 VM 和 rootless 的控制器委派也是边界。

追问 1：--cpus 0.5 是绑住半个物理核心吗？

不是。它表达一段周期内的 CPU 时间总额；--cpuset-cpus 才限定可运行核心集合，多线程还可能提前耗尽配额后等待。

追问 2：为什么给 JVM 的堆设置成容器全部内存仍可能 OOM？

容器还计入非堆、线程栈、native 内存、页缓存与其他进程等。堆上限必须留出余量，并用实际峰值和事件验证，不能把两者直接画等号。

追问 3：OOMKilled=false 能完全排除内存相关故障吗？

不能。可能是子进程被杀、应用自己分配失败退出，或其他层级的内存压力。继续看 memory.events、应用错误以及有权限时的内核日志，并明确观察的是哪个 cgroup。

容易混淆：“容器能看到宿主机很多内存，所以没有限制。”工具展示范围、cgroup 预算和 VM 总预算不是同一数值；以实际控制配置和事件为证。

06 · EVIDENCE

用证据判断是否掌握

  1. CPU 时间、内存容量、进程数是不同预算，不能用同一调参方式解决。
  2. 诊断要对齐配置、事件增量与业务负载时间窗。
  3. 137 是 SIGKILL 线索，不是 OOM 的充分证据。
  4. Desktop、rootless、cgroup 版本与祖先限制决定文件和预算如何解释。
