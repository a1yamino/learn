cgroups 与资源诊断

把“给多少”和“用了多少”分开，区分 CPU 节流、内存回收和 OOM。

先想一想

给容器设了 --cpus=1，接口延迟时高时低，可监控显示 CPU 使用率只有 40%。资源明明没用完，为什么会慢？

原理图解推演迁移面试小结
01原理

原理

cgroup 是一份预算

cgroup 把进程分组，再给这一组设上限：CPU 时间、内存、IO、进程数。Docker 为每个容器建一个 cgroup，--cpus、--memory、--pids-limit 写的都是这份预算。

预算和使用量是两回事。监控上的平均使用率很低，不代表某个瞬间没有撞到上限。

CPU 上限按周期切片

--cpus=1 的意思是每 100 毫秒周期内最多用 100 毫秒 CPU 时间。多线程应用可能在前 25 毫秒就用完了配额，剩下 75 毫秒全部被挂起，这就是节流。

看节流要看 cgroup 的 cpu.stat：nr_throttled 和 throttled_usec 在涨，说明请求在等配额。平均使用率被这些空闲时间稀释了，所以看起来不高。

内存上限先回收，再 OOM

接近 --memory 上限时，内核先回收页缓存等可回收内存，应用会变慢。实在回收不下来，cgroup 内的 OOM killer 会杀掉组内一个进程。

被杀的不一定是主进程。子进程被杀时，容器可能还在运行，只是某个功能坏了。memory.events 里的 oom_kill 计数能证明它发生过。

03推演

先猜，再看结果

容器内存上限 512M，Java 服务的堆上限设为 -Xmx512m。运行一段时间后最可能发生什么？

JVM 的内存不止堆：元空间、线程栈、直接内存、JIT 代码都要占。堆刚好等于容器上限，总量必然超标，内核会在 cgroup 内杀进程。通常把堆设成上限的 60%–75%，或用 -XX:MaxRAMPercentage。

示例输出 · 只读
$ docker inspect -f '{{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' api
137 OOMKilled=true
$ cat /sys/fs/cgroup/memory.events   # 容器内
oom 3
oom_kill 1
04迁移

换个场景

一个容器内存没满，CPU 也不高，但服务偶尔报“无法创建新线程”。你会往哪个方向查？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

除了 CPU 和内存，cgroup 还能限制进程数。--pids-limit 或编排平台的默认值可能卡住了线程数，因为在 Linux 上线程也算在 pids 里。

看 pids.current 和 pids.max，再看 pids.events 里的 max 计数。如果确实撞了上限，先查线程是否泄漏，再决定是否调高。

05面试

讲给面试官听

容器 CPU 使用率不高，但延迟很高，你怎么排查？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

先怀疑 CPU 节流。--cpus 按周期给配额，多线程应用可能在周期开头就用完，剩下的时间被挂起，平均使用率反而不高。我会看 cgroup 的 cpu.stat，确认 nr_throttled 和 throttled_usec 是否随延迟同步增长。确认后，要么提高配额，要么减少并行线程，让负载更平滑。

追问：--cpus 和 --cpu-shares 有什么区别？

--cpus 是硬上限，空闲时也不能超用；--cpu-shares 是竞争时的权重，CPU 空闲时容器可以用满。前者保证隔离，后者保证公平。

追问：怎么证明容器发生过 OOM？

docker inspect 的 State.OOMKilled，cgroup 的 memory.events 中 oom_kill 计数，以及宿主机内核日志里的 OOM 记录。只凭退出码 137 不够。

06小结

带走这几句

  1. cgroup 是预算，使用率是结果，两者要分开看。
  2. CPU 配额按周期切片，节流会让延迟升高而平均使用率不高。
  3. 内存先回收再 OOM，被杀的未必是主进程。
