可验证发布：让证据跟随最终运行产物

一次发布从构建到上线，每一步都留下与摘要绑定的证据。

先想一想

测试环境验证过的版本，上线后表现不一样。发布流水线里，哪一步让“测过的”和“上线的”不再是同一份东西？

原理图解推演迁移面试小结
01原理

原理

只构建一次

常见的错误是测试环境和生产环境各自构建一次。依赖、基础镜像、构建机都可能不同，测过的不等于上线的。

正确的流程是只构建一次，得到一个摘要，之后测试、预发、生产都部署这个摘要，环境差异放进配置里。

在最终产物上验证

单元测试跑在源码上，但运行的是镜像。发布前要用最终镜像启动服务，跑一次真实的业务检查：创建一条记录、再读回来。

检查结果连同摘要一起保存。以后有人问“这个版本测过吗”，可以拿出对应摘要的证据。

按摘要部署和回滚

部署清单里写摘要而不是标签。回滚就是部署上一个记录的摘要，内容确定，不会被别人推送的标签影响。

需要多平台时，记录索引摘要；对外发布时，再加上签名和来源证明。

常见误区

每个环境各自构建，才能用各自的配置
配置应该在运行时注入，镜像保持一份。
测试通过的标签就是可以上线的版本
标签可能被再次推送。可上线的是测试时记录下来的那个摘要。

放到生产里

发布记录至少包含：摘要、源码提交、构建时间、验证结果、部署时间和操作人。

回滚也是一次发布，同样要记录，并在回滚后跑同样的业务验证。

03推演

先猜，再看结果

流水线在测试阶段构建 api:1.5 并通过测试，生产阶段又执行了一次 docker build -t api:1.5 再部署。两次的摘要会一样吗？

时间戳、未锁定的依赖、基础镜像标签的更新，都会让两次构建内容不同。即使碰巧相同，你也无法证明。只构建一次，把摘要传给后续阶段。

示例输出 · 只读
test  : sha256:4b1e…c02a
prod  : sha256:d97f…31be
# 同一提交，不同产物
04迁移

换个场景

你们没有云上的镜像仓库和签名服务，只有一台内网服务器。怎么在这种条件下做到可验证发布？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

核心不依赖云服务。在内网跑一个 registry，CI 构建一次并推送，记录摘要；用最终镜像跑业务验证，把输出和摘要写进发布记录。

部署脚本只接受摘要；回滚脚本读取上一条记录。签名可以以后再加，但“同一摘要贯穿始终”这件事现在就能做到。

05面试

讲给面试官听

怎么保证上线的镜像就是测试通过的那个？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

只构建一次，后续所有环境都按同一个摘要部署，环境差异通过配置注入。测试和业务验证在最终镜像上执行，结果与摘要一起记录。部署清单写摘要，回滚换回上一个摘要。需要更强的保证时，再加签名和来源证明，部署时验证。

追问：配置为什么不打进镜像？

打进去就得为每个环境构建一个镜像，测试过的就不是上线的了。配置通过环境变量、挂载文件或配置服务注入。

追问：怎么证明某个线上容器运行的是哪个摘要？

docker inspect 容器看到的 Image 字段是镜像 ID，要对照 RepoDigests；在编排平台上可以看 Pod 状态里的 imageID。

06小结

带走这几句

  1. 只构建一次，摘要贯穿所有环境。
  2. 在最终镜像上做业务验证，并保存证据。
  3. 按摘要部署和回滚，配置在运行时注入。
