可验证发布：让证据跟随最终运行产物

先完成无需云账号的单平台构建、业务验证、内容固定和重新部署，再扩展到仓库摘要、身份验证与多平台发布。

建议 65 分钟，含实验；按观察结果调整进度。

先想一想

CI测试了test阶段，随后重新构建final并推送。部署配置虽然用了digest，为什么仍不能宣称部署的就是刚测试过的产物？

  • 让实际启动的最终镜像与验收证据使用同一内容身份。
  • 演示标签移动后仍能按已验证内容重新部署。
  • 解释本地image ID、仓库manifest digest与多平台证据之间的转换边界。
实验前提

Docker Engine或Desktop、Compose v2、宿主Python3。核心闭环完全本地；发布到远端仓库与cosign签名是可选扩展，要求明确的自有仓库权限和工具，不提供虚构可用地址。

01 · MODEL

建立因果模型

一次构建与一次验收必须连到同一对象

源码测试验证逻辑的一部分，test阶段还可能安装额外依赖、以root运行或省略最终入口。最终镜像的启动、监听、数据卷权限、健康检查与业务请求，应在实际发布运行产物上验证。共享缓存不能代替对象身份。

先取得最终镜像的内容身份，再让启动与验收引用这个对象。单机本地可按image ID启动并对照容器.Image；远端分发需要记录实际仓库manifest或index digest。image ID对应config，不能把它直接伪装成仓库可拉取的manifest摘要。

标签是入口，证据必须绑定不可变内容

candidate、main、版本号都可能重新指向别的镜像。以标签启动后再记录当前标签值，可能已经记录了另一次构建。应在运行前解析身份，并保存运行容器实际.Image、业务验收输出、配置与时间。

重新部署时还要固定适用配置、数据位置和运行环境。镜像内容固定不还原卷、数据库或外部服务，也不保证新旧数据库兼容。本课只对同一实验卷和配置做重部署；真正的回滚需要版本化配置与迁移兼容策略。

推送、扫描、签名和部署各有门禁

单平台在本地验证后可把同一对象推送到自有仓库，再解析真实manifest digest并拉取核对。扫描和签名都应针对该具体对象；部署方还要验证受信身份及必需证据，不能只信任一个可移动标签。核心实验没有远端签名步骤，所以不宣称已具备受信远程发布链。

多平台index需要逐个运行平台child manifest的启动/业务/扫描证据；amd64上的test通过不能覆盖arm64。先只发布已验证单平台是有效的范围选择。CI应使测试、风险或身份门禁失败时部署不执行；仓库里出现候选对象不等于它已被授权上线。

03 · EXPERIMENT

标签被移动后，重新部署同一份已验证内容

从仓库根目录进入docker/labs。项目learn-u16、端口18086和独立数据卷仅供本实验；所有步骤同一终端。无需远端仓库、GitHub账号或签名服务。

运行之前，先预测

把candidate标签改指向nginx后，正在运行的API会变吗？按记录的image ID重建后是否仍能通过订单验收？

01 · 构建最终应用并记录本地身份

cd docker/labs
U16_DIR=$(mktemp -d)
docker build -t learn-u16:candidate .
IMAGE_ID=$(docker image inspect learn-u16:candidate --format "{{.Id}}")
printf "%s
" "$IMAGE_ID" | tee "$U16_DIR/image-id.txt"
docker image inspect "$IMAGE_ID" > "$U16_DIR/image-inspect.json"

观察：得到真实本地config/image ID；不把它写成虚构仓库@digest。

解释：后续运行与证据将绑定同一个已经构建完成的对象。

02 · 按具体内容启动而不是再次按候选标签解析

LAB_IMAGE="$IMAGE_ID" LAB_PORT=18086 docker compose -p learn-u16 up -d --no-build --wait
API_ID=$(docker compose -p learn-u16 ps -q api)
ACTUAL=$(docker inspect "$API_ID" --format "{{.Image}}")
test "$ACTUAL" = "$IMAGE_ID" && printf "actual image matches
"

观察：容器.Image必须与记录的image ID完全一致；启动失败时停止验收。

解释：证明被测容器确实使用该对象，而不是另一次构建或旧标签。

03 · 保留真实运行验收与配置

python3 verify.py http://127.0.0.1:18086 > "$U16_DIR/verify-first.json"
cat "$U16_DIR/verify-first.json"
LAB_IMAGE="$IMAGE_ID" LAB_PORT=18086 docker compose -p learn-u16 config > "$U16_DIR/compose-effective.yaml"
docker inspect "$API_ID" > "$U16_DIR/container-first.json"

观察：verify成功并输出业务JSON；配置和容器证据保留实际用户、挂载和健康状态。

解释：测试对象、声明和运行结果放在同一证据目录。

04 · 移动标签并证明运行对象未随之改变

GATEWAY_ID=$(docker compose -p learn-u16 ps -q gateway)
GATEWAY_IMAGE=$(docker inspect "$GATEWAY_ID" --format "{{.Image}}")
docker image tag "$GATEWAY_IMAGE" learn-u16:candidate
docker image inspect learn-u16:candidate --format "{{.Id}}"
docker inspect "$API_ID" --format "{{.Image}}"
python3 verify.py http://127.0.0.1:18086 > "$U16_DIR/verify-after-tag.json"

观察：candidate标签现在指向本机已存在的nginx内容；运行API仍引用原image ID且业务验收成功。

解释：标签是可移动引用，已创建容器不随标签重标而替换文件系统。

05 · 按已记录内容重部署并保存最终断言

LAB_IMAGE="$IMAGE_ID" LAB_PORT=18086 docker compose -p learn-u16 up -d --no-build --force-recreate --wait api
NEW_API=$(docker compose -p learn-u16 ps -q api)
NEW_ACTUAL=$(docker inspect "$NEW_API" --format "{{.Image}}")
test "$NEW_ACTUAL" = "$IMAGE_ID"
python3 verify.py http://127.0.0.1:18086 > "$U16_DIR/verify-redeploy.json"
docker inspect "$NEW_API" > "$U16_DIR/container-redeploy.json"
printf "evidence directory: %s
" "$U16_DIR"

观察：新容器仍使用被验证的image ID，业务读写成功。若gateway仍缓存旧API地址导致短暂失败，先取证其DNS/上游行为再显式重建gateway；记录这项运行配置边界。

解释：这完成本地最终产物闭环；没有把应用重部署夸大成所有配置与数据均可回滚。

本实验的清理范围与命令
LAB_IMAGE="$IMAGE_ID" LAB_PORT=18086 docker compose -p learn-u16 down -v --remove-orphans
docker image rm learn-u16:candidate
# 将验收JSON与配置复制到发布证据目录后再删除临时文件
rm -rf "$U16_DIR"
04 · TRANSFER

换一个条件，还能解释吗

现在要发布到你有写权限的仓库，并增加arm64。请把本地证据扩展为部署方可验证的发布记录；若没有仓库或目标平台执行环境，明确哪些保证尚未取得。

提交这些证据

  • 自己控制的仓库引用、实际推送后解析的digest，不能填写示例哈希。
  • 每个发布平台child manifest对应的启动/订单/扫描结果，及index到child的对应表。
  • 部署方受信身份验证的正向和错误身份/缺平台证据的负向结果。
对照参考推理

单平台可在设置PUBLISH_REF为自己的实际仓库标签并登录后，将记录的IMAGE_ID打上该标签推送，再用docker buildx imagetools inspect "$PUBLISH_REF"读取真实digest。按真实仓库@digest拉取，检查配置身份和业务；不要把本地image ID直接拼成仓库manifest引用。

多平台需先构建并导出各平台manifest，安排原生节点或明确可用的模拟环境运行最终产物；对每个child收集业务与扫描证据，再组index。缺目标平台验证时可只发布当前已验证单平台，而不是沿用amd64结果。

有cosign与明确身份配置时按实际digest签名，部署前验证受信公钥或OIDC issuer/identity，再检查证据覆盖。无仓库或身份前提时保留本地证据并声明远端链未完成，不能把可选步骤写成已验收。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 设计一条“测试的就是部署的”流水线。为什么部署用了digest还不够？

查看参考回答与递进追问

先构建最终运行产物并取得不可变身份，以它启动真实运行配置，执行健康、业务、权限及必要风险检查并保存证据。推送后取得仓库实际manifest或index digest，将该身份与测试报告、扫描、签名身份连接；部署前验证策略，再按摘要拉取并核对实际实例。digest固定内容，但不自带“测过”的含义；如果只测了另一个test阶段、另一架构或另一次重建，固定部署摘要仍可能部署未经验证的内容。多平台要逐child取证，数据和配置兼容另有门禁。

追问 1：本地image ID能直接当仓库digest吗？

不能，本地image ID通常对应config哈希，仓库引用可能对应manifest或index；推送后必须解析实际仓库摘要。

追问 2：推送之后再扫描，是否一定不能安全发布？

不一定，可先推送候选对象，门禁通过后才授权部署或晋升引用；关键是扫描失败不能触发上线，并明确仓库对象存在与生产授权不同。

追问 3：同一个index只在amd64测试够吗？

不够，arm64可能有不同二进制、系统包和运行问题；必须为发布范围的每个child提供对应运行和风险证据，或缩小发布范围。

容易混淆：一次绿色test阶段、同一Git提交或共享构建缓存，都不能独立证明最终运行镜像已通过验收。

06 · EVIDENCE

用证据判断是否掌握

  1. 证据必须绑定最终运行产物的实际身份。
  2. 本地image ID与仓库manifest/index digest需要明确区分。
  3. 标签移动不改变已运行容器；重新创建时必须重新选择正确内容。
  4. 多平台、受信身份、数据兼容各有独立证据与门禁。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
