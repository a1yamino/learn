运行时安全边界：身份、能力与系统调用

按威胁来理解每一层防护：非 root、capabilities、seccomp、只读根目录和 rootless。

先想一想

一个 Web 应用有远程代码执行漏洞，攻击者在容器里拿到了 shell。接下来他能做到什么，取决于哪些设置？

01原理

原理

先回答“以谁的身份运行”

默认容器以 root 运行。虽然受到限制，但一旦逃逸，就是宿主机的 root。镜像里用 USER 指定一个非 root 的数字 UID，是代价最低的一层防护。

rootless 模式更进一步：连 dockerd 本身都以普通用户运行，容器里的 root 映射成宿主机上的普通用户。

capabilities 拆分 root 的权力

Linux 把 root 的特权拆成几十项能力，比如 NET_ADMIN 改网络、SYS_ADMIN 做挂载。Docker 默认只保留一小部分。--cap-drop ALL 再按需 --cap-add，是最小权限的做法。

--privileged 会给全部能力、关闭 seccomp、开放设备，等于拆掉了大部分边界，不应出现在普通应用里。

seccomp 和只读根目录

seccomp 按系统调用过滤，Docker 的默认配置挡住了几十个危险调用，比如加载内核模块。只读根目录（--read-only）让攻击者无法修改程序文件或留下持久化脚本，需要写的目录用 tmpfs 或卷单独开放。

这些措施针对不同的攻击步骤，彼此不能替代。

默认配置已经挡住了什么

Docker 默认只给容器保留了十几项能力，比如 CHOWN、NET_BIND_SERVICE、KILL，像 SYS_ADMIN、NET_ADMIN、SYS_MODULE 都被去掉了。默认 seccomp 配置拦截了数十个系统调用，例如 mount、reboot、kexec_load，以及在不需要时用于创建新 user namespace 的调用。

此外，在支持的系统上还会加载 AppArmor 或 SELinux 策略，限制对 /proc、/sys 中敏感路径的访问。这些都是默认就有的，--privileged 会一并关掉。

逃逸通常从哪里开始

常见的逃逸路径并不神秘：挂载了 docker.sock；以 --privileged 运行；把宿主机的根目录或 /proc 挂进来；容器内以 root 运行又恰好遇到内核漏洞。

前三种都是配置问题，完全可以通过审查避免。第四种靠非 root、seccomp 和及时更新内核来降低风险。

走一遍：给一个服务收紧权限

  1. 起点：服务以 root 运行，默认能力，可写根目录。
  2. 第一步：镜像里加 USER 10001，确认服务不需要绑定 1024 以下的端口，或者改成监听 8080。
  3. 第二步：--cap-drop ALL 启动，观察是否报错。大多数 Web 服务不需要任何能力。
  4. 第三步：--read-only，再为 /tmp 加 --tmpfs，为上传目录挂卷。最后加 --security-opt no-new-privileges。每一步都跑一次业务验证。

常见误区

非 root 运行就足够安全
非 root 降低了风险，但内核漏洞仍然可能被普通用户触发，其他层的防护依然需要。
rootless 模式没有代价
rootless 下部分网络功能和性能有差异，比如端口绑定和某些存储驱动受限，需要提前验证。

放到生产里

在 CI 中扫描 compose 和部署配置，拒绝 privileged、docker.sock 挂载、hostPath 根目录这类危险配置。

保持宿主机内核和 Docker 更新，很多容器逃逸漏洞的修复在内核和运行时里。

03推演

先猜，再看结果

容器以 --read-only 运行，应用启动时需要往 /tmp 写临时文件。会发生什么？

--read-only 让整个根目录只读，包括 /tmp。需要显式加 --tmpfs /tmp，或为数据目录挂卷。这样能写的地方清清楚楚。

示例输出 · 只读
$ docker run --rm --read-only app sh -c 'echo x > /tmp/a'
sh: can't create /tmp/a: Read-only file system
$ docker run --rm --read-only --tmpfs /tmp app sh -c 'echo x > /tmp/a && echo ok'
ok
04迁移

换个场景

监控 agent 的文档要求以 --privileged 运行。你只想让它读取主机的进程和网络统计。怎么评估和收紧？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

先列出它真正需要的东西：读 /proc 可能需要 --pid=host，读网络统计可能需要 --network=host 或某个能力，读 cgroup 需要挂载 /sys/fs/cgroup 为只读。

逐项给，而不是一次全给。用 --cap-drop ALL 起步，按报错补能力，并保留默认 seccomp。最后记录每一项的理由，方便审计。

05面试

讲给面试官听

怎么加固一个容器的运行时安全？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

从威胁出发分层做。镜像里用非 root 的数字 UID；--cap-drop ALL 再按需加回；保留默认 seccomp；--read-only 加上必要的 tmpfs；禁止 --privileged 和挂载 docker.sock；设置 --security-opt no-new-privileges 防止通过 setuid 提权。条件允许时使用 rootless 或 user namespace。

追问：no-new-privileges 防什么？

防止进程通过 setuid 程序或文件能力获得比父进程更多的权限，比如利用 sudo 或带 setuid 位的二进制提权。

追问：非 root 运行之后还需要 seccomp 吗？

需要。内核漏洞可以被普通用户的系统调用触发，seccomp 减少了可被攻击的内核接口。

06小结

带走这几句

  1. 非 root 是代价最低的一层，rootless 进一步隔离守护进程。
  2. cap-drop ALL 加按需添加；不用 --privileged。
  3. seccomp、只读根目录各自挡住不同的攻击步骤。
