运行时安全边界：身份、能力与系统调用

用威胁与可观察权限解释非root、capabilities、seccomp、只读挂载和rootless，避免把安全参数当成相同的防护层。

建议 60 分钟，含实验；按观察结果调整进度。

先想一想

容器已经USER 10001，为什么还要cap_drop和no-new-privileges？根文件系统只读后订单还能写入，又说明隔离失效了吗？

  • 按操作解释限制来自UID、capability、seccomp还是文件系统。
  • 在删除不必要权限后验证应用仍能读写订单。
  • 说明容器root、userns-remap与rootless的不同宿主权限边界。
实验前提

Docker Engine或Desktop。实机使用共用标准库API，不需要privileged或Docker socket挂载。rootless、userns及Linux安全模块的效果依实际环境而异，先记录配置。

01 · MODEL

建立因果模型

先定义攻击者能做的操作

假设应用被攻破，攻击者得到应用进程权限。非root减少对root拥有文件的写入与特权操作；capabilities把传统root权限拆成较小能力；seccomp限制系统调用；挂载权限决定哪些路径可写。它们覆盖不同操作，不能简单画成攻击者必须逐个穿透的六道完全独立墙。

Docker socket是另一类边界：拥有rootful daemon控制权通常可创建挂载宿主目录的高权限容器。给一个非root容器挂docker.sock，不会因为USER是10001就自动安全；socket访问权限、daemon身份和授权策略都要单独考虑。本课不需要挂入socket。

身份与提权通道不是同一件事

默认rootful且未启用user namespace时，容器UID 0在宿主也是UID 0，但受namespaces、能力和安全模块等限制。USER 10001选择运行身份；userns-remap把容器UID映射为宿主的非rootID；rootless进一步让daemon以普通用户运行。它们解决的风险不同。

no-new-privileges阻止通过exec时的setuid或文件capability获得额外权限，不撤销当前已经拥有的权限。cap_drop: ALL从能力上限删掉能力，但也不能代替非root或只读挂载。判断效果要读取实际进程与宿主映射，不能只看Compose字段出现了几次。

只读根与可写数据要共同设计

read_only限制容器根文件系统写入，命名卷与tmpfs仍可按配置写入。订单API将持久数据放/data，临时文件可放/tmp；因此根只读和订单写入成功可以同时成立。这是在缩小可写范围，而不是全局禁止write系统调用。

最小权限设计从必需操作出发：该标准库API监听8000，无需绑定低端口，也不需CHOWN、NET_ADMIN、SYS_ADMIN等能力。默认seccomp继续使用，不因一条EPERM便关闭全部过滤。发生拒绝时先识别路径、身份、能力和调用证据，再做范围最小的调整。

03 · EXPERIMENT

以最少权限运行同一个订单API

从仓库根目录进入docker/labs；独立项目learn-u14，只修改临时Compose覆盖文件。宿主有Python3，端口8080空闲。

运行之前，先预测

cap_drop ALL与根只读后，哪些操作仍必须成功？/app下写文件与/data下写订单预期各是什么结果？

01 · 明确安全覆盖配置

cd docker/labs
U14_CFG=$(mktemp)
cat > "$U14_CFG" <<'EOF'
services:
  api:
    user: "10001:10001"
    read_only: true
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    tmpfs: [/tmp]
EOF
docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" config

观察：确认api最终配置包含运行用户、只读根、能力删除、提权限制；/data保留命名卷。

解释：先检查合并结果，避免覆盖文件没有作用却误以为安全测试通过。

02 · 启动并执行真实业务验收

docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" up -d --build --wait
python3 verify.py http://127.0.0.1:8080

观察：verify创建订单并读回，输出JSON证据；不是只检查/health。

解释：删掉多余权限不应破坏明确需要的业务写入。

03 · 观察真实身份和能力状态

docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" exec -T api python -c "import os; print('uid/gid',os.getuid(),os.getgid()); print(''.join(x for x in open('/proc/self/status') if x.startswith(('CapEff:','CapBnd:','NoNewPrivs:','Seccomp:'))))"

观察：uid/gid应为10001；CapEff与CapBnd应为0；NoNewPrivs应为1。Seccomp字段按宿主支持与实际配置解释，通常2表示过滤模式。

解释：从进程观察配置结果，不能把参数名当生效证据。

04 · 负向与正向文件写入对照

docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" exec -T api python - <<'PY'
from pathlib import Path
for name in ("/app/should-not-write","/tmp/learn-u14.txt","/data/learn-u14.txt"):
    try:
        Path(name).write_text("probe")
        print(name,"WRITE_OK")
    except OSError as e:
        print(name,type(e).__name__,e.errno)
PY

观察：/app写入应失败；/tmp与/data写入应成功。记录errno，区分只读文件系统与普通权限拒绝。

解释：定位拒绝来自路径挂载还是身份权限；根只读不意味着所有挂载都只读。

05 · 检查宿主映射与最终配置

docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" exec -T api cat /proc/self/uid_map
API_ID=$(docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" ps -q api)
docker inspect "$API_ID" --format "{{.Config.User}} {{.HostConfig.ReadonlyRootfs}} {{json .HostConfig.CapDrop}} {{json .HostConfig.SecurityOpt}}"
docker info --format "{{json .SecurityOptions}}"

观察：uid_map和SecurityOptions用于判断当前是否userns/rootless；不预设所有环境都相同。inspect应对应覆盖配置。

解释：容器内身份、宿主映射与daemon身份应分别说明。

本实验的清理范围与命令
docker compose -p learn-u14 -f compose.yaml -f "$U14_CFG" down -v --remove-orphans
rm -f "$U14_CFG"
04 · TRANSFER

换一个条件，还能解释吗

某服务改为USER 10001后写卷被拒绝，管理员提议加privileged。你如何区分挂载权限问题与能力问题，并完成最小修复？

提交这些证据

  • 失败路径、errno、进程UID/GID与uid_map。
  • 卷挂载是否只读、目标目录实际owner/mode，以及宿主或卷内映射。
  • 修复后的业务写入与原有根只读、能力限制仍生效的负向证据。
对照参考推理

先看失败操作是否普通文件写入。核对卷内目录owner/mode是否允许10001写，以及挂载是否只读；这类错误不需要先猜SYS_ADMIN或关闭seccomp。

若为新卷初始化属主问题，在构建或受控初始化阶段赋给正确UID/GID，明确只调整本服务数据目录；启用userns时还要考虑映射。不要为了chmod整个宿主路径而扩大权限。

重新以非root运行，执行订单写入并复查cap/只读边界。privileged会放开大量无关能力与设备，不能作为文件权限的通用修复。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 容器里的root是不是宿主root？非root、capabilities、seccomp、no-new-privileges和rootless应该如何组合解释？

查看参考回答与递进追问

默认rootful且无userns时UID数值共享，容器root仍是UID0，但它处在namespaces和安全限制中，不拥有所有宿主能力。USER选择应用身份，capabilities限制特权操作，seccomp过滤系统调用，no-new-privileges阻止exec获取新权限；userns映射容器UID，rootless让daemon也以普通用户运行。按威胁与操作选组合，再验证身份、映射、能力位图、挂载和业务行为。任何单个字段都不等于抵御所有内核或配置风险。

追问 1：非root监听8000需要NET_BIND_SERVICE吗？

不需要，8000不是传统低端口；低端口行为还受网络空间sysctl等影响，不能靠固定能力清单猜。

追问 2：no-new-privileges能撤销已经拥有的root权限吗？

不能，它约束未来exec的额外权限获得；当前UID和能力仍需单独限制。

追问 3：rootless为什么仍不能代替补内核漏洞？

容器仍使用Linux内核；rootless降低daemon和映射权限暴露，不保证没有内核提权或其他共享内核漏洞。

容易混淆：EPERM不是“缺privileged”的同义词；只读根也不是“数据卷必须不能写”。

06 · EVIDENCE

用证据判断是否掌握

  1. 每项安全机制应对应具体威胁与可观察操作。
  2. 运行身份、宿主UID映射与daemon身份分别核对。
  3. 业务可用和越权拒绝必须双向验证。
  4. 从失败路径与errno找根因，不用privileged吞掉边界。
