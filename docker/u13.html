Compose：期望状态、就绪与运行中恢复

分清“已启动”“已健康”“能恢复”，让一次 up 之后的系统也站得稳。

先想一想

depends_on 里写了 db，api 却还是在启动时连不上数据库，崩溃退出。依赖不是已经声明了吗？

原理图解推演迁移面试小结
01原理

原理

Compose 描述的是期望状态

compose.yaml 写的是“应该有哪些服务、用什么镜像、接哪些网络和卷”。docker compose up 对比当前状态和期望状态，只创建或重建有差异的容器。

改了某个服务的镜像或配置再 up，只有它会被重建，其他服务不动。

启动顺序不等于就绪

depends_on 默认只保证 db 容器先启动，不等它能接受连接。数据库启动可能需要好几秒。

给 db 写 healthcheck，再在 api 里用 depends_on 的 condition: service_healthy，Compose 会等到健康检查通过才启动 api。

启动之后，还要能恢复

condition 只管启动那一刻。运行中数据库重启了，api 必须自己会重连。restart: unless-stopped 只在进程退出时重启，不会因为 unhealthy 自动重启。

所以可靠性要分三层：启动时等待依赖，运行时应用重试重连，进程崩溃时由重启策略拉起。

03推演

先猜，再看结果

api 设置了 restart: always。运行中它的健康检查持续失败，状态变成 unhealthy。Docker 会怎么做？

单机 Docker 和 Compose 的重启策略只看进程是否退出。unhealthy 只是一个状态，需要监控或编排平台（比如 Swarm、Kubernetes 的存活探针）去处理。

示例输出 · 只读
$ docker compose ps api
NAME   STATUS
api    Up 12 minutes (unhealthy)
04迁移

换个场景

凌晨数据库主机做了维护重启，之后 api 一直报“连接已关闭”，直到有人手动重启 api 才恢复。怎么让它自己恢复？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

问题在应用的连接池：旧连接断了，却没有检测和重建。启动依赖和重启策略都管不到这里，因为 api 进程一直活着。

让连接池在取用前做校验，失败时带退避重试；同时让 /ready 真实反映数据库是否可用，便于监控发现。修完以后，可以在测试环境重启 db，确认 api 能在不重启的情况下恢复。

05面试

讲给面试官听

Compose 里 depends_on 能保证什么，不能保证什么？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

默认只保证启动顺序：被依赖的容器先创建并启动。加上 condition: service_healthy 能保证在依赖健康检查通过后才启动，但只作用于启动那一刻。运行中依赖重启或断线，Compose 不会处理，需要应用自己重连。重启策略只在进程退出时生效。

追问：健康检查应该检查什么？

检查服务真正能做事，比如数据库能执行查询、API 能连到依赖。但要轻量、快速，避免把一次依赖抖动放大成连锁失败。

追问：修改 compose.yaml 后 up 会重启所有服务吗？

不会。Compose 只重建配置或镜像有变化的服务，以及依赖它而需要重建的服务。

06小结

带走这几句

  1. Compose 对比期望状态，只重建有差异的服务。
  2. depends_on 默认不等就绪，需要 healthcheck 配合。
  3. 运行中的恢复靠应用重连，重启策略只看进程退出。
