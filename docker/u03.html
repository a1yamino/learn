PID 1、信号与容器生命周期

把容器对象、一次进程运行和数据分开看，弄清 docker stop 背后发生了什么。

先想一想

一个容器 docker stop 总要等满 10 秒才停下，退出码是 137。它是被内存撑爆了吗？

原理图解推演迁移面试小结
01原理

原理

容器对象活得比进程久

create 生成一个容器对象，记下镜像、参数和挂载；start 在里面启动主进程。主进程退出后容器变成 exited，但对象和可写层还在。再次 start，是在同一个对象里启动一个新进程。

restart 只是停了再启，用的还是创建时的那个镜像。想换新版本，要删掉容器重新创建。

stop 先礼后兵

docker stop 先给主进程发停止信号，默认是 SIGTERM，可以被 STOPSIGNAL 或 --stop-signal 改掉。默认等 10 秒，主进程还没退出，就发 SIGKILL。SIGKILL 不能被捕获，应用没有机会收尾。

退出码 137 等于 128 加 9，只说明进程被 SIGKILL 结束。它可能来自超时，也可能来自 OOM 或手动 kill，要再看 State.OOMKilled 和日志才能下结论。

信号能不能到达应用，看 PID 1 是谁

如果 CMD 写成 shell 形式，PID 1 往往是 /bin/sh，它不会把 SIGTERM 转给子进程，应用就一直收不到信号，只好等到超时被杀。用 exec 形式，或在入口脚本最后一行写 exec，让应用自己成为 PID 1。

PID 1 还有一个职责是回收孤儿进程。应用会派生子进程时，可以加 --init，让一个小 init 负责转发信号和回收。它不会替应用做业务上的收尾。

03推演

先猜，再看结果

Dockerfile 里写的是 CMD python app.py（shell 形式），应用代码正确处理了 SIGTERM。docker stop 会怎样？

shell 形式会让 /bin/sh -c 成为 PID 1。有些 shell 会把单条命令直接 exec 掉，但不能指望。sh 作为 PID 1 时不转发 SIGTERM，应用收不到，最终超时被杀。改成 CMD ["python", "app.py"] 最稳。

示例输出 · 只读
$ time docker stop api
api
real    0m10.31s
$ docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' api
137 false
04迁移

换个场景

入口脚本做完初始化后，最后一行是 python app.py serve，镜像用的是 exec 形式 ENTRYPOINT ["/entrypoint.sh"]。stop 依然要等满宽限期。问题出在哪？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

exec 形式只保证 Docker 没有额外插一层 shell。PID 1 是 entrypoint.sh 本身，它启动 Python 作为子进程，自己并不转发信号。

把最后一行改成 exec python app.py serve，让 Python 替换掉脚本进程，成为 PID 1。修完以后，再用一个正在进行的慢请求去验证：请求成功返回、日志里有关闭完成、退出码为 0，才算真的优雅退出。

05面试

讲给面试官听

讲讲 docker stop 从发出到容器退出的全过程。

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

stop 先向主进程发送配置的停止信号，默认 SIGTERM，然后等待宽限期，默认 10 秒。应用应该在这段时间里停止接新请求、处理完在途工作、关闭连接再退出。超时后 Docker 发 SIGKILL 强制结束。退出后容器是 exited 状态，对象和可写层还在，rm 才会删除。信号能否到达应用，要看 PID 1 是不是应用本身。

追问：退出码 137 一定是 OOM 吗？

不一定。137 只说明进程被 SIGKILL 结束，停止超时、docker kill、OOM 都会导致。要看 State.OOMKilled、内核日志和事件时间线。

追问：--init 能代替应用处理 SIGTERM 吗？

不能。它负责转发信号和回收僵尸进程，但不知道你的请求、事务和连接该怎么收尾。业务上的优雅退出仍要应用自己实现。

06小结

带走这几句

  1. 容器对象、进程运行、数据是三种不同的寿命。
  2. stop 先发 SIGTERM，超时再 SIGKILL；137 不等于 OOM。
  3. 用 exec 形式或 exec 包装，让应用自己当 PID 1。
