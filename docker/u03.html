PID 1、信号与容器生命周期

把进程退出、容器状态和数据生命周期分开，用正在进行的请求证明优雅退出。

建议 50 分钟，含实验；按观察结果调整进度。

先想一想

一个容器 docker stop 用了很短时间，能证明它优雅退出了吗？另一个退出码是 137，能直接判定内存不足吗？

  • 解释 create、start、stop、restart、rm 对对象、进程、可写层分别做什么。
  • 沿 PID 1 和进程树说明信号路由、exec 包装与 init 的作用。
  • 用请求结果、关闭日志和退出状态验证停止过程。
实验前提

Linux 容器，Docker Compose、curl、可读写临时目录的本机 shell。Desktop 的 PID 位于 Linux VM；实验只用 Docker API，不需要宿主机 root。独立项目 learn-u03 使用本机 18003 端口，需确保端口未占用。

01 · MODEL

建立因果模型

容器对象的寿命长于一次进程运行

create 保存镜像引用、启动参数、挂载配置等并创建容器对象；start 在这个对象中启动主进程。默认隔离模式下，它在自己的 PID namespace 中是 PID 1。主进程退出后对象变成 exited，可写层与配置通常保留；再次 start 运行新的进程，但复用这个容器对象。

run 可理解为创建并启动；restart 停止后启动现有对象，不会重新拉取标签或换用新镜像。rm 删除对象与可写层，命名卷另有生命周期。created、running、paused、exited 是理解主线的简化状态，实际还可能有 restarting、removing、dead，删除终点不是一个仍可 inspect 的状态。

PID 1 的职责与包装进程决定信号到哪里

docker stop 首先向主进程发送配置的停止信号，未配置时为 SIGTERM。镜像 STOPSIGNAL、创建时 --stop-signal 以及支持该选项的 stop 命令都可能改变它。Linux 容器未配置停止时长时通常等待 10 秒，超过期限再发 SIGKILL；本课显式使用 -t 15，避免依赖默认值。

exec 形式不额外经过 shell；入口脚本中的 exec 会用应用替换脚本进程，保留 PID 并减少信号转发问题。shell 包装可能吞掉信号，也可以主动 trap/转发；因此不能说所有 shell 形式必然等满 10 秒。PID 1 还要正确回收孤儿子进程，--init 提供小型 init 辅助转发与回收，但不会为应用实现业务清理逻辑。

优雅退出是应用协议，不是一个计时成绩

订单应用收到停止信号后应停止接收新工作，等待在途请求完成，提交或关闭必要资源，然后退出。在途工作持续时间、代理超时和停止宽限期需要匹配。即便应用立即退出，也可能丢掉未完成响应；即便正确处理信号，超长请求也可能超过宽限期。

需要同时检查请求是否成功、REQUEST_STARTED/REQUEST_FINISHED 是否完整、SHUTDOWN_REQUESTED/SHUTDOWN_COMPLETE 是否出现，以及最终退出码。正常退出码与完整日志是多条证据，不是数学保证；还要按业务契约检查订单是否落盘。SIGKILL 不能被捕获，缺少收尾机会。

状态、健康与重启策略回答不同问题

running 说明主进程仍存活，不保证 API 可以接受请求；健康检查报告应用状态，不等于进程退出。普通 Docker/Compose 的 restart 策略针对进程退出，不会仅因 unhealthy 自动重启。pause 冻结进程执行，与应用主动退出或端口就绪也不同。

137 常对应 128+SIGKILL，可能由显式 docker kill、停止超时、cgroup OOM 等造成。先结合 OOMKilled、State.Error、日志与资源事件判断。启动新镜像版本要重建容器；仅 restart 会继续运行原对象中已确定的镜像。

03 · EXPERIMENT

在慢请求中停止 API，再验证独立容器的可写层

从仓库根目录进入 docker/labs，同一终端按顺序执行。项目 learn-u03 与对照容器 learn-u03-layer 均为本课独立环境；端口 18003 空闲。请等待就绪检查成功后继续；若超时先查看 api/gateway 日志。

运行之前，先预测

slow 请求已开始后执行 stop -t 15，应该先出现哪些证据？独立容器停止再启动时，真正写在其可写层的标记是否仍在？

01 · 启动独立项目并等待 API 真正就绪

cd docker/labs
LAB_PORT=18003 docker compose -p learn-u03 up -d --build
U03_API=$(docker compose -p learn-u03 ps -q api)
u03_ready() { n=0; until curl -fsS http://127.0.0.1:18003/ready; do n=$((n+1)); [ "$n" -lt 40 ] || return 1; sleep 0.5; done; }
u03_ready

观察：ready 请求成功；记录实际容器 ID。重试只等待应用就绪，不能把无限重试用作隐藏错误。

解释：容器 Started 与业务就绪不同，不能用固定 sleep 预设本机速度。

02 · 记录 Compose API 的启动命令与停止信号

docker exec "$U03_API" python -c 'from pathlib import Path; print(Path("/proc/1/cmdline").read_bytes().replace(b"\0",b" "))'
docker inspect -f 'ID={{.Id}} Image={{.Image}} StopSignal={{.Config.StopSignal}} ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}}' "$U03_API"

观察：主进程命令指向 python app.py serve；保留实际 ID 和 Image。StopSignal 为空时按默认 SIGTERM 解释。

解释：把信号目标固定下来。共用 Compose 的根文件系统只读，/tmp 是 tmpfs，/data 是命名卷；它们都不能证明容器可写层在 stop/start 后保留。

03 · 启动慢请求，确认处理已开始后才发送停止

U03_RESPONSE=$(mktemp)
curl -fsS 'http://127.0.0.1:18003/slow?seconds=3' > "$U03_RESPONSE" &
U03_CLIENT=$!
u03_started() { n=0; until docker logs "$U03_API" 2>&1 | grep -q REQUEST_STARTED; do n=$((n+1)); [ "$n" -lt 40 ] || return 1; sleep 0.1; done; }
u03_started && docker stop -t 15 "$U03_API"

观察：检测到 REQUEST_STARTED 后才执行 stop；请求时长是实验输入，不是对停止耗时的固定承诺。本次应使用新项目，避免旧日志误触发。

解释：先建立确有在途请求的前提，才能检验停止过程有没有排空工作。

04 · 联合请求、日志和退出状态验收

wait "$U03_CLIENT"
cat "$U03_RESPONSE"
docker logs "$U03_API"
docker inspect -f 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' "$U03_API"

观察：curl 成功返回，日志有请求开始/完成和关闭请求/关闭完成，最终 exited 且没有 OOM。不能用精确秒数或单条日志替代这些断言。

解释：请求成功证明客户端契约，完成日志说明排空，退出状态帮助排除强制终止或 OOM。

05 · 独立容器两次启动，验证真正的可写层

U03_IMAGE=$(docker inspect -f '{{.Image}}' "$U03_API")
docker create --name learn-u03-layer --user 0 --entrypoint python "$U03_IMAGE" -c 'from pathlib import Path; p=Path("/app/u03-marker"); print("EXISTED_BEFORE",p.exists()); p.write_text("same container object\n") if not p.exists() else None; print("CONTENT",p.read_text().strip())'
docker start -a learn-u03-layer
docker diff learn-u03-layer
docker start -a learn-u03-layer
docker inspect -f 'ID={{.Id}} Image={{.Image}} ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}}' learn-u03-layer

观察：第一次 EXISTED_BEFORE False，第二次 True；两次 CONTENT 相同，docker diff 显示 /app 下新增标记，ID 与 Image 不变。此独立容器默认可写根文件系统且无 /app 卷或 tmpfs。

解释：start 复用同一容器对象和可写层，但重建主进程。镜像默认 USER 10001 对 /app 目录无写权限，故此受控对照显式 --user 0；不要把它误当作共用 Compose 的安全配置。

本实验的清理范围与命令
docker rm -f learn-u03-layer
docker compose -p learn-u03 down -v
[ -z "${U03_RESPONSE:-}" ] || rm -f "$U03_RESPONSE"
unset U03_API U03_IMAGE U03_RESPONSE U03_CLIENT
# 仅删除 learn-u03 的实验容器、网络、卷和独立可写层对照容器。
04 · TRANSFER

换一个条件，还能解释吗

换成一个自定义入口脚本后，stop 常在宽限期结束时才退出，慢请求也失败。脚本最后一行是 python app.py serve，但镜像使用了 exec 形式 ENTRYPOINT。你会如何排查？

提交这些证据

  • 提供 /proc/1/cmdline 和进程父子关系，确认 PID 1 是否入口脚本。
  • 提供停止信号、宽限期、请求结果以及关闭完成日志是否存在。
  • 修复后重新执行在途请求停止实验，并对照同样的断言。
对照参考推理

exec 形式只保证 Docker 没额外插入 shell，不保证脚本内部最后启动的应用会自动取代脚本。先确认脚本是否把 Python 留作子进程，是否转发信号。

若脚本完成初始化后只需运行该应用，可把最后一行写成 exec python app.py serve；若脚本要管理多个进程，需实现转发和回收，不能机械替换。

再检查应用是否实际处理停止信号、3 秒请求是否在宽限期内，代理是否先超时。只有请求和关闭证据均完整，才可判定本次契约成立。

05 · INTERVIEW

面试中讲清原理

01 · 解释 docker stop 到容器退出的完整过程，并说明怎样证明服务优雅退出。

查看参考回答与递进追问

先找容器主进程和配置的停止信号。stop 向主进程发送信号，应用应停止接收新工作、排空在途请求并关闭资源，在宽限期内退出；超时后 Docker 发 SIGKILL。包装脚本可能需要 exec 或显式转发。我要用真实在途请求的结果、处理完成与关闭完成日志、退出状态一起证明，而不是只报一个很短的停止耗时。exited 后对象和可写层仍在，rm 才删除对象；命名卷另算。

追问 1：为什么服务 PID 1 活着却访问不了？

进程存活只证明 running；应用可能未绑定预期地址、未初始化数据库或卡住。要分别检查监听、/health、/ready 和业务请求。restart 策略不会自动解决 unhealthy。

追问 2：--init 能替代应用的 SIGTERM 处理吗？

不能。它帮助信号转发和孤儿子进程回收，但不知道订单事务、连接和在途请求如何完成；业务排空仍由应用实现。

追问 3：137 能证明 OOM 吗？怎么验证边界？

137 常表明 SIGKILL，显式 kill 或停止超时也可造成。结合 OOMKilled、cgroup memory.events、停止时序与日志判断；子进程被 OOM 杀死时主进程还可能继续运行。

容易混淆：“exec 形式就必然优雅退出。”它改善启动和信号路径；应用信号处理、在途工作、资源清理和宽限期仍决定最终行为。

06 · EVIDENCE

用证据判断是否掌握

  1. 区分容器对象、一次主进程运行和持久数据的寿命。
  2. 信号路由取决于 PID 1 与包装层，信号处理取决于应用。
  3. 优雅停止必须以在途请求和收尾证据验收。
  4. restart 不更新镜像；退出、健康与就绪是不同契约。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
