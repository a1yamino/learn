01原理

原理

交付：从提交到摘要

Dockerfile 先装依赖再拷源码，非 root 运行，exec 形式启动。CI 构建一次，生成 SBOM 和来源证明，签名后推送，记录索引摘要。

用最终镜像跑一次业务验证，结果和摘要一起存档。生产按摘要部署，配置在运行时注入。

运行：边界与恢复

Compose 或编排平台里，数据放命名卷，数据库有健康检查，api 等它健康再启动，并能自己重连。资源设置上限，堆和线程数与上限匹配。

安全上 cap-drop ALL、只读根目录加 tmpfs、端口只绑定需要的地址。备份用一致快照，定期恢复演练。

值班：从症状到根因

出问题时按层排查：名字、连接、应用、资源、数据。停止服务时确认优雅退出；看到 137 先查 OOMKilled；看到 refused 去查监听。

每次事故记录时间线，把这次学到的检查加入发布前的验证里。

毕业前的自查清单

镜像：基础镜像按摘要固定；依赖锁定；非 root；exec 形式启动；.dockerignore 排除了密钥和无关文件。

交付：只构建一次；SBOM、来源证明、签名都绑定摘要；最终镜像上做过业务验证；部署和回滚都按摘要。

运行：资源上限经过压测；健康检查合理；应用能重连；cap-drop ALL、只读根目录；端口只绑定必要的地址。

数据：卷与备份分离存放；恢复演练有记录；知道自己的恢复点和恢复时间。

走一遍：值班第一天的一次告警

  1. 02:10 告警：订单接口错误率升高。先看网关日志，错误是 upstream timed out，不是 refused。
  2. 超时指向处理慢。查 api 的 cpu.stat，节流计数在告警时间附近陡增；docker events 显示 01:55 有一次发布。
  3. 对比新旧版本：新版本引入了一个并行的报表任务，和请求抢配额。按摘要回滚止血，错误率恢复。
  4. 第二天修复：报表任务拆成独立服务，单独设配额。在发布前的压测中加入 cpu.stat 检查，并写下这次的时间线。

03推演

先猜，再看结果

综合推演：新版本上线后 api 每隔几分钟重启一次，日志最后一行是正常请求，退出码 137，OOMKilled=true。最合理的第一步修复方向是？

OOMKilled=true 明确指向内存超过 cgroup 上限。新版本引入了更多内存占用，或运行时（如 JVM 堆、工作进程数）配置超过了上限。先用 memory.events 和监控确认，再调整配置或修复内存增长，同时按摘要回滚止血。

示例输出 · 只读
$ docker inspect -f '{{.RestartCount}} {{.State.ExitCode}} {{.State.OOMKilled}}' api
7 137 true
$ docker stats --no-stream api
NAME  CPU %   MEM USAGE / LIMIT
api   34.1%   497MiB / 512MiB
04迁移

换个场景

毕业挑战：数据库卷所在的磁盘坏了。你只有昨晚的备份、发布记录和 compose.yaml。请写出恢复服务并证明恢复成功的完整步骤。

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

在新磁盘上建新卷；从异地取回昨晚的备份，核对校验和，恢复到新卷。按发布记录里的摘要启动数据库，等健康检查通过，再按摘要启动 api。

证明恢复：/ready 返回成功；创建一条新订单并读回；核对备份时刻之前的最后一笔订单存在。最后说明数据丢失的窗口（备份之后到故障之间），并记录时间线和改进项，比如缩短备份间隔。

05面试

讲给面试官听

请完整地讲一讲：你会怎样把一个服务容器化并安全、可靠地交付上线？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

镜像层面，先依赖后源码以利用缓存，多阶段构建只保留运行所需，非 root、exec 形式启动。交付层面，构建一次，生成 SBOM、来源证明并签名，记录摘要，在最终镜像上做业务验证，按摘要部署和回滚。运行层面，数据放卷并做恢复演练，健康检查配合依赖等待，应用自己重连，设置资源上限，cap-drop ALL、只读根目录、不暴露不需要的端口。出了问题按层排查，用证据说话。

追问：如果只能做三件事，你选哪三件？

按摘要部署和回滚；数据备份加恢复演练；非 root 加最小权限。它们分别守住了版本确定性、数据和安全边界，成本也都不高。

追问：容器和 Kubernetes 的关系，你怎么向新人解释？

Docker 解决单个应用的打包和运行；Kubernetes 管理很多台机器上的很多容器，负责调度、扩缩、自愈和服务发现。底层仍然是 OCI 镜像和容器运行时。

追问：回顾这门课，你认为最容易被误解的一点是什么？

“能启动”不等于“能用”，“能用”不等于“能恢复”。几乎每一课的坑都出在把这些状态当成了一回事。

06小结

带走这几句

  1. 交付：构建一次，证据和部署都绑定摘要。
  2. 运行：健康、限额、最小权限，数据能恢复。
  3. 值班：分层排查，用证据证明根因与恢复。
