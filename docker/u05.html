01原理

原理

CLI 只是一个 API 客户端

docker 命令把请求发给 dockerd 的 HTTP API，通常走本机的 unix socket。能访问这个 socket，就等于能让 dockerd 以 root 身份做任何事，所以把用户加进 docker 组相当于给了 root。

DOCKER_HOST 或 context 可以让 CLI 连到远程的 dockerd，命令看起来一样，实际执行在另一台机器上。

dockerd 管高层，containerd 管生命周期

dockerd 负责镜像构建、网络、卷和 API；容器的创建、启动、删除交给 containerd。containerd 为每个容器起一个 shim 进程，再调用 OCI runtime，通常是 runc。

runc 按照 OCI 规范的配置创建 namespace、设置 cgroup、切换根目录，然后执行主进程。完成这一步后 runc 就退出了，容器进程的父进程是 shim。

shim 让容器不依赖守护进程

因为容器挂在 shim 下面，dockerd 甚至 containerd 重启时，容器进程可以继续运行。开启 live-restore 后，dockerd 重启不会停掉容器。

docker exec 走的是同一条链：在已有容器的 namespace 里再启动一个进程。它不是容器的主进程，退出也不影响容器。

OCI 运行时规范：一个目录加一份配置

runc 不认识镜像。它只认一个 bundle：一个根文件系统目录，加一份 config.json。config.json 写明了要执行的命令、环境变量、要创建哪些 namespace、cgroup 的限制、挂载列表、能力和 seccomp 规则。

containerd 负责把镜像解包成根文件系统，再根据 Docker 的参数生成 config.json。所以你在 docker run 上加的每个选项，最后都会落到这份配置里的某个字段。

换一个运行时会怎样

因为接口是标准的，runc 可以被替换。gVisor 的 runsc 在用户态实现了一个内核，拦截容器的系统调用；Kata Containers 为每个容器起一个轻量虚拟机。它们都接受同样的 bundle。

这样做换来了更强的隔离，代价是性能和兼容性。用 --runtime 可以为单个容器选择运行时，前提是 daemon 里已经注册了它。

常见误区

docker 组只是方便不用 sudo
能访问 docker.sock 就能以 root 身份启动任意容器，加入 docker 组等同于获得 root。
dockerd 挂了，所有容器都会停
容器挂在 shim 下面。没开 live-restore 时，dockerd 正常关闭会主动停掉容器；开了以后，守护进程重启不会影响它们。

放到生产里

生产主机建议开启 live-restore，这样升级 Docker 引擎时不必中断业务容器。注意它不适用于 Swarm 模式。

需要运行不可信代码时（比如在线评测、多租户构建），考虑 gVisor 或 Kata 这类更强隔离的运行时。

03推演

先猜，再看结果

在启用了 live-restore 的 Linux 主机上执行 systemctl restart docker，正在运行的容器会怎样？

容器进程的父进程是 containerd-shim，不是 dockerd。live-restore 让 dockerd 退出时不去停容器，重启后再和 containerd 对上账。没开 live-restore 时，dockerd 退出会停掉容器。

04迁移

换个场景

团队把 /var/run/docker.sock 挂进了 CI 的构建容器，方便在里面执行 docker build。安全上有什么问题？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

拿到这个 socket，就能调用 dockerd 的全部 API，比如启动一个挂载宿主机根目录的特权容器。等于把宿主机 root 交给了 CI 里的任何代码。

更稳妥的做法是用独立的构建服务、rootless 的 BuildKit，或者把 CI 跑在用后即弃的虚拟机里，让被攻破的影响范围可控。

05面试

讲给面试官听

docker run 之后，进程是谁创建的？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

CLI 调用 dockerd 的 API；dockerd 准备镜像、网络、卷，然后让 containerd 创建容器；containerd 启动一个 shim，由 shim 调用 runc。runc 根据 OCI 配置创建 namespace、配置 cgroup、切换根文件系统，最后 exec 主进程并退出。所以主进程的父进程是 shim。

追问：为什么要有 shim？

让容器进程不依赖 containerd 和 dockerd 的存活，同时由 shim 保持标准输入输出、收集退出码。守护进程可以升级或重启而不打断容器。

追问：docker exec 和 SSH 进容器有什么不同？

exec 在已有容器的 namespace 里通过 runtime 再启动一个进程，不需要容器里跑 sshd。它退出不影响主进程，也不会成为 PID 1。

06小结

带走这几句

  1. CLI 只是 API 客户端，docker.sock 等同 root 权限。
  2. dockerd → containerd → shim → runc → 主进程，runc 建完就退出。
  3. shim 让容器在守护进程重启时继续运行。
