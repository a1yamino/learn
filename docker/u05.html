一次 docker run 背后的运行链路

把 CLI、Engine、containerd、OCI runtime 与内核进程串起来，解释 create、start、exec 的不同边界。

建议 50 分钟，含实验；按观察结果调整进度。

先想一想

执行 docker create 后已经有容器 ID，却没有正在运行的 PID；执行 start 后 CLI 退出，服务仍运行。到底是谁持有运行状态？

  • 沿请求路径解释 CLI 到容器主进程的职责分工，而非把 docker CLI 当成容器本体。
  • 用 created、running、exited、exec 的可观察状态辨认对象创建和进程创建。
  • 知道实现与版本可能改变进程树，选择稳定的 API 证据。
实验前提

需要 Linux 容器的 Docker Engine 或 Docker Desktop、Docker Compose v2、Python 3；从仓库根目录开始。Desktop 的 daemon、containerd、runtime 和容器都在 Linux VM，宿主 macOS/Windows 的进程树不是这条链路。实验只用 Docker API，不读宿主 /proc，也不要求 root。

01 · MODEL

建立因果模型

CLI 是请求入口，Engine 持有对象状态

docker CLI 解析参数，通过所选 context 的 Docker API 把 create、start、inspect 等请求交给 Engine daemon。context 可能指向远端 Engine；本地终端进程退出不等于容器停止。创建后的配置、挂载和镜像引用是 Engine 管理的容器对象状态。

docker run 通常把 create 与 start 连在一起，并按 -d、-it、--rm 等参数决定客户端是否等待、连接标准流或结束后自动删除。只见一个 run 命令，不表示底层只做了一步。

containerd、shim、OCI runtime 承接执行

常见 Docker Engine 路径是 daemon 把镜像与任务管理交给 containerd，containerd 通过 shim 管理容器任务，OCI runtime（常见为 runc）依据运行时规格设置 namespace、cgroup、挂载和进程，然后由 Linux 内核执行。runtime 创建任务后可以退出；不能把它当成长驻业务进程。

这是职责模型，不是每个版本都相同的进程名或父子树。不同 Engine 版本、Desktop 虚拟机、rootless 模式和替代 OCI runtime 会改变可见实现。诊断时先用 docker info/context 确定目标，再用 inspect 的状态、PID、镜像 ID 和事件证据；不要只按主机 ps 的固定树形推理。

容器对象、任务和 exec 进程的寿命不同

create 产出对象但不启动主进程；start 让其主进程开始运行。主进程退出后对象可保留为 exited；再次 start 在同一对象中启动新的一次运行。exec 只在运行中的容器里添加进程，不替换主进程，也不会使已退出的容器复活。

docker inspect 的 .State.Pid 是 Engine 所在 Linux 环境中的主进程 PID；Desktop 上这个 PID 位于 VM，不能直接等同于桌面宿主机 PID。容器内 /proc/1 与 Engine 侧 PID 也可不同，因为 PID namespace 映射不同。

运行规格与镜像规格解决不同问题

镜像提供 rootfs 与默认配置；创建容器时用户、环境变量、入口命令、挂载、网络和资源限制共同构成运行配置。OCI image 规范约束镜像描述，OCI runtime 规范约束运行时 bundle 与进程设置；Docker API 则是用户操作 Engine 的接口。

相同镜像可创建许多不同容器，镜像 ID 不等于容器 ID。修改容器配置通常需要重建对象；restart 不会重新解释最新标签，也不会重新运行 docker build。

03 · EXPERIMENT

把 create、start、exec 分别变成可观察证据

从仓库根目录执行；镜像名 learn-u05:lab、容器名 learn-u05-object 仅供本课使用。需要能构建共用应用镜像；不启动 Compose 的共享项目。所有命令在同一终端，若镜像拉取失败先解决网络问题。

运行之前，先预测

create 后 inspect 的 Status、Pid 应是什么？start -d 返回后 CLI 已结束，容器会继续运行吗？exec 产生的进程是否改变主进程 PID？

01 · 确认客户端连接位置和运行实现

docker context show
docker info --format 'Server={{.ServerVersion}} OSType={{.OSType}} Driver={{.Driver}}'
cd docker/labs
docker build -t learn-u05:lab .

观察：记录当前 context、Linux Server 和实际存储驱动；不要假设 Desktop 与原生 Linux 的进程可见范围一样。

解释：先确定谁是 Engine，避免把本机 CLI 进程误认为 daemon。

02 · 只创建对象，不启动主进程

docker create --name learn-u05-object --entrypoint python learn-u05:lab -u -c 'import os,time; print("MAIN_PID",os.getpid(),flush=True); time.sleep(300)'
docker inspect -f 'ID={{.Id}} Status={{.State.Status}} Pid={{.State.Pid}} Image={{.Image}}' learn-u05-object

观察：有容器 ID，状态 created；尚无运行中的主进程，Pid 通常为 0。记录本机真实值。

解释：create 产生的是对象配置，不等于 Linux 进程已经启动。

03 · 启动对象，再从另一个 CLI 观察

docker start learn-u05-object
docker inspect -f 'Status={{.State.Status}} Pid={{.State.Pid}} Image={{.Image}}' learn-u05-object
docker logs learn-u05-object

观察：状态 running，Engine 侧 Pid 非零，日志出现 MAIN_PID。start 命令结束后容器仍继续运行。

解释：请求客户端和受管理的容器任务具有不同寿命；容器内 PID 与 Engine 侧 PID 不必相同。

04 · exec 添加辅助进程而不替换主进程

docker exec learn-u05-object python -c 'import os; print("EXEC_PID",os.getpid()); print(open("/proc/1/cmdline","rb").read().replace(b"\0",b" "))'
docker inspect -f 'Status={{.State.Status}} Pid={{.State.Pid}}' learn-u05-object

观察：exec 有自己的 PID；/proc/1 仍是等待中的主进程，inspect 的主进程 PID 不变。

解释：exec 是现有容器里的附加进程，不是新的 start，也不会更换 PID 1。

05 · 停止后保留并再次启动同一对象

docker stop -t 5 learn-u05-object
docker inspect -f 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} ID={{.Id}}' learn-u05-object
docker start learn-u05-object
docker inspect -f 'Status={{.State.Status}} Pid={{.State.Pid}} ID={{.Id}}' learn-u05-object

观察：停止后为 exited，对象 ID 保留；再次启动为 running，同一个对象有新一次主进程运行。退出码受停止信号处理影响，不预设固定值。

解释：对象、主进程运行和 CLI 会话分别有自己的生命周期。

04 · TRANSFER

换一个条件，还能解释吗

你的 CLI 连接到远端 Docker context。docker run -d 已返回 ID，桌面宿主的 ps 找不到 runc 或应用进程，但远端 docker inspect 显示 running。如何判断是真故障还是观察位置错误？

提交这些证据

  • 提交 docker context show 与目标 Engine 的 docker info，确认 Server 位于哪里。
  • 提交该容器 inspect 的 ID、State.Status、State.Pid、Image 和 docker logs。
  • 在 Engine 所在环境或经 API 验证业务端口，不以本地 ps 缺席作唯一证据。
对照参考推理

先确认 CLI 的请求确实送往远端 Engine；本地 ps 只反映本地 OS，远端任务或 Desktop VM 内进程本就不应出现在这里。

若 inspect 为 running 且日志和服务响应正常，这是观察位置差异；若状态异常，再沿对象配置、容器日志、网络发布与运行时错误逐层排查。

runc 是否长驻不是验收条件；用 Engine API 状态和可观察业务行为验证容器，而非要求固定进程树。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · 从执行 docker run 到服务响应，按职责说明各层做了什么。

查看参考回答与递进追问

CLI 根据 context 调用 Engine API；Engine 解析镜像与容器配置并管理对象；常见实现经 containerd、shim 和 OCI runtime 建立任务，runtime 按规格配置 namespace、cgroup、挂载和主进程，Linux 内核实际执行。run 汇合 create 与 start，后台服务不依赖 CLI 一直存在。用 context、inspect 的对象状态/PID/镜像 ID 和业务响应核对，避免把某个版本的进程树当作稳定契约。

追问 1：create 与 start 的证据有何不同？

create 有对象 ID 和配置，通常是 created 且没有主进程 PID；start 后为 running，Engine 侧 PID 非零，日志或响应可观测。

追问 2：exec 能让 exited 容器恢复吗？

不能。exec 要求容器运行中，只增加一个进程；exited 对象需要 start，且启动的是新一次主进程运行。

追问 3：为什么 Desktop 的宿主 ps 找不到容器 PID？

Linux Engine 和容器运行在 VM 内，inspect 的 PID 属于该 Linux 环境；桌面宿主进程视图与 VM 不同。

容易混淆：“docker CLI 自己运行容器。”CLI 是请求客户端；容器进程由 Engine 所在 Linux 环境管理。

06 · EVIDENCE

用证据判断是否掌握

  1. 先确认 context 与 Engine，才能解释进程和文件出现在哪里。
  2. create 生成对象；start 启动主进程；exec 只增加附加进程。
  3. containerd、shim、OCI runtime 是常见执行链路，具体进程树不是跨版本契约。
  4. 镜像 ID、容器 ID 与一次进程运行标识不同。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
