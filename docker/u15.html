供应链证据：扫描、SBOM与身份验证

把软件清单、漏洞判断、内容摘要和签名身份拆开，建立能够解释通过与拒绝原因的发布证据。

建议 60 分钟，含实验；按观察结果调整进度。

先想一想

一个镜像扫描“零个可修复CRITICAL”，又有合法签名，是否足以允许部署？如果三天后数据库更新扫描失败，镜像内容一定变化了吗？

  • 说明SBOM、漏洞报告、来源证明与签名各自证明什么。
  • 基于实际扫描结果区分可修复、不可修复与需风险评估的项目。
  • 将扫描工具、漏洞库时间和镜像身份一起记录，避免用一组固定CVE数字判断安全。
实验前提

Docker Engine或Desktop、Buildx、宿主Python3。扫描需联网下载Trivy及漏洞库；不挂载docker.sock。签名扩展需要已安装cosign和自己控制的仓库/OIDC身份，可选，不影响本地扫描与证据实验。

01 · MODEL

建立因果模型

清单是观察，漏洞是带时间的判断

SBOM列出分析器识别到的软件组件、版本和关系；漏洞扫描把这些组件与当时的漏洞数据库匹配。镜像没有变化，数据库或分析器更新也可能改变结果。包管理器回补安全补丁、运行平台差异、分析覆盖不足都会影响解释。

扫描输出不应只剩一个总数。记录镜像身份、工具版本、漏洞库元数据、平台与规则，再判断组件是否在运行路径上、是否有修复、替代或缓解措施。--ignore-unfixed改变显示或门禁范围，不会让无修复漏洞消失。

digest、签名与身份是三种连接

digest把引用绑定到内容。签名把受信密钥或身份绑定到某份内容声明。验证者还需要选择可信公钥，或限制OIDC issuer、证书身份、工作流与引用范围；“存在一个能验证的签名”不等于来自你的发布流程。

签名者可以签一个有漏洞或没测过的镜像。来源证明记录构建输入和过程线索，其可信度依赖构建者与验证策略。验证内容完整性、验证来源身份、确认测试和风险门禁是彼此关联但不同的步骤。

门禁必须允许可解释的拒绝与更新

先定义发布策略：允许的平台、受信发布身份、必须提供的测试与扫描证据、漏洞阈值和有时限的例外。对无修复漏洞可以评估可达性、缓解与替换计划，但不能仅因为没有补丁就自动认定安全。

保持可重复的评估与及时更新存在取舍：固定扫描工具与数据库有利于复核，持续更新有利于发现新风险。应记录本次评估版本，并对已发布digest定期重扫；不得通过删除数据库或忽略全部失败让门禁“变绿”。

03 · EXPERIMENT

不用Docker socket，扫描一份本地应用镜像

从仓库根目录开始，所有命令同一终端。扫描器只读挂载导出目录，缓存使用本课独立卷。首次下载漏洞库可能较慢；网络/限额错误必须记作未完成，不能当“零漏洞”。

运行之前，先预测

不改变应用镜像，只更新扫描数据库，报告可能变化吗？关闭--ignore-unfixed前后差异说明什么，不能说明什么？

01 · 构建并记录被评估对象

U15_DIR=$(mktemp -d)
docker build -t learn-u15:api docker/labs
IMAGE_ID=$(docker image inspect learn-u15:api --format "{{.Id}}")
docker image inspect "$IMAGE_ID" > "$U15_DIR/image-inspect.json"
docker image save "$IMAGE_ID" -o "$U15_DIR/image.tar"
printf "%s
" "$IMAGE_ID" | tee "$U15_DIR/image-id.txt"

观察：保存本次真实image ID及镜像归档；本地image ID是config身份，不冒充仓库manifest digest。

解释：本地实验先明确对象，后续发布实验再取得仓库引用。

02 · 解析本次扫描工具的真实版本

TRIVY_DIGEST=$(docker buildx imagetools inspect aquasec/trivy:latest --format "{{.Manifest.Digest}}")
TRIVY_IMAGE="aquasec/trivy:latest@$TRIVY_DIGEST"
printf "%s
" "$TRIVY_IMAGE" > "$U15_DIR/scanner-ref.txt"
docker run --rm "$TRIVY_IMAGE" --version | tee "$U15_DIR/scanner-version.txt"

观察：工具名称仍保留latest便于阅读，但本次执行固定真实digest；记录实际版本。

解释：记录扫描工具输入，避免不同时间运行latest却宣称使用同一分析器。

03 · 产生完整漏洞报告并确认命令成功

docker run --rm -v "$U15_DIR":/work:ro -v learn-u15-trivy:/cache "$TRIVY_IMAGE" image --cache-dir /cache --input /work/image.tar --format json > "$U15_DIR/scan.json"
python3 - "$U15_DIR/scan.json" <<'PY'
import json,sys
p=json.load(open(sys.argv[1]))
rows=[v for result in p.get("Results",[]) for v in result.get("Vulnerabilities",[])]
print("identified vulnerabilities",len(rows))
print("fix version available",sum(bool(v.get("FixedVersion")) for v in rows))
print("without listed fix",sum(not v.get("FixedVersion") for v in rows))
for v in rows[:5]:
    print(v["VulnerabilityID"],v["PkgName"],v.get("InstalledVersion"),v.get("FixedVersion","no listed fix"),v["Severity"])
PY

观察：报告必须是有效JSON；数量取决于当前数据库。保留stderr中的下载错误，扫描失败时停止结论。

解释：完整报告保留“无修复”项目，避免过滤结果被误读为它们不存在。

04 · 生成清单并核对它与漏洞报告不同

docker run --rm -v "$U15_DIR":/work:ro -v learn-u15-trivy:/cache "$TRIVY_IMAGE" image --cache-dir /cache --input /work/image.tar --format spdx-json > "$U15_DIR/sbom.spdx.json"
python3 - "$U15_DIR/sbom.spdx.json" <<'PY'
import json,sys
p=json.load(open(sys.argv[1]))
print("SPDX",p.get("spdxVersion"),"packages",len(p.get("packages",[])))
for package in p.get("packages",[])[:5]:
    print(package["name"],package.get("versionInfo","unknown"))
PY

观察：SPDX中识别出组件，数量不等于漏洞数；没有识别出来不证明组件不存在。

解释：SBOM用于追踪软件组成，不自带全部漏洞和来源可信保证。

05 · 保存数据库线索并作出可复核判断

docker run --rm -v learn-u15-trivy:/cache --entrypoint cat "$TRIVY_IMAGE" /cache/db/metadata.json > "$U15_DIR/db-metadata.json"
python3 - "$U15_DIR" <<'PY'
import json,sys
from pathlib import Path
p=Path(sys.argv[1]); report=json.loads((p/"scan.json").read_text())
items=[v for x in report.get("Results",[]) for v in x.get("Vulnerabilities",[])]
blocked=[v for v in items if v.get("Severity")=="CRITICAL" and v.get("FixedVersion")]
result={"example_policy":"block fixable CRITICAL; other risk still requires review","blocking_count":len(blocked),"scanner_ref":(p/"scanner-ref.txt").read_text().strip(),"image_id":(p/"image-id.txt").read_text().strip()}
(p/"decision.json").write_text(json.dumps(result,indent=2)); print(json.dumps(result,indent=2))
print("请为至少一项发现或未发现的覆盖边界写下评估，不将门禁通过表述为安全证明。")
PY

观察：输出限定范围的门禁判断，保留工具、对象、数据库元数据。metadata路径若因新工具版本变化，应查看/cache实际布局并记录，不能伪造数据库时间。

解释：扫描结果、门禁策略与最终风险接受是不同对象，证据应能重新审核。

04 · TRANSFER

换一个条件，还能解释吗

镜像扫描通过并附有签名，部署方却必须拒绝它：签名来自同一组织的另一个测试工作流，且该index的arm64尚无扫描证据。请制定验证策略及负向用例。

提交这些证据

  • 实际index与各运行平台manifest的摘要清单。
  • 签名使用的可信公钥或OIDC issuer、精确身份/工作流/ref约束。
  • 正确身份、错误身份、篡改内容、缺平台证据四类接受或拒绝结果。
对照参考推理

先验证内容digest，再校验允许的签名身份，而非接受组织内任意签名。OIDC应限定issuer及明确工作流/引用范围；自管密钥则要验证公钥信任来源。

逐个平台收集对应child manifest的测试和扫描结果，缺失arm64证据时不能用amd64通过结果替代；可先只发布已验证单平台。

有cosign与自有仓库时，执行cosign verify --key 受信公钥.pem 实际镜像@真实digest，或按平台OIDC文档使用issuer和identity约束；替换错误公钥/身份预期失败。这里的参数来自自己的配置，不是可以直接运行的虚构仓库。记录退出码和stderr。

05 · INTERVIEW

面试中讲清原理

先用自己的话回答，再打开参考。回答按“结论 → 机制 → 边界 → 证据”组织；追问用来检验理解。

01 · SBOM、漏洞扫描、镜像签名和来源证明有什么区别？如何设计一个可解释的供应链门禁？

查看参考回答与递进追问

SBOM回答识别了哪些组件，扫描回答这些组件在指定数据库与规则下有哪些已知风险；digest固定内容，签名绑定内容声明与密钥或身份，来源证明描述构建输入和过程。门禁要明确受信身份、目标平台、测试与扫描范围、风险阈值和有期限的例外。记录工具、数据库和摘要，并用错误身份、篡改内容、缺证据等负向用例验证拒绝。签名合法和零可修复高危都不是安全充分条件。

追问 1：为什么镜像不变，扫描结果却改变？

漏洞库、分析器覆盖或匹配规则变了；应记录版本和时间，并对已发布digest持续重评。

追问 2：没有修复版本的CRITICAL如何处理？

评估组件可达性、利用前提、缓解与替换计划，必要时拒绝或给予限时例外；不能因为ignore-unfixed隐藏了它就认定安全。

追问 3：cosign验证成功为何仍可能来源不符？

验证策略可能接受了不该信任的密钥或过宽OIDC身份；要校验预期issuer、工作流/ref或受信公钥，不能只证明“某人签过”。

容易混淆：扫描减少未知风险，签名验证内容与身份；二者都不自动证明业务正确、权限最小或所有平台都验收。

06 · EVIDENCE

用证据判断是否掌握

  1. 扫描结论带有对象、工具、数据库、平台与策略边界。
  2. SBOM用于追踪组成，不等于零风险清单。
  3. 验证签名还要验证受信身份和证据范围。
  4. 为允许与拒绝都保存可复核证据。

自记进度与草稿只保存在本机浏览器；勾选不代表自动验收。
