网络空间：bridge、veth 与服务发现

沿着一次容器间连接，看清网卡、网桥和服务名解析各在做什么。

先想一想

同一个 Compose 项目里，api 能 ping 通 db，可连接 5432 端口被拒绝。名字解析成功了，网络为什么还是不通？

原理图解推演迁移面试小结
01原理

原理

veth 是一根两头的网线

每个容器有自己的 network namespace。Docker 创建一对 veth 设备，一端放进容器叫 eth0，另一端接在宿主机的网桥上。同一网桥上的容器就像插在同一台交换机上。

默认的 bridge 网络叫 docker0；Compose 会为每个项目建一个自定义网桥。

自定义网络才有服务名解析

在自定义网络里，Docker 内置的 DNS（容器里看到的是 127.0.0.11）会把服务名和容器名解析成对方的 IP。默认 bridge 网络没有这个功能，只能用 IP。

解析成功只说明名字能找到地址。能不能连上，还要看对方是否在那个地址和端口上监听。

连不上的三个层次

先看名字：getent hosts db 能否得到 IP。再看路径：两个容器是否在同一个网络。最后看服务：对方是否监听在 0.0.0.0 上，而不是只听 127.0.0.1，进程是否已经就绪。

ping 走的是 ICMP，能 ping 通不代表某个 TCP 端口开着。

内置 DNS 是怎么工作的

自定义网络里的容器，/etc/resolv.conf 指向 127.0.0.11。这个地址上的 DNS 由 dockerd 内嵌提供，通过 iptables 规则把请求转到守护进程。它先查本网络里的服务名、容器名和网络别名，查不到再转发给宿主机配置的上游 DNS。

Compose 的服务名会解析到该服务所有容器的 IP。扩容到多个副本时，解析结果有多个地址，客户端是否轮询取决于它自己的实现。

跨网络与网络别名

容器只能直接访问它所在网络里的其他容器。一个容器可以同时接入多个网络，比如网关接入 front 和 back，数据库只接入 back，这样前端网络里的东西就碰不到数据库。

网络别名（aliases）让一个容器在某个网络里多一个名字，适合平滑替换：新旧容器共用别名，切换时只改谁拥有它。

走一遍：一次请求从 api 到 db

  1. api 进程调用 getaddrinfo("db")，请求发往 127.0.0.11，内置 DNS 返回 db 在 back 网络中的 IP，比如 172.20.0.3。
  2. 内核查路由表，发现 172.20.0.0/16 走 eth0 直连。数据包从 eth0 发出，经过 veth 到达宿主机上的网桥。
  3. 网桥按 MAC 地址表把帧转给 db 的 veth，进入 db 的网络空间。db 的 PostgreSQL 在 0.0.0.0:5432 上接受连接，握手完成。

常见误区

能 ping 通就说明服务没问题
ping 用的是 ICMP，只说明主机可达。端口是否开、服务是否就绪，要用 TCP 连接或应用请求来验证。
容器 IP 是固定的，可以写进配置
容器重建后 IP 可能变化。应当使用服务名，让 DNS 解析当前地址。

放到生产里

按信任边界划分网络：对外的网关、内部服务、数据存储分属不同网络，只给必要的容器接入多个网络。

客户端要处理 DNS 结果变化，不要永久缓存第一次解析得到的 IP。

03推演

先猜，再看结果

两个容器用 docker run 启动，都没指定 --network（即默认 bridge）。在 a 里执行 curl http://b:8000，会怎样？

默认 bridge 网络不提供服务名解析，b 这个名字查不到。建一个自定义网络把两个容器都接进去就能用名字访问，这也是 Compose 默认的做法。

示例输出 · 只读
$ docker exec a curl -sS http://b:8000/health

04迁移

换个场景

api 和 db 在同一个 Compose 网络里，getent hosts db 能返回 IP，但 nc -zv db 5432 报 Connection refused。下一步看什么？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

名字和路由都没问题，拒绝说明数据包到了对方，但没人在这个端口接。去看 db 容器里的监听情况：是不是只监听了 localhost，或者进程还在初始化、尚未开始监听。

如果返回的是超时而不是拒绝，那才更可能是网络路径或防火墙的问题。拒绝和超时指向不同的层。

05面试

讲给面试官听

同一台主机上两个容器是怎么通信的？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

每个容器在自己的 network namespace 里有一块 eth0，它是一对 veth 的一端，另一端接在宿主机的 Linux 网桥上。同一网桥上的容器在二层直接互通。用户自定义网络还提供内置 DNS，把服务名解析成容器 IP。跨网络默认不通，需要把容器同时接入两个网络。

追问：Connection refused 和 timeout 分别说明什么？

refused 说明包到了目标主机，但端口上没有进程监听，或被 RST；timeout 说明包或回包在路上丢了，常见于路由、防火墙或对方不存在。

追问：为什么推荐自定义网络而不是默认 bridge？

自定义网络有服务名解析、更好的隔离，可以随时连接或断开容器。默认 bridge 只能用 IP 或已经废弃的 --link。

06小结

带走这几句

  1. veth 一端在容器，一端在网桥，网桥连起同网络的容器。
  2. 服务名解析只在自定义网络里有，能解析不等于能连接。
  3. 按名字、路径、监听三层排查；refused 与 timeout 指向不同问题。
