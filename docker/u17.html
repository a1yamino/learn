未知故障诊断：从症状到可证伪的根因

面对一个 502，按层取最小证据，每一步都排除一类原因。

先想一想

网关返回 502，api 容器状态显示 Up。你有五分钟，先看什么？

原理图解推演迁移面试小结
01原理

原理

先把症状翻译成问题

502 是网关说“我连上游失败了”或“上游给了无效响应”。所以问题在网关到 api 这一段，或者 api 本身。先看网关的错误日志，它通常会写明是 connect refused、timeout 还是 host not found。

这三种说法分别指向监听、路径或性能、名字解析。

每一步只问一个可证伪的问题

名字能解析吗？在网关容器里 getent hosts api。端口能连吗？nc -zv api 8000。应用回答正常吗？curl api:8000/ready。资源够吗？docker stats 和 OOM 记录。数据在吗？挂载和权限。

每个问题的答案都能排除一类原因。不要一上来就重启，重启会抹掉现场。

修复以后要证明恢复

找到根因、做出最小修复后，要用同样的检查证明问题消失，再跑一次业务验证：真实请求成功、数据完整。

最后写下时间线：现象、证据、根因、修复、验证。下次遇到相似症状能少走弯路。

02图解

502 的分层排查

03推演

先猜，再看结果

网关日志写着 connect() failed (111: Connection refused) while connecting to upstream，api 容器是 Up。最可能的原因是？

111 是 ECONNREFUSED：包到了目标，但端口上没人接。名字解析和路径都没问题，问题在 api 的监听。DNS 错误会是 host not found，丢包会是 timeout。

示例输出 · 只读
$ docker compose exec api sh -c 'cat /proc/net/tcp | head -3'
  sl  local_address rem_address   st
   0: 0100007F:1F40 00000000:0000 0A
# 0100007F = 127.0.0.1，1F40 = 8000：只监听回环地址
04迁移

换个场景

同样是 502，但这次网关日志是 upstream timed out，而且只在高峰期出现。你的排查顺序会怎么变？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

超时说明连接建立了或者包在路上等太久，更可能是 api 处理慢。先看 api 的延迟和 CPU 节流（cpu.stat）、内存回收、数据库连接池是否耗尽。

高峰期才出现，提示和负载相关。对照请求量和节流计数的时间曲线，能证伪或支持“配额不够”这个假设。

05面试

讲给面试官听

线上一个容器服务出问题，你的排查思路是什么？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

先保留现场，不急着重启。从用户可见的症状出发，读出它指向哪一层，再按名字、连接、应用、资源、数据逐层提出可以被证伪的问题，每个问题用一条最小命令回答。定位根因后做最小修复，用同样的检查和一次真实业务请求证明恢复，最后记录时间线。

追问：为什么不先重启？

重启可能暂时解决问题，但会丢掉日志、连接状态和内存现场，根因找不到，问题会再来。先收集证据，必要时再重启止血。

追问：容器里没有 curl、nc 怎么办？

用 docker run --network container:api 挂一个调试镜像，共享它的网络空间；或用 docker debug、nsenter 进入。不必在生产镜像里装工具。

06小结

带走这几句

  1. 先读懂症状指向哪一层。
  2. 每一步问一个可证伪的问题，用最小命令回答。
  3. 修复后用同样的检查和业务请求证明恢复。
