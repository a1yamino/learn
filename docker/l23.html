在你的电脑上练习

在自己的 GitHub 仓库里跑通一条流水线。
01

准备一个仓库，放入第 4 课的 API（或任何带 Dockerfile 的项目），Dockerfile 里有 test 阶段。

git init cicd && cd cicd
# 复制项目文件，确认本地可以构建
docker build --target test .
=> [test 2/2] RUN pytest -q
4 passed in 0.31s
02

添加 workflow 文件（内容见上一节，可以复制）。

mkdir -p .github/workflows
$EDITOR .github/workflows/docker.yml
git add . && git commit -m "ci" && git push -u origin main
（在 GitHub 的 Actions 页面看到任务开始运行）

看第一次构建的耗时，再随便改一个 README，推送第二次。

挑战

加上扫描和按 digest 部署

在 workflow 里：(1) 推送后对刚推送的镜像运行 Trivy，有可修复的 CRITICAL 时失败；(2) 增加一个 deploy 任务，只在 main 分支运行，拿到上一步输出的 digest，打印出要部署的完整引用。

查看参考答案
      - id: build
        uses: docker/build-push-action@v6
        with: { push: true, tags: ${{ steps.meta.outputs.tags }}, cache-from: type=gha, cache-to: type=gha,mode=max }
      - uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          severity: CRITICAL
          ignore-unfixed: true
          exit-code: 1
    outputs:
      digest: ${{ steps.build.outputs.digest }}

  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "deploy ghcr.io/${{ github.repository }}@${{ needs.build.outputs.digest }}"
deploy ghcr.io/alice/cicd@sha256:4b1e…

build-push-action 的 digest 输出通过 job outputs 传给 deploy。真实部署时把这个引用交给 docker compose（用变量）、Kubernetes 或其他平台。environment: production 可以在 GitHub 设置里配置人工审批。

小结

记住这几点

  1. 流水线顺序：检查 → 构建 → 测试 → 扫描 → 推送 → 签名 → 部署。前面的步骤失败，后面的不执行。
  2. CI 机器每次都是新的：用 cache-to/cache-from type=gha（或 registry）保留构建缓存（第 17 课）。
  3. 标签策略：每个提交打 sha-xxxxxxx（不可变），发布时打 1.4.2、1.4；latest 只作方便用途，部署不要依赖它。
  4. 测试用构建出来的同一个镜像跑（--target test 或 docker run），保证测的就是要发布的。
  5. 推送凭证用 CI 平台的密钥或 GITHUB_TOKEN，权限最小化。不要写进仓库。
  6. 部署按 digest：构建步骤输出 digest，部署步骤用 image@sha256:…，保证部署的就是刚测试过、签过名的那个镜像。
