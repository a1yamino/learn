容器本质与 namespace

用“同一个进程，不同的视图”来理解隔离：PID、网络、挂载各自是一张独立的表。

先想一想

在容器里执行 ps，只看得到寥寥几个进程，主进程还是 PID 1。可宿主机上它明明有一个很大的 PID。到底哪个才是真的？

01原理

原理

namespace 隔离的是“能看见什么”

内核给每类资源准备了一张表：进程编号、网络设备、挂载点、主机名、用户 ID 等。namespace 让一组进程拿到其中一类的独立副本，于是它们看到的世界和宿主机不一样。

两个 PID 都是真的。进程在自己的 PID namespace 里编号为 1，在宿主机的 namespace 里有另一个编号。内核同时维护着这两个编号。

每一种 namespace 解决一个具体问题

PID namespace 让容器里的进程看不到别人；network namespace 给容器独立的网卡、路由和 localhost；mount namespace 让它有自己的根目录；UTS 管主机名，IPC 管共享内存，user namespace 可以把容器里的 root 映射成宿主机上的普通用户。

这也是为什么容器里的 localhost 指的是容器自己，而不是宿主机。网络 namespace 不同，回环设备就不是同一个。

Docker Desktop 里还隔着一台虚拟机

在 macOS 和 Windows 上，容器跑在 Docker Desktop 管理的一台 Linux 虚拟机里。你在 Mac 的活动监视器里找不到容器进程，因为它们属于那台虚拟机的内核。

所以讲到 namespace、cgroup、iptables，指的都是那台 Linux 环境，而不是你的桌面系统。

namespace 是怎么被创建出来的

内核提供三个系统调用：clone 在创建新进程时顺便给它新的 namespace，unshare 让当前进程脱离原来的 namespace，setns 让进程加入一个已经存在的 namespace。runc 创建容器，本质就是带着一组 CLONE_NEW* 标志去 clone 主进程。

每个 namespace 在 /proc/<pid>/ns/ 下有一个链接，比如 net:[4026532281]。两个进程这里的编号相同，就说明它们在同一个 namespace 里。docker exec 正是用 setns 进入目标容器的这些 namespace，再启动新进程。

user namespace 让 root 不再是 root

user namespace 把容器里的 UID 映射到宿主机上的另一段 UID。容器里的 0 可以对应宿主机的 100000，这样即使进程逃出了其他边界，它在宿主机上也只是一个没有特权的普通用户。

Docker 默认不开启它，需要在 daemon 上配置 userns-remap；rootless 模式则天然依赖它。开启后，绑定挂载的文件属主也要按映射后的 UID 来准备。

走一遍：两个容器共享网络

  1. 用 --network container:api 启动一个调试容器，它会加入 api 的 network namespace，但 PID 和 mount namespace 仍然是自己的。
  2. 在调试容器里执行 ss -lnt，能看到 api 正在监听的端口；执行 ps，却看不到 api 的进程。
  3. 这就是 namespace 按类别拆开的直接证据：同一个网络视图，不同的进程视图。Kubernetes 的 Pod 里，多个容器共享网络也是这样实现的。

常见误区

容器就是一种轻量虚拟机
容器没有自己的内核。内核漏洞、内核参数、内核版本都和宿主机共用，这决定了它的隔离强度和虚拟机不在一个层级。
namespace 能限制资源使用
namespace 只管能看见什么。能用多少 CPU、内存，是 cgroup 的事，下一课会讲。

03推演

先猜，再看结果

容器 A 里的服务监听 localhost:5432。容器 B 里执行 psql -h localhost，能连上吗？

每个容器默认有独立的 network namespace，localhost 只指向自己。即使两个容器在同一个 bridge 网络里，也要用对方的服务名或 IP 访问，而且对方得监听在非回环地址上。

示例输出 · 只读
$ docker exec b psql -h localhost -U app
psql: error: connection to server at "localhost" (127.0.0.1),
port 5432 failed: Connection refused
04迁移

换个场景

有人用 --pid=host 启动了一个监控容器，发现它能看到宿主机上所有进程，甚至能给它们发信号。这说明了什么？

先在心里走一遍：现象说明了什么，哪条证据能区分你的几个猜测。

展开推理

--pid=host 让容器加入宿主机的 PID namespace，于是隔离在这一类资源上被取消了。能否发信号还取决于权限：容器里是 root、又没被能力和 seccomp 限制，就可能杀掉宿主机进程。

这说明 namespace 是一类一类开关的，不是一个整体。加入宿主机的某个 namespace 时，要清楚自己放弃了哪一层边界。

05面试

讲给面试官听

容器是怎么实现隔离的？

先用自己的话说一遍，大约一两分钟，再对照参考。

参考回答

主要靠两类内核机制。namespace 决定进程能看见什么：PID、网络、挂载、主机名、IPC、用户各有独立视图。cgroup 决定进程能用多少：CPU、内存、IO、进程数。再加上 capabilities、seccomp 和 LSM 限制它能做什么。容器共享宿主机内核，所以这些都是内核在帮忙划边界，而不是硬件虚拟化。

追问：容器里的 root 就是宿主机的 root 吗？

默认情况下 UID 是同一个 0，但 Docker 去掉了大部分 capability，并用 seccomp 挡住危险系统调用，所以能力有限。启用 user namespace 或 rootless 模式后，容器里的 root 会映射成宿主机上的普通用户。

追问：为什么在 Mac 上看不到容器进程？

Docker Desktop 把容器跑在一台 Linux 虚拟机里，进程属于那个内核。要观察 namespace 和 cgroup，需要进入那台虚拟机或使用原生 Linux。

06小结

带走这几句

  1. namespace 隔离视图，同一个进程可以在不同视图里有不同编号。
  2. 容器里的 localhost 只指向容器自己。
  3. 隔离是按资源类别逐个打开的，--pid=host 之类的选项会取消其中一类。
