单元测试与 TDD：整洁的测试

测试代码和生产代码一样重要：脏的测试会变得难以修改，最终被删除，生产代码也就失去了重构的安全网。本课讲 TDD 的三条定律与“红—绿—重构”循环，整洁测试的标准（可读性第一）、构造—操作—检验（Arrange-Act-Assert）结构、面向领域的测试语言、每个测试一个概念、F.I.R.S.T. 原则，以及测试替身（fake、stub、mock）的取舍和“过度 mock”的问题。练习用 TDD 从零写一个小功能。约 50 分钟。

03
测试替身
同一个名词“mock”常被用来指代几种不同的东西。


种类做什么例子何时用


Dummy只为填参数，不被使用None、空对象签名要求但与测试无关


Stub返回预设的数据总是返回 25℃ 的天气源为被测代码提供输入


Fake可工作的简化实现内存仓库、内存文件存储替代慢或外部的依赖；首选


Spy / Mock记录调用，事后断言RecordingMailer、unittest.mock.Mock交互本身就是要验证的行为


测试金字塔：大量快速的单元测试（毫秒级），较少的集成测试（验证适配器与真实数据库、服务），少量端到端测试。测试越慢、越依赖外部，就越不适合在每次保存时运行。

绿，然后重构：用列表保存名称与价格，保留重复添加的累计行为。不能直接改成 name → price 的字典，否则同名商品会被覆盖；现有测试通过不代表所有行为都保持不变。
cat > cart.py <<'EOF'
STANDARD_SHIPPING = 8

class Cart:
    def __init__(self, is_vip=False):
        self._items = []
        self._is_vip = is_vip

    def add(self, name, price):
        self._items.append((name, price))

    def total(self):
        return sum(price for name, price in self._items)

    def shipping_fee(self):
        return 0 if self._is_vip else STANDARD_SHIPPING
EOF

挑战
继续 TDD
继续上面的购物车，用 TDD 依次加入：① 增加 quantity_of(name)，可以查询同一商品累计数量；② 删除商品；③ 非 VIP 满 99 元免运费。对每一项先写出测试名，再写测试。
查看参考答案
def test_adding_same_item_twice_doubles_quantity(self):
    cart = Cart(); cart.add("pen", 10); cart.add("pen", 10)
    self.assertEqual(cart.total(), 20)
    self.assertEqual(cart.quantity_of("pen"), 2)

def test_removed_item_is_not_charged(self):
    cart = Cart(); cart.add("pen", 10); cart.add("ink", 5)
    cart.remove("pen")
    self.assertEqual(cart.total(), 5)

def test_free_shipping_from_99(self):
    cart = Cart(); cart.add("bag", 99)
    self.assertEqual(cart.shipping_fee(), 0)

def test_shipping_charged_below_99(self):
    cart = Cart(); cart.add("bag", 98.99)
    self.assertEqual(cart.shipping_fee(), 8)
第一个测试因尚未实现 quantity_of 而失败；原有列表已能正确累计同名商品金额。可以按列表统计数量，也可以改为 {name: (price, quantity)}，但要保留重复添加的既有行为。第三项需要两个测试，覆盖边界的两侧（99 与 98.99）。

小结
记住这几点


  1. TDD 三定律：① 在写出一个失败的测试之前，不写生产代码；② 只写刚好失败的测试（编译失败也算失败）；③ 只写刚好让测试通过的生产代码。循环很短：红 → 绿 → 重构。
  2. 测试保护的是可修改性：有了快速、可靠的测试，你才敢重构；没有测试，每次修改都是冒险，代码会逐渐腐烂。
  3. 可读性第一：测试是活的文档。用 Arrange-Act-Assert 三段结构；用领域语言的辅助函数（given_cart_with(...)）隐藏无关细节；测试名描述行为（test_vip_gets_free_shipping）。
  4. 每个测试一个概念：一个测试失败时，名字就应该说明哪个行为坏了。断言可以有多个，但它们应验证同一个概念。
  5. F.I.R.S.T.：快速（Fast）、独立（Independent）、可重复（Repeatable，不依赖网络、时间、随机数）、自足验证（Self-validating，通过或失败，不需要人看日志）、及时（Timely，与生产代码一起写）。
  6. 测试替身：优先用真实对象或内存假实现（fake）；对外部系统用 stub 提供数据；只在“交互本身就是行为”时（如“应发送一封邮件”）使用 mock 验证调用。过度 mock 会把测试绑在实现细节上，重构时大量测试无故失败。
