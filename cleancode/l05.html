注释：何时该写，何时该删

注释不能美化糟糕的代码。本课区分好注释与坏注释：法律信息、解释意图（为什么这样做）、警示后果、TODO、公共接口的文档字符串是有价值的；复述代码、日志式注释、误导性注释、注释掉的代码、位置标记、强制每个函数都写的注释则是噪音，并且会随着代码变化而过时。最后讨论“用代码代替注释”的手段，以及 Ousterhout 关于接口注释的不同观点。约 40 分钟。

def reserve(sku: str, quantity: int, *, hold_minutes: int = 15) -> Reservation:
    """为购物车预留库存。

    预留在 hold_minutes 分钟后自动释放，除非在此之前调用 confirm()。
    同一个 sku 的多次预留会累加，不会覆盖。

    Raises:

    """


应该写不应该写


行为的契约：前提条件、返回值、异常、副作用实现步骤（“首先查询数据库，然后……”）


单位、取值范围（“毫秒”“0–1 之间”）参数类型（类型注解已经写了）


不显然的行为（“累加，不覆盖”“不会部分预留”）复述函数名（“预留库存的函数”）

# 计算运费
def calc(w, r, vip):
    # 如果是 vip
    if vip:
        # vip 免运费
        return 0
    # 基础运费
    c = 8
    # 超过 1 公斤，每公斤加 2 元
    if w > 1:
        c += (w - 1) * 2
    # 偏远地区
    if r in ("XZ", "XJ"):
        # 偏远地区翻倍。物流合同第 4.2 条规定
        c *= 2
    # c = c * 1.06
    return c
EOF

02
之后：名字代替注释，只保留解释业务原因的那一条。
cat > shipping.py <<'EOF'
BASE_FEE = 8
INCLUDED_KG = 1
FEE_PER_EXTRA_KG = 2
# 物流合同第 4.2 条：西藏、新疆的运费为标准运费的两倍。
REMOTE_REGIONS = {"XZ", "XJ"}
REMOTE_MULTIPLIER = 2

def shipping_fee(weight_kg, region, is_vip):
    """返回一个包裹的运费（元）。VIP 免运费。"""
    if is_vip:
        return 0
    fee = BASE_FEE + max(0, weight_kg - INCLUDED_KG) * FEE_PER_EXTRA_KG
    if region in REMOTE_REGIONS:
        fee *= REMOTE_MULTIPLIER
    return fee
EOF
python3 -c "from shipping import shipping_fee as f; print(f(3, 'BJ', False), f(3, 'XZ', False), f(3, 'XJ', True))"
12 24 0

挑战
写一条好注释
下面的代码看起来像一个 bug，但其实是故意的：
def retry_delay(attempt):
    return min(2 ** attempt, 60) + random.uniform(0, 1)
同事想删掉 random.uniform(0, 1)，因为“它让测试不稳定”。写一条注释防止这种误改，并给出让测试稳定的办法。
查看参考答案
def retry_delay(attempt, *, jitter=random.uniform):
    # 加入 0–1 秒的随机抖动：避免大量客户端在同一次故障后
    # 以完全相同的节奏重试，造成周期性的流量尖峰（惊群效应）。
    return min(2 ** attempt, 60) + jitter(0, 1)
注释解释了为什么（不是“加一个随机数”这种复述），并说出了删掉它的后果。测试时通过参数注入一个确定的函数：retry_delay(3, jitter=lambda a, b: 0) == 8。

小结
记住这几点


  1. 注释会过时，代码不会说谎：代码被修改时，注释常常没有同步更新。一条错误的注释比没有注释更糟。
  2. 先尝试用代码表达：# 检查员工是否有资格享受全部福利 + 复杂条件 → if employee.is_eligible_for_full_benefits():。解释变量和提取函数能代替大部分“这段在做什么”的注释。
  3. 好注释解释“为什么”：业务原因、选择这个算法的理由、被否决的显而易见方案、外部系统的怪癖（“支付网关在周日返回 503，需重试”）、性能权衡、正则表达式的意图。
  4. 警示与 TODO：说明后果（“这个测试会运行 10 分钟”“该函数不是线程安全的”）；TODO 要具体、可追踪，最好链接到问题编号。
  5. 坏注释：复述代码（i += 1  # i 加 1）、日志式修改记录（用 git）、注释掉的代码（删掉，git 里有）、署名、##### 位置标记、为了规范而写的空洞 docstring。
  6. 接口文档：公共函数、类和模块的 docstring 描述做什么、参数含义、返回值、异常和前提，不描述怎么做。Ousterhout 认为接口注释是设计的一部分——在这点上它比书中的立场更积极，本课程赞同。
