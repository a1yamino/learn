并发代码的整洁

并发代码的 bug 很难复现，所以设计上的整洁更为重要。本课讲：并发代码的单一职责（把并发管理与业务逻辑分开）；限制共享数据的作用域；使用数据副本与不可变数据；线程尽量独立；了解标准库提供的安全工具（队列、线程池、锁、asyncio）；三种经典模型（生产者—消费者、读者—写者、哲学家就餐）及其问题；保持同步区域很小；正确地关闭；以及如何测试并发代码。示例使用 Python 的 threading、concurrent.futures 与 asyncio，并说明 GIL 不能替你保证正确性。约 50 分钟。

三种经典模型

模型问题Python 中的做法


生产者—消费者速度不匹配；如何结束queue.Queue(maxsize=N)（背压）+ 哨兵值或 q.shutdown()（3.13+）


读者—写者读多写少时，既要并发读又要写一致写时复制：构造新的不可变对象后整体替换引用（引用赋值在 CPython 中是原子的）


哲学家就餐多个资源，死锁与饥饿固定的获取顺序；或用一个更粗粒度的锁；或带超时的 acquire


线程、进程还是 asyncio？ I/O 密集且并发数大（成千上万个连接）→ asyncio；I/O 密集、使用阻塞库 → 线程池；CPU 密集 → 进程池（或使用自由线程构建的 Python 3.13+、或把计算交给 NumPy 等释放 GIL 的库）。

01
竞态：多运行几次，看看结果是否每次都等于 800000。（结果可能因 Python 版本和机器不同而不同。）
cat > race.py <<'EOF'
import sys, threading

sys.setswitchinterval(1e-6)   # 让线程切换更频繁，更容易观察到竞态
THREADS, N = 8, 100_000

def plus_one(x):   # 读—改—写之间有一次函数调用，真实代码中常常如此
    return x + 1

count = 0
def unsafe():
    global count
    for _ in range(N):
        count = plus_one(count)

lock = threading.Lock()
safe_count = 0
def safe():
    global safe_count
    for _ in range(N):
        with lock:
            safe_count = plus_one(safe_count)

for target in (unsafe, safe):
    ts = [threading.Thread(target=target) for _ in range(THREADS)]
    for t in ts: t.start()
    for t in ts: t.join()
print(f"unsafe={count} safe={safe_count} expected={THREADS * N}")
EOF

02
更好的方式：不共享。每个任务返回自己的结果，线程池负责收集。
cat > noshare.py <<'EOF'
from concurrent.futures import ThreadPoolExecutor

def count_words(text):          # 纯函数：可以单独测试
    return len(text.split())

docs = ["a b c", "d e", "f g h i"] * 1000
with ThreadPoolExecutor(max_workers=8) as pool:
    total = sum(pool.map(count_words, docs))
print(total)
EOF

03
生产者—消费者：有界队列 + 哨兵，正确关闭。
cat > pc.py <<'EOF'
import queue, threading

DONE = object()
q = queue.Queue(maxsize=10)
results = []

def producer():
    for i in range(25):
        q.put(i)
    q.put(DONE)

def consumer():
    while (item := q.get()) is not DONE:
        results.append(item * item)

threads = [threading.Thread(target=producer), threading.Thread(target=consumer)]
for t in threads: t.start()
for t in threads: t.join()
print(len(results), sum(results))
EOF
python3 pc.py
25 4900
挑战
重新设计
一个爬虫用 20 个线程抓取网页，所有线程共享一个 visited = set() 和一个 results = []，每个线程在抓取前检查 if url not in visited: visited.add(url)。指出问题，给出一个更整洁的设计。
查看参考答案
问题：“检查后添加”不是原子的，两个线程可能同时通过检查而重复抓取；共享的结构让业务逻辑（解析页面）与并发控制交织在一起。
设计：
  • 一个协调者（单线程）独占 visited，负责去重与调度：它从结果队列取出新链接，未访问过的放入任务队列。
  • 工作者只做一件事：fetch_and_parse(url) -> Page(links, data)，纯粹、可单独测试，不接触共享状态。
  • 两个队列（任务、结果）连接它们；用有界队列控制并发与内存；用哨兵或计数正确结束。
  • 如果使用 asyncio，协调者与工作者都在同一个事件循环中，visited 只在 await 点之间被访问，天然不需要锁——但抓取函数要是异步的。

小结
记住这几点


  1. 把并发与业务分开：业务逻辑写成普通的、可单独测试的函数；线程、队列、事件循环放在外层。并发代码有自己的生命周期和失败模式，应当有自己的模块。
  2. 限制共享可变数据：共享的东西越少，需要保护的就越少。优先选择：不共享（每个任务自己的数据）→ 共享不可变数据 → 通过队列传递消息 → 最后才是加锁的共享状态。
  3. GIL 不保证正确性：counter += 1 是“读—改—写”多条字节码，线程切换可能发生在中间。在较新的 CPython 中，简单的 += 很少表现出竞态，但这只是实现细节而不是保证；只要读与写之间有函数调用或 I/O，问题马上出现。需要原子性时使用锁或线程安全的数据结构。
  4. 使用标准库的高层工具：queue.Queue、concurrent.futures.ThreadPoolExecutor、asyncio.TaskGroup，而不是自己用裸线程和条件变量拼装。
  5. 同步区域保持很小：锁内只做必要的读写，不做 I/O、不调用外部回调；多个锁按固定顺序获取以避免死锁。
  6. 正确关闭与测试：设计时就考虑如何停止（哨兵值、取消、超时）。测试并发代码：先让业务逻辑在单线程下正确，再用更多线程、更多迭代、随机延迟反复运行；把偶发失败当作真问题对待。
