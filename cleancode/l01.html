为什么要写整洁的代码：混乱的代价与童子军规则

《代码整洁之道》开篇的论点：代码被阅读的次数远多于被编写的次数，混乱会让每一次修改变得更慢，最终拖垮团队。本课讲“整洁”到底指什么（几位资深程序员的不同定义），混乱如何以复利方式累积，“以后再清理”为何几乎从不发生，童子军规则（离开时让营地比来时更干净），以及如何把整洁当作专业态度而不是审美偏好。最后也介绍对这本书的常见批评，帮你在本课程中有判断地吸收它。约 40 分钟。

“整洁”的几种定义
书中引用了几位资深程序员的看法，归纳起来是同一件事的不同侧面。


侧面含义反面


优雅、高效逻辑直接，缺陷难以藏身，依赖最少绕弯的流程让 bug 有地方躲


像好文章一样可读读起来像在叙述意图，不需要逆向工程读者要在脑中模拟执行


他人可以改进有测试、有清楚的边界，别人敢改只有作者敢动的代码


看得出作者在乎没有明显可改进之处遗留的 TODO、注释掉的代码、随意的命名


没有重复、表达力强、抽象恰当每个概念只在一处表达同一规则改三处


符合预期每个函数都基本是你读之前猜的样子名为 get_user 的函数还会发邮件


还有一些对本书的讨论值得在开始前知道：


  • John Ousterhout（《软件设计的哲学》）认为过度拆分出大量很浅的小函数会增加接口数量与阅读跳转，好的模块应该“深”：接口简单、隐藏大量实现。第 3 课会对比两种观点。
    • 

  • 书中一些 Java 重构示例的结果被批评为可读性反而下降（例如依赖大量实例变量在小方法间传递状态）。本课程会指出这些地方，给出更稳妥的写法。
    • 

  • 测试先行、小步重构、命名、去重复、关注点分离等核心观点则被广泛接受。

03
在测试保护下重构：引入 Order、改名、命名常量。旧函数保留为一个薄包装，调用方不用一次全改。
cat > orders.py <<'EOF'
from dataclasses import dataclass

PAID = 1
DISCOUNT_RATE = 0.9

@dataclass(frozen=True)
class Order:
    id: int
    amount: float
    status: int

    @property
    def is_paid(self):
        return self.status == PAID

def total_of_paid_orders(orders, discount_threshold):
    total = 0
    for order in orders:
        if not order.is_paid:
            continue
        if order.amount > discount_threshold:
            total += order.amount * DISCOUNT_RATE
        else:
            total += order.amount
    return total

def calc(rows, threshold):  # 兼容旧调用方，逐步迁移后删除
    return total_of_paid_orders([Order(*r) for r in rows], threshold)
EOF

挑战
童子军规则：一次小清理
在下面这个函数里只做三处最有价值的小改进（不改变行为），并说明为什么选它们：
def proc(d):
    # 检查
    if d["a"] < 18:
        return False
    x = d["e"].split("@")
    if len(x) != 2:
        return False
    # TODO 以后支持手机号
    return True
查看参考答案
  1. 函数名：proc → is_valid_signup。它返回布尔值并判断注册数据是否合法，名字应该说出来。
  2. 局部名称：将 d 命名为 signup，再用 age = signup["a"]、email = signup["e"] 表达含义。这里保留原字典键；改成 age/email 会改变输入契约，需另行迁移调用方，不能当作行为不变的小清理。
  3. 魔法数和无用注释：18 → MINIMUM_AGE = 18；删除“# 检查”这种复述代码的注释；TODO 移到问题跟踪系统里。
没有选择大改结构：童子军规则要求的是每次一点点、有测试兜底，而不是在修 bug 时顺手重写模块。

小结
记住这几点


  1. 读远多于写：修改代码之前必须先读懂它，读与写的时间比经常超过 10:1。让代码易读，就是让后续每一次修改都更快。
  2. 混乱有复利：每一处“先这样凑合”都会让下一处修改更难，于是又多一处凑合。生产率随时间下降，加人也救不回来，最后常常走向“推倒重写”——而重写的系统又会重复同样的过程。
  3. “以后再清理”通常等于“永不清理”（LeBlanc 定律）。真正可行的是在每次修改时顺手清理一点点。
  4. 整洁的特征：意图一目了然、只做一件事并做好、没有重复、有测试保护、最小惊讶——读到的每个函数都基本是你预期的样子。
  5. 童子军规则：每次签入代码时，让它比你签出时更干净一点：改一个名字、拆一个长函数、删一处重复。小步、持续、有测试兜底。
  6. 有判断地吸收：书中的 Java 示例与“函数越短越好”等主张受到不少批评（例如 Ousterhout 的“深模块”观点）。本课程把原则当成可权衡的工具：目标始终是降低理解与修改的成本，而不是机械地遵守规则。
