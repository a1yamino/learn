系统：关注点分离与依赖注入

一座城市能运转，是因为有分工和恰当的抽象层级。软件系统也一样。本课讲把系统的“构造”与“使用”分开：对象不应该自己去创建或查找依赖，而是在一个组装点（main / 组合根）统一创建，再注入进去；延迟初始化的代价；工厂；横切关注点（日志、事务、权限、重试）如何用装饰器、中间件或上下文管理器与业务逻辑分开；以及“先做简单的，再按需演进”的系统架构观。约 45 分钟。

01
业务与基础设施分开，依赖由外部注入。本例只重试通知调用，且模拟的超时发生在发送之前；times=3 是总尝试 3 次。真实网络超时不代表对方未发送，必须先明确幂等键或去重契约，不能把整个 place() 无条件重试，否则可能重复保存订单。通知与保存跨系统的一致性还需 Outbox 等设计，本例不实现它。
cat > orders.py <<'EOF'
import functools

def retry(times, on):
    if type(times) is not int or times < 1:
        raise ValueError("times 必须是至少为 1 的总尝试次数")
    def wrap(fn):
        @functools.wraps(fn)
        def inner(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except on as e:
                    if attempt == times:
                        raise
                    print(f"[retry] {fn.__name__} 失败 {type(e).__name__}，第 {attempt} 次重试")
        return inner
    return wrap

class OrderService:
    def __init__(self, orders, notifier):
        self._orders = orders
        self._notifier = notifier

    def place(self, order_id, email):
        self._orders.save(order_id)
        self._notifier.notify(email, f"订单 {order_id} 已提交")

class InMemoryOrders:
    def __init__(self):
        self.saved = []
    def save(self, order_id):
        self.saved.append(order_id)

class FlakyNotifier:
    """教学模拟：前两次在发送前失败，第三次才发送。"""
    def __init__(self):
        self.calls = 0
    @retry(times=3, on=(TimeoutError,))
    def notify(self, email, text):
        self.calls += 1
        if self.calls < 3:
            raise TimeoutError()
        print(f"-> {email}: {text}")

def build_service():
    return OrderService(InMemoryOrders(), FlakyNotifier())

import unittest
from orders import OrderService, InMemoryOrders

class RecordingNotifier:
    def __init__(self):
        self.sent = []
    def notify(self, email, text):
        self.sent.append((email, text))

class OrderServiceTest(unittest.TestCase):
    def test_placing_order_saves_and_notifies(self):
        orders, notifier = InMemoryOrders(), RecordingNotifier()
        OrderService(orders, notifier).place(7, "bob@example.com")
        self.assertEqual(orders.saved, [7])
        self.assertEqual(notifier.sent, [("bob@example.com", "订单 7 已提交")])

if __name__ == "__main__":
    unittest.main(argv=["x", "-v"])

查看参考答案
隐式依赖：ORM 全局查询、当前日期、环境变量、HTTP 库、SMTP 服务器（还在循环里重复连接）。
def send_daily_digest(*, subscribers: SubscriberSource, items: ItemFeed,
                      mailer: Mailer, today: date) -> int:
    new_items = items.since(today)          # 只取一次，不在循环里
    body = render(new_items)
    count = 0
    for user in subscribers.subscribed():
        mailer.send(user.email, body)
        count += 1
    return count

小结
记住这几点


  1. 把构造与使用分开：业务对象如果在内部 new 出数据库连接、读取环境变量，它就和这些细节绑死了，也无法在测试中替换。让 main（组合根）负责创建并连接所有对象。
  2. 依赖注入（DI）：对象通过构造函数参数获得依赖。在 Python 中通常不需要 DI 框架——在一个 build_app(config) 函数里手动组装就足够清楚。
  3. 延迟初始化的隐患：if self._service is None: self._service = RealService() 把具体类型硬编码进来，并在每个使用处引入一个隐式的全局状态与时间依赖。
  4. 工厂：当对象需要在运行时（而不是启动时）创建，且应用需要控制“何时创建”，注入一个工厂（可以就是一个函数）。
  5. 横切关注点：日志、计时、事务、重试、鉴权会散布在每个函数里。用装饰器、中间件、上下文管理器把它们集中起来，业务函数只保留业务逻辑。
  6. 演进的架构：不必在第一天设计好一切。只要关注点分得好、依赖方向正确，系统可以从单体逐步演进；过早引入复杂框架反而会锁死选择。
