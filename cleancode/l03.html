函数：短小、只做一件事、一个抽象层级

函数是程序的第一层组织单位。本课讲书中关于函数的核心主张：短小；只做一件事（以及如何判断“一件事”）；每个函数只处在一个抽象层级，代码能自顶向下像报纸一样阅读（下降规则）；switch / if-elif 链的处理；描述性的名字。然后把它和 Ousterhout 的“深模块”观点放在一起比较：拆分的目的是降低理解成本，过度拆分同样会增加成本。练习把一个 40 行的混合函数拆成清晰的层级。约 50 分钟。

两种观点并排
把书中的主张和“深模块”放在一起看，得到一个可操作的标准。


问题《代码整洁之道》《软件设计的哲学》本课程建议


函数多长？越短越好，几行长度不是问题，接口复杂度才是一屏之内，意图一眼可见


何时拆分？能提取出新名字就拆能隐藏复杂度、简化接口才拆按概念拆：新函数有可复用或可独立理解的意义


拆分的代价很少讨论接口数量增加、阅读跳转、“共享状态”变隐式如果读者必须同时看 5 个小函数才能理解一件事，就合回去


注释尽量用名字代替接口注释必不可少见第 5 课


书中一个常被引用的反例：为了让方法短，把局部变量提升为实例字段，让多个小方法通过字段传递数据。这会让数据流变得隐式，读者必须追踪“谁在什么时候写了这个字段”。更好的做法是让小函数通过参数和返回值传递数据（尽量写成纯函数）。

01
写一个找出最长函数的小工具（用标准库 ast）。
cat > longest.py <<'EOF'
import ast, pathlib, sys

def function_lengths(path):
    tree = ast.parse(pathlib.Path(path).read_text())
    for node in ast.walk(tree):
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            yield node.end_lineno - node.lineno + 1, f"{path}:{node.name}"

if __name__ == "__main__":
    paths = []
    for arg in sys.argv[1:]:
        p = pathlib.Path(arg)
        paths.extend(sorted(p.rglob("*.py")) if p.is_dir() else [p])
    found = [f for p in paths for f in function_lengths(p)]
    for length, where in sorted(found, reverse=True):
        print(f"{length:4}  {where}")
EOF
02
一个混合层级的函数。
cat > report.py <<'EOF'
def monthly_report(rows):
    totals = {}
    for line in rows:
        parts = line.strip().split(",")
        if len(parts) != 3:
            continue
        region, status, amount = parts
        if status != "paid":
            continue
        totals[region] = totals.get(region, 0) + int(amount)
    out = []
    for region in sorted(totals):
        cents = totals[region]
        out.append(f"{region:<6}{cents // 100:>8,}.{cents % 100:02d}")
    out.append("-" * 17)
    grand = sum(totals.values())
    out.append(f"{'total':<6}{grand // 100:>8,}.{grand % 100:02d}")
    return "\n".join(out)
EOF

03
拆成三个层级：解析、汇总、渲染。保留旧行为：非 paid 行不解析金额；paid 行金额非法时仍报 ValueError。测试故意包含金额无效的退款行，防止调整执行顺序时引入异常。
cat > report.py <<'EOF'
from typing import NamedTuple

class Payment(NamedTuple):
    region: str
    status: str
    amount_text: str

def monthly_report(lines):
    payments = parse_payments(lines)
    totals = paid_totals_by_region(payments)
    return render(totals)

def parse_payments(lines):
    for line in lines:
        parts = line.strip().split(",")
        if len(parts) == 3:
            region, status, amount = parts
            yield Payment(region, status, amount)

def paid_totals_by_region(payments):
    totals = {}
    for p in payments:
        if p.status == "paid":
            totals[p.region] = totals.get(p.region, 0) + int(p.amount_text)
    return totals

def render(totals):
    lines = [row(region, totals[region]) for region in sorted(totals)]
    lines.append("-" * 17)
    lines.append(row("total", sum(totals.values())))
    return "\n".join(lines)

def row(label, cents):
    return f"{label:<6}{format_money(cents):>11}"

def format_money(cents):
    return f"{cents // 100:,}.{cents % 100:02d}"
EOF

挑战
拆分，还是不拆？
对下面每个提取方案判断是否值得，并说明理由：① 从 render 中提取 format_money(cents)；② 从 paid_totals_by_region 中提取 is_paid(p)，内容是 return p.status == "paid"；③ 把 monthly_report 的三行再合并回一个函数；④ 把 parse_payments 的局部变量改为实例字段，让它拆成三个无参数的方法。
查看参考答案
  1. 值得。“金额格式化”是独立的概念，在发票、邮件中也会用，且有边界情况（负数、千分位）值得单独测试。
  2. 可以，但不是必须。如果“已支付”的判断在多处出现，或者未来会变复杂（部分退款），把它放到 Payment.is_paid 属性上最好——它属于数据本身，而不是一个游离的函数。
  3. 不值得。三行的编排函数是这个模块最有价值的“目录”，合并会把三个层级重新混在一起。
  4. 不值得，而且有害。用实例字段在方法之间传数据会让数据流隐式化、产生顺序依赖，也让函数无法单独测试。用参数和返回值传递。

小结
记住这几点


  1. 只做一件事：判断方法——如果还能从函数中提取出一个名字不是简单复述原实现的新函数，它就在做不止一件事；或者，如果函数中的语句分属不同的抽象层级，它也在做不止一件事。
  2. 一个抽象层级：render_report() 中同时出现 build_sections()（高层）与 line.strip().split(",")（低层）会让读者在层级之间来回跳。把低层细节下沉到命名良好的函数中。
  3. 下降规则：调用者在上，被调用者紧随其下，读代码像读报纸：先标题，再段落，再细节。
  4. 短小是结果而不是目标：书中主张很短（几行）；更稳妥的标准是“一屏之内、一眼能看懂意图”。拆分后每个函数应当有一个有意义的名字，否则拆分只是增加跳转。
  5. 深模块（Ousterhout）：接口简单、内部隐藏大量复杂度的模块才有价值。很多只有一两行、仅被调用一次的“浅”函数，会让读者在十个文件间跳转才能拼出逻辑。两种观点的交集：按概念拆分，不按行数拆分。
  6. 条件分支链：根据类型选择行为的 if/elif 链如果在多处重复出现，用多态或查表替代，只在一处（工厂）出现一次。
