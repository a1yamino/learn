边界：包装第三方代码

我们的系统依赖大量不受自己控制的代码：第三方库、HTTP API、云服务。本课讲如何让这些边界保持整洁：不要让第三方类型渗透到整个代码库（把 Map、requests 的 Response、SDK 对象挡在边界之内）；用适配器包装它们，只暴露我们需要的接口；写“学习测试”来探索并锁定第三方行为；在接口尚不存在时先定义我们想要的接口（端口与适配器）；以及如何用假实现测试边界两侧。约 40 分钟。

03
端口与适配器
“我们想要的接口”放在中心，第三方代码在外围。


层内容依赖


领域 / 用例订单、发票逻辑；端口（FileStore、PaymentGateway 协议）不依赖任何第三方库


适配器S3FileStore、StripeGateway、InMemoryFileStore实现端口，依赖 SDK


组装（main）根据配置选择适配器并注入依赖一切（第 13 课）


不要过度包装：标准库、语言内置类型和非常稳定的库（如 datetime、pathlib）通常不需要包装。包装的价值与“这个依赖变化或被替换的可能性”以及“它让测试变难的程度”成正比。

# 模拟一个第三方 SDK：我们不能修改它
class WeatherClient:
    def fetch(self, q):
        if q == "nowhere":
            raise KeyError("city")
        return {"data": {"current": {"temp_k": 293.15, "cond": [{"txt": "Clear"}]}}}

class LearningWeatherClient(unittest.TestCase):

03
适配器 + 端口 + 假实现：业务代码只认识 Weather。
cat > weather.py <<'EOF'
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Weather:
    celsius: float
    summary: str

class CityNotFound(Exception):
    pass

class WeatherSource(Protocol):
    def current(self, city: str) -> Weather: ...

class VendorWeatherSource:
    def __init__(self, client):
        self._client = client

    def current(self, city):
        try:
            raw = self._client.fetch(city)
        except KeyError as e:
            raise CityNotFound(city) from e
        now = raw["data"]["current"]
        return Weather(round(now["temp_k"] - 273.15, 1), now["cond"][0]["txt"])

class FakeWeatherSource:
    def __init__(self, table):
        self._table = table

    def current(self, city):
        if city not in self._table:
            raise CityNotFound(city)
        return self._table[city]

def clothing_advice(source: WeatherSource, city):
    w = source.current(city)
    return "带外套" if w.celsius < 15 else "短袖即可"
EOF

挑战
设计一个边界
你的应用要发送短信验证码。目前用供应商 A 的 SDK，明年可能换成供应商 B；测试时不能真的发短信；供应商 A 的 SDK 在限流时抛出 AThrottleError，在号码无效时返回 {"code": 4001}。设计端口、适配器与异常。
查看参考答案
class SmsError(Exception): ...
class InvalidPhoneNumber(SmsError): ...
class SmsRateLimited(SmsError): ...

class SmsSender(Protocol):
    def send_code(self, phone: PhoneNumber, code: str) -> None: ...

class VendorASmsSender:
    def send_code(self, phone, code):
        try:
            r = self._sdk.send(to=phone.e164, template="verify", params={"code": code})
        except AThrottleError as e:
            raise SmsRateLimited() from e
        if r.get("code") == 4001:
            raise InvalidPhoneNumber(phone)

class RecordingSmsSender:      # 测试用
    def __init__(self): self.sent = []
    def send_code(self, phone, code): self.sent.append((phone, code))
端口用业务语言命名（“发送验证码”，不是“发送模板消息”）；两种不同风格的错误（异常与返回码）在适配器中统一为领域异常；换供应商时只需新增 VendorBSmsSender，并让两个适配器通过同一套契约测试。

小结
记住这几点


  1. 第三方接口为通用而设计，我们的需求是具体的。直接在业务代码里到处使用 boto3 客户端或 requests.Response，会让升级、替换和测试都牵一发而动全身。
  2. 适配器：用一个小类包装第三方代码，只暴露应用需要的操作，用应用的语言命名（FileStore.save(name, data) 而不是 s3.put_object(Bucket=..., Key=..., Body=...)），并把第三方异常翻译成领域异常。
  3. 学习测试：在使用新库之前，写几个测试验证你对它行为的理解。这些测试免费地成为升级时的回归检查：新版本行为变了，学习测试会先失败。
  4. 先定义我们想要的接口：依赖的系统还没做好时，先写下理想中的接口（Protocol），用假实现推进开发；真实系统到位后再写适配器。这就是“端口与适配器”（六边形架构）的思想。
  5. 边界上的测试：业务逻辑用内存假实现（fake）测试，快且稳定；适配器本身用少量集成测试（或契约测试）对真实服务验证。
  6. 让边界保持很少：一个第三方类型只应出现在少数几个文件里。可以用 grep 检查：import boto3 出现在 30 个文件里就是信号。
