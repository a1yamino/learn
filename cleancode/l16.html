之后：行为移到数据旁边；数据流强制顺序。
cat > gen.py <<'EOF'
from dataclasses import dataclass

FREE_SHIPPING_MIN_YEARS = 3

@dataclass(frozen=True)
class Customer:
    tier: str
    years: int
    country: str

    def shipping_fee(self):
        if self.tier == "gold" and self.years > FREE_SHIPPING_MIN_YEARS:
            return 0
        return 10 if self.country == "CN" else 30

def parse(raw):
    return [line.split(",") for line in raw]

def summarize(rows):
    return sum(int(amount) for _, amount in rows)

def render(total):
    return f"total={total}"

def report(raw):
    return render(summarize(parse(raw)))
EOF
python3 -c "
from gen import *
print(report(['a,1', 'b,2']))
print(Customer('gold', 5, 'US').shipping_fee(), Customer('basic', 1, 'CN').shipping_fee())"

挑战
选择方向
Order 类中有一个方法 discount()，它读取 customer.tier、customer.years、customer.coupons，以及 self.total。它应该留在 Order、移到 Customer，还是放到新的地方？说出你的判断依据。
查看参考答案
它同时依恋两个对象。判断依据是“什么变化会导致它改变”：
  • 如果折扣规则主要是“会员等级的权益”（由会员体系决定），移到 Customer.discount_for(total)，Order 只传入金额。
  • 如果折扣规则经常变化、由营销团队调整、还会涉及商品与活动，提取一个 DiscountPolicy.discount(order, customer)（策略对象），两者都不依恋。
  • 只有当它主要依赖订单内容时才留在 Order。
“依恋情结”提示的是数据与行为离得太远；解决方案是让行为靠近变化原因所在的地方。

小结
记住这几点


  1. 发散式变化与散弹式修改是一对：前者是一个类承担了多个变化原因（拆分它）；后者是一个变化原因散落在多个类（合并它们）。目标是让“一个变化原因 ↔ 一个模块”。
  2. 依恋情结：一个方法频繁访问另一个对象的数据，计算的逻辑应搬到数据所在的类（移动函数）。“把行为放在数据旁边”。
  3. 消息链与中间人：a.b().c().d() 让调用方依赖整条结构（隐藏委托）；但如果一个类的一半方法都只是转发给另一个对象，它就成了多余的中间人（移除中间人）。两者之间需要平衡。
  4. 全局可变数据：任何地方都能修改，因此任何地方都可能是 bug 的来源。封装它（只能通过函数修改），缩小作用域，或改为不可变。
  5. 封装条件、避免否定：if timer.has_expired() and not timer.is_recurrent() → if should_be_deleted(timer)；if not buffer.should_not_compact() → if buffer.should_compact()。
  6. 隐藏的时间耦合：必须先调用 a() 再调用 b()，但代码中没有任何体现。让每一步的输出成为下一步的输入，顺序就由数据流强制。
