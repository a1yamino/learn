Clean Code · 第 14 课

简单设计四规则与涌现式设计

Kent Beck 的简单设计四规则按优先级排列：① 通过所有测试；② 没有重复；③ 表达了程序员的意图；④ 类和方法的数量尽量少。本课逐条解释它们为什么这样排序、彼此如何冲突（去重复与可读性、最小化与表达力），什么是“知识的重复”与“偶然的相似”，以及如何在 TDD 的重构步骤中让良好的设计逐步涌现，而不是一开始就设计好。约 40 分钟。

03
错误的抽象
把偶然相似合并之后会发生什么。


一个常见的演化过程：


  1. 两处代码看起来相同，于是提取了共享函数 process(data)。
    2. 

  2. 新需求只影响其中一个调用者，于是加了一个参数 process(data, legacy=False)。
    3. 

  3. 又一个需求，加了 if mode == "x"。几轮之后，共享函数里充满了只为某个调用者服务的分支。
    4. 

  4. 没有人敢改，因为每个分支都可能影响所有调用者。


修复方法（Sandi Metz 的建议）：把共享函数内联回每个调用者，删掉每个调用者用不到的分支，然后重新观察真正的重复。预防方法：问“这两段代码会因为同一个原因而改变吗？”——只有答案为“是”时才合并。


信号多半是


修改一处时，你总是也要改另一处知识重复 → 合并


共享函数中的布尔参数和模式分支越来越多错误的抽象 → 内联并重新拆分


两段代码属于不同的业务方 / 模块可能是偶然相似 → 观察一段时间

在 TDD 的重构步骤中应用四条规则：先去掉知识重复，再改善表达，最后删除多余元素。

起点：测试通过（规则 1），但税率重复了三次。
cat > billing.py <<'EOF'
def checkout_total(subtotal):
    return round(subtotal * 1.13, 2)

def invoice_tax(lines):
    return round(sum(l * 0.13 for l in lines), 2)

def vat_report(revenue):
    return f"VAT: {revenue * 0.13:.2f}"
EOF
cat > test_billing.py <<'EOF'
import unittest
from billing import *
class T(unittest.TestCase):
    def test_checkout(self): self.assertEqual(checkout_total(100), 113)
    def test_invoice(self): self.assertEqual(invoice_tax([100, 50]), 19.5)
    def test_report(self): self.assertEqual(vat_report(1000), "VAT: 130.00")
    def test_checkout_keeps_current_float_rounding(self):
        self.assertEqual(checkout_total(1.50), 1.69)
if __name__ == "__main__":
    unittest.main(argv=["x"], verbosity=0)
EOF

02
规则 2 与 3：一个知识只有一处，名字表达意图。保留原来的浮点运算顺序；不要在结构重构时顺便改变金额舍入。1.50 的当前结果1.69由特征测试固定，金额类型的改进放到下一课单独处理。
cat > billing.py <<'EOF'
VAT_RATE = 0.13

def vat_of(amount):
    return amount * VAT_RATE

def checkout_total(subtotal):
    return round(subtotal * (1 + VAT_RATE), 2)

def invoice_tax(lines):
    return round(sum(vat_of(line) for line in lines), 2)

def vat_report(revenue):
    return f"VAT: {vat_of(revenue):.2f}"
EOF

挑战
合并还是保留？
一个电商系统中：① 商品详情页和购物车页面都显示“预计送达日期”，计算逻辑相同；② 注册表单和收货地址表单都校验手机号，正则相同；③ 管理员报表与用户订单页面都把金额格式化为“¥1,234.50”；④ 用户密码与 API 密钥都要求“至少 12 位”。逐一判断是知识重复还是偶然相似。
查看参考答案
  1. 知识重复：同一条业务规则（物流承诺），必须一致，否则用户会看到两个日期。合并。
  2. 知识重复：“什么是合法的中国手机号”是同一个知识。合并为 PhoneNumber.parse()。
  3. 知识重复：货币显示格式是全站统一的约定。合并。
  4. 偶然相似：密码长度由安全策略与用户体验决定；API 密钥长度由密钥生成方式决定（通常更长、随机生成）。它们会独立变化，保持分开，各自命名：MIN_PASSWORD_LENGTH、API_KEY_LENGTH。

小结
记住这几点


  1. 规则 1：通过所有测试。系统必须首先按预期工作，且能被验证。可测试性会反过来推动更好的设计：难测的类通常耦合太紧、职责太多。
  2. 规则 2：没有重复。重复意味着同一个知识需要在多处维护（DRY）。注意区分知识的重复（同一条业务规则写了两次）与偶然的相似（两段代码碰巧长得像，但会因不同原因变化）——后者合并反而有害。
  3. 规则 3：表达意图。好名字、短函数、标准模式名（Command、Visitor）、测试当作文档。写完之后多花一点时间让下一个读者轻松。
  4. 规则 4：尽量少的元素。前三条规则不应被教条推到极端：为每个类都建接口、为每种可能都留扩展点，会产生大量无用的类。在满足前三条的前提下，越少越好。
  5. “三次法则”：第一次直接写，第二次出现时注意到重复，第三次再抽象。过早抽象会把偶然的相似固化下来，之后拆开它比去重复更难（“错误的抽象比重复更昂贵”——Sandi Metz）。
  6. 涌现：在 TDD 的每个“重构”步骤应用这四条规则，好的结构会从小步改进中长出来，而不需要提前完整设计。
