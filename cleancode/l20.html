综合项目：一步步重构一个混乱的订单模块

把整门课的手法用在一个真实感很强的模块上：一个混乱的 process_order 函数，混合了解析、校验、库存、定价、折扣与通知（库存和通知均为内存模拟），使用 dict 和魔法数，返回码与 None 混用，直接依赖全局状态。先用特征测试记录旧行为，再区分结构重构与有意的契约变更。本课给出旧实现和新接口的终态对照：异常替代返回码、Decimal 舍入政策、非法数量拒绝和重复商品库存修复都须单独评审，不能统称为保行为重构。最后在新结构上添加满减规则，并比较度量。约 90 分钟。

起点代码
先读一遍，列出你闻到的坏味道。练习中会逐步重构它。


STOCK = {"pen": 20, "ink": 2, "pad": 0}
PRICES = {"pen": 12.5, "ink": 30.0, "pad": 8.0}
COUPONS = {"SAVE10": 10}
SENT = []

def process_order(d, flag):
    # 检查
    if not d.get("items"):
        return None
    t = 0
    for i in d["items"]:
        s, q = i.split(":")
        q = int(q)
        if s not in PRICES:
            return -1
        if STOCK[s] < q:
            return -2
        t += PRICES[s] * q
    # 折扣
    if d.get("type") == 2 and t > 200:
        t = t * 0.95
    c = d.get("coupon")
    if c:
        if c in COUPONS:
            t = t - COUPONS[c]
    if t < 0:
        t = 0
    # 扣库存
    for i in d["items"]:
        s, q = i.split(":")
        STOCK[s] -= int(q)
    # 通知
    if flag:
        SENT.append((d["email"], "订单金额 %.2f" % t))
    return round(t, 2)


旧实现逐行检查库存，重复SKU可能超卖，负数量还会反向增加库存。新接口会明确修复这些行为，这些修复属于业务变更。坏味道清单（与课程对应）：神秘的名字（d、t、s、q、flag）；魔法数（2、200、0.95）；基本类型偏执（str 解析、float 金额）；返回码与 None 混用；标识参数；全局可变数据；重复的解析逻辑；混合抽象层级；段落注释；隐藏的副作用（扣库存、发通知）。

新接口的终态对照：领域对象、拆分阶段、异常、策略与注入。实际修改时应分成小提交；先做结构变换，再单独审查返回码→异常、Decimal 舍入与数量/库存规则的变更。下面的旧特征测试仍针对 order.py，下一步才测试 order_after.py；不能把两者混为同一套安全网。
cat > order_after.py <<'EOF'
from dataclasses import dataclass
from decimal import Decimal, ROUND_HALF_UP
from enum import Enum
from typing import Protocol


@dataclass(frozen=True, order=True)
class Money:
    amount: Decimal

    @classmethod
    def of(cls, value):
        return cls(Decimal(str(value)).quantize(Decimal("0.01"), ROUND_HALF_UP))

    def __add__(self, other): return Money.of(self.amount + other.amount)
    def __sub__(self, other): return Money.of(max(self.amount - other.amount, Decimal(0)))
    def times(self, factor): return Money.of(self.amount * Decimal(str(factor)))

ZERO = Money.of(0)


class OrderError(Exception): pass
class EmptyOrder(OrderError): pass
class UnknownProduct(OrderError): pass
class OutOfStock(OrderError): pass
class InvalidQuantity(OrderError): pass


class CustomerType(Enum):
    REGULAR = 1
    VIP = 2


@dataclass(frozen=True)
class OrderLine:
    sku: str
    quantity: int


@dataclass(frozen=True)
class OrderRequest:
    lines: tuple
    email: str
    customer_type: CustomerType = CustomerType.REGULAR
    coupon: str | None = None


@dataclass(frozen=True)
class Quote:
    request: OrderRequest
    subtotal: Money
    discount: Money

    @property
    def total(self):
        return self.subtotal - self.discount


class Discount(Protocol):
    def amount(self, request: OrderRequest, subtotal: Money) -> Money: ...


VIP_DISCOUNT_MIN = Money.of(200)
VIP_PAYABLE_RATE = Decimal("0.95")

class VipDiscount:
    def amount(self, request, subtotal):
        if request.customer_type is CustomerType.VIP and subtotal > VIP_DISCOUNT_MIN:
            return subtotal - subtotal.times(VIP_PAYABLE_RATE)
        return ZERO


class CouponDiscount:
    def __init__(self, coupons):
        self._coupons = coupons

    def amount(self, request, subtotal):
        return self._coupons.get(request.coupon, ZERO)


def parse_request(data):
    lines = []
    for item in data.get("items") or []:
        sku, qty = item.split(":")
        try:
            quantity = int(qty)
        except ValueError as e:
            raise InvalidQuantity(f"{sku}: 数量必须为正整数") from e
        if quantity <= 0:
            raise InvalidQuantity(f"{sku}: 数量必须为正整数")
        lines.append(OrderLine(sku, quantity))
    if not lines:
        raise EmptyOrder()
    return OrderRequest(tuple(lines), data["email"], CustomerType(data.get("type", 1)), data.get("coupon"))


def price(request, catalog, discounts):
    subtotal = ZERO
    for line in request.lines:
        if line.sku not in catalog:
            raise UnknownProduct(line.sku)
        subtotal = subtotal + catalog[line.sku].times(line.quantity)
    after_vip = subtotal - VipDiscount().amount(request, subtotal)
    discount = (subtotal - after_vip) + sum((d.amount(request, after_vip) for d in discounts), ZERO)
    return Quote(request, subtotal, discount)


def place(quote, stock, notify):
    total = quote.total
    required = {}
    for line in quote.request.lines:
        required[line.sku] = required.get(line.sku, 0) + line.quantity
    for sku, quantity in required.items():
        if stock[sku] < quantity:
            raise OutOfStock(f"{sku}: 需要 {quantity}，库存 {stock[sku]}")
    for sku, quantity in required.items():
        stock[sku] -= quantity
    notify(quote.request.email, f"订单金额 {total.amount:.2f}")
    return total


def process_order(data, *, catalog, stock, discounts, notify):
    request = parse_request(data)
    quote = price(request, catalog, discounts)
    return place(quote, stock, notify)
EOF

04
在新接口上对应测试旧场景，并增加有意修正的边界：重复SKU按合计数量检查、拒绝非正整数数量、VIP按应付金额舍入。新接口返回 Money、以领域异常拒绝订单；Decimal 的 ROUND_HALF_UP 与旧 float/round 不在所有输入上等价，旧调用方需要适配或明确迁移。库存与通知之间没有事务：通知失败时库存已扣减，生产系统还需持久化订单、幂等和 Outbox 等设计，不能整单盲目重试。

class OrderTest(unittest.TestCase):

挑战
继续扩展
在整洁的结构上完成两个新需求，并说明各自修改了哪些地方：① 优惠券与 VIP 折扣不能叠加，取其中较大者；② 下单成功后除了邮件，还要写一条审计日志，业务拒绝的订单也要记录原因。
查看参考答案
  1. 折扣互斥：把“如何组合多个折扣”提取为一个策略，price() 接收 combine：
    def best_of(discounts):
    def combine(request, subtotal):
        return max((d.amount(request, subtotal) for d in discounts), default=ZERO)
    return combine
    修改点：price() 一处（改为调用 combine）+ 组装处。VipDiscount 也作为普通策略注册，不再写死在 price() 中——这是对第一次重构的进一步改进。为“同时满足两者时取较大者”写测试。
  2. 审计日志：这是横切关注点，不应写进 place()。在组合根包装 process_order：
    def audited(process, audit):
    def run(data, **deps):
        try:
            total = process(data, **deps)
        except OrderError as e:
            audit("rejected", data, repr(e))
            raise
        audit("placed", data, total)
        return total
    return run
    修改点：只新增代码。process_order 本身与它的测试都没有改变。

小结
记住这几点


  1. 先安全网，后重构：特征测试固定当前行为（包括可疑的行为），参数接缝让依赖可替换（第 18 课）。
  2. 按坏味道推进：神秘的名字 → 改名；魔法数 → 常量与枚举；基本类型偏执 → Money、OrderLine；过长函数 → 拆分阶段（解析 / 定价 / 执行）；返回码 → 异常；隐藏依赖 → 注入（第 2–17 课）。
  3. 结构重构应保持已覆盖行为；修改返回类型、异常、舍入或输入规则属于行为变更，应先明确新契约再调整对应测试。旧模块测试通过不能证明新模块正确。
  4. 结构服务于变化：最后添加的新需求（新的折扣规则）只需要新增一个类和一行注册，证明了重构的价值（开闭原则）。
  5. 度量只是参考：函数长度、复杂度、参数个数都下降了，但真正的检验是：下一个读者需要多长时间理解它，下一个需求需要改动多少地方。
  6. 课程回顾：整洁代码的目标始终是降低理解与修改的成本。原则之间会冲突，判断依据是“什么会变化、谁会阅读”。
