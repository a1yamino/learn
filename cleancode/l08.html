03
EAFP、异常与结果类型
Python 社区偏好 EAFP（先做再处理异常），但并非所有场景都适合异常。


风格写法适合


LBYL（先检查）if key in d: v = d[key]检查很便宜，并且没有竞态


EAFP（先做）try: v = d[key] except KeyError: ...Python 惯用；文件、网络等“检查后状态可能已变”的操作（避免 TOCTOU 竞态）


结果类型Ok(value) | Err(reason)（Rust、Go 的多返回值）失败是业务上常见、调用方必须处理的结果（如表单校验）


判断标准：失败是“例外”（磁盘满、网络断）还是“正常的另一种结果”（密码错误、库存不足）？前者用异常，在边界统一处理；后者可以作为返回值的一部分，让类型系统提醒调用方处理。书中主张一律使用异常；在今天的多语言实践里，这两种风格各有位置。


# 在边界统一处理：请求处理器是最外层
def handle(request):
    try:
        return ok(place_order(parse(request)))
    except ValidationError as e:
        return bad_request(e.errors)
    except OutOfStock as e:

没有优惠券时出现了 TypeError：None 被传到了算术里。之后：异常 + 特例对象。先计算总价再扣库存，避免计价失败后库存已减少；本例仅适用于单线程内存演示，异常本身不提供事务或并发保护。

from dataclasses import dataclass

STOCK = {"pen": 3, "ink": 0}

class CheckoutError(Exception):
    pass

class UnknownProduct(CheckoutError):
    pass

class OutOfStock(CheckoutError):
    pass

@dataclass(frozen=True)
class Coupon:
    rate: float
    def apply(self, amount):
        return amount * (1 - self.rate)

class NoCoupon:
    def apply(self, amount):
        return amount

COUPONS = {"SAVE10": Coupon(0.1)}

def reserve(sku, qty):
    if isinstance(qty, bool) or not isinstance(qty, int) or qty <= 0:
        raise ValueError("数量必须为正整数")
    if sku not in STOCK:
        raise UnknownProduct(f"没有商品 {sku!r}")
    if STOCK[sku] < qty:
        raise OutOfStock(f"{sku} 库存 {STOCK[sku]}，需要 {qty}")
    STOCK[sku] -= qty

def coupon_for(code):
    return COUPONS.get(code, NoCoupon())

def checkout(sku, qty, price, code=None):
    total = coupon_for(code).apply(price * qty)
    reserve(sku, qty)
    return total
EOF

DEFAULT = Settings(db_url="sqlite:///app.db", pool_size=5)

class SettingsError(Exception):
    pass

def load_settings(path) -> Settings:
    try:
        with open(path) as f:
            data = json.load(f)
    except FileNotFoundError:
        return DEFAULT
    except json.JSONDecodeError as e:
        raise SettingsError(f"{path} 不是合法的 JSON（第 {e.lineno} 行）") from e
    try:
        db = data["db"]
        return Settings(db_url=db["url"], pool_size=int(db["pool"]))
    except (KeyError, TypeError, ValueError) as e:
        raise SettingsError(f"{path} 中 db 配置不完整或格式错误: {e!r}") from e
  • 原函数用 except Exception 吞掉了所有错误（包括编程错误），并返回 None，调用方解包时才失败，远离原因。
  • 新版本区分了三种情况：可恢复（文件不存在 → 默认值）、配置错误（带上下文的领域异常）、其他（向上传播）。返回值是一个类型明确的 Settings，从不为 None。

小结
记住这几点


  1. 异常代替返回码：返回码迫使调用方在每次调用后立即检查，主逻辑被 if err 淹没。异常把正常路径与错误处理分开。
  2. 把 try 块当作事务来写（原书原则）：try 中的代码要么全部完成，要么在 except 里让程序回到一致的状态。注意这是写代码的要求，try/except 本身不会自动回滚已经发生的修改。先完成校验和可能失败的计算，再修改状态；跨多次写入则需数据库事务、显式补偿或其他一致性机制。先写出异常的测试，再填充实现。资源用 with 管理，保证释放。
  3. 提供上下文：异常消息应说明失败的操作和原因（哪个文件、哪个订单号、期望什么）。包装底层异常时用 raise NewError(...) from e 保留因果链。
  4. 按调用者的需要定义异常：调用者通常只关心“能否恢复、如何恢复”。把第三方库抛出的多种异常包装成少数几个有意义的领域异常（第 9 课）。
  5. 别返回 None，也别传入 None：返回 None 让每个调用者都要检查，漏掉一处就是 AttributeError。改为抛出异常、返回空集合，或使用特例对象（如 GuestUser、空的 NoDiscount）。用类型注解 Optional 标明真正可选的值。
  6. 不要吞掉异常：except Exception: pass 会隐藏 bug。只捕获你能处理的异常类型，范围尽量小；不能处理就让它向上传播，在边界（请求处理器、任务入口）统一记录。
