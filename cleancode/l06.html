格式：垂直与水平的排版

格式是沟通的一部分。本课讲垂直格式（文件大小、报纸隐喻、用空行分隔概念、相关的代码靠近、变量在使用处附近声明、调用者在被调用者之上）与水平格式（行宽、空格表达优先级、缩进），以及团队规则为什么比个人偏好更重要——在 Python 中这意味着把格式交给 Black 或 Ruff 自动处理，把精力留给名字和结构。约 35 分钟。

Python 项目的格式配置
一份典型配置：格式与 lint 交给 Ruff，在提交前和 CI 中运行。


# pyproject.toml
[tool.ruff]
line-length = 88

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM"]   # 风格、错误、导入顺序、常见 bug、升级、简化

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff         # lint，--fix 自动修复
        args: [--fix]
      - id: ruff-format  # 格式化


一旦格式由工具决定，团队就把讨论集中在工具无法判断的事情上：名字、函数边界、模块边界、概念的远近。这正是本课程后面所有课的主题。

一个顺序混乱的模块：被调用者在调用者之前，相关函数分散。
cat > export.py <<'EOF'
def _format_cell(v):
    return str(v).replace(",", " ")

def unrelated_helper():
    return 42

def export_orders(orders):
    return "\n".join(_to_row(o) for o in orders)

def _to_row(order):
    return ",".join(_format_cell(v) for v in order)
EOF
02
写一个小检查：如果函数在它的第一个调用者之前定义，就报告并返回非零退出码。这里只演示本课的排列约定，不是 Python 语法要求，也不是通用静态分析器。
cat > stepdown.py <<'EOF'
import ast, sys

def check(path):
    tree = ast.parse(open(path).read())
    defs = {n.name: n.lineno for n in tree.body if isinstance(n, ast.FunctionDef)}
    first_caller = {}
    for fn in tree.body:
        if not isinstance(fn, ast.FunctionDef):
            continue
        for node in ast.walk(fn):
            if isinstance(node, ast.Call) and isinstance(node.func, ast.Name) and node.func.id in defs:
                first_caller.setdefault(node.func.id, fn.lineno)
    violations = 0
    for name, line in defs.items():
        caller = first_caller.get(name)
        if caller and caller > line:
            print(f"{path}:{line}: {name} 定义在调用者（第 {caller} 行）之前")
            violations += 1
    return violations

raise SystemExit(1 if check(sys.argv[1]) else 0)
EOF
python3 stepdown.py export.py
export.py:1: _format_cell 定义在调用者（第 10 行）之前
03
按报纸顺序重排，删除无关函数（它应在别的模块里）。
cat > export.py <<'EOF'
"""把订单导出为 CSV 文本。"""


def export_orders(orders):
    return "\n".join(_to_row(o) for o in orders)


def _to_row(order):
    return ",".join(_format_cell(v) for v in order)


def _format_cell(value):
    return str(value).replace(",", " ")
EOF

挑战
排列一个类
一个 ReportGenerator 类有这些方法：_fetch_rows、generate（公共入口，依次调用 _fetch_rows、_summarize、_render）、_render（调用 _format_money）、__init__、_summarize、_format_money。按报纸顺序排列它们。
查看参考答案
class ReportGenerator:
    def __init__(...)
    def generate(...)        # 公共入口：读者从这里开始
    def _fetch_rows(...)     # 按 generate 中的调用顺序
    def _summarize(...)
    def _render(...)
    def _format_money(...)   # _render 的细节，紧跟其后
构造函数在最前（约定），公共方法在私有方法之前，私有方法按首次被调用的顺序排列，最底层的细节在最后。

小结
记住这几点


  1. 格式是给人看的：今天的写法会影响以后每一个读者。一致性比任何具体规则都重要。
  2. 报纸隐喻：文件顶部是高层概念与公共接口，越往下越是细节。名字（文件名、模块名）应当能告诉读者是否找对了地方。
  3. 垂直间距与靠近：空行分隔不同概念；紧密相关的代码放在一起；局部变量在第一次使用处附近声明；调用者在被调用者之上，相关函数相邻。
  4. 水平格式：行宽保持适中（Black 默认 88）；空格表达结构（a*b + c*d 中的空格暗示了优先级——但自动格式化工具会统一处理）；不要为了对齐而加空格，它会在改名后失效。
  5. 团队规则：由工具执行格式（Black、Ruff format、isort），在 CI 与提交钩子中检查，代码评审就不必再讨论空格和引号。
  6. 文件大小：大多数模块在数百行以内就足够；一个数千行的文件往往混合了多个概念，按概念拆成包。
