连接池：PgBouncer

第 6 课的应用内连接池解决了单个实例的问题，但当有几十个服务、几百个实例或大量短生命周期的进程（无服务器函数、PHP）时，总连接数仍会失控。本课讲 PgBouncer 的三种池模式、事务模式下哪些功能不能用、关键配置参数、监控命令，以及部署位置的选择。约 55 分钟。

在你的电脑上练习
在 pgnet 网络中运行 PgBouncer，连接 pg 容器。


01
写一个最小配置。
mkdir -p ~/pgb && cat > ~/pgb/pgbouncer.ini <<'EOF'
[databases]
shop = host=pg port=5432 dbname=shop
[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = plain
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
default_pool_size = 5
max_client_conn = 1000
admin_users = postgres
EOF
echo '"postgres" "pg"' > ~/pgb/userlist.txt
02
启动 PgBouncer（社区镜像 edoburu/pgbouncer）。
docker run -d --name pgb --network pgnet -p 6432:6432 -v ~/pgb:/etc/pgbouncer edoburu/pgbouncer
docker exec -e PGPASSWORD=pg -u postgres pg psql -h pgb -p 6432 -d shop -c "SELECT 1"

挑战
迁移一个服务到事务模式
一个 Python 服务目前直连 PostgreSQL，代码里有：连接建立后 SET search_path = tenant_42；用 pg_advisory_lock 保证定时任务单实例；用 LISTEN orders_changed 接收通知。要改为通过 transaction 模式的 PgBouncer 连接，逐项说明怎么改。
查看参考答案
  • search_path：会话级 SET 会泄漏给共享同一服务端连接的其他客户端，也会在下一个事务中丢失。改为在每个事务开头 SET LOCAL search_path = tenant_42，或在 SQL 中写全限定名 tenant_42.orders，或为每个租户使用不同的角色并 ALTER ROLE … SET search_path（PgBouncer 按用户分池，每个池的连接都带着这个设置）。
  • 咨询锁：会话级锁在事务结束后服务端连接被别人拿走，锁仍然挂在那个连接上，释放时也可能发到别的连接。改为事务级 pg_try_advisory_xact_lock，并让整个任务（或其“领取”步骤）在一个事务中完成。
  • LISTEN：需要一个长期保持的会话，事务模式下无法工作。为监听者单独建一个直连 PostgreSQL 的连接（或通过 session 模式的另一个 PgBouncer 池）。NOTIFY 可以照常通过事务池发送。
另外检查：驱动是否使用协议级预备语句（psycopg 3 默认会在执行多次后自动 prepare，需 PgBouncer 1.21+ 并设置 max_prepared_statements，或在驱动中设 prepare_threshold=None）；临时表；WITH HOLD 游标。

小结
记住这几点


  1. PgBouncer 是一个轻量的单进程代理：客户端连到它（可以上万个），它只维护少量到 PostgreSQL 的服务端连接，并把客户端的请求分配到这些连接上。
  2. 池模式：session 客户端断开前独占一个服务端连接，兼容性最好但省不了连接；transaction 只在事务期间占用，事务结束立即归还，最常用；statement 每条语句归还，不允许多语句事务。
  3. 事务模式下，跨事务的会话状态不再可靠：SET（用 SET LOCAL 代替）、会话级咨询锁、LISTEN、WITH HOLD 游标、临时表都可能“串”到别的客户端。协议级预备语句从 PgBouncer 1.21 起可通过 max_prepared_statements 支持。
  4. 关键参数：default_pool_size（每个“用户+数据库”对的服务端连接数）、max_client_conn、reserve_pool_size、server_idle_timeout、query_wait_timeout（客户端排队等待的上限）。
  5. 用管理控制台 psql -p 6432 pgbouncer 执行 SHOW POOLS：cl_waiting 持续大于 0 而 sv_idle 为 0，说明池不够或有慢事务占着连接；同时检查 PostgreSQL 端是否已经饱和。
  6. 部署：放在数据库服务器旁（集中管理），或作为应用的 sidecar（减少一跳延迟，但每个 sidecar 各有池，总数要再算）。PgBouncer 是单线程的，单个进程约能处理几万 QPS，更多时运行多个进程（so_reuseport）。
