复制：流复制与逻辑复制

挑战
用逻辑复制做大版本升级
生产库运行 PostgreSQL 16，800 GB，要升级到 18，停机时间不超过 5 分钟。写出基于逻辑复制的步骤，并列出必须注意的坑。
查看参考答案
  1. 新建 18 集群，用 pg_dump --schema-only 导入表结构（逻辑复制不复制 DDL）。
  2. 旧库 wal_level = logical，CREATE PUBLICATION up FOR ALL TABLES；新库 CREATE SUBSCRIPTION … PUBLICATION up，开始初始数据同步（每张表先 COPY 再追增量）。
  3. 等 pg_stat_subscription_stats 无错误、所有表在 pg_subscription_rel 中状态为 r（ready）、延迟接近 0。在新库上验证行数和关键查询，ANALYZE。
  4. 切换窗口：应用停写（或把旧库设为只读），等延迟归零；把序列值同步到新库（setval 设为旧库当前值加余量）；应用切到新库；DROP SUBSCRIPTION。
注意：每张表必须有主键或设置 REPLICA IDENTITY，否则 UPDATE/DELETE 无法复制；迁移期间冻结 DDL 变更；大对象（pg_largeobject）不会复制；初始同步期间旧库会保留 WAL，留够磁盘；订阅端的冲突（例如唯一键已存在）会让复制停止，需要监控。PostgreSQL 17 起也可以用 pg_createsubscriber 把一个物理备库直接转成逻辑订阅端，省掉 800 GB 的初始拷贝。

小结
记住这几点


  1. 物理流复制：主库的 walsender 进程把 WAL 记录流式发送给备库的 walreceiver，备库的 startup 进程持续重放。备库是主库逐字节的副本（同一大版本、同一架构），可以开启 hot_standby 提供只读查询。
  2. 建备库：pg_basebackup -h primary -D $PGDATA -R -X stream -C -S replica1 复制数据目录，-R 写入 primary_conninfo 并创建 standby.signal，-C -S 创建复制槽。主库需要 wal_level = replica（默认）和一个有 REPLICATION 属性的角色。
  3. 复制槽让主库保留备库尚未接收的 WAL，备库断开再久也能接上；代价是备库长期不回来时主库的 pg_wal 会无限增长。用 max_slot_wal_keep_size 设上限。
  4. 默认异步：主库提交不等备库，故障切换时可能丢失最近的事务。synchronous_standby_names = 'ANY 1 (r1, r2)' 加 synchronous_commit：remote_write / on（备库刷盘）/ remote_apply（备库已重放，读自己写入的数据可见）。同步复制增加提交延迟，备库全挂时主库写入会卡住。
  5. 延迟分三段：发送（sent_lsn）、备库写入/刷盘（write/flush_lsn）、重放（replay_lsn）。备库上的长查询与重放冲突时，等待 max_standby_streaming_delay 后被取消；hot_standby_feedback = on 避免取消，但会让主库保留旧版本（第 16 课）。
  6. 逻辑复制：wal_level = logical，主库把 WAL 解码成行级变更。CREATE PUBLICATION 选择表，订阅端 CREATE SUBSCRIPTION。可以跨大版本、只同步部分表或行列、订阅端可写。不复制 DDL 和序列值，表要有主键或 REPLICA IDENTITY。Debezium 等 CDC 工具也基于逻辑解码。
