WAL：预写日志与检查点

PostgreSQL 修改数据页时并不立即写回数据文件，而是先把“做了什么”写进预写日志（WAL）。本课讲 WAL 如何保证提交不丢、LSN 是什么、崩溃恢复怎么从检查点开始重放、full-page writes 为什么存在，以及 checkpoint 和 max_wal_size 的调优。WAL 也是复制（第 18 课）和 PITR（第 23 课）的基础。约 60 分钟。

挑战
估算 max_wal_size
某服务在高峰期每分钟产生约 300 MB WAL，日志里频繁出现 “checkpoints are occurring too frequently (24 seconds apart)”。希望检查点约每 15 分钟一次。给出 checkpoint_timeout 和 max_wal_size 的设置，并说明调大的代价。
查看参考答案
ALTER SYSTEM SET checkpoint_timeout = '15min';
ALTER SYSTEM SET max_wal_size = '8GB';
SELECT pg_reload_conf();
15 分钟 × 300 MB ≈ 4.5 GB。max_wal_size 是两次检查点之间允许的 WAL 量的软上限（大致对应 1 + completion_target 个检查点周期），设到 8 GB 左右，让检查点主要由时间触发。收益：检查点少了，full-page writes 显著减少，WAL 量和 I/O 都下降。代价：pg_wal 需要更多磁盘空间（峰值可能超过设置）；崩溃恢复需要重放更多 WAL，恢复时间变长（重放通常比生成快，几 GB 一般在一两分钟内）。两个参数都只需 reload。

小结
记住这几点


  1. 预写规则：数据页被写回磁盘之前，描述这次修改的 WAL 记录必须先落盘。提交时只需顺序写并 fsync WAL，数据页可以在之后慢慢写，随机写变顺序写。
  2. WAL 是一串记录，位置用 LSN（如 0/1A3C2F8，字节偏移）表示，存放在 pg_wal/ 下 16 MB 的段文件中。每个数据页头记录最后修改它的 LSN。
  3. 检查点把所有脏页写回数据文件并记录一个位置。崩溃后从最近的检查点开始重放 WAL 到末尾，就恢复到崩溃前已提交的状态。检查点之前的 WAL 段可以回收（除非复制槽或归档还需要）。
  4. 检查点由 checkpoint_timeout（默认 5 min）或 WAL 量达到 max_wal_size（默认 1 GB）触发。checkpoint_completion_target = 0.9 把写入摊开。日志中频繁出现 “checkpoints are occurring too frequently” 说明 max_wal_size 太小。
  5. full_page_writes：检查点后某页第一次被修改时，WAL 中写入整页镜像，防止断电造成的半页写（torn page）无法恢复。这也是检查点越频繁、WAL 越多的原因。
  6. synchronous_commit = off 让 COMMIT 不等 WAL 刷盘：崩溃时可能丢最近几百毫秒的已提交事务，但不会损坏数据。可以按事务设置，适合可丢的日志类写入。fsync = off 则可能损坏整个库，生产不要用。
