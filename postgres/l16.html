VACUUM、autovacuum 与事务 ID 回卷

MVCC 的代价是死元组：被删除和被替换的旧版本会一直留在表里，直到 VACUUM 确认没有任何快照还需要它们。本课讲 VACUUM 做的几件事、可见性映射和冻结映射、autovacuum 何时触发以及如何调优、什么在阻止清理，以及 32 位事务 ID 用尽时的回卷保护。约 65 分钟。

在你的电脑上练习
使用 shop 库。先关闭一张测试表的 autovacuum，手动观察。


01
准备：一张 100 万行的表。
CREATE TABLE bloat (id int PRIMARY KEY, v text) WITH (autovacuum_enabled = off);
INSERT INTO bloat SELECT i, md5(i::text) FROM generate_series(1, 1000000) i;
SELECT pg_size_pretty(pg_relation_size('bloat'));

----------------

02
全表更新一次：大小翻倍，一半是死元组。
UPDATE bloat SET v = v || 'x';
SELECT pg_size_pretty(pg_relation_size('bloat')), n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'bloat';
 pg_size_pretty | n_live_tup | n_dead_tup
----------------+------------+------------
 130 MB         |    1000000 |    1000000
03
VACUUM：死元组清掉，文件大小不变，但空间可以复用。
VACUUM (VERBOSE) bloat;
SELECT pg_size_pretty(pg_relation_size('bloat')), n_dead_tup FROM pg_stat_user_tables WHERE relname = 'bloat';
INFO:  vacuuming "shop.public.bloat"
INFO:  finished vacuuming "shop.public.bloat": index scans: 1
pages: 0 removed, 16667 remain …
tuples: 1000000 removed, 1000000 remain, 0 are dead but not yet removable
 pg_size_pretty | n_dead_tup
----------------+------------
 130 MB         |          0

05
长事务阻止清理：窗口 2 开一个 REPEATABLE READ 事务读一次，窗口 1 更新并 VACUUM。
-- 窗口 2
BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT count(*) FROM bloat;
-- 窗口 1
UPDATE bloat SET v = v || 'z' WHERE id <= 100000;
VACUUM (VERBOSE) bloat;
-- 看到 dead but not yet removable 后，在窗口 2 释放快照
ROLLBACK;
-- 回到窗口 1，验证旧版本现在可清理，并恢复测试表自动维护
VACUUM (VERBOSE) bloat;
ALTER TABLE bloat RESET (autovacuum_enabled);

挑战
给大表调 autovacuum
events 表 8 亿行，每天更新约 500 万行。现在 autovacuum 大约每 30 天才处理它一次，每次运行 10 小时，期间查询变慢，表已膨胀到 2 倍。给出表级配置并解释每一项。
查看参考答案
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.005,   -- 约 400 万死元组触发
  autovacuum_vacuum_threshold = 10000,
  autovacuum_vacuum_insert_scale_factor = 0.01,
  autovacuum_analyze_scale_factor = 0.005,
  autovacuum_vacuum_cost_limit = 2000        -- 放宽这张表的节流
);
-- 全局：ALTER SYSTEM SET autovacuum_vacuum_cost_delay = '2ms'; maintenance_work_mem 或 autovacuum_work_mem = '1GB'
默认 20% 意味着 1.6 亿个死元组才触发，一次要处理的量巨大。把阈值降到 0.5%，大约每天一次，每次处理的量小、时间短，死元组在膨胀之前就被复用。放宽 cost_limit 让单次运行更快完成；足够大的 autovacuum_work_mem 让死元组 TID 一次装下（PostgreSQL 17 起用更紧凑的结构），索引只需扫描一遍。已有的膨胀不会因此消失：用 pg_repack 在线重写一次。同时检查是否有长事务或废弃复制槽阻挡 xmin 视界，否则怎么调都没用。

小结
记住这几点


  1. 普通 VACUUM：扫描表，找出对所有事务都不可见的死元组，删除指向它们的索引条目，标记堆中的空间可复用（更新 FSM），更新可见性映射（VM）和统计信息。它不阻塞读写，但通常不会把文件变小（只截断表尾的空页）。
  2. VACUUM FULL 重写整张表和索引，回收全部空间，但持有 ACCESS EXCLUSIVE 锁、需要额外一份空间。生产上用 pg_repack 或 pg_squeeze 在线重写。
  3. autovacuum 在死元组数超过 autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples（默认 50 + 20%）时触发；插入量达到阈值也会触发（让 VM 和冻结跟上）。大表的 20% 太大，应按表调小 scale_factor。autovacuum_vacuum_cost_limit 控制节流，默认偏保守。
  4. VACUUM 只能清理比所有会话的最老快照（xmin 视界）更旧的死元组。长事务、idle in transaction、废弃的复制槽、开启 hot_standby_feedback 的副本上的长查询、未提交的两阶段事务都会让视界停住，表就持续膨胀。
  5. xid 是 32 位，比较按模 232 的“环”进行，只能区分前后约 20 亿个事务。为防止回卷后旧数据“变成未来”，VACUUM 会把足够老的元组冻结（标记为对所有人可见）。age(relfrozenxid) 超过 autovacuum_freeze_max_age（2 亿）时强制进行防回卷 VACUUM，即使 autovacuum 被关闭。
  6. 剩余 xid 少于约 300 万时，数据库拒绝分配新事务 ID，只能停机维护。监控 age(datfrozenxid)，远在此之前就要找出阻止冻结的原因。
