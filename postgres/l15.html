HOT 更新：只改未建索引的列。
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'accounts';
UPDATE accounts SET balance = balance + 1 WHERE name = 'B';
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'accounts';
 n_tup_upd | n_tup_hot_upd
-----------+---------------
        12 |            10
 n_tup_upd | n_tup_hot_upd
-----------+---------------
        13 |            11
挑战
为什么 HOT 比例这么低
orders 表每笔订单平均被 UPDATE 5 次（status 流转），pg_stat_user_tables 显示 n_tup_hot_upd / n_tup_upd 只有 8%，索引膨胀严重。表上有索引 (user_id)、(status)、(created_at)、(updated_at)。分析原因并给出改进。
查看参考答案
HOT 的两个条件：不修改任何被索引的列；同一页有空间放新版本。这里每次 UPDATE 都会改 status 和 updated_at，两者都有索引，所以 HOT 不可能发生，每次更新都要在 4 个索引中各插一个新条目。
  • 评估这两个索引是否必要：updated_at 索引常常只是“可能有用”，用 idx_scan 确认后删除。status 基数低，通常改为部分索引 (created_at) WHERE status = 'pending'——注意部分索引的谓词列也算被索引的列，改 status 时仍不能 HOT，但只有进出 pending 时才需要改这个小索引。
  • 剩下的索引都不含被频繁修改的列后，把 fillfactor 调到 80–90（ALTER TABLE orders SET (fillfactor = 85)，对新页生效，可用 pg_repack 重写旧页），给页内留出放新版本的空间。
预期 HOT 比例会升到 80% 以上，索引写入和膨胀明显下降，VACUUM 也更轻松：HOT 链的旧版本可以在页内被“剪枝”（读取时就能清理），不需要等 VACUUM。PostgreSQL 16 起修改 BRIN 索引列也不再阻止 HOT。

小结
记住这几点


  1. 每个写事务分配一个递增的 32 位事务 ID（xid）。事务的最终状态（进行中、已提交、已中止）记录在 pg_xact（原来叫 clog）中，每个事务 2 位。
  2. 每个元组版本带 xmin（创建它的事务）和 xmax（删除它或用新版本替换它的事务，0 表示仍有效）。UPDATE = 把旧版本的 xmax 设为自己 + 插入一个 xmin 为自己的新版本。
  3. 快照 = xmin:xmax:xip_list。小于 xmin 的事务都已结束；大于等于 xmax 的事务在快照之后才开始，一律不可见；xip_list 是取快照时仍在进行的事务，也不可见。
  4. 可见性规则（简化）：一个版本可见，当且仅当 xmin 已提交且对快照可见，并且 xmax 为空、或 xmax 已中止、或 xmax 对快照不可见。自己事务的修改另有命令号（cmin/cmax）规则。
  5. 查 pg_xact 有开销，第一次确认后在元组的 infomask 中设置提示位（如 XMIN_COMMITTED），之后不用再查。这就是只读查询也会让页变脏的原因（第 9 课）。
  6. HOT 更新（heap-only tuple）：如果没有修改任何被索引的列，且同一页里有空间放新版本，新版本只在页内用链连接，不新增索引条目。降低表的 fillfactor 给页内留空间，可以提高 HOT 比例。
