性能调优：配置、监控与 pg_stat_statements

挑战
为一台新服务器给出初始配置
专用数据库服务器：16 核、64 GB 内存、NVMe SSD，OLTP 为主，应用通过 PgBouncer 连接，服务端连接约 60 个；每天凌晨有几个报表任务。给出 postgresql.conf 中主要参数的初始值并说明理由。
查看参考答案
shared_buffers = 16GB                 # 25%
effective_cache_size = 48GB           # 给规划器的总缓存估计
work_mem = 32MB                       # (64-16)GB / (60×~3) ≈ 270MB 上限，保守取 32MB
maintenance_work_mem = 2GB
autovacuum_work_mem = 1GB
max_connections = 100                 # PgBouncer 后 60 + 管理与复制余量
random_page_cost = 1.1
effective_io_concurrency = 200
max_wal_size = 16GB
checkpoint_timeout = 15min
wal_compression = lz4
max_worker_processes = 16
max_parallel_workers = 8
max_parallel_workers_per_gather = 2
autovacuum_max_workers = 5
autovacuum_vacuum_cost_limit = 2000
shared_preload_libraries = 'pg_stat_statements,auto_explain'
log_min_duration_statement = 500ms
log_lock_waits = on
idle_in_transaction_session_timeout = 60s
huge_pages = try
work_mem 是按节点分配的，一个复杂查询可能同时用到多份，所以全局值保守；报表任务在自己的会话里 SET work_mem = '512MB'。连接数通过 PgBouncer 控制，不需要很大的 max_connections。NVMe 上随机读便宜，调低 random_page_cost 让规划器更愿意用索引。并行查询主要服务于报表，OLTP 的短查询基本用不到，per_gather 设 2 避免报表占满 CPU。autovacuum 放宽节流，因为 NVMe 承受得起。之后用 pg_stat_statements 和监控数据逐项验证，而不是一次性改完。

小结
记住这几点


  1. 内存：shared_buffers 约 25% 内存；effective_cache_size 约 50–75%；work_mem 每个排序/哈希节点的内存，默认 4 MB，按 (内存 − shared_buffers) / (max_connections × 2~3) 估算后保守设置，复杂报表可在会话中单独调高；maintenance_work_mem 1–2 GB 加速 VACUUM 和建索引。
  2. I/O 与 WAL：SSD 上 random_page_cost = 1.1、effective_io_concurrency = 200；max_wal_size 按检查点间隔估算（第 8 课）；wal_compression = lz4。并行：max_parallel_workers_per_gather 2–4。
  3. pg_stat_statements 按归一化后的语句（常量替换为 $1）累计调用次数、总耗时、平均耗时、行数、缓冲区命中与读取、WAL 量。按 total_exec_time 排序找出对系统整体影响最大的查询，它往往不是单次最慢的那条。
  4. 等待事件（pg_stat_activity.wait_event_type / wait_event）显示活跃会话此刻在等什么：Lock（锁）、LWLock（内部锁，如 WALWrite、BufferMapping）、IO（DataFileRead 读盘、WALSync 刷 WAL）、Client（等客户端，常见于应用处理慢或 idle in transaction）。周期采样就是简易的“活跃会话历史”。
  5. 需要报警的指标：连接数与 max_connections 的比例、活跃会话数相对于 CPU 核数、长事务与 idle in transaction、复制延迟、事务 ID 年龄、磁盘空间（含 pg_wal）、缓存命中率、死元组与 autovacuum 运行情况、检查点频率、锁等待、错误日志（log_min_duration_statement、死锁）。
  6. 调优的方法：一次只改一项，有基准数据（pgbench 或回放真实流量），记录改动前后的指标。不要照搬网上的“最佳配置”——它们不知道你的工作负载。
