挑战
优化“最近活跃用户”报表
查询：SELECT u.id, u.name, max(o.created_at) FROM users u JOIN orders o ON o.user_id = u.id WHERE o.created_at > now() - interval '7 days' GROUP BY u.id, u.name ORDER BY 3 DESC LIMIT 50。orders 有 5000 万行，最近 7 天约 50 万行，只有 user_id 索引，耗时 30 秒。给出分析过程和改法。
查看参考答案
先 EXPLAIN (ANALYZE, BUFFERS)：很可能是 orders 的 Parallel Seq Scan 读完 5000 万行，Rows Removed by Filter 约 4950 万，再 Hash Join users、HashAggregate、Top-N 排序。耗时集中在扫描。
CREATE INDEX CONCURRENTLY orders_created_at_idx ON orders (created_at) INCLUDE (user_id);
有了时间索引，只读最近 7 天的 50 万个条目；INCLUDE user_id 并且表 VACUUM 及时时可以 Index Only Scan，不回表。如果计划仍不对，检查 created_at 的统计是否过期：大量新数据刚写入、ANALYZE 还没运行时，直方图上界还停留在过去，规划器会以为最近 7 天几乎没有数据——对只追加的大表可以调低 autovacuum_analyze_scale_factor。
如果报表频繁被调用，进一步用预聚合：在 users 上维护 last_order_at 列（下单时更新），加索引后变成 ORDER BY last_order_at DESC LIMIT 50，毫秒级。代价是每次下单多一次更新。

小结
记住这几点


  1. ANALYZE 随机抽样（默认 default_statistics_target = 100，约 3 万行），在 pg_stats 中为每列记录：null_frac、n_distinct、most_common_vals/freqs（最多 100 个）、histogram_bounds（其余值的等频分桶）、correlation。autovacuum 在表变化约 10% 后自动 ANALYZE。
  2. 规划器默认假设各列相互独立：city = '台北' AND zip = '100' 的选择率被估为两者相乘，严重低估。CREATE STATISTICS … (dependencies, ndistinct, mcv) ON city, zip FROM t 让它知道列之间的关系。
  3. Nested Loop：外层每行查一次内层，内层有索引且外层行少时最好，启动快。Hash Join：用较小的一边建哈希表，扫描另一边探测，适合大表等值连接，需要 work_mem。Merge Join：两边都按连接键有序（索引或排序）后归并，适合两个大的有序输入和范围外的等值连接。
  4. 估算偏低是最危险的情况：规划器以为外层只有几行而选了 Nested Loop，实际有几十万行，内层被执行几十万次。
  5. 慢查询排查顺序：① 用 pg_stat_statements 找出总耗时最多的语句（第 22 课）；② EXPLAIN (ANALYZE, BUFFERS)；③ 找估算与实际偏差最大、耗时最多的节点；④ 依次考虑：缺索引、统计过期或不足、写法让索引用不上、work_mem 不够、确实需要的数据量太大（改需求或预计算）。
  6. 常见写法问题：对索引列做运算或隐式类型转换；OR 跨列（可改写为 UNION）；NOT IN (子查询) 遇到 NULL 语义问题且难以优化（用 NOT EXISTS）；OFFSET 100000 深分页（用键集分页 WHERE id > $last ORDER BY id LIMIT 20）。
