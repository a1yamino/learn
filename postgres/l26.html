下单函数：一个事务、原子扣库存（第 5、14 课）。
CREATE FUNCTION shop.place_order(p_user bigint, p_product bigint, p_qty int) RETURNS bigint
LANGUAGE plpgsql SET search_path = shop, pg_temp AS $$
DECLARE v_price bigint; v_order bigint;
BEGIN
  UPDATE products SET stock = stock - p_qty WHERE id = p_product AND stock >= p_qty RETURNING price_cents INTO v_price;
  IF NOT FOUND THEN RAISE EXCEPTION 'out of stock' USING ERRCODE = 'P0001'; END IF;
  INSERT INTO orders (user_id, total_cents) VALUES (p_user, v_price * p_qty) RETURNING id INTO v_order;
  INSERT INTO order_items VALUES (v_order, p_product, p_qty, v_price);
  RETURN v_order;
END $$;
ALTER FUNCTION shop.place_order OWNER TO shop_owner;

挑战
写一份事故复盘
上线一个月后的某天 10:05，下单接口 p99 从 30 ms 升到 8 s，持续 25 分钟。你掌握的信息：10:00 有一次部署，迁移脚本执行了 CREATE INDEX orders_status_idx ON orders (status)（没有 CONCURRENTLY）；同一时间运营在跑一个导出报表；PgBouncer 的 cl_waiting 峰值 1800；10:30 索引建完后自动恢复。写出时间线、根因、为什么影响这么大，以及至少四条改进措施（标出对应课程）。
查看参考答案
时间线：10:00 部署开始，迁移执行普通 CREATE INDEX，拿到 orders 的 SHARE 锁 → 10:00 起所有对 orders 的 INSERT/UPDATE 阻塞（下单、支付回调）→ 每个阻塞的请求占着一个 PgBouncer 服务端连接，池被占满，连只读请求也开始排队（cl_waiting 1800）→ 10:05 告警 → 10:30 索引建完，锁释放，积压请求在两分钟内消化完。
根因：在 2 亿行的热表上执行了阻塞写入的 DDL。为什么持续 25 分钟：表大，而且导出报表在争抢 I/O，建索引更慢。为什么波及读接口：所有请求共用一个事务池，被阻塞的写占满了连接（第 17、21 课）。
改进：① 索引一律 CREATE INDEX CONCURRENTLY，在 CI 中用 lint（如 squawk）拦截不安全的 DDL（第 4、25 课）；② 所有迁移设置 lock_timeout，拿不到锁就失败而不是阻塞业务（第 17、25 课）；③ 下单接口设置合理的 statement_timeout，PgBouncer 设置 query_wait_timeout，让故障快速失败而不是无限排队；读写分池，重要接口单独的池（第 6、21 课）；④ 报表改到只读副本执行（第 18 课）；⑤ 迁移安排在低峰期，并在执行前检查 pg_stat_activity 中的长查询（第 22 课）；⑥ 告警加上“锁等待会话数”指标，比 p99 更早发现（第 22 课）。

小结
记住这几点


  1. 设计：bigint identity 主键；金额用 numeric 或整数分；时间用 timestamptz；状态用 CHECK 约束；外键列都建索引；按访问模式设计复合索引，等值列在前、排序列在后（第 2、4、11 课）。
  2. 应用接入：参数化查询、事务短小、原子更新防丢失更新、只重试 40001/40P01、设置 statement_timeout 和 idle_in_transaction_session_timeout、通过 PgBouncer 事务模式连接（第 5、6、14、21 课）。
  3. 可靠性：一主两备 + Patroni 同步模式；pgBackRest 全量/差异备份 + 连续 WAL 归档到隔离的对象存储；每周自动恢复演练（第 18、19、23 课）。
  4. 运维：pg_stat_statements 按总耗时找优化目标；监控连接、长事务、复制延迟、事务 ID 年龄、死元组、磁盘、检查点；大表单独调 autovacuum；日志类大表按月分区（第 16、20、22 课）。
  5. 安全与变更：owner / rw / ro 角色分离，scram + TLS，多租户表可加 RLS；所有迁移设置 lock_timeout，危险 DDL 用 NOT VALID / CONCURRENTLY / 扩展—迁移—收缩（第 17、24、25 课）。
  6. 排障思路：先看现象（等待事件、锁、复制、日志），再看数据（EXPLAIN (ANALYZE, BUFFERS)、估算与实际），然后用对应的内部原理解释原因（MVCC、WAL、缓冲区、规划器），最后选代价最小、可回滚的修复。
