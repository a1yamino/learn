04
事务：with 块正常结束时提交，抛出异常时回滚。
python3 - <<'PY'
import psycopg
with psycopg.connect("postgresql://postgres:pg@localhost/shop") as conn:
    with conn.transaction():
        conn.execute("UPDATE accounts SET balance = balance - 30 WHERE name = %s", ("A",))
        conn.execute("UPDATE accounts SET balance = balance + 30 WHERE name = %s", ("B",))
    print(conn.execute("SELECT name, balance FROM accounts ORDER BY 1").fetchall())
PY

05
连接池：10 个线程共用 4 个连接。
python3 - <<'PY'
from psycopg_pool import ConnectionPool
from concurrent.futures import ThreadPoolExecutor
pool = ConnectionPool("postgresql://postgres:pg@localhost/shop?application_name=pooldemo", min_size=4, max_size=4, timeout=5)
def work(i):
    with pool.connection() as c:
        return c.execute("SELECT pg_backend_pid(), pg_sleep(0.2)").fetchone()[0]
with ThreadPoolExecutor(10) as ex:
    print(sorted(set(ex.map(work, range(20)))))
pool.close()
PY
[1904, 1905, 1906, 1907]

挑战
写一个带重试的事务函数
写一个 Python 函数 run_tx(pool, fn)：从池中取连接，在事务中执行 fn(conn)；遇到序列化失败（40001）或死锁（40P01）时最多重试 3 次，每次退避随机时间；其他错误直接抛出。
查看参考答案
import random, time, psycopg
RETRY = {"40001", "40P01"}
def run_tx(pool, fn, attempts=3):
    for i in range(attempts):
        try:
            with pool.connection() as conn:
                with conn.transaction():
                    return fn(conn)
        except psycopg.Error as e:
            if e.sqlstate not in RETRY or i == attempts - 1:
                raise
            time.sleep(random.uniform(0, 0.05 * 2 ** i))
重试的单位是整个事务：conn.transaction() 在异常时已经回滚，重新调用 fn 会基于最新数据重新执行全部语句。随机退避避免冲突的事务同时重试再次冲突。只重试这两类错误，是因为它们表示“换个时机再做一次就可能成功”；唯一约束冲突、检查约束失败重试也不会变。fn 里不要有发邮件、调用外部接口这类不能重复的副作用。连接在 with 结束时归还给池，异常时也一样。

小结
记住这几点


  1. 连接字符串 postgresql://user:pass@host:5432/db?sslmode=require&application_name=api。设置 application_name，在 pg_stat_activity 里能认出是哪个服务。
  2. 永远用参数化查询：SQL 文本和参数分开发送（扩展查询协议的 Parse/Bind），参数不会被当作 SQL 解析，从根本上杜绝 SQL 注入。不要用字符串拼接或格式化拼 SQL。表名、列名不能参数化，用白名单或 psycopg.sql.Identifier。
  3. 每个连接是一个后端进程（第 1 课），建立连接要几毫秒并占用数 MB 内存。应用用连接池复用连接；池大小通常从 核数 × 2 量级起步，所有实例的池加起来不能超过 max_connections。
  4. 池不是越大越好：并发执行的查询超过 CPU 和磁盘能承受的数量后，吞吐不升反降，延迟变长。等待连接的请求应在池中排队并有超时。
  5. 设置超时：connect_timeout、statement_timeout（单条语句）、lock_timeout、idle_in_transaction_session_timeout。没有超时的查询可能拖垮整个池。
  6. 只对确定已回滚的 40001 serialization_failure、40P01 deadlock_detected 自动重试整个事务。连接断开时先重建连接；若发生在 COMMIT 前后，提交结果可能未知，须用业务幂等键或状态查询确认后再决定是否重试。唯一约束冲突 23505 之类是业务错误，不要重试。
