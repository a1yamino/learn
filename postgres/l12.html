查询规划器与 EXPLAIN

同一条 SQL 有很多种执行方式，规划器估算每种方式的代价并选最便宜的。本课讲一条查询从解析到执行的过程、计划树的读法、cost 的含义和代价参数、EXPLAIN ANALYZE 的各个字段，以及估算行数与实际行数相差很大时意味着什么。约 60 分钟。

05
在你的电脑上练习
使用 shop 库的 users（1000 行）和 orders（10 万行）。第 3 课 amount 约在 1–501 之间，450 以上约占一成。以下页数、行数和耗时为示例；前课写入、VACUUM、随机数据和本机设置会改变实际计划。


01
只估算，不执行。
EXPLAIN SELECT * FROM orders WHERE amount > 450;
 Seq Scan on orders  (cost=0.00..2620.00 rows=10050 width=29)
   Filter: (amount > '450'::numeric)
02
验证代价公式：1370 页 × 1.0 + 100000 行 × 0.01 + 100000 × 0.0025。
SELECT relpages, reltuples, relpages * 1.0 + reltuples * 0.01 + reltuples * 0.0025 AS cost FROM pg_class WHERE relname = 'orders';
 relpages | reltuples |  cost
----------+-----------+---------
     1370 |    100000 | 2620.00
03
估算与实际。
EXPLAIN ANALYZE SELECT * FROM orders WHERE amount > 450;

   Filter: (amount > '450'::numeric)

   Buffers: shared hit=1370

04
连接查询的计划树。
EXPLAIN ANALYZE SELECT u.name, count(*) FROM users u JOIN orders o ON o.user_id = u.id WHERE u.id < 10 GROUP BY u.name;
 HashAggregate  (actual time=0.512..0.514 rows=9 loops=1)
   Group Key: u.name
   ->  Nested Loop  (actual time=0.031..0.441 rows=1012 loops=1)
         ->  Index Scan using users_pkey on users u  (actual time=0.009..0.014 rows=9 loops=1)
               Index Cond: (id < 10)
         ->  Index Scan using orders_user_id_idx on orders o  (actual time=0.004..0.038 rows=112 loops=9)
               Index Cond: (user_id = u.id)

06
诊断：关掉顺序扫描，看索引计划的代价和真实耗时。
SET enable_seqscan = off;
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id > 10;
RESET enable_seqscan;
 Bitmap Heap Scan on orders  (cost=1897.40..4021.12 rows=98890 …) (actual time=4.8..21.6 rows=98880 loops=1)
 …
 Execution Time: 25.010 ms
挑战
解释一个反直觉的计划
SELECT * FROM orders WHERE user_id = 42 ORDER BY id LIMIT 1 有 user_id 索引，但计划却是 Limit → Index Scan using orders_pkey，Filter: (user_id = 42)，实际耗时 40 ms。只查 user_id = 999（该用户没有订单）时更是要几百毫秒。解释规划器的想法和问题所在，给出两种修复。
查看参考答案
规划器的推理：按主键顺序扫描，第一条满足 user_id = 42 的行就能结束。它估计 42 号用户有 111 行、均匀分布在 10 万行中，平均扫描 100000 / 111 ≈ 900 行就会遇到一个，代价很低，还省掉了排序。
问题在“均匀分布”的假设：如果 42 号用户的订单都是最近才产生的（id 很大），就要扫描几乎整个表才能遇到第一条；没有订单的用户则会扫完全表。LIMIT 让规划器对“提前结束”过于乐观。
修复一（推荐）：建复合索引 (user_id, id)，直接定位 user_id = 42 并按 id 有序，读一个条目就结束，任何用户都很快。修复二：改写让规划器不能用 pkey 的顺序，例如 ORDER BY id + 0，或先在 CTE/子查询中取出该用户的行（PostgreSQL 12+ 需加 MATERIALIZED），代价是需要排序。修复一更稳定。

小结
记住这几点


  1. 一条查询依次经过：解析（语法树）→ 分析/重写（解析名字、展开视图和规则）→ 规划（生成候选路径，估代价，选最便宜的）→ 执行（按计划树从上到下拉取行）。
  2. 计划是一棵树，从最里层（缩进最深）的节点开始读。每个节点向父节点逐行提供数据。cost=启动代价..总代价，单位是抽象的“顺序读一页”的倍数；rows 是估算的输出行数，width 是平均行宽。
  3. 代价参数：seq_page_cost = 1、random_page_cost = 4（SSD 上通常调到 1.1–1.5）、cpu_tuple_cost = 0.01、cpu_operator_cost = 0.0025。Seq Scan 代价 ≈ 页数 × 1 + 行数 × 0.01 + 过滤条件的运算代价。
  4. EXPLAIN ANALYZE 会真正执行语句（对 UPDATE/DELETE 要放在 BEGIN … ROLLBACK 中）。actual time=首行..末行 毫秒，按每次循环计；loops 是执行次数，总耗时 ≈ 时间 × loops。PostgreSQL 18 的 EXPLAIN ANALYZE 默认带 BUFFERS。
  5. 先比较每个节点的估算 rows 与实际 rows：相差 10 倍以上，后续的连接方式和顺序就可能选错。常见原因：统计信息过期、多列相关、表达式或函数无法估算（第 13 课）。
  6. 不要用 enable_seqscan = off 这类开关“修复”生产查询，它们只用于诊断：确认另一种计划确实更快后，去解决估算或索引问题。PostgreSQL 没有内置的查询提示（hint）。
