挑战
给常见查询设计索引
接口“我的订单”执行：SELECT id, amount, status, created_at FROM orders WHERE user_id = $1 AND status <> 'cancelled' ORDER BY created_at DESC LIMIT 20。设计一个索引让它不需要排序就能直接按顺序取出前 20 行，并用 EXPLAIN 验证。说明为什么不把 status 放在索引第二列。
查看参考答案
CREATE INDEX orders_user_created_idx ON orders (user_id, created_at DESC);
EXPLAIN ANALYZE SELECT id, amount, status, created_at FROM orders
WHERE user_id = 42 AND status <> 'cancelled' ORDER BY created_at DESC LIMIT 20;
 Limit  (actual time=0.031..0.064 rows=20 loops=1)
   ->  Index Scan using orders_user_created_idx on orders  (actual time=0.030..0.061 rows=20 loops=1)
         Index Cond: (user_id = 42)
         Filter: (status <> 'cancelled'::text)
         Rows Removed by Filter: 3
 Execution Time: 0.081 ms
索引按 user_id 分组、组内按 created_at 降序，于是扫描到第 20 个满足条件的行就停止，没有 Sort 节点。status 用的是不等条件（<>），放在第二列会把 created_at 的顺序拆成多段，规划器就不能直接按时间顺序读，需要额外排序。被排除的取消订单很少，作为 Filter 逐行跳过即可。这里可以把建好的单列 user_id 索引删掉：新索引的第一列就是 user_id，能覆盖它的所有用途。

小结
记住这几点


  1. 没有合适的索引时只能 顺序扫描（Seq Scan）：读出表的每一页逐行判断。表越大越慢。
  2. B-tree 索引按键值排序存储（键 → 行位置 ctid），支持 =、范围（< > BETWEEN）、ORDER BY、前缀 LIKE 'abc%'（需要 C 排序规则或 text_pattern_ops）。主键和 UNIQUE 约束自动创建 B-tree 索引；外键不会。
  3. 复合索引 (a, b) 先按 a 排序、a 相同再按 b：能用于 a = ?、a = ? AND b = ?、a = ? ORDER BY b，但单独 b = ? 基本用不上。经验：等值条件的列在前，范围或排序的列在后。
  4. 索引不是越多越好：每次 INSERT / UPDATE / DELETE 都要维护所有相关索引，占用磁盘和缓存。用 pg_stat_user_indexes.idx_scan 找出从未使用的索引。
  5. 规划器可能故意不用索引：要返回的行占表的很大比例时，顺序扫描反而更快。对列做函数运算（lower(email)、created_at::date）或类型不一致时，普通索引也用不上，需要表达式索引（第 11 课）。
  6. 生产环境建索引用 CREATE INDEX CONCURRENTLY：不阻塞写入，代价是更慢，且失败时会留下一个 INVALID 索引需要删除重建。
