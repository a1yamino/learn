事务隔离级别

多个事务同时读写同一份数据时会出现哪些异常，SQL 标准用四个隔离级别描述能防止哪些异常。本课讲 PostgreSQL 实际提供的三个级别——READ COMMITTED、REPEATABLE READ、SERIALIZABLE——各自看到的数据是什么样、写冲突怎样处理、需要应用做什么，以及丢失更新和写偏斜这两个最常见的并发 bug。约 65 分钟。

02
窗口 2 修改并提交，窗口 1 再读：看到了新值。
-- 窗口 2

-- 窗口 1

 balance
---------

03
REPEATABLE READ：窗口 1 的两次读取一致。
-- 窗口 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE name = 'A';
-- 窗口 2
UPDATE accounts SET balance = 80 WHERE name = 'A';
-- 窗口 1
SELECT balance FROM accounts WHERE name = 'A';
 balance
---------
      50
 balance
---------
      50

05
写偏斜：值班表要求至少一人在班。两个窗口用 SERIALIZABLE。
CREATE TABLE oncall (doctor text PRIMARY KEY, on_duty bool);
INSERT INTO oncall VALUES ('alice', true), ('bob', true);
-- 窗口 1 和 窗口 2 都执行：
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM oncall WHERE on_duty;   -- 2，可以请假
-- 窗口 1
UPDATE oncall SET on_duty = false WHERE doctor = 'alice';
-- 窗口 2
UPDATE oncall SET on_duty = false WHERE doctor = 'bob';
-- 窗口 1
COMMIT;
-- 窗口 2
COMMIT;
COMMIT
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.

挑战
修复库存扣减
库存扣减代码：SELECT stock FROM items WHERE id = $1，应用里判断 stock >= qty，然后 UPDATE items SET stock = $new WHERE id = $1，$new = stock - qty。高峰期出现超卖。说明在 READ COMMITTED 下为什么会超卖，给出至少两种正确写法并比较。
查看参考答案
两个请求同时 SELECT 到 stock = 1，都判断通过，都写回 0：卖出 2 件，只扣了 1 件（丢失更新）。第二个 UPDATE 虽然等了第一个，但写回的是应用算好的常量 0，而不是基于最新值计算。
-- 写法 1：原子条件更新（推荐）
UPDATE items SET stock = stock - $2 WHERE id = $1 AND stock >= $2;
-- 受影响行数为 0 表示库存不足

-- 写法 2：先锁行再判断
BEGIN;
SELECT stock FROM items WHERE id = $1 FOR UPDATE;
-- 应用判断后
UPDATE items SET stock = stock - $2 WHERE id = $1;
COMMIT;

-- 写法 3：REPEATABLE READ / SERIALIZABLE + 重试 40001
写法 1 一条语句完成，行锁只持有一瞬间，并发最好；配合 CHECK (stock >= 0) 兜底。写法 2 适合判断逻辑复杂、要在应用里做的情况，代价是锁持有时间更长，热门商品会排队。写法 3 不需要显式锁，但冲突时要重试，热点行上重试率很高，不适合这里。

小结
记住这几点


  1. READ COMMITTED（默认）：每条语句开始时取一个快照，只看到在此之前已提交的数据。同一事务内两次 SELECT 可能看到不同结果（不可重复读、幻读）。
  2. READ COMMITTED 下 UPDATE/DELETE 遇到被并发事务修改的行，会等待对方结束；对方提交后，重新读取该行最新版本并重新检查 WHERE，满足就基于新版本修改。所以 SET x = x + 1 不会丢失更新，但“先 SELECT 到应用、计算后再 UPDATE 写回值”会。
  3. REPEATABLE READ：整个事务使用第一条语句时取的快照，读到的数据不会变（PostgreSQL 的实现也防住了幻读）。如果要修改的行已被并发事务修改并提交，报 40001 could not serialize access due to concurrent update，应用需要重试整个事务。
  4. SERIALIZABLE：在 REPEATABLE READ 的基础上用 SSI（可串行化快照隔离）跟踪读写依赖，保证结果等价于某种串行执行顺序，能检测写偏斜（两个事务各自读到对方会修改的数据、各写各的行）。有冲突时其中一个事务报 40001。
  5. READ UNCOMMITTED 在 PostgreSQL 中等同于 READ COMMITTED，不存在脏读。
  6. 选择建议：大部分 OLTP 用 READ COMMITTED，配合原子 UPDATE、SELECT … FOR UPDATE（第 17 课）或约束；需要一致的多语句读（报表、导出）用 REPEATABLE READ；业务规则跨多行且难以用锁表达时用 SERIALIZABLE，并在应用层实现重试。
