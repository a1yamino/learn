模式变更与在线迁移

在 7×24 运行的系统上改表结构，难点不是 SQL 怎么写，而是锁和兼容性：一条看似无害的 ALTER TABLE 可能锁表几十分钟，一次字段改名可能让正在运行的旧版本代码全部报错。本课讲哪些 DDL 安全、哪些危险以及替代写法，lock_timeout 与重试，以及“扩展—迁移—收缩”的多步发布模式。约 60 分钟。

分批回填：每次 5000 行。
ALTER TABLE orders ADD COLUMN amount_cents bigint;
DO $$
DECLARE lo bigint := 0; hi bigint;
BEGIN
  SELECT max(id) INTO hi FROM orders;
  WHILE lo <= hi LOOP
    UPDATE orders SET amount_cents = (amount * 100)::bigint WHERE id > lo AND id <= lo + 5000 AND amount_cents IS NULL;
    lo := lo + 5000;
    COMMIT;
  END LOOP;
END $$;

挑战
把 orders.id 从 int 改为 bigint
orders 有 15 亿行，id integer 主键由序列生成，已用到 19 亿，预计 3 个月后溢出（上限约 21.4 亿）。直接 ALTER COLUMN TYPE bigint 要锁表重写数小时。设计一个在线方案。
查看参考答案
  1. ALTER TABLE orders ADD COLUMN id_new bigint;（瞬间）。建触发器：INSERT/UPDATE 时 NEW.id_new := NEW.id，此后新行自动有值。
  2. 按主键范围分批回填 UPDATE … SET id_new = id WHERE id BETWEEN $a AND $b AND id_new IS NULL，监控复制延迟和膨胀，必要时暂停。
  3. CREATE UNIQUE INDEX CONCURRENTLY orders_id_new_idx ON orders (id_new); 加 CHECK (id_new IS NOT NULL) NOT VALID 并 VALIDATE。
  4. 引用 orders.id 的外键列也要同样改成 bigint（往往才是工作量最大的部分），先处理它们。
  5. 切换（一个短事务，设 lock_timeout 并重试）：
    BEGIN;
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
ALTER TABLE orders DROP CONSTRAINT orders_pkey;
ALTER TABLE orders ADD CONSTRAINT orders_pkey PRIMARY KEY USING INDEX orders_id_new_idx;
ALTER TABLE orders RENAME COLUMN id TO id_old;
ALTER TABLE orders RENAME COLUMN id_new TO id;
ALTER SEQUENCE orders_id_seq AS bigint OWNED BY orders.id;
ALTER TABLE orders ALTER COLUMN id SET DEFAULT nextval('orders_id_seq');
ALTER TABLE orders ALTER COLUMN id_old DROP NOT NULL;
DROP TRIGGER orders_sync_id ON orders;
COMMIT;
    利用已验证的 CHECK 约束，PRIMARY KEY USING INDEX 不需要重新扫描。
  6. 观察一段时间后删除 id_old。
应用代码在整个过程中都只读写 id，不需要改动；只要确认 ORM 中的类型能容纳 bigint（尤其是 JavaScript 的 Number 超过 253 会丢精度）。新建表从一开始就用 bigint。

小结
记住这几点


  1. 每条 DDL 都要问两个问题：拿什么锁、持有多久（只改系统目录是毫秒级；需要重写表或全表扫描验证则与表大小成正比）。即使是毫秒级的 ACCESS EXCLUSIVE，也会因为锁队列阻塞所有查询（第 17 课），所以所有迁移都设置 lock_timeout 并在失败时重试。
  2. 安全（只改目录）：ADD COLUMN（含常量或非 volatile 默认值，PostgreSQL 11+）、DROP COLUMN（只是标记）、改名、ALTER COLUMN … DROP NOT NULL、扩大 varchar 长度、CREATE INDEX CONCURRENTLY。
  3. 危险及替代：加 NOT NULL → 先 ADD CONSTRAINT … CHECK (col IS NOT NULL) NOT VALID，再 VALIDATE CONSTRAINT（只拿 SHARE UPDATE EXCLUSIVE），然后 SET NOT NULL 会利用这个约束跳过扫描；加外键 → 同样 NOT VALID + VALIDATE；修改列类型（如 int → bigint）会重写整张表 → 新建列、回填、切换。PostgreSQL 18 起 NOT NULL 约束本身也支持 NOT VALID。
  4. 回填大表要分批：每批几千行、单独提交、按主键范围推进，中间可以暂停，给 VACUUM 和复制留出空间。一条 UPDATE big SET new = old 会产生一个巨大的事务、翻倍的表和长时间的复制延迟。
  5. 扩展—迁移—收缩（expand / migrate / contract）：部署期间新旧代码同时运行，所以每一步的结构都必须同时兼容两个版本。改名一列要拆成：加新列 → 代码双写 → 回填 → 代码改读新列 → 停止写旧列 → 删除旧列，跨越多次发布。
  6. 迁移工具（Flyway、Liquibase、Alembic、sqitch 等）管理版本顺序；但工具不会替你判断锁的影响。注意事务：CREATE INDEX CONCURRENTLY 不能在事务块中执行，需要让工具单独运行这一步。
