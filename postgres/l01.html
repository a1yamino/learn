PostgreSQL 是什么：进程、连接与 psql

挑战

连接用完了会怎样

在 psql 中执行 ALTER SYSTEM SET max_connections = 5; 并重启容器，然后用一个 shell 循环在后台打开 6 个连接（每个执行 SELECT pg_sleep(60)）。哪些连接会失败、看到什么错误？为什么超级用户此时仍然可以连接？最后恢复设置。

查看参考答案
docker exec pg psql -U postgres -c "ALTER SYSTEM SET max_connections = 5"
docker restart pg
for i in 1 2 3 4 5 6; do
  docker exec -e PGPASSWORD=pg pg psql -h 127.0.0.1 -U app -d shop -c "SELECT pg_sleep(60)" &
done
psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  remaining connection slots are reserved for roles with the SUPERUSER attribute

（先用 CREATE ROLE app LOGIN PASSWORD 'pg'; GRANT CONNECT ON DATABASE shop TO app; 创建一个普通用户。）superuser_reserved_connections 默认 3，max_connections=5 时普通用户只能用 2 个，所以第 3 个起就被拒绝；超级用户还能用保留的连接登录进来排查和终止会话（pg_terminate_backend）。这个参数需要重启才能生效，因为共享内存按最大连接数分配。恢复：ALTER SYSTEM RESET max_connections; 后再次重启。生产中连接耗尽的正确解决方式是连接池，而不是无限调大。

小结

记住这几点

  1. PostgreSQL 是客户端/服务器架构。主进程 postmaster 监听端口，每来一个连接就 fork 一个后端进程专门为它服务，连接断开进程退出。
  2. 所以连接是昂贵的：每个连接一个进程、几 MB 内存，max_connections 默认 100。应用应该用连接池，而不是每个请求新建连接（第 6、21 课）。
  3. 后台进程各司其职：checkpointer 和 background writer 把脏页写回磁盘、walwriter 写日志、autovacuum 清理旧版本、WAL sender 负责复制。它们和后端进程通过共享内存（shared_buffers 等）协作。
  4. 一条 SQL 的路径：解析（语法树）→ 分析与改写（解析名字、展开视图）→ 规划（选择执行计划，第 12 课）→ 执行（读写共享缓冲区中的数据页）。
  5. 层级：一个实例（cluster）包含多个数据库；数据库包含多个 schema（默认 public）；schema 包含表、索引、函数等。连接时只能选择一个数据库。
  6. psql 常用元命令：\l 数据库、\dt 表、\d 表名 结构、\x 竖排显示、\timing 计时、\e 编辑器、\? 帮助。
