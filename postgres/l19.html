挑战
设计一个 RPO = 0 的方案
业务要求：任何单点故障都不能丢已提交的订单，切换时间不超过 1 分钟；可以接受写入延迟增加几毫秒。用 Patroni 设计节点数量、同步配置和应用连接方式，并说明这个方案在什么情况下仍会丢数据或停写。
查看参考答案
三个 PostgreSQL 节点放在三个可用区，etcd 三节点（可与 PG 同机，也可独立）。Patroni 配置 synchronous_mode: true、synchronous_node_count: 1：至少一个备库同步确认，提交才返回（synchronous_commit = on）。Patroni 只会把同步备库提升为主库，因此被提升的节点一定拥有全部已提交事务。ttl: 30、loop_wait: 10，切换在 30–40 秒内完成。
应用通过 HAProxy（检查 Patroni 的 /primary 接口）或 Kubernetes Service 连接，连接断开后指数退避重连，事务级重试。
边界：两个备库同时不可用时，严格模式（synchronous_mode_strict: true）会停止写入以保证不丢数据；非严格模式则降级为异步，此时主库再故障会丢数据——这是可用性与 RPO 的取舍，要明确选择。另外，多个可用区同时失联或 etcd 失去多数派时，主库会降级为只读，写入停止。复制保护不了误删数据（DROP TABLE 会被同步到所有备库），那需要 PITR（第 23 课）。

小结
记住这几点


  1. RPO（最多丢多少数据）和 RTO（多久恢复服务）是设计目标。异步复制 RPO 为几秒内的事务，同步复制可以做到 0；自动故障切换的 RTO 通常是 30 秒左右。
  2. 手动提升：备库上 SELECT pg_promote() 或 pg_ctl promote。提升后它切换到新的时间线（timeline ID 加一），WAL 段文件名的前 8 位就是时间线，历史记录在 .history 文件中。
  3. 旧主库恢复后不能直接作为新主库的备库：它可能有新主库没有的 WAL（异步复制时丢的那部分）。用 pg_rewind 把它倒回分叉点再跟随新主库（需要 wal_log_hints = on 或数据校验和），否则只能重新 pg_basebackup。
  4. 脑裂：网络分区时旧主库还活着并继续接受写入，同时备库被提升，两个主库各写各的，数据分叉且无法自动合并。防止它需要可靠的共识和隔离：确认旧主库已停止写入（fencing），或者让它在失去多数派时自己降级。
  5. Patroni：每个节点运行一个代理，通过 etcd / Consul / Kubernetes 等分布式存储竞争一个带 TTL 的 leader 锁。持有锁的是主库；主库代理无法续约时自降为只读；锁过期后由复制最及时的备库接管。配置 synchronous_mode 可保证不丢已提交事务。
  6. 应用如何找到主库：Patroni 的 REST 接口配合 HAProxy 健康检查；Kubernetes 中由 operator（CloudNativePG 等）更新 Service；或在 libpq 连接串中列出多个主机并指定 target_session_attrs=read-write。切换时连接会断开，应用必须能重连和重试。
