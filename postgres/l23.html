备份与时间点恢复（PITR）

复制保护的是硬件故障，备份保护的是一切其他情况：误删数据、错误的迁移、勒索软件、整个机房不可用。本课讲逻辑备份 pg_dump 和物理备份的区别、WAL 归档、如何把数据库恢复到任意一秒，以及 pgBackRest 这类工具和“定期恢复演练”为什么不可省略。约 65 分钟。

05
在你的电脑上练习
在一个新的容器 pitr 中开启归档，做一次完整的 PITR。使用独立练习实例和命名卷；本练习恢复前会清空它的数据目录。


01
启动一个开启归档的实例，归档到命名卷 /archive，让停止实例后的恢复 helper 也能读取备份（生产中应使用独立对象存储）。
docker run -d --name pitr -e POSTGRES_PASSWORD=pg -v pitr-data:/var/lib/postgresql -v pitr-archive:/archive postgres:18 \
  -c archive_mode=on -c archive_command='test ! -f /archive/%f && cp %p /archive/%f' -c archive_timeout=60
docker exec pitr bash -c "mkdir -p /archive && chown postgres /archive"
# 官方镜像初始化时会先启动仅监听 Unix socket 的临时服务器。
# 必须等待最终服务器接受 TCP 连接，避免提前进入下一步。
for attempt in $(seq 1 60); do
  docker exec -u postgres pitr pg_isready -q -t 1 -h 127.0.0.1 -U postgres && break
  sleep 1
done

03
继续写入，创建命名恢复点，然后“误删”。恢复点位于第二批数据提交之后、DROP 之前，避免手抄时间或截断小数秒造成偏差。
docker exec -u postgres pitr psql -c "INSERT INTO t SELECT generate_series(1001,2000)" -c "SELECT pg_create_restore_point('before_drop')" -c "DROP TABLE t"
WAL=$(docker exec -u postgres pitr psql -Atc "SELECT pg_walfile_name(pg_current_wal_lsn())")
docker exec -u postgres pitr psql -c "SELECT pg_switch_wal()"
# 归档异步进行，确认含恢复点的 WAL 段已经出现在共享归档卷
ARCHIVED=f
for attempt in $(seq 1 60); do
  docker exec pitr test -f "/archive/$WAL" && { ARCHIVED=t; break; }
  sleep 1
done
if [ "$ARCHIVED" != t ]; then
  printf '%s\n' '60 秒内没有看到归档文件，请检查 archive_command 和 docker logs pitr，不要继续下一步。' >&2
  false
fi

04
恢复：停止实例，清空数据目录，解压基础备份。
docker exec pitr bash -c "cp -r /tmp/base /archive/base"
docker stop pitr
docker run --rm --volumes-from pitr -u postgres postgres:18 bash -c "
  rm -rf /var/lib/postgresql/18/docker/* && cd /var/lib/postgresql/18/docker && tar xzf /archive/base/base.tar.gz"
05
设置恢复目标并启动。
docker run --rm --volumes-from pitr -u postgres postgres:18 bash -c "cd /var/lib/postgresql/18/docker &&
  echo \"restore_command = 'cp /archive/%f %p'\" >> postgresql.auto.conf &&
  echo \"recovery_target_name = 'before_drop'\" >> postgresql.auto.conf &&
  echo \"recovery_target_action = 'promote'\" >> postgresql.auto.conf && touch recovery.signal"
docker start pitr
# TCP 可连接还不等于已经重放到恢复点并完成提升。
# 只有 pg_is_in_recovery() 为 false，才允许继续做恢复结果查询。
PITR_READY=f
for attempt in $(seq 1 60); do
  PITR_READY=$(docker exec -e PGPASSWORD=pg -e PGCONNECT_TIMEOUT=1 -u postgres pitr psql -h 127.0.0.1 -U postgres -d postgres -Atqc "SELECT NOT pg_is_in_recovery()" 2>/dev/null) || PITR_READY=f
  [ "$PITR_READY" = t ] && break
  sleep 1
done
if [ "$PITR_READY" = t ]; then
  docker logs pitr 2>&1 | tail -4
else
  docker logs pitr 2>&1 | tail -20
  printf '%s\n' '恢复尚未完成或启动失败，请先检查日志，不要继续下一步。' >&2
  false
fi

挑战
制定备份策略
一个 2 TB 的生产库，每天产生约 200 GB WAL。要求：RPO ≤ 1 分钟（对误删等逻辑错误）、恢复时间 ≤ 2 小时、保留 30 天内任意时间点。用 pgBackRest 给出备份类型和频率、归档配置、存储位置，并估算恢复耗时的组成。
查看参考答案
  • 归档：archive_command = 'pgbackrest --stanza=main archive-push %p'，开启异步归档（archive-async=y）和压缩（zstd）。archive_timeout = 30s 可为切段预留约半分钟预算，但切段不代表 WAL 已上传并持久化，异步归档也不保证完成时限。这里的 RPO ≤ 1 分钟是需要实测的目标：前提是基础备份与连续 WAL 链完整、异地仓库可用，且最旧未持久化 WAL 的年龄始终不超过 60 秒。监控 pg_stat_archiver 的失败/成功变化、待归档队列、pgBackRest 日志和仓库实际到达位置，接近时限就告警并处理积压。网络、仓库故障或归档积压会突破这个目标；若要求在这些故障下也有严格的 1 分钟上限，必须另行设计具备明确故障边界的同步持久化机制。用 pgBackRest 的仓库（S3 等对象存储，另一个区域，开启对象锁定/版本，凭据与生产隔离）。
  • 备份：每周日全量；其他每天差异备份（相对上一次全量）；可选每 6 小时增量。从备库执行（backup-standby=y）减轻主库负担。保留 repo1-retention-full=5（5 周，覆盖 30 天）。
  • 恢复耗时 ≈ 下载并解压最近的全量 + 差异（2 TB，并行 process-max=16，~1 GB/s 时约 35 分钟；--delta 在已有数据目录上只拉取变化的文件）+ 重放最多 1 天的 WAL（200 GB，重放约 100–200 MB/s，20–30 分钟）+ 检查与切换。用每日差异备份是为了限制需要重放的 WAL 量。
最重要的一条：每周自动恢复一次到临时实例并跑校验，测得的时间才是真实的 RTO。并且保留 pg_dump 作为不依赖物理格式的第二种备份（例如每周一次关键表），防备工具本身的问题。

小结
记住这几点


  1. 逻辑备份 pg_dump：导出 SQL 或自定义格式（-Fc/-Fd 可以并行恢复、选择性恢复单张表），跨版本可用；但只是某一时刻的快照，大库导出和恢复都很慢（要重建索引），不能做时间点恢复。pg_dumpall --globals-only 备份角色和表空间。
  2. 物理备份：复制数据目录（pg_basebackup 或 pgBackRest、Barman、WAL-G）。备份期间数据库照常写入，所以文件本身不一致，必须配合备份期间及之后的 WAL 才能恢复到一致状态。
  3. WAL 归档：archive_mode = on 加 archive_command（或 archive_library），每个写满的 WAL 段都被复制到安全的地方（对象存储）。archive_timeout 限制低流量下等待切段的时间；端到端 RPO 还取决于归档积压、传输及目标存储持久化的延迟。
  4. PITR：恢复一个基础备份，设置 restore_command 从归档取 WAL，recovery_target_time = '2026-10-22 14:29:00+08'（或 target_xid / target_lsn / target_name），创建 recovery.signal 启动，数据库重放到目标点后停下。recovery_target_action = pause 让你先检查再提升。
  5. PostgreSQL 17 起 pg_basebackup --incremental 支持增量备份（配合 summarize_wal 和 pg_combinebackup）。pgBackRest 提供全量/差异/增量备份、并行、压缩、加密、校验和保留策略，是生产中最常见的选择。
  6. 没有演练过恢复的备份不算备份。定期（自动化）把备份恢复到一台临时机器、跑校验查询、记录恢复耗时——它就是你真实的 RTO。备份要异地、并且与生产凭据隔离，防止被同一次事故（或攻击者）一起删除。
