分区表

一张表到了几亿行、几百 GB 时，维护（VACUUM、建索引、删除旧数据）会越来越痛苦。分区把一张逻辑表拆成多张物理表，查询只访问相关的分区，过期数据可以整块删除。本课讲声明式分区的三种方式、分区裁剪、分区上的索引和约束、ATTACH / DETACH，以及什么时候不该分区。约 60 分钟。

挑战
把一张大表在线改成分区表
现有 events 表 6 亿行、未分区，持续写入。要改为按月分区，不能停机。描述可行的迁移步骤。
查看参考答案
PostgreSQL 不能把现有表直接转换为分区表，但可以把它整个挂成一个分区：
BEGIN;
SET lock_timeout = '3s';
ALTER TABLE events RENAME TO events_legacy;
CREATE TABLE events (LIKE events_legacy INCLUDING DEFAULTS INCLUDING CONSTRAINTS)
  PARTITION BY RANGE (created_at);
-- 事先在 events_legacy 上加好 CHECK (created_at < '2026-11-01') NOT VALID，再 VALIDATE（不阻塞写入）
ALTER TABLE events ATTACH PARTITION events_legacy FOR VALUES FROM (MINVALUE) TO ('2026-11-01');
CREATE TABLE events_2026_11 PARTITION OF events FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
COMMIT;
预先存在的 CHECK 约束证明了所有行都在范围内，ATTACH 不需要再扫描 6 亿行，整个事务只需要短暂的排他锁。新数据从此写进按月的新分区。旧数据留在 legacy 分区里，随着时间推移，可以按月从 legacy 中搬出（INSERT 到新的月份分区再从 legacy 删除，分批进行），或者干脆等它整体过期后一次 DETACH + DROP。注意：主键必须包含 created_at；序列/identity 列、外键引用、视图依赖都要事先处理；应用中引用表名的地方不变。也可以用逻辑复制或触发器双写同步到一张新的分区表再切换，适合需要同时重新组织旧数据的情况。

小结
记住这几点


  1. 声明式分区：CREATE TABLE events (…) PARTITION BY RANGE (created_at)，再为每个范围建分区 CREATE TABLE events_2026_10 PARTITION OF events FOR VALUES FROM ('2026-10-01') TO ('2026-11-01')。父表本身不存数据。还有 LIST（按地区、租户）和 HASH（均匀打散）。
  2. 分区裁剪：WHERE 中有分区键的条件时，规划阶段（常量）或执行阶段（参数、子查询结果）跳过不相关的分区。查询不带分区键时要扫描所有分区，比不分区还慢。
  3. 在父表上建索引会自动在每个分区上建；主键和唯一约束必须包含分区键，因为唯一性只能在每个分区内部检查。所以按时间分区时，主键往往是 (id, created_at)。
  4. 删除旧数据：ALTER TABLE events DETACH PARTITION events_2025_01 CONCURRENTLY 后 DROP，瞬间完成，没有死元组也没有 VACUUM 压力。加载数据：先建好独立的表、导入并建索引，再 ATTACH PARTITION（预先加一个匹配的 CHECK 约束可以避免扫描验证）。
  5. 设一个 DEFAULT 分区接收不匹配任何范围的行，但要监控它：它有数据时，新建与之重叠的分区需要扫描它。新分区要提前创建，通常用 pg_partman 或定时任务。
  6. 不要过早分区：几千万行、索引得当的表通常不需要。分区数量保持在几百以内；太多分区会让规划时间和锁开销上升。分区键应该是绝大多数查询都会带上的列。
