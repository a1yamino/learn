挑战
审查一个不安全的配置
某服务的现状：应用用 postgres 超级用户连接；pg_hba.conf 有一行 host all all 0.0.0.0/0 md5；数据库端口对公网开放；连接串明文写在仓库的 config.yaml 中；多租户靠应用代码里每条 SQL 加 WHERE tenant_id = ?。按优先级列出风险和修复。
查看参考答案
  1. 端口对公网开放 + 0.0.0.0/0：任何人都能尝试暴力破解，md5 哈希泄露后可直接用于登录。放进私有网络/安全组，只允许应用子网；pg_hba 改为 hostssl shop api 10.0.0.0/16 scram-sha-256，删除宽泛规则；password_encryption = scram-sha-256 后重设所有密码。
  2. 超级用户连接：一次 SQL 注入就等于整台服务器（COPY … TO PROGRAM 可以执行系统命令）。建立 app_owner / app_rw / api 结构，应用只用 api；迁移用单独的凭据。
  3. 密码在仓库里：视为已泄露，立即轮换；改为从密钥管理服务或环境变量注入，扫描 git 历史。
  4. 租户隔离只靠应用：漏写一个 WHERE 就会跨租户泄露数据。在多租户表上启用 RLS 作为第二道防线，应用在每个事务开头 SET LOCAL app.tenant_id；注意 api 角色不能是表的所有者，也不能有 BYPASSRLS。
  5. 开启 TLS（ssl = on，客户端 sslmode=verify-full），并用 pgaudit 记录 DDL 和权限变更。

小结
记住这几点


  1. 角色统一了用户和组：有 LOGIN 的角色可以登录，角色可以被授予给其他角色以继承权限。超级用户绕过所有权限检查，应用永远不要用它连接。
  2. 权限分层：先要有数据库的 CONNECT、schema 的 USAGE，才谈得上表的 SELECT/INSERT/UPDATE/DELETE、序列的 USAGE。PostgreSQL 15 起普通用户默认不能在 public schema 中建表。ALTER DEFAULT PRIVILEGES 让之后新建的对象自动授权。
  3. 推荐结构：app_owner（NOLOGIN，拥有所有对象，迁移时 SET ROLE 使用）、app_rw（读写）、app_ro（只读，报表与排查）。应用以继承了 app_rw 的 LOGIN 角色连接，因此不能 DROP 或 ALTER 表。PostgreSQL 14+ 有预定义角色 pg_read_all_data、pg_write_all_data，16+ 有 pg_maintain（18 可用）等。
  4. pg_hba.conf 按顺序匹配“连接类型 + 数据库 + 用户 + 来源地址 → 认证方式”。使用 scram-sha-256（md5 已弃用，18 中会给出警告），只对需要的网段开放，远程连接用 hostssl 强制 TLS，客户端用 sslmode=verify-full 校验证书。
  5. 行级安全：ALTER TABLE … ENABLE ROW LEVEL SECURITY 后，除所有者和 BYPASSRLS 角色外，每条查询都自动加上策略的条件。CREATE POLICY tenant ON orders USING (tenant_id = current_setting('app.tenant_id')::int)；所有者也要受限时加 FORCE ROW LEVEL SECURITY。
  6. 其他要点：SECURITY DEFINER 函数必须 SET search_path 防止被劫持；定期 REVOKE 不再需要的权限；用 pgaudit 记录敏感操作；备份和日志中同样有敏感数据；密码不要写进连接串提交到代码库，使用密钥管理或 .pgpass。
