限流、排行榜与计数器

令牌桶（容量 5，每秒 1 个）。
EVAL "local t=redis.call('TIME') local now=t[1]+t[2]/1e6 local b=redis.call('HMGET',KEYS[1],'tk','ts') local tk=tonumber(b[1]) or 5 local ts=tonumber(b[2]) or now tk=math.min(5,tk+(now-ts)*1) local ok=0 if tk>=1 then tk=tk-1 ok=1 end redis.call('HSET',KEYS[1],'tk',tk,'ts',now) redis.call('EXPIRE',KEYS[1],60) return ok" 1 tb:u42

挑战
设计一个游戏排行榜
一款游戏有 3000 万玩家，需要：① 全服实时总榜，显示前 100 名和“我的名次”；② 同分时先达到该分数的排前面；③ 每周一 00:00 清空周榜，保存上周前 100 名；④ 每秒约 2 万次加分。写出键设计、分数编码、主要命令，以及大 key 和热点的考虑。
查看参考答案
  • 分数编码：enc = score × 2^21 + (2^21 − 1 − 秒级偏移)，其中偏移为距本周开始的秒数（一周 604800 < 2^21）；只要 score < 2^32，编码值 < 2^53，double 可精确表示。读取时 score = floor(enc / 2^21)。
  • 周榜：rank:week:2026w43，加分用 Lua：读旧分数、算新编码、ZADD（需要先读出旧值，因为编码中的时间部分要更新为当前时间）。
  • 查询：前 100 名 ZREVRANGE … 0 99 WITHSCORES；我的名次 ZREVRANK + 1，都是 O(log N)。
  • 换周：键名带周号，新周自然使用新键；周一 00:05 由任务读取上周前 100 名写入数据库，旧键 EXPIRE 7 天 后由 UNLINK/过期释放，不需要“清空”。
  • 规模：3000 万成员约 3 GB 的单个 ZSET，在 Cluster 中只能在一个分片上；2 万次/秒的写入对单个分片可承受。如果担心，可按 uid % 16 拆成 16 个子榜（分散到不同分片），前 100 名取每个子榜的前 100 后合并；“我的名次”需要对 16 个子榜分别 ZCOUNT 比我高的数量求和。

小结
记住这几点


  1. 固定窗口：INCR rl:<uid>:<分钟>，第一次时 EXPIRE 60，超过上限拒绝。简单省内存，但窗口边界前后各一次突发可以在 2 秒内通过 2 倍流量。INCR 与 EXPIRE 要放进同一个脚本或 MULTI，否则可能留下没有 TTL 的键。
  2. 滑动窗口日志：有序集合中每个请求一个成员（分数为时间戳），ZREMRANGEBYSCORE 删掉窗口外的，ZCARD 计数。精确，但每个请求占用一个成员，适合限额小的场景（如每分钟 10 次登录）。滑动窗口计数用当前窗口和上一窗口的计数加权估算，内存小。
  3. 令牌桶：哈希保存 tokens 和 ts，每次请求在 Lua 中按经过的时间补充令牌（不超过容量），够就扣减。允许一定突发、平均速率受限，是 API 网关最常用的算法。所有逻辑必须在一个脚本里原子执行；时间可以用 redis.call("TIME") 避免各应用服务器时钟不一致。
  4. 排行榜：ZINCRBY rank 10 u42，ZREVRANGE rank 0 9 WITHSCORES 取前十，ZREVRANK 查名次，都是 O(log N)。同分时按成员字典序排序；要“先达到的排前面”，把分数编码为 score × 10^10 + (MAX_TS − ts)（注意 double 只有 53 位精确整数）。
  5. 超大榜单只需要前 N 名时，可以定期 ZREMRANGEBYRANK rank 0 -10001 只保留前一万；需要每个人的精确名次时保留全部，并考虑按时间（日榜、周榜用 ZUNIONSTORE 合并）或分片拆分。
  6. 计数器：INCR/HINCRBY 是原子的。极高频的计数（阅读数、点赞）可以在应用内存中聚合几百毫秒再 INCRBY，减少写入；定期把 Redis 中的计数批量写回数据库，Redis 宕机时以数据库为基准恢复，接受少量误差。
