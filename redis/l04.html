数据结构编码：SDS、listpack、intset 与 quicklist

同一种类型在内部可以有不同的实现。小集合用紧凑的连续内存，元素变多或变大时自动转换为指针结构。本课讲 redisObject、字符串的三种编码与 SDS、listpack 的布局、intset、quicklist，以及控制转换阈值的配置项——这是理解 Redis 内存占用的基础。约 60 分钟。

挑战
用小 Hash 存 1000 万个用户的积分
需要存 1000 万个 user_id → 积分（整数）的映射。方案 A：每个用户一个 String 键 score:{uid}；方案 B：按 uid 分桶 score:{uid / 100}，每个桶一个 Hash，字段为 uid % 100。估算两者的内存差异并解释原因，说明方案 B 的代价。
查看参考答案
方案 A：每个键都是全局字典中的一个条目（dictEntry 约 24 字节 + 键的 SDS 约 20 字节 + redisObject 16 字节 + 分配器对齐），值是 int 编码。实测大约每个键 60–70 字节，1000 万个约 650 MB。
方案 B：10 万个 Hash，每个 100 个字段，低于 Hash 默认 512 的阈值，都是 listpack：每个字段只需几个字节（字段名 “37” 和值 “1520” 紧凑存放），每个桶约 600–800 字节。总计约 70–80 MB，节省近 90%。
HSET score:123456 78 1520      # uid = 12345678
HINCRBY score:123456 78 10
代价：桶内查找是 O(N)，但 N ≤ 100，实际只有几百纳秒；不能对单个用户设置过期时间（7.4+ 的 HEXPIRE 可以，但带过期的字段会使用额外的编码和内存）；一定要保证每个桶的字段数不超过阈值，否则会整体转为 hashtable，节省就没了。可以用 MEMORY USAGE 抽样验证。

小结
记住这几点


  1. 每个值是一个 redisObject：类型（type）、编码（encoding）、LRU/LFU 信息、引用计数和指向数据的指针，约 16 字节。OBJECT ENCODING key 查看编码。
  2. String 有三种编码：int（可表示为 64 位整数的值，直接存在指针位置）；embstr（≤ 44 字节，对象头和字符串一次分配、连续存放）；raw（更长，分开分配）。字符串本身用 SDS：记录长度和剩余容量，O(1) 取长度、二进制安全、追加时预分配空间。
  3. listpack（Redis 7 起取代 ziplist）：一整块连续内存，元素依次紧凑存放，每个元素记录自身长度以便双向遍历。没有指针开销，缓存友好；但查找是 O(N)，插入删除要移动内存。适合元素少且小的 Hash、ZSet、Set 和 List 节点。
  4. intset：只含整数的小集合，按大小有序存放，二分查找，按最大值选择 16/32/64 位宽度。
  5. quicklist：较长 List 的实现，是由多个 listpack 节点组成的双向链表；Redis 7.2+ 的短列表可以直接使用 listpack，兼顾两端操作 O(1) 和内存紧凑。list-max-listpack-size -2 表示每个节点最大 8 KB。
  6. 转换阈值（默认）：Hash 字段数 ≤ 512、ZSet 成员数 ≤ 128，且字段名/成员和值均不超过 64 字节时用 listpack；Set 全为整数且 ≤ 512 用 intset，否则 ≤ 128 个小元素用 listpack；超出就转为 hashtable / skiplist，而且不会再转回去。把一个大对象拆成多个小 Hash，可以大幅节省内存。
