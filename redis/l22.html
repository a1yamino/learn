安全：ACL、TLS 与危险命令

暴露在网络上、没有密码的 Redis 是常见的入侵入口：攻击者可以读取全部数据，甚至利用 CONFIG SET 写文件获得服务器权限。本课讲网络隔离与保护模式、Redis 6 起的 ACL 用户与权限、TLS 加密、禁用和限制危险命令，以及最小权限的账户设计。约 60 分钟。

挑战
为三个团队设计 ACL
一个 Redis 实例被三个服务共享：订单服务（键前缀 order:，需要读写、Lua 脚本）、推荐服务（只读 product: 和 rec:，写 rec:）、数据看板（只读所有键的统计信息，不能读取数据）。再加一个运维账户。写出 ACL 规则，并说明默认用户如何处理、密码如何下发。
查看参考答案
user default off
user order on #<sha256> ~order:* +@read +@write +@scripting -@dangerous
user rec on #<sha256> %R~product:* ~rec:* +@read +@write -@dangerous
user board on #<sha256> +info +ping +dbsize +slowlog|get +latency|latest +memory|stats
user ops on #<sha256> ~* &* +@all
  • 密码以 SHA-256 写入 aclfile（# 后跟哈希），配置文件中不出现明文；应用从密钥管理服务获取明文密码。
  • %R~product:* 让推荐服务对商品键只读；~rec:* 读写。看板账户没有任何键模式，即使命令允许也读不到数据。
  • 禁用 default 用户，强制所有客户端用自己的账户认证，便于 ACL LOG 和 CLIENT LIST 中区分来源。
  • ops 只从跳板机使用；网络层仅允许三个服务的网段访问。更好的做法是把三个服务拆到不同实例，避免互相影响。

小结
记住这几点


  1. 第一道防线是网络：Redis 只在内网监听（bind 10.0.0.5），用安全组/防火墙只允许应用服务器访问 6379（以及 Cluster 的 16379）；不要映射到公网。protected-mode yes（默认）在没有密码且监听非本地地址时拒绝外部连接。注意 docker run -p 6379:6379 会在所有网卡上开放端口。
  2. 经典攻击：未授权访问后 CONFIG SET dir /root/.ssh + CONFIG SET dbfilename authorized_keys + SAVE 写入公钥；或者 SLAVEOF 恶意主库加载模块执行代码。Redis 7 起 enable-protected-configs 和 enable-module-command 默认为 no，能阻止运行时修改 dir 等敏感配置和加载模块，但前提仍然是不应让人连上。
  3. ACL（Redis 6+）：每个用户有密码、可执行的命令（+@read、-@dangerous、+get）、可访问的键模式（~shop:*，%R~ 只读、%W~ 只写）和 Pub/Sub 频道（&news:*）。default 用户对应旧的 requirepass，应设置密码或禁用（user default off）。
  4. 按用途建账户：应用账户只能访问自己的键前缀和需要的命令类别，不能用 @admin、@dangerous；运维账户全部权限，仅从跳板机使用；监控账户只能执行 INFO、PING、SLOWLOG 等。ACL 写在 aclfile 中，用 ACL SAVE/ACL LOAD 管理；ACL LOG 记录被拒绝的访问。
  5. TLS：tls-port 6379、port 0，配置证书和 CA；复制和集群总线也可以加密（tls-replication yes、tls-cluster yes）。会增加 CPU 开销，可以用 I/O 线程缓解。云托管服务通常提供传输加密开关。
  6. 危险命令：FLUSHALL、FLUSHDB、KEYS、CONFIG、DEBUG、SHUTDOWN、MODULE。用 ACL 对应用账户禁止它们（推荐），而不是旧的 rename-command（它会影响复制和 AOF，而且对所有用户生效）。密码等秘密不要写进代码仓库，通过密钥管理服务或环境注入。
