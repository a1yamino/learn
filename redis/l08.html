挑战
一台缓存实例频繁淘汰热点
商品缓存实例 8 GB，allkeys-lru。每晚 2 点有一个离线任务遍历全部商品写入缓存（大部分是冷门商品）。之后几十分钟里缓存命中率从 98% 降到 70%，数据库压力剧增。解释原因，给出至少两种改进。
查看参考答案
LRU 只看“最近一次访问时间”：离线任务把几百万个冷门商品依次写入，每一个都比白天的热点商品“更新”，于是热点被大量淘汰。早上热点重新回源，命中率要很久才能恢复。
  • 改用 allkeys-lfu：热点商品的访问计数高，批量写入的冷门商品计数很低（新键初始计数为 5，且会衰减），淘汰时优先淘汰它们。
  • 离线任务不要写入在线缓存：它真正需要的通常只是读取数据，或者写入另一个实例。
  • 如果必须预热，只预热访问量排名靠前的商品，并给它们较短的过期时间。
  • 按需扩容：观察 evicted_keys 的增长速度和命中率（keyspace_hits / (hits + misses)），淘汰持续发生说明内存不足以容纳工作集。

小结
记住这几点


  1. used_memory 是分配器（jemalloc）分配出去的字节数：数据集 + 键空间字典开销 + 客户端输入/输出缓冲区 + 复制积压缓冲区 + AOF 缓冲区等。used_memory_rss 是操作系统看到的常驻内存。二者之比为碎片率：明显大于 1.5 表示碎片多（可开启 activedefrag），小于 1 说明发生了 swap。
  2. 单个 Lua 脚本执行期间不会逐条触发淘汰，可能暂时超过上限；实验要从客户端分批写入。一定要设置 maxmemory，并给 fork 时的写时复制、缓冲区和操作系统留出余量（通常为物理内存的 60%–75%）。默认 0 表示不限制，最终会被 OOM killer 杀掉或开始 swap。
  3. 达到 maxmemory 后，每条可能增加内存的写命令执行前都会尝试淘汰。策略 maxmemory-policy：noeviction（默认，写命令报 OOM 错误）；allkeys-lru / allkeys-lfu / allkeys-random（在所有键中选）；volatile-lru / volatile-lfu / volatile-random / volatile-ttl（只在设置了过期时间的键中选）。
  4. 纯缓存用 allkeys-lru 或 allkeys-lfu；Redis 同时存放缓存和不能丢的数据时用 volatile-*，但没有过期时间的键过多时，可淘汰的键不够，仍会 OOM。更好的做法是把两类数据放到不同的实例。
  5. 近似 LRU：每个对象只存 24 位的最近访问时钟；淘汰时随机抽样 maxmemory-samples（默认 5）个键，放入大小为 16 的淘汰池，删除最久未访问的。样本越大越接近真实 LRU，CPU 越高。
  6. LFU：同一个 24 位字段改存 16 位时间 + 8 位对数计数器（最大 255，访问越多增加概率越小，lfu-log-factor），计数随时间衰减（lfu-decay-time 分钟）。LFU 能抵抗一次性批量扫描把热点数据挤出去。
