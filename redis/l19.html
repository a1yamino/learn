热 key 与大 key

Redis 的性能问题很多来自“个别键”：一个被集中访问的热 key 会让单个分片的 CPU 或网卡打满，一个几百 MB 的大 key 会在读取、删除、迁移时阻塞主线程。本课讲如何发现它们、它们分别造成什么问题，以及拆分、本地缓存、读副本、异步删除等处理方法。约 60 分钟。

挑战
处理一个直播间的热 key 和大 key
某直播间同时 200 万人在线：① 直播间信息 live:9527（字符串，2 KB）每秒 50 万次读；② 在线观众集合 live:9527:viewers（SET，200 万成员）用来显示在线人数和随机展示 50 个头像；③ 直播结束后需要清理这些数据。现在 Cluster 有 8 个分片。给出改造方案。
查看参考答案
  1. 直播间信息：应用实例本地缓存 1–2 秒（变化时通过 Pub/Sub 广播失效），绝大多数读不到 Redis；回源时读 live:9527:{n} 中随机一份（n=0..7，分布在不同分片，写入时更新全部 8 份）。
  2. 在线观众：在线人数不需要整个集合：不能用 HyperLogLog 统计“当前在线”（HLL 不能移除离线用户）；可用带心跳超时的有序集合，或用经过连接去重、断线补偿的 INCR/DECR 计数器（按分片拆成 live:9527:cnt:0..15 后求和）；观众集合按 uid % 64 拆为 64 个 SET，每个约 3 万成员；随机头像从随机一个分片 SRANDMEMBER k 50。
  3. 清理：对每个分片键执行 UNLINK，并开启 lazyfree-lazy-user-del yes、lazyfree-lazy-expire yes；也可以直接给这些键设 TTL，结束后自然过期。
  4. 上线前用 --bigkeys/--memkeys 和压测验证，监控各分片 CPU 是否均衡。

小结
记住这几点


  1. 热 key：少数键承受了大部分访问（爆款商品、热门直播间、全局配置）。在 Cluster 中一个键只能在一个分片上，加机器也无法分担它的流量；单个分片可能 CPU 100%、网卡打满，进而影响同分片的其他键。
  2. 发现热 key：redis-cli --hotkeys（要求 LFU 淘汰策略，扫描全库）、MONITOR 抽样（开销大，只能短时间用）、客户端或代理层统计、云厂商的热 key 分析。
  3. 处理热 key：① 进程内本地缓存（短 TTL，如 1–5 秒）挡住绝大部分读；② 复制成 N 份 k:0..k:N-1，读时随机选一个，写时全部更新；③ 读写分离，从副本读；④ 热点写（如计数）在本地聚合后批量 INCRBY。
  4. 大 key：单个字符串几 MB 以上，或集合类型有几十万、上百万个元素。问题：HGETALL、SMEMBERS、LRANGE 0 -1 一次返回大量数据，阻塞主线程并占满带宽；DEL 释放内存可能耗时数百毫秒；Cluster 迁移槽时 MIGRATE 阻塞；内存分布不均。
  5. 发现大 key：redis-cli --bigkeys 或 --memkeys（SCAN 遍历，可在副本上执行），MEMORY USAGE key，离线分析 RDB 文件。
  6. 处理大 key：按字段或 ID 哈希拆分为多个键；用 HSCAN/SSCAN/ZRANGE … LIMIT 分批读取；删除用 UNLINK（后台线程释放），并开启 lazyfree-lazy-user-del、lazyfree-lazy-expire 等；大值压缩或不放在 Redis 中（放对象存储，Redis 只存引用）。
