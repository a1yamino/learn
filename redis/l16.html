挑战
为一个商品详情接口加缓存
接口 GET /products/:id 每秒 2 万次，组装结果需要查 4 张表（约 25 ms）；商品信息每天改动几次，价格改动后 5 秒内必须生效；库存实时变化，单独有接口。写出：缓存哪些内容、键名与值格式、TTL、读路径和写路径的伪代码，以及 Redis 不可用时的行为。
查看参考答案
  • 缓存组装好的商品详情（不含库存和价格）：shop:product:{id}:v1，值为 JSON（压缩可选），TTL 3600 s ± 10% 随机抖动。
  • 读路径：
    v = redis.get(key)            // 设置 50 ms 超时
if v: return decode(v)
v = db.load_product(id)       // 4 张表
redis.set(key, encode(v), ex=3600 + rand(-360, 360))
return v
  • 写路径（价格等变更）：价格属于有明确时效要求的字段，单独从数据库主库读取；详情缓存的删除与 CDC 是尽快失效机制，不能单独保证并发回填、删除失败或复制延迟时 5 秒内更新。其他详情字段在事务提交之后 redis.del(key)，删除失败进入重试队列。
  • 库存和价格不进这个长 TTL 缓存；如价格主库读取压力过大，需要另行设计并验证带版本水位的短期价格缓存，不能直接沿用 1 小时 TTL。
  • Redis 超时或不可用：捕获异常直接读数据库，同时用限流/熔断保护数据库（2 万 QPS × 25 ms 数据库扛不住，需要降级为只返回核心字段或本地缓存的旧值）。

小结
记住这几点


  1. 缓存的收益取决于命中率：平均延迟 ≈ 命中率 × 缓存延迟 + (1 − 命中率) × (缓存延迟 + 数据库延迟)。命中率从 90% 提到 99%，回源到数据库的请求减少 10 倍。读多写少、计算代价高、能容忍短暂旧数据的数据最适合缓存。
  2. Cache-Aside（旁路缓存）：读时先查缓存，未命中再查数据库并写入缓存（带 TTL）；写时先更新数据库，再删除缓存。应用自己控制，最常用；缓存宕机时可以退化为直接读数据库。
  3. Read-Through / Write-Through：应用只和缓存层打交道，由缓存层（库或代理）负责回源和同步写数据库。Write-Behind：先写缓存，异步批量写回数据库，写入快、能合并，但缓存故障会丢数据，适合计数、点赞等可以容忍少量丢失的数据。
  4. 键名：<服务>:<实体>:<id>[:版本]，例如 shop:product:1001:v3；版本号便于修改数据结构时整体切换。值：小对象可以用 JSON 字符串一次读写；字段多、部分更新频繁时用哈希。注意序列化体积，压缩大于几 KB 的值。
  5. TTL：每个缓存键都要有 TTL，作为一致性的最后保障和内存回收手段；在基准值上加随机抖动（如 ±10%）避免同时过期（第 18 课）。给缓存实例设置 maxmemory 和 allkeys-lru 或 allkeys-lfu。
  6. 本地缓存（进程内，如 Caffeine）+ Redis 组成两级缓存，可以挡住极热的键，但多实例之间一致性更难：用较短 TTL，或通过 Pub/Sub 广播失效消息，或使用 Redis 的客户端缓存追踪（CLIENT TRACKING）。
