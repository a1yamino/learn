挑战
排查一次延迟抖动
线上 Redis（24 GB 数据，开启 AOF everysec 和每小时 RDB，运行在云虚拟机上）每隔约一小时出现 P99 从 1 ms 升到 300 ms、持续几秒的抖动，其余时间正常。SLOWLOG 里没有超过 10 ms 的命令。写出你的排查步骤、最可能的原因和修复方法。
查看参考答案
  1. SLOWLOG 没有慢命令，说明不是某条命令执行慢，而是主线程被别的事情阻塞或请求在排队。周期约一小时，与 RDB 的 save 3600 … 吻合。
  2. 验证：INFO stats 中 latest_fork_usec（24 GB 在虚拟机上 fork 可能数百毫秒）；LATENCY LATEST 中的 fork、aof-fsync-always/aof-write-pending-fsync 事件；同时检查透明大页是否开启、rdb_last_cow_size 是否很大、是否发生 swap（/proc/<pid>/smaps 中的 Swap）。RDB 写盘时磁盘繁忙也会让 AOF 的 fsync 变慢，主线程在 write 时被阻塞（aof_delayed_fsync 增长）。
  3. 修复：关闭透明大页；在主库上关闭 RDB（AOF 已足够，或只在副本上生成 RDB 备份）；设置 no-appendfsync-on-rewrite yes 减少重写期间的 fsync 阻塞（接受此期间稍大的丢失窗口）；使用更好的磁盘；将实例拆小（多个分片，每个几 GB），降低单次 fork 的代价。
  4. 修复后对比 latest_fork_usec 和 P99 监控确认。

小结
记住这几点


  1. 核心指标：instantaneous_ops_per_sec、命中率（keyspace_hits/misses）、connected_clients 与 rejected_connections、used_memory 与 maxmemory 的比例、evicted_keys、mem_fragmentation_ratio、复制延迟、latest_fork_usec、主线程 CPU。用 redis_exporter + Prometheus 采集并设告警。
  2. 延迟排查顺序：先确认是网络还是服务端（redis-cli --latency 在本机和应用服务器上分别测；--intrinsic-latency 测宿主机本身的调度延迟）；再看服务端：SLOWLOG GET 找执行慢的命令，LATENCY LATEST/LATENCY DOCTOR 看 fork、AOF fsync、过期、淘汰等事件。
  3. SLOWLOG 只记录命令执行时间（不含排队和网络），超过 slowlog-log-slower-than（默认 10000 微秒，建议 1000）记录。单线程意味着一条慢命令会让所有排队的请求都变慢，所以客户端看到的延迟常常比 SLOWLOG 高得多。
  4. 常见原因：O(N) 命令（KEYS、HGETALL 大 key、SMEMBERS、SORT、大范围 ZRANGE）；大 key 的 DEL；大量键同时过期；fork（内存越大越慢，虚拟机上更慢）；AOF fsync 被磁盘阻塞；swap；CPU 被其他进程抢占；客户端连接数暴涨或输出缓冲区过大。
  5. 内存分析：INFO memory 看 used_memory、dataset/overhead、碎片率；MEMORY DOCTOR 给出建议；--bigkeys/--memkeys 找大户；CLIENT LIST 中 omem 看输出缓冲区占用。碎片率高时开启 activedefrag yes。
  6. 操作系统：关闭透明大页（echo never > /sys/kernel/mm/transparent_hugepage/enabled，否则 fork 后写时复制以 2 MB 为单位，延迟和内存都会飙升）；vm.overcommit_memory = 1（避免 fork 失败）；避免 swap（vm.swappiness 调低并留足内存）；net.core.somaxconn 不小于 tcp-backlog。
