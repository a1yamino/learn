分布式锁

多个服务实例需要互斥地做一件事时，常用 Redis 实现分布式锁。本课从 SET NX EX 开始，逐步补上锁的各种缺陷：防止误删别人的锁、业务没做完锁就过期（续期）、主从切换导致锁丢失，并讨论 Redlock 的争议、fencing token，以及什么时候不该用 Redis 锁。约 65 分钟。

挑战
判断哪些场景可以用 Redis 锁
对下面四个需求，判断能否只用 Redis 锁（SET NX PX + 比较删除 + 续期），不能的话给出方案：① 每天凌晨的报表任务在 10 个实例上只运行一次；② 用户提现时防止同一用户并发提交两笔导致超额；③ 缓存重建时只让一个请求回源；④ 多个工作进程修改对象存储中同一个文件，同时写会损坏文件。
查看参考答案
  1. 可以。偶尔两个实例都执行只是重复计算；报表写入最好按日期幂等（覆盖同一份结果）。
  2. 不能只靠 Redis 锁。可以用它挡住绝大多数并发提交，但正确性必须由数据库保证：在事务中 SELECT … FOR UPDATE 锁定账户行并检查余额，或用 UPDATE … SET balance = balance - x WHERE id = ? AND balance >= x 判断影响行数；提现请求带幂等号并有唯一约束。
  3. 可以。失败的代价只是多一次回源（第 18 课）。
  4. 不能只靠 Redis 锁。GC 停顿或网络延迟时，锁过期后的旧持有者仍会写入。需要 fencing：由具备共识和持久化保证的锁服务在授予锁时生成单调 token，存储原子校验并记录最高 token。普通 Redis 的异步故障切换可能让 INCR 回退，不能据此保证正确性。写入时使用存储的条件写（如对象存储的 If-Match/版本号，或在元数据中记录最大 token，小于它的写入被拒绝）；或改用 etcd/ZooKeeper 的租约加 revision。

小结
记住这几点


  1. 加锁：SET lock:order:42 <唯一值> NX PX 30000。NX 保证互斥，过期时间保证持有者崩溃后锁能释放。不要用 SETNX + EXPIRE 两条命令：中间崩溃会留下永不过期的锁。
  2. 解锁：只能删除自己的锁。值用唯一 ID（UUID + 线程 ID），解锁用 Lua 原子地“比较再删除”：if redis.call("GET",KEYS[1])==ARGV[1] then return redis.call("DEL",KEYS[1]) end return 0。直接 DEL 可能删掉锁过期后别人拿到的锁。
  3. 续期：业务耗时可能超过过期时间。持有者启动一个“看门狗”定时任务（如每 10 秒）把 TTL 延长到 30 秒（同样用 Lua 校验值），业务完成或进程退出后停止。Redisson 等客户端库已实现；进程卡顿（GC 停顿）时看门狗也会卡住，锁仍可能过期。
  4. 主从切换丢锁：锁写在主库后、复制到副本前主库宕机，副本被提升后锁不存在，另一个客户端也能加锁。Redlock 在 N 个（通常 5 个）独立主库上加锁，多数成功且总耗时小于有效期才算成功；但它依赖时钟和进程停顿的假设，Martin Kleppmann 等人认为它不足以保证正确性。
  5. 对正确性有要求时（同时两个持有者会造成数据错误），锁必须配合 fencing token：每次获得锁时同时得到一个单调递增的号码；令牌授予要与锁所有权绑定，令牌序列跨故障不能回退。单独在 SET 成功后再执行 INCR 不满足绑定要求；可以用一个 Lua 脚本原子地执行 SET NX 和 INCR，让授锁和发号同时完成，但普通 Redis 的异步故障切换仍可能让号码回退，跨故障单调需要持久化或共识服务。写存储时带上号码，存储拒绝比已见过的更小的号码；也可以直接用数据库的行锁/唯一约束/乐观锁版本号，或使用 etcd/ZooKeeper 这类基于共识的协调服务。
  6. Redis 锁适合效率场景：避免重复计算、避免同一定时任务在多个实例上同时运行，偶尔两个实例同时执行只是浪费资源。还要考虑：可重入（哈希记录持有者和次数）、等待锁时用退避重试或 Pub/Sub 通知而不是忙等、锁的粒度要小。
