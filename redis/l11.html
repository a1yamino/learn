发布订阅与 Stream

Redis 可以在服务之间传递消息。本课比较两种方式：即发即弃的 Pub/Sub（包括 Redis 7 的分片 Pub/Sub），以及可持久化、可回放、支持消费者组和确认机制的 Stream，并讲清楚 List 做队列的局限、Stream 的 ID、PEL 与消息认领。约 60 分钟。

挑战
设计订单事件的可靠消费
订单服务每秒写入约 2000 条“已支付”事件，积分服务和通知服务都要各自处理全部事件；处理可能失败，进程可能被重启。用 Stream 设计：键与裁剪、消费者组划分、确认与重试、死信处理、如何保证积分不重复发放。
查看参考答案
  1. 一个 Stream events:order:paid，XADD … MAXLEN ~ 5000000（约 40 分钟），超出部分以数据库为准。
  2. 两个消费者组 points 和 notify：每个组独立获得全部消息；组内多个实例（消费者名用实例 ID）分摊。
  3. 每个实例循环 XREADGROUP GROUP points <id> COUNT 100 BLOCK 2000 STREAMS … >，处理成功后 XACK。启动时先读 ID 为 0 的自己的待处理消息（重启前没确认的）。
  4. 后台任务每 30 秒 XAUTOCLAIM … 60000 认领空闲超过 60 秒的消息；XPENDING 返回的投递次数超过 5 次的写入 events:order:paid:dead 并 XACK，告警人工处理。
  5. “至少一次”意味着可能重复：积分发放以订单号做幂等，如数据库唯一约束 (order_id, type)，或 SET points:done:<order> 1 NX EX 86400 成功才发放。

小结
记住这几点


  1. Pub/Sub：PUBLISH 把消息推给此刻在线的订阅者，不存储。订阅者断线期间的消息永久丢失；订阅者处理太慢，输出缓冲区超过 client-output-buffer-limit pubsub 32mb 8mb 60 会被断开。适合实时通知、缓存失效广播这类可以丢的场景。
  2. Cluster 中普通 PUBLISH 会广播到所有节点；Redis 7 的 SPUBLISH/SSUBSCRIBE（分片 Pub/Sub）按频道名的槽只发到对应分片，能水平扩展。
  3. List 做队列：LPUSH + BRPOP 简单，但消息被取走后消费者崩溃就丢了；LMOVE 移到“处理中”列表可以补救，但没有多消费者组、没有回放。
  4. Stream 是只追加的日志。XADD 返回形如 1761104210123-0（毫秒时间-序号）的 ID，严格递增。XRANGE 按 ID 范围读，XREAD BLOCK 阻塞等待新消息；MAXLEN ~ 100000 近似裁剪长度。
  5. 消费者组：XGROUP CREATE 建组，XREADGROUP … > 让组内多个消费者分摊消息；每条被读出的消息进入该消费者的 PEL（待确认列表），处理完 XACK。消费者崩溃后，其他消费者用 XPENDING 发现超时消息并用 XAUTOCLAIM 认领重试。这提供的是“至少一次”投递，所以处理逻辑要幂等。
  6. 规模更大、需要长期保留或跨数据中心的消息流仍应选 Kafka 等专门系统；Stream 适合已经有 Redis、消息量中等、保留时间短的场景。
