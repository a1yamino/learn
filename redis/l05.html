哈希表与渐进式 rehash、有序集合与跳表

挑战
分页读取一个大排行榜
排行榜 ZSet 有 500 万成员，前端要按名次分页，每页 50 条，用户经常跳到第 2 万页附近。ZRANGE rank 1000000 1000049 REV 的复杂度是多少？还有什么需要注意的？如果要“从我的名次附近开始显示”，怎么写？
查看参考答案
ZRANGE 按下标取范围的复杂度是 O(log N + M)：借助每层的跨度信息，跳表可以在 O(log N) 内定位到第 100 万名，再顺序取 M = 50 个。所以深分页在 Redis 的 ZSet 里依然很快（和数据库 OFFSET 不同），不需要特殊处理。
ZREVRANK rank u42          → (integer) 812345
ZRANGE rank 812320 812370 REV WITHSCORES
注意：两条命令之间排名可能变化，对展示通常无妨；需要一致时可以用 Lua 把两步放在一起执行。分数相同的成员按成员名的字典序排列，排名会因此看起来“不公平”，常见做法是把时间编码进分数（例如 分数 × 1010 + (最大时间戳 − 达成时间)），让先达到的排在前面。不要用 ZRANGE 0 -1 取全部。

小结
记住这几点


  1. 字典 = 桶数组 + 链地址法解决冲突。键经过哈希函数（SipHash）定位到桶。负载因子 = 元素数 / 桶数；达到 1 时扩容为 ≥ 2 倍的 2 的幂（正在 fork 子进程做持久化时放宽到 4，避免写时复制产生大量内存拷贝），低于 1/8 时缩容。
  2. 扩容时一次性迁移几百万个元素会阻塞主线程几百毫秒，所以 Redis 采用渐进式 rehash：同时持有新旧两张表，之后每次对该字典的增删查改顺带迁移一个桶，空闲时 serverCron 也每毫秒迁移一批。期间查找要查两张表，新元素只写入新表。
  3. SCAN 用游标遍历桶，游标按“反向二进制位”递增。这样无论表在两次 SCAN 之间扩容还是缩容，所有在遍历全程都存在的元素至少返回一次（可能重复，应用要能去重）。COUNT 只是提示，每次返回的数量不固定。
  4. Sorted Set（大于阈值时）= 跳表 + 字典：字典负责成员 → 分数的 O(1) 查找（ZSCORE）；跳表按（分数, 成员）有序，负责范围查询和排名，平均 O(log N)。
  5. 跳表是多层有序链表：每个节点随机获得层数（每层概率 1/4，最多 32 层），高层是低层的“快速通道”。查找从最高层开始向右走，走不动就下降一层。每层记录跨度（span），因此 ZRANK 也是 O(log N)。
  6. 为什么不用平衡树：跳表实现简单，范围遍历只需在最底层链表上顺序前进，插入只修改局部指针、不需要旋转。
