过期：惰性删除与定期删除

缓存几乎都带过期时间，但一个键过期后并不会在那一刻被删除。本课讲过期时间存在哪里、Redis 如何组合“访问时检查”和“后台抽样清理”两种策略、为什么过期的键仍可能占着内存、哪些命令会悄悄清除过期时间，以及过期在复制和持久化中的处理方式。约 50 分钟。

挑战
排查“设了过期时间却永不过期”
一个服务把用户的会话存成 SET session:{id} {json} EX 1800，每次请求时更新会话中的最后访问时间：SET session:{id} {新 json}。运行几周后内存不断增长，INFO keyspace 中 expires 远小于 keys。找出原因并修复，说明如何清理存量。
查看参考答案
更新时的 SET 没有带过期参数，会清除原有的过期时间：用户第一次请求后，会话就变成了永久键。expires 远小于 keys 正是这个症状。
SET session:{id} {新 json} EX 1800        # 滑动过期：每次续期 30 分钟
# 或者只想保留原来的过期时间：
SET session:{id} {新 json} KEEPTTL
# 更好的结构：Hash，只更新一个字段，TTL 不受影响
HSET session:{id} last_seen 1761103900
EXPIRE session:{id} 1800
清理存量：用 SCAN 遍历 session:*，对 TTL 为 -1 的键补设过期时间（例如 EXPIRE key 1800 NX，NX 表示只在没有过期时间时设置），分批执行，避免一次处理太多。之后在监控中加入 keys 与 expires 比例的告警。

小结
记住这几点


  1. 设置了过期时间的键，除了在键空间中，还登记在每个数据库的过期字典（expires）里：键 → 毫秒级的绝对过期时间戳。EXPIRE/PEXPIRE 设置相对时间，EXPIREAT 设置绝对时间；Redis 7 起支持 NX/XX/GT/LT 条件。
  2. 惰性删除：每次访问键之前检查是否已过期，过期则删除并当作不存在。只靠它，从不被访问的过期键会永远占着内存。
  3. 定期删除：serverCron 中的主动过期循环逐步扫描各数据库的过期字典，删除已过期的键；如果某次扫描中过期键比例较高就继续，并限制总耗时（约占 CPU 的 25%，active-expire-effort 可调）。每轮事件循环之前还有一个耗时很短的快速循环。
  4. 所以过期键会在内存中“滞留”一段时间。大量键在同一时刻过期时，主动清理会占用较多 CPU，同时缓存突然集体失效还会压垮数据库——给过期时间加随机抖动（第 18 课）。
  5. 会清除过期时间的操作：SET（未带 KEEPTTL）、GETSET、PERSIST、对整个键重新赋值的命令。INCR、HSET、LPUSH、RENAME（过期时间随键转移）保留原过期时间。TTL 返回 -1 表示没有过期时间，-2 表示键不存在。
  6. 副本不会自己删除过期键，而是等主库删除后通过复制流收到 DEL；但副本上读取逻辑上已过期的键会返回空。AOF 中过期以 PEXPIREAT 绝对时间记录；加载 RDB 时，主库会跳过已过期的键。
