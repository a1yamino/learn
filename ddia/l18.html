弱隔离级别：读已提交与快照隔离

可串行化代价高，所以大多数数据库默认使用更弱的隔离级别——PostgreSQL 默认读已提交，MySQL InnoDB 默认可重复读。弱隔离会导致真实的 bug（甚至造成过资金损失）。本课讲读已提交防止什么（脏读、脏写）以及怎样实现；快照隔离如何用多版本并发控制（MVCC）让每个事务看到一致的快照；以及“丢失更新”这一经典问题的五种防止方法。练习需要开两个 psql 窗口，亲手制造这些异常。约 65 分钟。

01
T1（读已提交）：第一次读取。
BEGIN;
SELECT balance FROM acct WHERE id = 1;
 balance

02
T2：修改并提交。
UPDATE acct SET balance = 400 WHERE id = 1;
UPDATE 1
03
T1：再次读取，看到了新值（不可重复读）。
SELECT balance FROM acct WHERE id = 1;
COMMIT;
 balance
---------
     400
04
T1 改用可重复读（快照隔离）：快照在第一条语句时确定。
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM acct WHERE id = 1;
 balance
---------
     400
05
T2：再次修改并提交。T1 再读，仍然是快照中的值。
-- T2:
UPDATE acct SET balance = 300 WHERE id = 1;
-- T1:
SELECT balance FROM acct WHERE id = 1;
 balance
---------
     400
06
T1 尝试基于旧值写入：PostgreSQL 检测到丢失更新，中止 T1。
UPDATE acct SET balance = balance - 50 WHERE id = 1;
ROLLBACK;
ERROR:  could not serialize access due to concurrent update
07
显式锁：在读已提交下用 FOR UPDATE 串行化“读—改—写”。
-- T1:
BEGIN; SELECT balance FROM acct WHERE id = 1 FOR UPDATE;
-- T2（会阻塞，直到 T1 提交）:
BEGIN; SELECT balance FROM acct WHERE id = 1 FOR UPDATE;
-- T1:
UPDATE acct SET balance = balance - 50 WHERE id = 1; COMMIT;
-- T2 此时返回 250，而不是 300
COMMIT;
（T1）300
（T2 等待……然后）250
挑战
修复一个丢失更新的 bug
代码（读已提交）：
doc = db.query("SELECT data FROM docs WHERE id = %s", id)
doc["likes"] += 1
doc["last_liked_by"] = user
db.execute("UPDATE docs SET data = %s WHERE id = %s", doc, id)
高峰时点赞数明显少于实际点赞次数。请给出三种修复方式并比较。
查看参考答案
  1. 原子操作（首选）：
    UPDATE docs SET data = jsonb_set(jsonb_set(data, '{likes}', to_jsonb((data->>'likes')::int + 1)), '{last_liked_by}', to_jsonb(%s::text)) WHERE id = %s;
    在数据库内部完成读—改—写，持有行锁，没有竞争窗口。更好的做法是把 likes 拆成单独的整数列，SET likes = likes + 1。
  2. 显式锁：在事务中 SELECT data FROM docs WHERE id = %s FOR UPDATE，后续并发请求排队。正确，但热门文档上会形成锁等待，吞吐受限；容易被后来的代码修改遗漏。
  3. 乐观并发（CAS / 版本号）：增加 version 列，UPDATE … SET data = %s, version = version + 1 WHERE id = %s AND version = %s，影响行数为 0 时重新读取再试。无锁，适合冲突少的场景；冲突多时大量重试。也可以把事务改为可重复读，让 PostgreSQL 检测并报错，再重试。
如果点赞量极大，可以把点赞记录为独立的行（或事件），计数作为派生数据异步汇总。

小结
记住这几点


  1. 读已提交保证两点：① 没有脏读——只能读到已提交的数据；② 没有脏写——只能覆盖已提交的数据（并发写同一行时，后者等待前者提交或中止，通常用行锁实现）。防止脏读通常不用读锁，而是为每个被修改的对象保存旧的已提交值，其他事务读旧值。
  2. 读已提交下仍有不可重复读（读偏差）：同一事务中两次读取，中间别人提交了修改，看到的数据不一致。例如：转账进行中你查询两个账户余额，一个是转账前、一个是转账后，总额少了 100。对普通请求来说这只是暂时的，但对备份、分析查询、完整性检查这类长时间读取来说是不可接受的。
  3. 快照隔离：每个事务从开始时起，读取的是数据库在那一刻的一致快照，看不到之后其他事务的提交。实现是 MVCC：每行保存多个版本，每个版本标记创建它的事务 ID（PostgreSQL 的 xmin）和删除它的事务 ID（xmax）；读取时按可见性规则判断：版本由已在快照前提交的事务创建、且没有被快照前提交的事务删除，才可见。原则是读不阻塞写，写不阻塞读。旧版本由垃圾回收清理（PostgreSQL 的 VACUUM）。SQL 标准中的“可重复读”定义含糊，PostgreSQL 的可重复读就是快照隔离。
  4. 丢失更新：两个事务并发执行“读—改—写”（计数器加一、修改 JSON 文档中的一个字段、两个人同时编辑维基页面），后写入的覆盖了前一个的修改。快照隔离本身不一定能防止。
  5. 五种对策：① 原子写操作——UPDATE … SET v = v + 1，数据库内部加锁执行，首选；② 显式加锁——SELECT … FOR UPDATE，应用逻辑太复杂、无法用原子操作表达时使用，容易忘记；③ 自动检测——PostgreSQL 可重复读检测到并发更新同一行时让后者报错（MySQL InnoDB 的可重复读不检测）；④ 比较并设置——UPDATE … WHERE v = 旧值，注意在快照下 WHERE 可能读到旧快照；⑤ 多副本（多主/无主）环境下锁和 CAS 都不适用，只能保留并发值后合并，或使用可交换的原子操作（CRDT，第 13 课），LWW 会丢失更新。
