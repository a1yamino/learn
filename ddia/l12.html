复制延迟带来的问题与对策

异步从节点总会落后主节点一点点——通常不到一秒，但在负载高、网络差或从节点在恢复时，可能落后几分钟。只要应用从从节点读取，就会看到“过去”。本课讲三种典型异常：读不到自己刚写的数据、时间倒流（单调读被破坏）、看到答案却看不到问题（一致前缀被破坏），以及每种异常的对策，包括用 PostgreSQL 的 LSN 实现“读己之写”。约 60 分钟。

挑战
为一个问答社区设计读路由
架构：一个主库、三个异步从库，最大延迟偶尔达到 30 秒。需求：① 用户发帖或回答后，立即在自己的页面和帖子页看到；② 同一用户反复刷新，看到的回答数不能变少；③ 不能出现“先看到回答、后看到问题”。请写出路由规则（伪代码），并说明用户在手机上发帖、在电脑上查看时如何处理。
查看参考答案
write(user, sql):
    lsn = primary.exec(sql + "; SELECT pg_current_wal_lsn()")
    session_store.set(f"lsn:{user}", max(lsn, 已有值), ttl=60s)   # 服务端存储，跨设备有效

read(user, sql):
    need = session_store.get(f"lsn:{user}")        # 可能为空
    seen = session_store.get(f"seen:{user}")       # 单调读：已读到的位置
    floor = max(need, seen)
    r = replicas[hash(user) % 3]                   # 粘性路由：同一用户读同一副本
    if floor and r.replay_lsn() < floor:
        r = first(x for x in replicas if x.replay_lsn() >= floor) or primary
    rows, pos = r.exec(sql), r.replay_lsn()
    session_store.set(f"seen:{user}", max(pos, seen))
    return rows
  1. 读己之写：写入位置保存在服务端（Redis 等），不是设备本地，所以手机发帖后电脑也能读到；也可以简单地“写后 60 秒内读主库”。
  2. 单调读：粘性路由 + 记录已读位置，副本切换时也不会倒退。
  3. 一致前缀：问题和回答在同一个数据库（单一的复制日志）中按提交顺序复制，从节点按顺序重放，天然满足；如果将来按帖子分片，要保证同一帖子的问题与回答在同一分片。

小结
记住这几点


  1. 最终一致性：停止写入并等待足够久，所有从节点最终会与主节点一致。但“最终”没有上限，应用要考虑：延迟增加到几秒、几分钟时，用户会看到什么？如果答案是“会出问题”，就需要比最终一致更强的保证。
  2. 读己之写（read-after-write / read-your-writes）：用户提交了一条评论，刷新后却看不到，因为读请求被发到了落后的从节点。对策：用户自己可能修改的数据（自己的个人资料）从主节点读；写入后的一段时间（如 1 分钟）内从主节点读；客户端记住最近一次写入的日志位置（LSN 或时间戳），读取时只用已经追上该位置的从节点，或者等它追上。跨设备时，这个位置要放在服务端，而不是某台设备的本地。
  3. 单调读：用户刷新两次，第一次请求落到较新的从节点，第二次落到较旧的，数据好像时间倒流。单调读保证不会看到比已经看过的更旧的数据。对策：同一用户总是读同一个副本（按用户 ID 哈希选择副本）；副本故障时需要重新路由，同时带上已读位置。
  4. 一致前缀读：A 提问、B 回答，两条写入在不同分区（第 15 课）中以不同的延迟复制，观察者先看到回答、后看到问题。一致前缀读保证：如果一系列写入按某个顺序发生，读到它们的人也按同样的顺序看到。对策：有因果关系的写入放在同一个分区；或者显式跟踪因果依赖（第 24 课）。
  5. 根本的取舍：在应用层处理这些问题复杂且容易出错。这正是数据库提供更强保证（事务、线性一致性）的价值所在。另一个方向是让应用天然容忍延迟：例如写入后在本地乐观地显示结果。跨区域部署时延迟更大，这些问题会更常见。
