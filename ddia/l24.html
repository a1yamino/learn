class Node:
    def __init__(self, name): self.name, self.c = name, 0
    def local(self, what):
        self.c += 1; print(f"{self.name} {what:<14} 时间戳 ({self.c},{self.name})"); return (self.c, self.name)
    def send(self, what): return self.local("发送 " + what)
    def recv(self, ts, what):
        self.c = max(self.c, ts[0])               # 收到消息时，先追上对方的计数
        return self.local("收到 " + what)

a, b, c = Node("A"), Node("B"), Node("C")
events = []
events.append(a.local("写 x=1"))
m = a.send("m1")
b.local("写 y=1"); b.local("写 y=2"); b.local("写 y=3")
events.append(b.recv(m, "m1"))
events.append(c.local("写 z=1"))
print("全序：", sorted(events))

小结
记住这几点


  1. ID 生成：单机自增 ID 简单且有序；分布式环境下常见做法有 UUID（随机，无序；UUIDv7 带时间前缀）、Snowflake 式 ID（时间戳 + 节点号 + 序号）、按节点预分配 ID 区段。它们都能保证唯一，但顺序不一定与因果一致：时钟偏差会让后发生的事件拿到更小的 ID。
  2. Lamport 时间戳：每个节点维护一个计数器，每个事件加一；发送消息时附带计数，接收方把自己的计数更新为 max(本地, 收到的) 再加一。(计数, 节点 ID) 构成一个全序，且与因果一致：如果 A 发生在 B 之前，A 的时间戳更小。混合逻辑时钟（HLC）把物理时间与逻辑计数结合，既与因果一致又接近真实时间（CockroachDB、YugabyteDB 使用）。版本向量（第 14 课）则能判断两个事件是否并发——Lamport 时间戳做不到。
  3. 逻辑时钟不够用的地方：两个用户同时注册同一个用户名，事后比较时间戳可以决定谁赢——但节点在处理请求时必须立即决定是否成功，它无法知道是否有另一个节点正在处理更小时间戳的请求。要做出这种决定，需要所有节点就顺序达成一致，并且知道这个顺序何时确定。线性一致的 ID 生成器：单节点发号器（或 Spanner 的 TrueTime、TiDB 的时间戳预言机 TSO），通过批量分配提升性能，用复制保证容错——而复制的发号器本身就需要共识。
  4. 共识的多种面孔：① 单值共识——多个节点提议值，所有节点决定同一个值，决定后不再改变；② 比较并设置（线性一致的 CAS）；③ 共享日志（全序广播）——所有节点以相同顺序收到相同的消息；④ 原子提交（第 20 课，要求所有参与者都同意）。它们可以互相归约，是同一个问题的不同形式。FLP 定理指出：在完全异步、可能有节点崩溃的模型中，没有确定性算法能保证共识一定终止——实际算法借助超时（部分同步模型）来绕过。
  5. Raft（etcd、Consul、TiKV、CockroachDB、Kafka KRaft 都使用）：时间被分成编号递增的任期，每个任期至多一个主节点。从节点在超时内没收到主节点的心跳，就成为候选人，任期加一并请求投票；获得多数选票者成为主节点（日志不比投票者新的候选人得不到选票）。主节点把客户端请求追加到日志并复制给从节点，主节点当前任期的条目被多数节点持久化后才可据此判定提交，并连带提交它之前的条目；不能仅凭副本数提交旧任期的条目。两个多数派必然有交集，因此不会有两个任期相同的主节点，已提交的条目不会丢失。代价：每次写入需要多数确认；需要固定的成员（变更成员需要特殊流程）；在网络不稳定时可能频繁选主。Paxos、Zab、Viewstamped Replication 是同一类算法。
  6. 协调服务（ZooKeeper、etcd）：用共识实现的小型、高可用、线性一致的键值存储，数据量很小（全部放在内存），供其他系统使用：线性一致的原子操作（CAS 实现锁）、操作的全序（单调递增的版本号可作 fencing 令牌）、基于会话/租约的故障检测（临时节点）、变更通知（watch）。典型用途：选主、分片分配与服务发现（第 16 课）、分布式锁。应用一般不直接实现共识，而是使用这些服务。
