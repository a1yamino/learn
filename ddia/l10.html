01
保存为 lose.py：旧代码读出再写回，丢掉了新字段。
import json
db = {"u1": json.dumps({"name": "lin", "email": "lin@example.com"})}   # 新版本写入，带 email

class OldUser:                       # 旧版本的模型类：不知道 email
    def __init__(self, d): self.name = d["name"]
    def to_dict(self): return {"name": self.name}

u = OldUser(json.loads(db["u1"]))    # 旧代码读出、改名、写回
u.name = "Lin"
db["u1"] = json.dumps(u.to_dict())
print("旧代码写回后：", db["u1"])

def safe_update(raw, changes):        # 正确做法：保留不认识的字段
    d = json.loads(raw); d.update(changes); return json.dumps(d)
db["u2"] = json.dumps({"name": "wang", "email": "w@example.com"})
db["u2"] = safe_update(db["u2"], {"name": "Wang"})
print("保留未知字段：", db["u2"])
旧代码写回后： {"name": "Lin"}
保留未知字段： {"name": "Wang", "email": "w@example.com"}

03
保存为 wf.py：一个极简的持久化执行引擎。
import json, os
JOURNAL = "journal.json"
journal = json.load(open(JOURNAL)) if os.path.exists(JOURNAL) else {}

def step(name, fn):
    """持久化执行：已完成的步骤直接返回记录的结果，不再执行"""
    if name in journal:
        print(f"  {name}: 重放（{journal[name]}）"); return journal[name]
    result = fn()
    journal[name] = result; json.dump(journal, open(JOURNAL, "w"))
    print(f"  {name}: 执行 → {result}"); return result

def charge():
    return "charge-ok"
def ship():
    if not os.path.exists("crashed"):           # 第一次运行时在这里崩溃
        open("crashed", "w").close(); raise SystemExit("  ship: 进程崩溃！")
    return "shipped"

print("运行工作流：")
step("reserve", lambda: "reserved")
step("charge", charge)
step("ship", ship)
print("完成")

挑战
让一次支付调用可以安全重试
订单服务通过 HTTP 调用支付服务 POST /charges {order_id, amount}，超时 2 秒后重试最多 3 次。线上发现极少数订单被扣款两次。请：① 解释重复扣款是如何发生的；② 设计幂等方案（接口与存储）；③ 说明为什么持久化执行框架也需要这个幂等键。
查看参考答案
  1. 第一次请求在支付服务端已执行（扣款成功），但响应在网络中丢失或超过 2 秒才返回；订单服务认为失败并重试，支付服务把它当作新请求再扣一次。超时只说明“不知道结果”，不说明“失败了”。
  2. 客户端为每个逻辑操作生成一个幂等键（例如 Idempotency-Key: order-1001-charge，或直接用订单号），重试时使用同一个键。支付服务：
    CREATE TABLE charges(idem_key text PRIMARY KEY, order_id bigint, amount_cents bigint, status text, response jsonb);
-- 在同一个事务中：
INSERT INTO charges(idem_key, …) VALUES ($1, …) ON CONFLICT (idem_key) DO NOTHING RETURNING …;
-- 插入成功 → 执行扣款并保存响应；冲突 → 返回已保存的响应
    还要校验同一个键的请求参数一致，键保留足够长的时间。
  3. 持久化执行只保证“步骤完成后不再执行”；如果在调用支付服务之后、记录结果之前崩溃，这一步会被再次执行。所以对外部系统的调用仍需幂等键（通常由框架提供稳定的步骤 ID 作为键）。

小结
记住这几点


  1. 经过数据库：写入数据库就像给未来的自己发消息。滚动升级时，新代码写的数据可能被旧代码读取并写回——如果旧代码把记录解码成只认识部分字段的对象再整体写回，新字段就会丢失。要保留不认识的字段。数据比代码活得久：五年前写入的行仍按当年的格式存放，除非做迁移；添加带默认值的新列通常不需要重写旧数据。归档与导出（转成 Parquet 等）是一次性重新编码的好时机。
  2. 经过服务：客户端与服务端独立部署，通常先升级服务端，所以请求需要向后兼容、响应需要向前兼容。REST 用 HTTP 的语义（URL、方法、状态码、缓存），常配 OpenAPI 描述；gRPC 用 Protobuf 定义接口。API 版本可以放在 URL、请求头中，或按 API 密钥记录版本。
  3. RPC 不是本地调用：网络请求可能丢失、超时（不知道对方是否执行了）、重试可能导致重复执行（需要幂等键）、延迟不可预测、参数要编码、两端可能是不同语言。把远程调用伪装成本地函数会掩盖这些问题——要显式处理它们。服务发现、负载均衡、超时与重试通常由服务网格或客户端库处理。
  4. 持久化执行与工作流（Temporal、Restate 等）：把一个跨多个服务的业务流程写成普通代码，框架把每一步的结果记录到持久日志；进程崩溃后在另一台机器上重新执行代码，已完成的步骤直接返回记录的结果，从中断处继续。要求工作流代码是确定性的（不直接读时钟、随机数，这些也要经由框架记录），并且修改代码时要兼容正在运行的旧工作流。
  5. 事件驱动：发送方把消息交给消息代理（Kafka、RabbitMQ），不需要知道接收方是谁、是否在线。好处：缓冲接收方的不可用与过载、自动重投、一条消息可以发给多个订阅者、发送方与接收方解耦。消息是单向的，需要回复时用另一个通道。Actor 模型把逻辑封装为各自处理消息的 Actor，分布式 Actor 框架（Akka、Orleans）在节点间透明地传递消息，滚动升级时同样要考虑消息格式的兼容。
  6. 四种模式都在后面的课程中展开：复制（第 11 课起）本质是经过日志的数据流，第 26 课讲基于日志的消息代理，第 27 课讲用数据流组织整个应用。
