分布式事务：两阶段提交与精确一次

第 8 章最后一部分。当一个事务涉及多个节点（多个分片，或者数据库加消息队列），如何保证所有节点要么都提交、要么都中止？本课讲两阶段提交（2PC）的流程与“提交点”，协调者故障时参与者为何只能干等（存疑事务），跨异构系统的 XA 事务的问题，数据库内部的分布式事务如何用共识复制协调者来避免阻塞，以及用原子提交实现“精确一次”的消息处理。练习中用 PostgreSQL 的 PREPARE TRANSACTION 亲手扮演协调者。约 65 分钟。

挑战
设计一个跨两个数据库的转账
账户分布在两个 PostgreSQL 分片上（A 库、B 库）。用 PREPARE TRANSACTION 实现跨库转账：① 写出协调者的伪代码，包括它自己需要持久化什么；② 协调者在每一步崩溃后如何恢复；③ 为什么生产环境中更推荐其他方案，有哪些替代方案？
查看参考答案
def transfer(txid, from_db, to_db, amt):
    if amt <= 0: raise ValueError("金额必须为正")
    A, B = from_db, to_db
    log.write(txid, "started")                         # 协调者自己的持久日志
    try:
        A.begin(); B.begin()
        debited = A.exec("UPDATE acct SET balance = balance - %s WHERE id = … AND balance >= %s", amt, amt)
        if debited.rowcount != 1: raise ValueError("付款账户不存在或余额不足")
        credited = B.exec("UPDATE acct SET balance = balance + %s WHERE id = …", amt)
        if credited.rowcount != 1: raise ValueError("收款账户不存在")
        A.exec(f"PREPARE TRANSACTION '{txid}-a'")
        B.exec(f"PREPARE TRANSACTION '{txid}-b'")
    except Exception:
        log.write(txid, "abort"); rollback_all(txid); return False
    log.write(txid, "commit")    # ← 提交点：fsync 之后决定不可更改
    commit_all(txid)             # 对 A、B 执行 COMMIT PREPARED，失败就重试直到成功
    log.write(txid, "done")

def recover():                   # 协调者重启时
    for txid, state in log.unfinished():
        if state == "commit": commit_all(txid)      # 必须提交
        else: rollback_all(txid)                   # started 或 abort：回滚已准备事务及仍存活连接上的普通事务
  1. 2PC 只保证各参与者共同提交或中止，不会自动检查“扣款是否真的发生”。UPDATE 影响 0 行不是 SQL 错误，必须在 PREPARE 前检查两边各更新 1 行；否则余额不足仍可能凭空入账。中止时，对已经 PREPARE 的参与者执行 ROLLBACK PREPARED，对尚未 PREPARE 的连接执行 ROLLBACK。提交与恢复操作还应能识别已完成的参与者，避免把重复 COMMIT PREPARED 的“事务不存在”误当成未提交。崩溃在提交点之前：恢复时中止，各库上可能存在的已准备事务被 ROLLBACK PREPARED。崩溃在提交点之后：恢复时必须重试 COMMIT PREPARED 直到两边都成功。协调者日志丢失 = 存疑事务无人能决定，只能人工处理。
  2. 不推荐：协调者是单点且带持久状态，存疑期间锁住账户；还需要监控 pg_prepared_xacts 中的“孤儿”事务。
  3. 替代方案：① 把同一笔转账涉及的账户放在同一分片（按客户分片）；② 使用内部实现了分布式事务的数据库（CockroachDB、YugabyteDB、Citus 的 2PC 由数据库自身管理）；③ Saga：A 库扣款并通过 outbox 发出事件，B 库幂等入账，失败时发补偿事件退款——放弃原子性的中间状态，换取无阻塞（第 27 课）。

小结
记住这几点


  1. 为什么单节点的提交不够：单节点上，提交是否成功取决于提交记录是否写入了磁盘——一个确定的时刻。多节点时，如果简单地让每个节点各自提交，可能一些节点成功、另一些因违反约束、冲突或崩溃而失败，结果不一致。而提交一旦生效就不能撤回（其他事务已经看到了它）。
  2. 两阶段提交（2PC）：协调者先向所有参与者发送准备请求；参与者把事务的所有写入持久化、检查约束，回答“是”就意味着放弃了中止的权利——无论之后发生什么（包括崩溃重启），只要被要求就必须能提交。协调者收到所有“是”后，把提交决定写入自己的日志——这就是提交点，然后通知所有参与者提交，失败就一直重试。任何一个参与者回答“否”或超时，协调者决定中止。
  3. 协调者故障：参与者投了“是”之后，如果协调者崩溃，参与者既不能自行提交（别人可能投了否），也不能自行中止（协调者可能已决定提交），只能等待协调者恢复——这些存疑事务一直持有锁，相关的行无法被其他事务修改。如果协调者的日志丢失，就需要人工介入。所以 2PC 是一种阻塞的原子提交协议。
  4. 跨异构系统的分布式事务（XA）：数据库和消息队列等不同的技术通过 XA 接口参与 2PC。问题：协调者通常是应用进程中的一个库，应用服务器就成了带持久状态的单点；存疑事务锁住数据；XA 是所有参与者能力的最小公分母，无法检测跨系统的死锁，也与 SSI 不兼容；性能开销大。实际中越来越少用。
  5. 数据库内部的分布式事务（Spanner、CockroachDB、TiDB、YugabyteDB、FoundationDB）：所有参与者是同一个系统的分片，协议可以针对性优化；协调者的状态和每个分片一样，用共识（第 24 课）复制到多个节点，协调者节点故障时其他副本接替，不再永久阻塞。
  6. 再谈精确一次：消息处理要做到“效果上精确一次”，需要把确认消息已处理和处理产生的写入原子地提交——可以用跨系统的分布式事务，但更常见的做法是在同一个系统内完成：Kafka 事务把消费位移和输出消息放在同一个事务中（Kafka 第 11 课）；或者把消费位移和处理结果存到同一个数据库事务中；或者用幂等写入（消息 ID 去重）。第 27 课会从端到端的角度再讨论。
