反规范化：城市名复制在每份文档中，要逐个修改。
INSERT INTO profiles SELECT g, jsonb_build_object('name', '用户'||g, 'city', '上海') FROM generate_series(2,500) g;
UPDATE profiles SET doc = jsonb_set(doc, '{city}', '"沪"') WHERE doc->>'city' = '上海';

小结
记住这几点


  1. 对象—关系不匹配：应用代码里是嵌套的对象，关系库里是扁平的行与表，中间需要 ORM 转换。ORM 减少了样板代码，但也可能产生 N+1 查询等问题。文档模型（JSON）对一棵自包含的树（一份简历、一个订单及其明细）表达更直接：一次读取得到全部内容，局部性好。
  2. 规范化：同一个事实只存一份，其他地方用 ID 引用（例如城市、公司、标签）。好处：改名只改一处，不会不一致；可以本地化显示；方便搜索。代价：读取时要连接。反规范化：把数据复制到需要的地方，读更快，但要负责保持副本一致——反规范化的数据本质上是派生数据。第 2 课的物化时间线就是反规范化。
  3. 关系的形状：一对多（一个订单的多条明细）适合文档嵌套；多对一（很多人住在同一个城市）和多对多（学生与课程）需要引用，文档库要么在应用代码里做连接，要么本身支持连接。实际数据往往从树开始，随着功能增加长出越来越多的交叉引用。
  4. 写时模式与读时模式：关系库在写入时强制模式（schema-on-write），类似静态类型；文档库通常读时才解释结构（schema-on-read），类似动态类型——改结构时不必迁移全部旧数据，但读取代码要处理各种旧格式。两者都需要演进，区别是谁承担成本。
  5. 星型模式：数据仓库中，中间一张巨大的事实表（每行一个事件：一次销售、一次点击），外键指向若干维度表（谁、什么、何时、何地）。维度再细分成子维度就是雪花模式；为了查询简单，分析系统也常把维度直接展开成“宽表”（一个大表，几百列）。
  6. 如何选择：树状、整体读写、结构多变 → 文档；关系多、需要连接、需要强约束 → 关系。今天两者正在融合：PostgreSQL 有 JSONB 和 GIN 索引，文档库也支持连接与模式校验。
