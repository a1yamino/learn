线性一致性

第 10 章开篇。最终一致性下，同时问两个副本可能得到两个不同的答案。线性一致性（也叫原子一致性、强一致性）提供最强的单对象保证：让系统看起来只有一份数据，所有操作都是原子的。本课讲它的精确定义（时间线上的“生效点”）、它与可串行化的区别、哪些场景真正依赖它（选主与锁、唯一性约束、跨通道的时序依赖），哪些复制方式能实现它，以及它的代价：CAP 定理与性能。练习里你会写一个小程序判断一段执行历史是否可线性化。约 65 分钟。

01
保存为 lin.py：暴力枚举顺序，检查一段读写历史是否可线性化。
from itertools import permutations
# 每个操作：(客户端, 类型, 值, 开始时间, 结束时间)；寄存器初始值为 0
def linearizable(history):
    for order in permutations(history):
        # 1) 实时顺序：若 a 结束早于 b 开始，a 必须排在 b 前面
        if any(order.index(a) > order.index(b) for a in history for b in history if a[4] < b[3]):
            continue
        # 2) 按这个顺序执行，每次读都要读到最近一次写入的值
        v, ok = 0, True
        for c, op, val, s, e in order:
            if op == "w": v = val
            elif val != v: ok = False; break
        if ok: return " → ".join(f"{c}:{op}({val})" for c, op, val, s, e in order)
    return None

h1 = [("A", "w", 1, 0, 10), ("B", "r", 1, 5, 6), ("C", "r", 1, 7, 8)]
h2 = [("A", "w", 1, 0, 10), ("B", "r", 1, 2, 3), ("C", "r", 0, 4, 5)]   # B 读到新值之后，C 又读到旧值
for name, h in (("历史 1", h1), ("历史 2", h2)):
    r = linearizable(h)
    print(name, "可线性化：" + r if r else "不可线性化")
历史 1 可线性化：A:w(1) → B:r(1) → C:r(1)
历史 2 不可线性化

03
用 PostgreSQL 主从复现非线性一致：从节点暂停重放后，主节点写入，客户端 B 从主节点读到新值，随后客户端 C 从从节点读到旧值。
docker exec pg2 psql -U postgres -c "SELECT pg_wal_replay_pause();"
docker exec pg1 psql -U postgres -c "CREATE TABLE IF NOT EXISTS reg(id int PRIMARY KEY, v int); INSERT INTO reg VALUES (1, 1) ON CONFLICT (id) DO UPDATE SET v = reg.v + 1 RETURNING v;"
docker exec pg2 psql -U postgres -Atc "SELECT v FROM reg WHERE id = 1;"
（主节点）v = 新值
（从节点）旧值或报错：表尚未复制到从节点
04
恢复重放。若需要线性一致的读，就从主节点读，或在主节点上使用同步复制 remote_apply 并从同步从节点读。
docker exec pg2 psql -U postgres -c "SELECT pg_wal_replay_resume();"
挑战
判断这些需求是否需要线性一致性
对每一项说明是否需要线性一致性，以及推荐的做法：① 用户名注册不能重复；② 社交网络的点赞数显示；③ 秒杀活动中库存不能超卖；④ 用户修改头像后，好友的页面在几秒后显示新头像即可；⑤ 后台任务调度：同一个任务同一时间只能由一个工作节点执行。
查看参考答案
  1. 需要（唯一性约束）：用单主数据库的唯一索引（在主节点上检查），或线性一致的比较并设置。
  2. 不需要：近似计数，最终一致即可，甚至可以用 CRDT 计数器或异步汇总。
  3. 需要（对库存的原子扣减）：在单个主节点上原子地 UPDATE stock SET n = n - 1 WHERE id = … AND n > 0，或 Redis 单实例上的 DECR/Lua；热点商品可以把库存拆成多个分桶，每个桶内线性一致。
  4. 不需要：最终一致 + 缓存过期即可；但上传者本人应满足读己之写（第 12 课）。
  5. 需要（锁/选主）：使用 etcd/ZooKeeper 等基于共识的协调服务获取租约，并在执行副作用时使用 fencing 令牌（第 22 课）。

小结
记住这几点


  1. 定义：每个操作在其开始与结束之间的某个时刻原子地生效（线性化点）。一旦某个读返回了新值，之后开始的所有读（无论哪个客户端）都必须返回新值或更新的值——不能“回到过去”。这是一种新近性保证：读到的总是最新的值。直观地说：系统表现得像只有一个副本。
  2. 与可串行化的区别：可串行化是事务的隔离属性（多对象），保证结果等价于某个串行顺序，但这个顺序不必与真实时间一致；线性一致性是单个对象读写的新近性保证，不涉及事务。两者都满足叫严格可串行化。基于 2PL 或真正串行执行的可串行化通常也是线性一致的；SSI 不是（从快照读）。
  3. 依赖线性一致性的场景：① 选主与锁——所有节点必须就“谁持有锁”达成一致（etcd、ZooKeeper 提供线性一致的写操作）；② 唯一性约束——用户名、文件路径、座位不能重复分配，相当于对一个“锁”的线性一致的比较并设置；③ 跨通道的时序依赖——网站把图片写入存储后，通过消息队列通知缩略图服务；如果存储不是线性一致的，缩略图服务可能读到旧图片——消息队列比存储复制更快，形成竞争。
  4. 实现方式：单主复制——从主节点（或同步更新的从节点）读，有可能线性一致，但前提是确实知道谁是主（脑裂时不成立），异步复制的故障切换会丢失已确认的写入，也违反线性一致性；共识算法——是的（正确实现时），第 24 课；多主复制——不是；无主复制——通常不是：即使 w + r > n，读写并发时也可能违反（除非读时同步执行读修复、写前先读 Quorum，代价很高），LWW 基于时钟更不可能。
  5. CAP 定理：网络分区时，系统要么保持线性一致（某些节点无法服务请求，不可用），要么保持可用（返回可能过时的数据，非线性一致）。不需要线性一致性的应用可以容忍分区。CAP 常被误读为“三选二”——分区不是可以选择的，它总会发生；而且 CAP 只考虑一种一致性和一种故障，实际意义有限。更现实的考量是性能：线性一致的读写的响应时间至少与网络延迟的不确定性成正比，跨区域时尤其慢。很多系统放弃线性一致性不是为了容错，而是为了性能。
