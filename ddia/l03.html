在你的电脑上练习
用 Docker 体会“故障 → 自动恢复”和“人为错误 → 从备份恢复”。需要第 1 课的 pg 容器。


01
保存为 disk.py 并运行。
import random
random.seed(1)
AFR = 0.02          # 每块磁盘年故障率 2%
DISKS = 10000
days = 365
fails = sum(1 for _ in range(DISKS) if random.random() < AFR)
print(f"{DISKS} 块盘一年坏 {fails} 块，平均每天 {fails/days:.2f} 块")
p_day = AFR / days
print(f"单块盘某天坏的概率 {p_day:.2e}")
print(f"3 副本在同一修复窗口内全坏的概率 {p_day**3:.2e}")
10000 块盘一年坏 226 块，平均每天 0.62 块
单块盘某天坏的概率 5.48e-05
3 副本在同一修复窗口内全坏的概率 1.65e-13

挑战
为一个支付系统写可靠性设计
系统：支付 API（无状态，8 台）、PostgreSQL 主库 + 1 个同机房从库、Redis 缓存、每晚全量备份。过去一年的事故：一次机房断电（停机 4 小时）、一次错误配置推送导致全部 API 节点崩溃、一次 DBA 误删表（从昨晚备份恢复，丢失 14 小时数据）。请针对每次事故提出改进，并列出你会主动做的故障演练。
查看参考答案
  1. 机房断电：单机房是单点故障。至少跨两个可用区部署 API 与数据库副本；主库故障时自动或半自动切换（第 11 课）；定期演练切换。
  2. 错误配置：同一个错误同时击中所有节点，是相关性故障。配置也要走代码评审与校验；灰度发布（先 1 台、再 5%、再全量）并自动比较错误率；一键回滚；配置变更要有审计记录。
  3. 误删表：每晚全量备份的 RPO 是 24 小时。加入 WAL 归档实现时间点恢复（PITR，见 PostgreSQL 课程），RPO 降到秒级；生产库权限最小化，危险操作需要两人确认；延迟从库（如延迟 1 小时）可以快速找回误删数据；定期做恢复演练，确认备份真的可用。
  4. 演练清单：随机杀掉一台 API 节点；关闭主库，测量切换时间；断开可用区间网络；把 Redis 清空看数据库能否扛住；磁盘写满；在预发环境从备份做一次完整恢复并计时。

小结
记住这几点


  1. 故障与失效：故障（fault）是某个组件偏离了规格，失效（failure）是整个系统不再向用户提供所需服务。容错的目标是让故障不演变成失效。不可能容忍所有故障（整个地球消失），所以要说清楚容忍哪些故障。单点故障是指一个组件出错就会导致整个系统失效。可以用混沌工程主动注入故障，确认容错机制真的有效。
  2. 硬件故障：大量机器下故障是常态——磁盘年故障率约 1–2%，一万块盘每天都会坏几块；还有内存位翻转、CPU 计算错误、整个机房断电。对策是冗余（RAID、多副本、多可用区），并让软件能容忍整台机器丢失，这样还可以滚动升级。软件故障彼此相关：同一个 bug 会同时击中所有节点（例如闰秒、证书过期、某个输入触发的崩溃），比随机的硬件故障更危险。
  3. 人为错误是线上事故的主要原因之一（配置变更尤甚）。对策不是责怪个人，而是改进系统：好的抽象与默认值、在沙箱或预发环境演练、渐进发布与快速回滚、详细监控（遥测）、无责复盘（blameless postmortem）。
  4. 可扩展性不是一个二元标签，而是“负载增长到某个程度时，系统如何应对”。先用负载参数描述负载（请求率、读写比、数据量、并发用户、分布偏斜），再问：负载翻倍时性能如何变化？要保持性能需要增加多少资源？架构：共享内存（垂直扩展，一台更大的机器），共享磁盘（多台机器共享存储阵列或云存储服务），无共享（水平扩展，每个节点独立，通过网络协调）。
  5. 扩展的原则：把系统拆成可以独立运作的部分；不要为远期规模过早设计（10 倍增长时多半需要重新设计）；简单的方案往往能撑很久；弹性伸缩适合负载不可预测的场景，手动扩容更简单、意外更少。
  6. 可维护性：软件的大部分成本在上线之后。可操作性——让运维容易：良好的监控、文档、可预测的行为、避免依赖单台机器、合理的默认值同时允许覆盖。简单性——区分本质复杂度与偶然复杂度；好的抽象（如 SQL、事务）隐藏实现细节。可演化性——让需求变化时容易修改（第 9–10 课的模式演进就是一例）。
