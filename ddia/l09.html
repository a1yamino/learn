编码格式：JSON、Protocol Buffers 与 Avro

第 5 章前半部分。数据在内存里是对象和指针，写入文件或发到网络时要编码成字节序列。应用会不断升级，新旧版本的代码会同时读写同一份数据，所以编码格式必须支持向前与向后兼容。本课比较语言自带的序列化、JSON/XML 及其二进制变体、Protocol Buffers 的字段号与 Avro 的写者/读者模式，并动手按字节手工编码一条 Protobuf 消息。约 60 分钟。

01
保存为 enc.py：手工编码 Protobuf，并模拟旧代码跳过未知字段。
import json, struct
rec = {"name": "lin", "age": 30, "tags": ["db", "go"]}
j = json.dumps(rec, separators=(",", ":")).encode()
print("JSON    ", len(j), "字节", j)

def varint(n):
    out = b""
    while True:
        b = n & 0x7F; n >>= 7
        out += bytes([b | (0x80 if n else 0)])
        if not n: return out
def field(tag, wtype): return varint(tag << 3 | wtype)
def s(tag, v): v = v.encode(); return field(tag, 2) + varint(len(v)) + v
# message Person { string name = 1; int32 age = 2; repeated string tags = 3; }
pb = s(1, rec["name"]) + field(2, 0) + varint(rec["age"]) + b"".join(s(3, t) for t in rec["tags"])
print("Protobuf", len(pb), "字节", pb.hex(" "))

# 旧代码读取新数据：遇到不认识的字段号 4，按线类型跳过
new = pb + s(4, "lin@example.com")
i, known = 0, {}
while i < len(new):
    key = new[i]; tag, wt = key >> 3, key & 7; i += 1
    if wt == 0: val = new[i]; i += 1
    else: ln = new[i]; val = new[i+1:i+1+ln]; i += 1 + ln
    if tag in (1, 2, 3): known.setdefault(tag, []).append(val)
    else: print(f"跳过未知字段 {tag}（线类型 {wt}）")
print("旧代码读到的字段：", sorted(known))

02
保存为 av.py：用旧的写者模式写入，用新的读者模式读取。
import io, fastavro
w = {"type": "record", "name": "Person", "fields": [
      {"name": "name", "type": "string"},
      {"name": "age", "type": "int"}]}
r = {"type": "record", "name": "Person", "fields": [          # 读者模式：新增字段带默认值
      {"name": "name", "type": "string"},
      {"name": "email", "type": ["null", "string"], "default": None}]}
buf = io.BytesIO()
fastavro.schemaless_writer(buf, fastavro.parse_schema(w), {"name": "lin", "age": 30})
data = buf.getvalue()
print(len(data), "字节", data.hex(" "))
print(fastavro.schemaless_reader(io.BytesIO(data), fastavro.parse_schema(w), fastavro.parse_schema(r)))
5 字节 06 6c 69 6e 3c
{'name': 'lin', 'email': None}
03
解读 Avro 的 5 个字节：06 是字符串长度 3（zigzag 编码，3 → 6），6c 69 6e 是 lin，3c 是 30 的 zigzag 编码 60。读者模式没有 age，所以它被丢弃；email 取默认值 null。
挑战
设计一次安全的模式演进
订单消息当前的 Protobuf 定义：message Order { int64 id = 1; string user = 2; double amount = 3; string status = 4; }。需求：① 金额改为“分”为单位的整数，避免浮点误差；② 增加 coupon_code；③ status 改为枚举；④ user 改成 user_id（int64）。生产者和 6 个消费者服务无法同时升级。请给出新的定义和上线步骤。
查看参考答案
message Order {
  int64 id = 1;
  string user = 2 [deprecated = true];   // 过渡期继续写
  double amount = 3 [deprecated = true]; // 过渡期继续写
  string status = 4 [deprecated = true]; // 过渡期继续写
  int64 amount_cents = 5;
  string coupon_code = 6;
  OrderStatus status_enum = 7;
  int64 user_id = 8;
}
enum OrderStatus { ORDER_STATUS_UNSPECIFIED = 0; CREATED = 1; PAID = 2; SHIPPED = 3; }
  1. 不能直接改字段 3、2、4 的类型：类型变化会让旧代码错误解析。一律用新字段号新增字段，旧字段先保留。
  2. 步骤 1：生产者同时写新旧字段（双写）。旧消费者只认识旧字段，不受影响；跳过未知字段。
  3. 步骤 2：逐个升级消费者，改为读新字段；读到旧数据（新字段缺失，值为 0/空）时回退读旧字段。
  4. 步骤 3：所有消费者升级完成、且旧消息已过保留期后，生产者停止写旧字段；把 2、3、4 标记为 reserved 2, 3, 4; reserved "user", "amount", "status";，防止被复用。
  5. 枚举第一个值必须是 0（未知/未指定），这样新增枚举值时，旧代码读到不认识的值会保留为未知值，而不是出错。

小结
记住这几点


  1. 两种兼容性：向后兼容——新代码能读旧代码写的数据（通常容易，因为写新代码时知道旧格式）；向前兼容——旧代码能读新代码写的数据（更难，要求旧代码忽略不认识的部分）。滚动升级时新旧版本同时运行，两者都需要。
  2. 语言自带的序列化（Java Serializable、Python pickle）：绑定一种语言，反序列化任意类可能导致远程代码执行，版本兼容性和效率都差。除了临时用途，不要用它们存储或传输数据。
  3. JSON、XML、CSV：人可读、跨语言，但有缺陷：数字精度含糊（大于 253 的整数在 JavaScript 中会丢失精度，所以很多 API 用字符串传 ID）；不支持二进制（要 Base64，膨胀 33%）；模式可选（JSON Schema 能力强但复杂）；CSV 没有模式，转义规则含糊。二进制变体（MessagePack、BSON）只节省一点空间，因为字段名仍在每条记录里。
  4. Protocol Buffers：用模式定义每个字段的字段号和类型，编码中只出现字段号，不出现字段名。演进规则：可以随时增加新字段（新字段号），旧代码遇到不认识的字段号按线类型跳过（向前兼容）；新代码读旧数据时缺失的字段取默认值（向后兼容）；字段名可以改，字段号不能改也不能复用；删除字段时把字段号标记为 reserved。
  5. Avro：编码中既没有字段名也没有字段号，只是按模式顺序把值拼接起来，所以最紧凑。读取时需要写者模式（写数据时用的）和读者模式（应用期望的），Avro 按字段名对两者做解析：写者有读者没有的字段被忽略，读者有写者没有的字段取默认值。因此只能增删有默认值的字段。写者模式从哪来：大文件在文件头存一次；数据库记录带模式版本号；Kafka 消息带 Schema Registry 中的模式 ID（Kafka 第 13 课）。Avro 不需要字段号，所以适合从数据库表结构自动生成模式。
  6. 模式的好处：比 JSON 紧凑得多；模式本身就是始终最新的文档；可以在部署前用模式注册表检查兼容性；静态类型语言可以生成代码。它兼具“无模式”的灵活与“有模式”的可靠。
