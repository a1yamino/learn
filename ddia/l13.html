多主复制、同步引擎与冲突解决

单主复制的限制是：所有写入都要经过一个节点。多主复制允许多个节点同时接受写入，用于多区域部署、离线可用的客户端与实时协作编辑——第 2 版把“同步引擎与本地优先软件”作为重点。代价是写冲突。本课讲多主的使用场景与复制拓扑，冲突是如何产生的，以及处理冲突的几种办法：避免冲突、最后写入者胜、手动合并、CRDT 与操作转换。约 65 分钟。

# 两个离线副本各自修改，之后合并
# 1) 最后写入者胜（LWW）：按时间戳取一个值，另一个修改静默丢失
a = ("标题：周会", 1001)            # (值, 时间戳)
b = ("标题：周例会", 1002)
print("LWW 合并：", max(a, b, key=lambda x: x[1])[0], "（副本 A 的修改丢失）")

# 2) G-Counter：每个副本只增加自己的槽，合并取各槽最大值
class GCounter:
    def __init__(self, me): self.me, self.c = me, {}
    def inc(self, n=1): self.c[self.me] = self.c.get(self.me, 0) + n
    def merge(self, o):
        for k, v in o.c.items(): self.c[k] = max(self.c.get(k, 0), v)
    def value(self): return sum(self.c.values())
x, y = GCounter("A"), GCounter("B")
x.inc(3); y.inc(2); x.merge(y); y.merge(x); x.merge(y)   # 重复合并也没关系（幂等）
print("计数器：", x.value(), y.value())

# 3) OR-Set：添加带唯一标签，删除只删除自己看到的标签 → 并发的“添加”胜出
import uuid  # 跨设备添加也必须使用唯一标签
class ORSet:
    def __init__(self): self.adds, self.removes = set(), set()
    def add(self, e): self.adds.add((e, uuid.uuid4().hex))
    def remove(self, e): self.removes |= {t for t in self.adds if t[0] == e}
    def merge(self, o): self.adds |= o.adds; self.removes |= o.removes
    def value(self): return sorted({e for e, t in self.adds - self.removes})
s1 = ORSet(); s1.add("牛奶"); s1.add("鸡蛋")
s2 = ORSet(); s2.merge(s1)
s1.remove("牛奶")                 # A 删除牛奶
s2.add("牛奶"); s2.add("面包")     # B 同时又加了一次牛奶、加了面包
s1.merge(s2); s2.merge(s1)
print("购物清单：", s1.value(), s2.value())
LWW 合并： 标题：周例会 （副本 A 的修改丢失）
计数器： 5 5
购物清单： ['牛奶', '面包', '鸡蛋'] ['牛奶', '面包', '鸡蛋']
02
思考：为什么 OR-Set 中“牛奶”还在？因为 A 删除时只删除了自己看到过的那个标签，B 后来添加的牛奶带有新标签，A 从未见过。这种语义叫“添加胜出”。如果你需要“删除胜出”，就要用另一种 CRDT。

挑战
为一个离线优先的待办应用选择数据结构
功能：待办列表（可以增删、重排）、每项有标题、完成状态、截止日期；同一用户的手机与电脑可能都离线修改几天。请为每种操作选择冲突解决语义，并说明哪些可以用现成的 CRDT、哪些需要提示用户。
查看参考答案
  1. 列表成员（增删）：OR-Set（添加胜出）保证并发的“添加”胜过删除；只修改标题等字段不会自动重新添加成员，因此不能推出“删除与编辑并发时保留该项”。若产品需要编辑使条目复活，编辑操作必须显式产生新的添加标签，或采用带删除标记的复活策略；还要把字段合并与成员关系分别定义。
  2. 顺序：列表 CRDT（如 RGA，或 Automerge/Yjs 的 list），每项有稳定的位置标识；或者给每项一个分数位置（fractional index），重排时只改被移动项的位置，冲突时以 LWW 解决该项的位置。
  3. 标题：短文本可用 LWW 寄存器（按 Lamport 时间戳 + 设备 ID 打破平局，而不是墙上时钟）；若希望保留两边的编辑，用文本 CRDT 或多值寄存器，把冲突显示给用户选择。
  4. 完成状态：LWW 寄存器即可；或者“完成胜出”的标志。
  5. 截止日期：LWW 寄存器；如果两个设备都改了，可以在同步后提示“该项在另一设备上也被修改了”。
  6. 整体：用 Automerge/Yjs 之类的库，文档存在本地（IndexedDB/SQLite），同步服务器只转发和存储变更，不需要理解冲突。

小结
记住这几点


  1. 多区域部署：每个区域一个主节点，区域内是普通的单主复制，区域之间异步地互相复制。写入在本地区域完成，延迟低，某个区域故障或区域间网络中断时其他区域仍可写。代价：两个区域可能并发修改同一份数据，产生冲突；自增 ID、触发器、约束等特性与多主配合困难。很多数据库的多主功能是后加的，要谨慎使用。
  2. 同步引擎与本地优先：离线可用的应用（笔记、日历）在每台设备上都有一个本地数据库，可以离线读写，联网后与服务器及其他设备同步——每台设备都是一个“主节点”，复制延迟可能长达几天。实时协作（多人同时编辑文档）是同一个问题的极端情况：每次按键都是一次本地写入，再异步同步给其他人。同步引擎把这些复杂性封装起来，让 UI 直接读写本地数据，本地优先软件进一步强调数据由用户掌握、无需服务器也能工作。
  3. 复制拓扑：环形、星形、全互连。环形和星形中一个节点故障会中断复制；全互连容错更好，但消息可能经由不同路径以不同顺序到达，一个“更新”可能比它依赖的“插入”先到——需要版本向量等机制来排序（第 14 课）。
  4. 冲突处理：① 避免冲突——同一条记录的写入总是路由到同一个主节点（例如用户的“主区域”）；最简单，但区域故障时仍要切换。② 最后写入者胜（LWW）——给每个写入一个时间戳，保留最大的；会静默丢失并发写入，而且依赖时钟（第 22 课）。③ 手动解决——保存所有冲突的版本（兄弟值），让应用或用户合并（如 Git）。④ 自动合并——用 CRDT 或操作转换。
  5. CRDT（无冲突复制数据类型）：设计成任意顺序、任意次数合并都得到相同结果的数据结构（合并满足交换律、结合律、幂等）。例如：计数器（每个副本只加自己的槽，合并取最大）、集合（添加带唯一标签，删除只删除看到过的标签，因此并发的添加胜出）、文本（为每个字符分配稳定的位置标识，Automerge、Yjs）。操作转换（OT）是协作编辑的另一种方法（Google Docs），依赖中心服务器为操作排序并相应地变换索引。
  6. 冲突的形式不只是“同一字段被改成两个值”：两个人同时预订了同一个会议室，在各自的副本上都没有违反约束，合并后却违反了——这类问题需要协调（第 19、27 课）。
