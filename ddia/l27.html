01
保存为 uniq.py：按用户名分区的日志 + 顺序处理实现唯一性，并按请求 ID 去重。
import hashlib
from collections import defaultdict
# 注册请求先追加到按用户名分区的日志；每个分区由一个处理器顺序处理
requests = [("r1", "alice"), ("r2", "bob"), ("r3", "alice"), ("r4", "carol"), ("r2", "bob")]   # r2 被客户端重试了一次
P = 3
log = defaultdict(list)
for rid, name in requests:
    log[int(hashlib.md5(name.encode()).hexdigest(), 16) % P].append((rid, name))

taken, seen, results = {}, set(), {}
for p in range(P):                       # 每个分区独立、顺序地处理：不需要锁
    for rid, name in log[p]:
        if rid in seen: continue          # 端到端去重：同一个请求 ID 只处理一次
        seen.add(rid)
        if name in taken: results[rid] = f"拒绝（{name} 已被 {taken[name]} 注册）"
        else: taken[name] = rid; results[rid] = f"成功（{name}）"
for rid in sorted(results): print(rid, results[rid])
r1 成功（alice）
r2 成功（bob）
r3 拒绝（alice 已被 r1 注册）
r4 成功（carol）

挑战
用事件日志实现跨账户转账
账户按 account_id 分成 16 个分区，每个分区由一个流处理器顺序处理。要求：不使用分布式事务，转账不能丢、不能重复、余额不能为负。请设计事件流程，并说明在处理器崩溃、客户端重试时为什么仍然正确。
查看参考答案
  1. 客户端为转账生成 request_id，把 TransferRequested{request_id, from, to, amount} 追加到按 from 账户分区的请求日志。
  2. from 分区的处理器顺序处理：检查 request_id 是否处理过（状态中保存）；检查余额，不足则输出 TransferRejected；足够则在本地状态中扣款，并输出 Debited{request_id, from, amount} 与 CreditRequested{request_id, to, amount}（后者写入按 to 分区的日志）。状态更新、输出与输入位移原子提交（Kafka 事务 / 检查点）。
  3. to 分区的处理器按 request_id 去重后入账，输出 Credited。
  4. 崩溃：处理器从上次提交的位移和状态恢复，重新处理未提交的输入；因为输出与位移原子提交，不会重复发出扣款。客户端重试：同一个 request_id 再次写入日志，处理器发现已处理，直接返回原结果（端到端去重）。
  5. 中间状态（已扣款、未入账）只存在很短时间，是及时性问题而非完整性问题：钱一定会到达，余额检查发生在 from 分区的顺序处理中，不会透支。

小结
记住这几点


  1. 用派生数据集成：同一份数据往往需要以多种形式存在——数据库、缓存、全文索引、数据仓库、推荐模型。把一个系统定为记录系统，其他系统通过一个全序的事件日志（CDC 或事件溯源）派生，比分布式事务更松耦合、更容错：一个派生系统故障只会让它暂时落后，而不会拖垮写入。限制：全序日志的吞吐受单个分区的限制；跨区域、跨服务时没有全局顺序，需要处理因果关系。
  2. 批处理与流处理：两者都是从输入派生输出，区别在于有界还是无界。新的视图可以用批处理从历史数据构建，再用流处理保持更新；也可以统一用流处理（kappa 架构：重置位移、从头重放日志即可重建）。渐进地迁移：同时维护旧视图和新视图，逐步把读流量切到新视图，出错时随时切回——这是派生数据带来的演进能力。
  3. 拆解数据库：数据库内部本来就有二级索引、物化视图、复制日志——它们都是派生数据。“拆解”是把这些功能用独立的组件实现，用日志把它们串起来：应用写入记录系统，各种派生视图通过订阅日志自动维护（就像 Unix 管道把小工具组合起来）。围绕数据流设计应用：应用代码是从一个状态到另一个状态的确定性函数；读取变成对物化视图的查询；甚至可以把状态变化推送到客户端（订阅），让终端设备也成为数据流的一环。
  4. 端到端原则：只有在通信的两端才能真正实现某些功能。TCP 去重、数据库事务都不能防止用户点击两次“提交”导致的重复——要在客户端为每个操作生成一个唯一的请求 ID，一路传递到最终的写入，用它去重。实现约束：唯一性需要共识，但不一定需要分布式事务——把请求按需要唯一的值分区写入日志，每个分区由一个处理器顺序处理，第一个请求胜出，结果再通过日志返回。多分区的请求（转账涉及两个账户）可以拆成多个阶段：先把请求作为一个事件写入日志，再由各分区处理器各自根据它派生出扣款、入账事件——无需原子提交也不会丢失或重复。
  5. 及时性与完整性：一致性这个词混合了两件事：及时性（读到最新的状态）和完整性（没有损坏、没有丢失或矛盾的数据）。违反及时性是暂时的，等一等就好；违反完整性是永久的。对大多数应用，完整性远比及时性重要。基于事件日志的系统可以在异步的情况下保证完整性（精确一次、确定性派生），同时放宽及时性。很多约束其实可以事后补偿（超卖后道歉、退款），只要业务能接受。
  6. 信任但要验证：硬件和软件都会出错（静默的数据损坏、数据库 bug）。要定期审计：校验和、对比源数据与派生数据、从备份恢复演练。事件日志加确定性派生使端到端的完整性检查成为可能。第 14 章：做正确的事——预测性分析可能固化偏见与歧视（“用过去的数据训练，就会重复过去的不公”）；自动化决策需要问责与解释；推荐系统会形成反馈循环；数据收集应当最小化，尊重用户的知情同意与删除权；数据是资产也是负债。工程师有责任考虑系统对人的影响。
