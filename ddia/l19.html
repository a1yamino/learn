写偏斜、幻读与可串行化

快照隔离防住了脏读、读偏差和（在 PostgreSQL 中）丢失更新，但还有一类更隐蔽的异常：两个事务读取同一批数据，各自根据读到的结果修改了不同的对象，合起来却破坏了不变式——写偏斜。本课用值班医生、会议室预订、用户名注册等例子讲写偏斜与幻读，然后讲实现可串行化的三种方法：真正的串行执行、两阶段锁（2PL）和可串行化快照隔离（SSI）。约 70 分钟。

挑战
识别并修复写偏斜
一个优惠券系统：每个用户每天最多领 3 张券。代码：
BEGIN;  -- 读已提交
SELECT count(*) FROM claims WHERE user_id = $1 AND day = current_date;
-- 若 < 3：
INSERT INTO claims(user_id, day, coupon_id) VALUES ($1, current_date, $2);
COMMIT;
用户用脚本并发请求，领到了 7 张。请：① 解释为什么这是写偏斜/幻读；② 给出至少三种修复方式及其取舍。
查看参考答案
  1. 每个并发事务都读到 count < 3，然后各自插入新行——它们修改的不是同一行，行锁冲突不存在；检查的是“满足条件的行数”，新插入的行正好改变了其他事务查询的结果，是幻读导致的写偏斜。SELECT … FOR UPDATE 也不行：它只锁已有的行。
  2. SERIALIZABLE：把事务改为可串行化，SSI 会中止其中冲突的事务，应用重试。改动最小；需要重试逻辑，热点用户冲突多。
  3. 物化冲突 / 锁一个父行：在 user_daily(user_id, day, n) 中维护计数，UPDATE user_daily SET n = n + 1 WHERE user_id = $1 AND day = current_date AND n < 3，影响 0 行则拒绝——原子操作 + 行锁，简单高效；也可以先 SELECT … FROM users WHERE id = $1 FOR UPDATE 串行化同一用户的请求。
  4. 约束：增加 slot smallint CHECK (slot BETWEEN 1 AND 3) 并建唯一约束 (user_id, day, slot)，插入时依次尝试 slot 1、2、3，冲突即换下一个——用唯一约束表达上限。
  5. 咨询锁 pg_advisory_xact_lock(user_id) 也可以串行化同一用户的事务，但只在所有代码路径都使用它时有效。

小结
记住这几点


  1. 写偏斜：医院要求任何时候至少有一名医生值班。两名值班医生同时请假：各自的事务都检查“当前值班人数 ≥ 2”，都成立，于是各自把自己的记录改为不值班——两个事务修改的是不同的行，所以既不是脏写也不是丢失更新，但提交后没人值班了。模式：① SELECT 检查条件；② 根据结果决定；③ 写入，而这次写入改变了 ① 的结果。
  2. 更多例子：会议室预订（检查时间段无冲突后插入）、多人游戏中两个玩家把棋子移到同一格、用户名注册（检查不存在后插入，可用唯一约束解决）、防止重复花费（余额检查）。
  3. 幻读：一个事务中的写入改变了另一个事务中某个查询条件的结果。当检查的是“不存在满足条件的行”时（会议室没有冲突的预订），SELECT FOR UPDATE 无行可锁。物化冲突：人为创建可以加锁的行（例如为每个会议室的每 15 分钟时段预先建一行），把幻读变成行锁冲突——容易出错，是最后的手段。
  4. 真正的串行执行：在单个线程上逐个执行事务，根本不存在并发（VoltDB、Redis 的 Lua 脚本与 MULTI）。前提：事务短小，整个事务以存储过程形式一次性提交（不能与用户交互等待），数据集能放进内存，写吞吐一个 CPU 核扛得住（或者能按分片划分，跨分片事务很少）。
  5. 两阶段锁（2PL）：读需要共享锁，写需要排他锁，锁一直持有到事务结束（第一阶段获取、第二阶段全部释放）。写者阻塞读者、读者也阻塞写者。为了防止幻读还需要谓词锁（锁住满足某个条件的所有行，包括还不存在的）——实际用索引范围锁近似。代价：吞吐量和响应时间明显变差，死锁频繁。MySQL InnoDB 的 SERIALIZABLE、SQL Server 使用 2PL。
  6. 可串行化快照隔离（SSI）：乐观的方法——事务照常在快照上执行，提交时检查是否可能违反可串行化：① 读取了已被其他事务修改、但修改在快照时尚未提交的数据（读到了过时的前提）；② 写入影响了其他事务之前的读取（通过记录读过的索引范围）。检测到冲突就中止，由应用重试。没有阻塞，只读事务从不需要等待；代价是冲突率高时大量中止。PostgreSQL 的 SERIALIZABLE、CockroachDB、FoundationDB 都基于这类思想。
