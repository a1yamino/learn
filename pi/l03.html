统一的消息模型与流式事件

pi 支持几十家模型提供方，但上层代码只认识一种消息格式和一种事件流。这一课精读 packages/ai/src/types.ts 中的核心类型：四种消息角色（system、user、assistant、toolResult）、五种内容块、七种停止原因，以及把“流式回复”统一成一串有序事件的 AssistantMessageEvent。理解了这一层，后面的循环、会话、压缩、TUI 都只是在处理这些数据。约 50 分钟。

export class AssistantMessageEventStream extends EventStream<AssistantMessageEvent, AssistantMessage> {
  readonly #startedAt = Date.now();
  readonly #startedAtMonotonic = performance.now();

  constructor() {
    super(
      (event) => event.type === "done" || event.type === "error",
      (event) => {
        if (event.type === "done") {
          return event.message;
        } else if (event.type === "error") {
          return event.error;
        }
        throw new Error("Unexpected event type for final result");
      },
    );
  }
与 Codex 对照：Codex 直接以 OpenAI Responses API 的 ResponseItem 为内部转录格式，并在其上定义了自己的协议层（EventMsg）。pi 选择自己定义一个与提供方无关的最小模型，再为每个 API 写转换。见 Codex 第 3 课 · 协议与 ResponseItem。

const faux = registerFauxProvider();
faux.setResponses([

const s = streamSimple(faux.getModel(), {

for await (const e of s) {
  const extra = "delta" in e ? JSON.stringify(e.delta) : e.type === "toolcall_end" ? JSON.stringify(e.toolCall.arguments) : "";

}
const msg = await s.result();
console.log("stopReason =", msg.stopReason, "| 内容块 =", msg.content.map((c) => c.type).join(","));

挑战
渲染器
写一个最小渲染器：只用事件（不读 partial），在终端里实时拼出最终文本，并在 toolcall_end 时打印 ⚙ read(a.txt)。然后思考：为什么每个事件还要带上 partial？
查看参考答案
let out = "";
for await (const e of s) {
  if (e.type === "text_delta") { process.stdout.write(e.delta); out += e.delta; }
  if (e.type === "toolcall_end") console.log(`\n⚙ ${e.toolCall.name}(${e.toolCall.arguments.path})`);
  if (e.type === "error") console.error("错误:", e.error.errorMessage);
}
带上 partial 的原因：订阅者可能中途加入（例如 TUI 重绘、扩展在 message_update 中检查内容），或者只关心“此刻完整的样子”而不想自己维护拼接状态。增量（delta）适合高效追加，快照（partial）适合无状态渲染；pi 两者都给。

小结
记住这几点


  1. Message：system（指令、命名 sections、toolsAdded/toolsRemoved）、user（文本/图片）、assistant（文本、thinking、toolCall + usage、stopReason、provider/model）、toolResult（toolCallId、content、details、isError）。
  2. 系统消息可以出现在转录中间：后续的 system 消息按名称替换或删除 section（null 表示删除），并增减工具。把所有系统消息依次重放，就得到当前的提示与工具集。支持中途系统消息的提供方原样发送，不支持的则重建开头的系统消息。
  3. 内容块：text、thinking（可带不透明的 thinkingSignature 以便多轮回放，可被 redacted）、image、toolCall（id、name、arguments；若模型给出的参数不是合法 JSON，则 arguments={} 并设置 argumentsError）。
  4. StopReason：stop、length、toolUse、error、aborted、deferred，以及流式进行中的 pending。循环据此决定下一步（例如 length 时，被截断的工具调用会被判为失败）。
  5. 事件流：start → 每个内容块的 *_start / *_delta / *_end（带 contentIndex）→ done 或 error。每个事件都带当前的 partial 消息快照，所以 UI 可以随时渲染完整状态。错误也以事件交付，而不是抛出异常。
  6. EventStream：一个可异步迭代的推送队列，外加一个 result() Promise：遇到 done/error 时完成。提供方只管 push，消费者只管 for await。
