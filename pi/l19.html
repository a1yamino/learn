信任边界：pi 刻意不做什么

pi 的哲学是“内核最小，策略交给扩展”。它没有内置沙箱，不会在每次工具调用前请求批准，也没有内置的计划模式或子 agent。官方文档写得很直接：模型生成的命令和代码应视为不可信，安全来自操作系统或虚拟化边界，而不是看着记录。本课用实验划清 pi 真正提供的唯一边界——项目信任——以及它不保护什么。约 40 分钟。

Treat model-generated commands and code as untrusted. Pi can read, change, and execute files with the permissions of the account that started it, and it does not ask for approval before every tool call. Extensions, package installers, language servers, and other child processes run with those same permissions unless an operating-system or virtualization boundary restricts them.

Files, comments, instructions, command output, and model responses can steer the model through prompt injection. Project trust controls which project resources load at startup, but it does not make that content or the resulting actions safe.

Safety comes from limiting the files, credentials, processes, and network services Pi can access and affect if a generated action is wrong or hostile. Watching the transcript, using project trust, and reviewing changes do not create a security boundary.

export default function (pi: ExtensionAPI) {
  const dangerousPatterns = [/\brm\s+(-rf?|--recursive)/i, /\bsudo\b/i, /\b(chmod|chown)\b.*777/i];

  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName !== "bash") return undefined;

    const command = event.input.command as string;
    const isDangerous = dangerousPatterns.some((p) => p.test(command));

    if (isDangerous) {
      if (!ctx.hasUI) {
        // In non-interactive mode, block by default
        return { block: true, reason: "Dangerous command blocked (no UI for confirmation)" };
      }

      const choice = await ctx.ui.select(`⚠️ Dangerous command:\n\n  ${command}\n\nAllow?`, ["Yes", "No"]);

      if (choice !== "Yes") {
        return { block: true, reason: "Blocked by user" };
      }
    }

    return undefined;
  });

在你的电脑上练习
脚本在临时目录里构造一个“陌生项目”：带一个项目扩展和一个 build 目录；faux 模型总是要求执行 rm -rf build。一切发生在临时 HOME 与临时目录中，不会碰你的文件。


01
运行实验。
cat > pi-mono/scratch/l19.sh <<'EOF'
#!/bin/bash
# 信任边界实验：项目扩展是否加载？危险命令谁来拦？
ROOT="$(cd .. && pwd)"; CLI="node $ROOT/packages/coding-agent/dist/cli.js"
export HOME=$(mktemp -d); W=$(mktemp -d)
# 一个让模型执行 "rm -rf build" 的 faux 扩展
cat > $W/faux.ts <<'TS'
import { fauxAssistantMessage, fauxToolCall, registerFauxProvider } from "@earendil-works/pi-ai/compat";
export default function (pi: any) {
  const f = registerFauxProvider();
  f.setResponses([
    fauxAssistantMessage([fauxToolCall("bash", { command: "rm -rf build && echo 已删除" })], { stopReason: "toolUse" }),
    (ctx: any) => fauxAssistantMessage("工具结果：" + JSON.stringify(ctx.messages.at(-1).content[0].text)),
  ]);
  pi.registerProvider("faux", { baseUrl: "http://localhost:0", apiKey: "k", api: f.api,
    models: f.models.map((m: any) => ({ ...m, reasoning: false, input: ["text"] })) });
}
TS
# 被测项目：带一个项目扩展
P=$W/project; mkdir -p $P/.pi/extensions $P/build
echo 'export default function () { console.error("!! 项目扩展被加载并执行了"); }' > $P/.pi/extensions/hello.ts
cd $P
PI="$CLI --no-session -e $W/faux.ts --model faux/faux-1"
echo "== 1. 默认（非交互，无保存的决定）"; $PI -p "清理" </dev/null; ls -d build 2>/dev/null || echo "(build 已被删除)"
mkdir -p build
echo "== 2. --approve：信任本项目"; $PI --approve -p "清理" </dev/null
mkdir -p build
echo "== 3. 加载官方示例 permission-gate"
$PI -e $ROOT/packages/coding-agent/examples/extensions/permission-gate.ts -p "清理" </dev/null
ls -d build && echo "(build 仍在)"
EOF
cd pi-mono/scratch && bash l19.sh 2>&1

挑战
写一个用户级信任策略
写一个扩展，处理 project_trust 事件：路径位于 ~/work/ 下的项目自动信任，其他一律拒绝。用 -e 加载它重新运行实验，看第 1 步的结果。
查看参考答案
import { homedir } from "node:os";
export default function (pi: any) {
  pi.on("project_trust", async (event: any) =>
    event.cwd.startsWith(homedir() + "/work/") ? { trusted: "yes" } : { trusted: "no" });
}
按文档，用户级与命令行扩展可以处理 project_trust，第一个给出是/否的扩展决定结果，优先于 trust.json 与 defaultProjectTrust。事件只有 cwd，返回 { trusted: "yes"|"no"|"undecided", remember? }（types.ts 中的 ProjectTrustEventResult）；返回 undecided 则交给后续规则。注意：这仍然只控制资源加载，模型发出的命令照样执行。

小结
记住这几点


  1. 没有内置沙箱与审批：工具以启动 pi 的用户权限运行。docs/security.md 建议把 pi 整个放进容器/虚拟机/沙箱（docs/containerization.md 列出 Docker、Docker Sandboxes、OpenShell 等方式）。
  2. 项目信任（trust-manager.ts）：当前目录存在 .pi/settings.json、mcp.json、extensions、skills、prompts、themes、SYSTEM.md、APPEND_SYSTEM.md（或项目 .agents/skills）时需要决定是否加载。只有空 .pi 目录不需要。
  3. 决定顺序：命令行 --approve/--no-approve → 用户级扩展处理 project_trust 事件 → ~/.pi/agent/trust.json 中最近的父目录决定 → 设置 defaultProjectTrust（默认 ask）。非交互模式下 ask 等同于跳过。
  4. 信任不保护什么：AGENTS.md/CLAUDE.md 不受信任控制、始终加载；项目信任也完全不限制工具调用能访问的路径。它只阻止一个文件夹静默执行扩展代码。
  5. 策略在扩展里：官方示例 permission-gate.ts（危险命令确认，无 UI 时直接拦截）、protected-paths.ts、confirm-destructive.ts、sandbox/（用 sandbox-runtime 在 macOS sandbox-exec / Linux bubblewrap 中运行 bash）、plan-mode/（第 16 课）、subagent/。
  6. 对比：Codex 把沙箱、审批策略与执行策略做成内置的核心功能——这是两者最大的设计分歧。
