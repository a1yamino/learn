run_turn 循环

pi 的 runLoop 只有 159 行。Codex 的 run_turn（core/src/session/turn.rs）是它的“生产版本”：同样是“请求模型 → 执行工具 → 再请求”的循环，但每一圈都要处理排队的用户输入、钩子、上下文窗口检查、自动压缩、Stop 钩子要求继续等。本课抓住它的骨架：needs_follow_up 如何决定是否再来一圈，并用三个场景验证。约 45 分钟。

01
三个场景的剧本。
cat > codex/scratch/s_loop.py <<'EOF'
# 剧本：用环境变量 SCEN 选择场景
import os
S = os.environ.get("SCEN", "a")
def reply(n, body):
    if S == "a":  # 只回答文字：1 次请求就结束
        return [msg("直接回答，不用工具")]
    if S == "b":  # 文字 + 工具调用在同一个响应里：仍需继续
        if n == 1: return [msg("我先看看目录"), call("exec_command", {"cmd": "ls"}, "c1")]
        return [msg("看完了")]
    if S == "c":  # 一个响应里两个工具调用
        if n == 1: return [call("exec_command", {"cmd": "echo A"}, "c1"), call("exec_command", {"cmd": "echo B"}, "c2")]
        return [msg("两个都执行了")]
EOF

挑战
证明“边流边执行”
设计实验证明工具在响应流结束前就开始执行：让 mock 在发出 function_call 的 output_item.done 之后 sleep 2 秒再发 response.completed，工具执行 date +%s.%N，比较命令时间与 mock 发送 completed 的时间。
查看参考答案
在 mock.py 的循环里，对带 "sleep_after": 2 的项在发送后 time.sleep(2)，并在发 response.completed 前打印 time.time()。命令输出的时间戳会比 completed 早约 2 秒，说明工具在 output_item.done 到达时就派发了。这正对应源码注释 “handle_tool_call dispatches immediately, not when its future is polled”（有 post-model 钩子时会延后）。

小结
记住这几点


  1. 骨架：loop { 取出排队输入 → 记录 → 捕获本步上下文 → run_sampling_request → 计算 needs_follow_up → 可能压缩 → 若不需继续则跑 Stop 钩子并 break }。
  2. needs_follow_up = 模型需要继续 || 有排队输入。模型需要继续 ⇔ 本次响应中出现了工具调用（stream_events_utils.rs 中处理每个输出项时置位）。只回文字就结束 turn；文字与工具调用并存时仍然继续（场景 b）。
  3. 边流边执行：每个工具调用在 output_item.done 到达时就立即派发（注释：“handle_tool_call dispatches immediately”），不等整个响应结束；未完成的调用进入 in_flight 队列，响应结束后统一等待。
  4. 并行与顺序：场景 c 中 echo B 先于 echo A 完成（事件按完成顺序），但写回历史的 function_call_output 保持调用顺序。
  5. 自动压缩：每圈之后检查 token 状态，超过阈值就在 turn 中途或结束后压缩（第 16 课）。
  6. Stop 钩子：turn 将要结束时运行；钩子可以阻止结束并注入一条继续提示（should_block → continue），这是 /goal 之外另一种“让 agent 继续干活”的机制（第 21 课）。
