沙箱：Linux（bubblewrap 与 seccomp）

在 Linux 上，Codex 通过一个辅助程序 codex-linux-sandbox 运行命令：文件系统隔离交给 bubblewrap（只读绑定整个根目录，再把可写根重新以读写方式绑定；新的用户、PID、IPC 命名空间，按需断网），进程内再加上 no_new_privs 与 seccomp 过滤网络相关系统调用。旧的 Landlock 文件系统实现仍保留，但已是“legacy”模式。本课用 codex sandbox 直接在沙箱中运行命令，逐项验证这些限制。约 45 分钟。

在你的电脑上练习
本课只需要 Linux 与第 1 课构建好的 codex（它自带 bubblewrap，也可使用系统的 bwrap）。codex sandbox 不调用模型。所有写入都发生在临时目录中。


01
沙箱实验。
cat > codex/scratch/l12.sh <<'EOF'
#!/bin/bash
# Linux 沙箱实验：codex sandbox 在本机沙箱中运行命令（不经过模型）
export CODEX_HOME=$(mktemp -d); W=$(mktemp -d); cd $W; git init -q --template= .
try() { local mode=$1; shift; printf "  %-16s %-34s → " "$mode" "$*"
  if codex sandbox -c sandbox_mode="\"$mode\"" -- bash -c "$*" >/tmp/sbx.out 2>&1; then echo "成功"; else echo "失败：$(tail -1 /tmp/sbx.out | cut -d: -f2- | head -c 60)"; fi; }
echo "== 只读（默认）"
try read-only "cat /etc/hostname > /dev/null"
try read-only "touch a.txt"
echo "== workspace-write"
try workspace-write "touch a.txt"
try workspace-write "touch \$HOME/escape.txt"
try workspace-write "touch /tmp/t.txt"
try workspace-write "echo x >> .git/config"
try workspace-write "curl -sS -m 3 https://example.com -o /dev/null"
echo "== 沙箱内看到的进程（PID 命名空间）"
codex sandbox -- bash -c 'ps -e --no-headers | wc -l | xargs echo "  进程数:"'
echo "  宿主进程数: $(ps -e --no-headers | wc -l)"
EOF
cd codex/scratch && bash l12.sh
== 只读（默认）
  read-only        cat /etc/hostname > /dev/null      → 成功
  read-only        touch a.txt                        → 失败： cannot touch 'a.txt': Read-only file system
== workspace-write
  workspace-write  touch a.txt                        → 成功
  workspace-write  touch $HOME/escape.txt             → 失败： cannot touch '/home/box/escape.txt': Read-only file system
  workspace-write  touch /tmp/t.txt                   → 成功
  workspace-write  echo x >> .git/config              → 失败： line 1: .git/config: Read-only file system
  workspace-write  curl -sS -m 3 https://example.com -o /dev/null → 失败： (6) Could not resolve host: example.com
== 沙箱内看到的进程（PID 命名空间）
  进程数: 5
  宿主进程数: 117
挑战
允许网络
在 workspace-write 下让 curl 成功：查找配置项 [sandbox_workspace_write] network_access，用 -c 打开它再试。此时 bwrap 参数会有什么变化？
查看参考答案
codex sandbox -c sandbox_mode='"workspace-write"' -c sandbox_workspace_write.network_access=true -- curl -sS -m 5 https://example.com -o /dev/null && echo ok
打开 network_access 后网络沙箱策略变为启用，should_unshare_network() 为假，bwrap 不再加 --unshare-net，seccomp 也不再安装网络过滤；如果你的机器本身能访问外网，命令会输出 ok。

小结
记住这几点


  1. 两层（linux-sandbox/src/lib.rs）：进程内限制（no_new_privs + seccomp）与 bubblewrap 文件系统隔离。Landlock 只在 legacy 模式使用。
  2. bwrap 参数（bwrap.rs）：--new-session --die-with-parent、文件系统参数（--ro-bind / / 加可写根的 --bind）、--unshare-user（即使以 root 运行也显式请求）、--unshare-pid、--unshare-ipc、按需 --unshare-net、新的 /proc。
  3. 实验结果：read-only 下可以读 /etc，不能写工作目录；workspace-write 下可写工作目录与 /tmp，不能写 $HOME，也不能改 .git/config（受保护的元数据，与 macOS 相同）；网络不可用；沙箱内只看得到 5 个进程（宿主有一百多个）。
  4. seccomp 网络过滤（seccomp.rs）：禁止 connect 等调用，socket/socketpair 只允许 AF_UNIX；启用托管代理时只放行到代理的路由。
  5. 错误信息：被拒绝的写入表现为 “Read-only file system”——这正是 bind 挂载为只读的结果。unified exec 用 is_likely_sandbox_denied 识别这类失败，按策略决定是否询问用户以无沙箱重试（下一课）。
  6. codex sandbox：调试用子命令，不经过模型直接在当前平台的沙箱中运行命令，可用 -c sandbox_mode=… 或 -P 权限配置文件选择策略。
