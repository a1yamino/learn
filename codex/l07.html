Codex CLI · 第 7 课

工具规格、路由与并行

pi 的工具是一个带 TypeBox 参数模式的对象，循环负责校验与并行执行。Codex 把这件事拆成三层：规格（ToolSpec，发给模型的 JSON 描述，包括 function、custom 自由格式、tool_search 等类型）、注册表与路由（把 ResponseItem 转成 ToolCall 并派发给处理器）、并行闸门（用一把读写锁决定哪些工具能同时运行）。本课故意让模型调用不存在的工具和传错参数，看错误如何回到模型。约 40 分钟。

pub(crate) fn supports_parallel_tool_calls(&self, name: &ToolName) -> Option<bool> {
    let tool = self.tools.get(&name.clone().with_default_namespace())?;
    Some(tool.exposure != ToolExposure::Hidden && tool.runtime.supports_parallel_tool_calls())

sandbox_permissions 取值 use_default 或 require_escalated（不在沙箱中运行）；后者需要 justification 作为给用户的审批问题。prefix_rule 只能与 require_escalated 一起使用，是一个可复用的审批前缀（例如 ["git","pull"]），批准后同前缀的命令不再询问。第 13 课讲审批与执行策略时会用到。

小结
记住这几点


  1. 工具规格：gpt-5.5 下模型看到 10 个工具；exec_command 有 cmd、workdir、tty、yield_time_ms、sandbox_permissions、justification、prefix_rule 等参数；apply_patch 是 custom 类型，格式由 Lark 语法定义。请求带 parallel_tool_calls: true。
  2. build_tool_call（tools/router.rs）：FunctionCall → ToolPayload::Function{arguments}（字符串原样传递），ToolSearchCall、CustomToolCall 等各有载荷类型。
  3. 错误回给模型而不是终止：未知工具 → unsupported call: no_such_tool；参数反序列化失败 → failed to parse function arguments: missing field `cmd`。这些都是 FunctionCallError::RespondToModel，作为工具输出写回历史。
  4. 并行闸门（tools/parallel.rs）：supports_parallel_tool_calls() 为真的工具获取读锁，可以同时运行；其余获取写锁，独占执行。默认实现返回 false。
  5. 谁支持并行：exec_command、write_stdin、view_image、tool_search、MCP 中声明只读的工具等；apply_patch 未覆盖默认值，因此独占执行——修改文件时不会与其他工具交错。
  6. 对比 pi：pi 默认全部并行，可整体切换为顺序；Codex 按工具粒度决定。
