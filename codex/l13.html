审批与执行策略

沙箱回答“命令能碰到什么”，审批回答“命令要不要先问人”。Codex 把三样东西组合起来：沙箱模式（read-only / workspace-write / danger-full-access）、审批策略（untrusted / on-request / granular / never），以及用户可写的执行策略规则（~/.codex/rules/*.rules，Starlark 语法的 prefix_rule）。本课用 app-server 扮演用户，在一个 turn 里观察四条命令分别走向：沙箱内直接运行、请求提升权限被拒、被规则禁止、被规则要求询问后批准。约 50 分钟。

cat > codex/scratch/l13.py <<'EOF'
# 审批：app-server 把审批请求发给客户端，由我们（扮演用户）决定
import os, sys, json; sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from apc import AppServer, text
a = AppServer(cwd=os.getcwd())
answers = iter(["decline", "accept"])
def on_request(method, params):
    decision = next(answers)
    print(f"  ← 审批请求 {method}: {params.get('command')}  理由={params.get('reason')!r}  → 我们回答 {decision}")
    return {"decision": decision}
a.on_request = on_request
a.request("initialize", {"clientInfo": {"name": "course", "title": None, "version": "0"}}); a.notify("initialized")
tid = a.request("thread/start", {"cwd": os.getcwd(), "approvalPolicy": "on-request", "sandbox": "workspace-write"})["thread"]["id"]
a.request("turn/start", {"threadId": tid, "input": text("干活")})
def show(m):
    it = m.get("params", {}).get("item", {})
    if m["method"] == "item/completed" and it.get("type") == "commandExecution":
        print(f"  命令 {it['command']!r:44} status={it['status']} exit={it.get('exitCode')}")
a.wait("turn/completed", show=show); a.close()
EOF

把客户端对 cp 的回答改为 {"acceptWithExecpolicyAmendment": {"execpolicy_amendment": ["cp"]}}，运行后查看 $CODEX_HOME/rules/default.rules，再用 codex execpolicy check 检查 cp a b。结果出乎意料吗？
查看参考答案
文件末尾被追加了一行 prefix_rule(pattern=["cp"], decision="allow")。但 check 的结果仍是 "decision":"prompt"：两条规则都匹配（prompt 与 allow），总决定取最严格的那个（Decision 枚举按 Allow < Prompt < Forbidden 排序）。所以“记住”只在没有更严格规则时生效——要真正放行，需要删掉我们手写的 prompt 规则。

小结
记住这几点


  1. 规则（execpolicy crate）：prefix_rule(pattern=[…], decision="allow"|"prompt"|"forbidden", justification=…)，按命令前缀匹配；还可写 match/not_match 作为自测样例。codex execpolicy check -r 文件 命令… 单独检验。
  2. 决策 → 要求（core/src/exec_policy.rs）：Forbidden → 直接拒绝（附理由）；Prompt → 需要审批，但若审批策略不允许询问（如 never）就变成拒绝；Allow → 跳过审批，并且只有当命令的每一段都被规则显式允许时才绕过沙箱。
  3. 没有规则匹配时：交给审批策略与内置的安全命令启发式；on-request 下普通命令在沙箱中直接运行，模型可通过 sandbox_permissions: "require_escalated" + justification 主动请求无沙箱执行。
  4. 编排器（tools/orchestrator.rs）：审批（跳过 / 缓存 / 询问）→ 选择沙箱 → 运行 → 若被沙箱拒绝且策略允许，询问后以无沙箱重试。
  5. 前端看到的审批：app-server 发送服务器→客户端请求 item/commandExecution/requestApproval；客户端回答 accept、acceptForSession、acceptWithExecpolicyAmendment（记住为规则）、decline（继续 turn）或 cancel（同时中断 turn）。
  6. 模型看到的结果：被拒绝时工具输出 “exec_command failed: … Rejected("rejected by user")” 或规则给出的理由，turn 继续，由模型决定下一步。
