压缩与 /compact

上下文窗口是有限的。pi 在接近上限时让模型写摘要并替换旧消息（第 14 课）；Codex 也是如此，但多了两条路径：支持远程压缩的 provider（OpenAI）走服务端压缩，其余 provider 走本地压缩——把 prompt.md 作为一条用户消息追加到历史末尾，请模型写“交接摘要”，再用“初始上下文 + 用户消息 + 摘要”重建历史。本课把阈值调到 1500 token，观察一次真实的回合中压缩。约 40 分钟。

pub fn auto_compact_token_limit(&self) -> Option<i64> {
    let context_limit = self
        .resolved_context_window()
        .map(|context_window| (context_window * 9) / 10);
    let config_limit = self.auto_compact_token_limit;
    if let Some(context_limit) = context_limit {
        return Some(
            config_limit.map_or(context_limit, |limit| std::cmp::min(limit, context_limit)),
        );
    }
    config_limit
}

挑战
无限压缩
去掉 s_compact.py 中对 “Another language model” 的判断再运行。为什么会一直压缩下去？真实环境中什么能阻止这种情况？
查看参考答案
去掉后，压缩完成的新历史中没有工具输出，剧本又从 ls 开始；而 mock 报告的 input_tokens 是 1000×n，随请求数单调增长，永远超过 1500，于是每两次请求就压缩一次——这正是作者第一次运行时看到的 500 多个请求（用 timeout 中止）。
真实环境中，压缩后的历史明显变短，服务端报告的 token 数随之下降；另外摘要会告诉模型“已经执行过 ls”，模型不会重来。教训：压缩依赖于“摘要足够好”与“token 统计真实”两个前提。

小结
记住这几点


  1. 触发阈值：ModelInfo::auto_compact_token_limit（protocol/src/openai_models.rs）= min(配置项 model_auto_compact_token_limit, 上下文窗口 × 90%)。
  2. 时机：回合前（PreTurn）、回合中（MidTurn，工具调用之间）、回合后（PostTurn）都会检查；实验中第 2 次工具调用之后触发了回合中压缩。换到更小窗口的模型时也会压缩（CompactionReason::ModelDownshift）。
  3. 路径选择（session/turn.rs）：provider.capabilities().remote_compaction 为 V2 时走 compact_remote_v2；Unsupported（如本课的 mock）时走本地 compact.rs::run_inline_auto_compact_task。
  4. 本地压缩请求：历史 + 一条 user 消息 prompts/templates/compact/prompt.md（“CONTEXT CHECKPOINT COMPACTION…”），工具列表为空（实验 req03 工具 0 个）。
  5. 重建历史（build_compacted_history）：初始上下文 + 最近的用户消息（总量上限 COMPACT_USER_MESSAGE_MAX_TOKENS = 20 000）+ 以 summary_prefix.md 开头的摘要。工具调用与输出不再保留（实验 req04 只剩 5 条）。
  6. 持久化：rollout 写入一行 compacted，恢复时据此直接还原压缩后的历史。
  7. 手动：TUI 的 /compact（tui/src/chatwidget/slash_dispatch.rs），app-server 的 thread/compact/start。
