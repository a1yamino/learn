毕业项目：在 Codex 上搭一个可审计的修复流程

pi 的毕业项目用 SDK 写了一个迷你编码 agent（第 20 课）。Codex 的内核已经完整，我们要做的是在它之上搭流程：用 app-server 协议（第 23 课）启动一个线程，沙箱为 workspace-write、审批为 on-request（第 11–13 课），让模型跑测试、打补丁（第 10 课）、再验证；所有越权请求都交给我们自己的审批策略——只放行白名单；每个条目与每次审批决定都写进 audit.jsonl。整个流程不到 60 行 Python，却用到了本课程的大部分机制。约 60 分钟。

01
剧本：测试 → 补丁 → 测试 → 越权推送。
cat > codex/scratch/s_fix.py <<'EOF'
# 剧本：跑测试（失败）→ 打补丁 → 再跑（通过）→ 申请越权 git push → 总结
FIX = """*** Begin Patch
*** Update File: calc.py
@@ def mean(xs):
-    return sum(xs) / len(xs)
+    return sum(xs) / len(xs) if xs else 0.0
*** End Patch
"""
def reply(n, body):
    last = body["input"][-1]
    if n > 1: print(f"[mock] req{n:02d} 上一步输出：{str(last.get('output'))[-70:]!r}", flush=True)
    if n == 1: return [msg("先跑测试"), call("exec_command", {"cmd": "python3 -m unittest -q 2>&1 | tail -3"}, "t1")]
    if n == 2: return [{"type": "custom_tool_call", "name": "apply_patch", "call_id": "p1", "input": FIX}]
    if n == 3: return [call("exec_command", {"cmd": "python3 -m unittest -q 2>&1 | tail -1"}, "t2")]
    if n == 4: return [call("exec_command", {"cmd": "git push origin main", "sandbox_permissions": "require_escalated",
                                             "justification": "推送修复"}, "g1")]
    return [msg("已修复 mean([]) 的除零错误，测试通过；推送被拒绝，留给人工处理。")]
EOF
02
可审计的修复流程。
cat > codex/scratch/fixflow.py <<'EOF'
# fixflow.py：一个可审计的修复流程（app-server 客户端）
#  - 沙箱 workspace-write + 审批 on-request：越权操作必须经过我们
#  - 审批策略：只放行白名单前缀的命令，其余一律拒绝
#  - 审计：每个完成的条目、每次审批决定都追加到 audit.jsonl
import json, os, re, shlex, sys, subprocess; sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from apc import AppServer, text
ALLOW = ("python3 -m unittest",)
audit = open("audit.jsonl", "a")
def log(kind, **kw): audit.write(json.dumps({"kind": kind, **kw}, ensure_ascii=False) + "\n"); audit.flush()

a = AppServer(cwd=os.getcwd())
def on_request(method, params):
    cmd = params.get("command") or ""
    m = re.match(r"^\S*bash -lc (.*)$", cmd)          # 审批里的命令带着 shell 包装：/bin/bash -lc '…'
    inner = shlex.split(m.group(1))[0] if m else cmd
    ok = inner.startswith(ALLOW)
    decision = "accept" if ok else "decline"
    log("approval", method=method, command=inner, reason=params.get("reason"), decision=decision)
    print(f"  审批 {inner!r} 理由={params.get('reason')!r} → {decision}")
    return {"decision": decision}
a.on_request = on_request
a.request("initialize", {"clientInfo": {"name": "fixflow", "title": None, "version": "0"}}); a.notify("initialized")
tid = a.request("thread/start", {"cwd": os.getcwd(), "approvalPolicy": "on-request", "sandbox": "workspace-write"})["thread"]["id"]
a.request("turn/start", {"threadId": tid, "input": text("修复失败的测试")})
def show(m):
    if m["method"] != "item/completed": return
    it = m["params"]["item"]; t = it["type"]
    if t == "commandExecution":
        log("command", command=it["command"], exit=it.get("exitCode"), status=it["status"])
        print(f"  命令 {it['command'][:48]!r} status={it['status']} exit={it.get('exitCode')}")
    elif t == "fileChange":
        log("patch", files=[c["path"] for c in it["changes"]], status=it["status"])
        print(f"  补丁 {[os.path.basename(c['path']) for c in it['changes']]} status={it['status']}")
    elif t == "agentMessage":
        log("message", text=it["text"]); print(f"  消息 {it['text']}")
a.wait("turn/completed", show=show); a.close()
print("== 审计摘要", dict(__import__("collections").Counter(json.loads(l)["kind"] for l in open("audit.jsonl"))))
print(subprocess.run(["git", "diff", "--stat"], capture_output=True, text=True).stdout.rstrip())
EOF

挑战
跑到全绿为止
把 fixflow.py 改成：不发 turn/start，而是 thread/goal/set（objective=“让 python3 -m unittest 全部通过”），等待目标变为 complete 或 budgetLimited；剧本在测试通过后调用 update_goal(complete)。审计里还需要记录什么？
查看参考答案
流程：tid = thread/start(...) → thread/goal/set {threadId, objective, origin:"user", tokenBudget:20000} → 循环 wait("thread/goal/updated") 直到 status 不是 active（第 20 课的 l20.py）。剧本在看到 “OK” 的工具输出后返回 call("update_goal", {"status": "complete"})。审计中应额外记录每个 turn/started（它们没有用户输入、由 goal 触发）与每次 thread/goal/updated 的状态和 tokensUsed，这样复盘时能区分“人发起的回合”和“自动续跑的回合”，也能看出预算消耗。

小结
记住这几点


  1. 边界由内核保证：沙箱内的命令（跑测试）与工作区内的补丁不需要审批，直接执行；需要越权（sandbox_permissions: "require_escalated"）的 git push 触发一次服务器→客户端的审批请求。
  2. 策略由我们决定：on_request 去掉 /bin/bash -lc 包装后按前缀白名单判断——这一点很重要：审批里看到的是包装后的命令，直接 startswith 会全部失败。
  3. 拒绝不是失败：被拒绝的命令以 status=declined 结束，模型收到 “rejected by user” 并据此调整，最终总结里如实写出“推送被拒绝，留给人工处理”。
  4. 审计：只依赖 app-server 的 item/completed 通知与审批请求本身，不需要解析日志；rollout 文件（第 15 课）是另一份完整记录，可用于复盘。
  5. 可扩展：把白名单换成 execpolicy 规则（第 13 课）、加一个 PreToolUse 钩子（第 21 课）、用 thread/goal/set 让它跑到测试全绿为止（第 20 课）、用 --output-schema 输出机器可读的结论（第 23 课）。
