apply_patch：补丁格式与解析

pi 的 edit 工具做“精确文本替换”（oldText → newText），再加一点模糊匹配。Codex 让模型写一种专门设计的补丁语言：*** Begin Patch … *** End Patch，一个补丁里可以新增、删除、修改、移动多个文件。在 gpt-5.5 上它是一个 custom（自由格式）工具，语法用 Lark 文法约束模型输出，补丁原文不必塞进 JSON 字符串。本课在真实 codex 中应用三个补丁：新增、修改并删除、以及一个对不上的补丁。约 45 分钟。

读代码


codex-rs/apply-patch/src/parser.rs  L1–24 ↗
//! This module is responsible for parsing & validating a patch into a list of "hunks".
//! (It does not attempt to actually check that the patch can be applied to the filesystem.)
//!
//! The official Lark grammar for the apply-patch format is:
//!
//! start: begin_patch environment_id? hunk+ end_patch
//! begin_patch: "*** Begin Patch" LF
//! environment_id: "*** Environment ID: " filename LF
//! end_patch: "*** End Patch" LF?
//!
//! hunk: add_hunk | delete_hunk | update_hunk
//! add_hunk: "*** Add File: " filename LF add_line+
//! delete_hunk: "*** Delete File: " filename LF
//! update_hunk: "*** Update File: " filename LF change_move? change?
//! filename: /(.+)/
//! add_line: "+" /(.+)/ LF -> line
//!
//! change_move: "*** Move to: " filename LF
//! change: (change_context | change_line)+ eof_line?
//! change_context: ("@@" | "@@ " /(.+)/) LF
//! change_line: ("+" | "-" | " ") /(.+)/ LF
//! eof_line: "*** End of File" LF
//!
//! The parser below is a little more lenient than the explicit spec and allows for
逐级放宽的匹配：

/// Returns the starting index of the match or `None` if not found. Matches are attempted with
/// decreasing strictness: exact match, then ignoring trailing whitespace, then ignoring leading
/// and trailing whitespace. When `eof` is true, we first try starting at the end-of-file (so that
/// patterns intended to match file endings are applied at the end), and fall back to searching
/// from `start` if needed.

// Exact match first.
for i in search_start..=lines.len().saturating_sub(pattern.len()) {
    if lines[i..i + pattern.len()] == *pattern {

练习使用第 1 课的 mock.py（假的 Responses API 服务器）和 run.sh（以临时 CODEX_HOME 启动它并运行 codex exec）。剧本文件定义 reply(n, body)，返回第 n 次请求的输出项；每次请求的完整 JSON 保存在 $CODEX_HOME/requests/。 自由格式工具调用的输出项类型是 custom_tool_call，字段 input 是补丁原文。


01
三个补丁。
cat > codex/scratch/s_patch.py <<'EOF'
# 剧本：apply_patch（自由格式工具）新增、修改、删除文件，再故意给一个对不上的补丁
def patch(cid, text):
    return {"type": "custom_tool_call", "name": "apply_patch", "call_id": cid, "input": text}
P1 = """*** Begin Patch
*** Add File: greet.py
+def greet(name):
+    return "hello " + name
*** Add File: old.txt
+obsolete
*** End Patch
"""
P2 = """*** Begin Patch
*** Update File: greet.py
@@ def greet(name):
-    return "hello " + name
+    return f"你好，{name}！"
*** Delete File: old.txt
*** End Patch
"""
P3 = """*** Begin Patch
*** Update File: greet.py
@@
-    return "this line does not exist"
+    return None
*** End Patch
"""
def reply(n, body):
    if n <= 3: return [patch(f"p{n}", [P1, P2, P3][n - 1])]
    return [msg("完成")]
EOF

小结
记住这几点


  1. 文法（apply-patch/src/parser.rs 顶部注释，core/assets/tools/apply_patch.lark）：hunk 分为 Add File（全部为 + 行）、Delete File、Update File（可带 Move to，用 @@ 上下文 定位，+ - 空格 三种行，可选 End of File）。
  2. 定位（seek_sequence.rs）：在文件中查找要替换的旧行，按严格程度递减尝试：完全相等 → 忽略行尾空白 → 忽略首尾空白（还有 Unicode 标点规范化）。@@ def greet(name): 这样的上下文行先把搜索起点移到该行。
  3. 先验证再写入：找不到旧行就整体失败：“apply_patch verification failed: Failed to find expected lines …”，文件保持不变，错误回给模型重试。
  4. 结果：成功时输出 “Success. Updated the following files:” 与 A/M/D 列表，并报告退出码与耗时。
  5. 与沙箱、审批的关系：apply_patch 也要通过安全检查——默认 read-only 沙箱、审批策略 never 时得到 “patch rejected: writing is blocked by read-only sandbox; rejected by user approval settings”。--sandbox workspace-write 允许写工作目录。
  6. 独占执行：apply_patch 不支持并行（第 7 课），修改文件时不会与其他工具交错；修改还会被 turn_diff_tracker 记录，生成整个 turn 的 diff。
