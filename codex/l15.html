rollout：恢复与分叉

pi 把会话存成一棵 JSONL 树，分支就是树上的另一条路径（第 13 课）。Codex 的做法更“线性”：每个线程一个 rollout 文件（$CODEX_HOME/sessions/年/月/日/rollout-时间-线程id.jsonl），追加写入；resume 读回它并在同一线程继续，fork 则把历史复制进一个新线程、生成新文件。可查询的元数据（标题、时间、cwd……）另存于 SQLite。本课用一个“报告自己看到了哪些用户消息”的剧本，验证恢复与分叉后的历史。约 40 分钟。

codex-rs/thread-store/README.md  L1–30 ↗
# Thread Store

`codex-thread-store` is the storage boundary for Codex threads. It defines the
`ThreadStore` trait plus local and in-memory implementations. Other storage
implementations may live outside this repository.

## Responsibilities

- `ThreadStore::append_items` is the raw canonical history append API. It does
  not infer metadata from item contents.
- `ThreadStore::update_thread_metadata` is the only thread metadata write API.
  It accepts a single literal metadata patch shape, regardless of whether the
  caller is applying a user/API mutation or facts derived above the store from
  appended history.
- `LiveThread` is the preferred API for active session persistence. It owns a
  per-thread metadata sync helper, applies the rollout persistence policy,
  appends canonical history, and then sends metadata patches through
  `ThreadStore::update_thread_metadata`.
- `ThreadManager` routes metadata mutations for loaded and cold threads through
  one entrypoint. Loaded threads use their `LiveThread`; cold threads go
  directly to the store.
- `LocalThreadStore` persists history through `codex-rollout` JSONL files and
  persists queryable metadata through the SQLite state database when available.
  Local explicit metadata mutations also maintain JSONL/name-index compatibility
  so reading old or SQLite-less local storage keeps working.
- `RolloutRecorder` is the local JSONL writer. It writes already-canonical
  items for `ThreadStore::append_items`; it no longer decides metadata updates
  for live thread-store appends.
- `core/session` creates or resumes `LiveThread` handles and does not need to
  know whether persistence is backed by local files or another store.

# 剧本：回显“模型看到了几条用户消息”，便于观察恢复/分叉后历史是否保留
def reply(n, body):
    users = [i["content"][0]["text"] for i in body["input"] if i.get("role") == "user"
             and not i["content"][0]["text"].startswith(("<", "#"))]
    return [msg(f"我看到的用户消息：{' / '.join(users)}")]
EOF

#!/bin/bash
# rollout：会话写成 JSONL；resume 继续同一线程，fork 复制出新线程
S=$(pwd); export CODEX_HOME=$(mktemp -d); cd $(mktemp -d)

echo "   rollout 文件：sessions/…/$(basename $F)"
echo "   各行类型：$(python3 -c "import json,sys,collections;print(dict(collections.Counter(json.loads(l)['type'] for l in open(sys.argv[1]))))" $F)"

echo "== rollout 文件数：$(ls $CODEX_HOME/sessions/*/*/*/*.jsonl | wc -l)"

import json, sys
for l in open(sys.argv[1]):
    r = json.loads(l)
    if r["type"] != "response_item": continue
    p = r["payload"]; t = p.get("type"); role = p.get("role", "")
    text = "".join(c.get("text", "") for c in p.get("content", []) or [])
    print(t, role, text[:40].replace("\n", " "))

小结
记住这几点


  1. RolloutItem（history/src/lib.rs）：每行一个条目——SessionMeta（线程元信息）、ResponseItem（发给模型的历史）、TurnContext（每个 turn 的设置）、EventMsg（给前端的事件）、Compacted（压缩结果）、WorldState、TokenUsageRecord 等。实验中一个最简单的 turn 写出 1+6+4+1+1+1 行。
  2. 两种数据：ResponseItem/Compacted 用来重建模型看到的历史；EventMsg 用来重放界面。恢复时据此重建上下文与 UI。
  3. thread store（thread-store/README.md）：ThreadStore 是存储边界；本地实现用 rollout JSONL 存历史、SQLite 存可查询元数据；LiveThread 负责活动会话的持久化。
  4. resume：codex exec resume --last 或按 id/名字；交互模式 codex resume 提供选择器。实验中第二句时模型看到了“第一句 / 第二句”。
  5. fork：codex exec fork <id>、交互式 codex fork、TUI 的 /fork；内核 ThreadManager::fork_thread_from_history 以快照历史启动新线程。分叉后 --last 指向最新的那个线程（实验第 4 步继续的是分叉线）。
  6. 对比 pi：pi 在同一文件里用 parentId 形成树，可在树上任意跳转；Codex 用“复制成新线程”实现分支，每个线程的文件保持线性。
