Kafka Connect

把数据库、文件、搜索引擎、对象存储和 Kafka 连起来，是很多团队最常写、也最容易写错的代码。Kafka Connect 是一个专门做这件事的框架：用配置而不是代码描述数据管道，由框架负责分布式运行、偏移量管理、重试和扩缩容。本课讲 Source 与 Sink、Worker 与 Task、分布式模式的内部主题、转换器与单消息转换（SMT），以及错误处理和死信队列。约 60 分钟。

在你的电脑上练习
在单节点 kafka 容器里用自带的文件连接器跑一个独立模式的管道。


01
准备配置：把文件连接器加入插件路径。
cp config/connect-standalone.properties /tmp/w.properties
echo "plugin.path=/opt/kafka/libs/connect-file-4.4.0.jar" >> /tmp/w.properties
printf "a\nb\nc\n" > /tmp/in.txt
（无输出）
02
Source：读取文件写入主题 lines。
cat > /tmp/src.properties <<'X'
name=file-src
connector.class=FileStreamSource
tasks.max=1
file=/tmp/in.txt
topic=lines
X
（无输出）
03
Sink：从 lines 读取写入另一个文件。
cat > /tmp/sink.properties <<'X'
name=file-sink
connector.class=FileStreamSink
tasks.max=1
topics=lines
file=/tmp/out.txt
X
（无输出）
04
启动独立模式 Worker（后台）。
bin/connect-standalone.sh /tmp/w.properties /tmp/src.properties /tmp/sink.properties > /tmp/connect.log 2>&1 &
sleep 15; cat /tmp/out.txt
a
b
c

挑战
设计一个 MySQL → Kafka → Elasticsearch 的管道
把 MySQL 的 products 表同步到 Elasticsearch，用于搜索：每秒约 500 次变更，要求删除也同步，ES 短暂不可用时不丢数据，个别字段格式异常的记录不能卡住整个管道。写出两个连接器的关键配置和理由（Connect 集群、转换器、主题、SMT、错误处理）。
查看参考答案
  • Connect 集群：分布式模式 3 个 Worker，内部主题副本因子 3，offset.storage.topic 等使用 compact。
  • Source：Debezium MySQL 连接器读 binlog（而不是 JDBC 轮询，才能捕获删除和每次变更）；tasks.max=1（binlog 单线程读取）；输出主题 db.shop.products，key 为主键；使用 Avro 转换器 + Schema Registry；SMT ExtractNewRecordState（Debezium 提供）把变更信封展开为新行，删除生成墓碑（delete.handling.mode + drop.tombstones=false）。主题可以开启压缩，方便重建索引。
  • Sink：Elasticsearch Sink，key.ignore=false（主键作为文档 ID，写入是 upsert，重复写入幂等），behavior.on.null.values=delete（墓碑 → 删除文档）；tasks.max 与分区数一致（如 6）。
  • 错误处理：errors.tolerance=all，errors.deadletterqueue.topic.name=dlq.products-es，开启 context headers，监控 DLQ 增长；errors.retry.timeout=600000 让 ES 短暂不可用时持续重试而不是失败；Sink 只有在写入成功后才提交偏移量，所以 ES 恢复后从未确认的位置继续。

小结
记住这几点


  1. Connector 是一个插件：Source 从外部系统读出数据写入 Kafka（如 Debezium 读 MySQL binlog、JDBC Source），Sink 从 Kafka 读出写到外部系统（如 Elasticsearch、S3、JDBC Sink）。Connector 把工作拆成多个 Task（tasks.max），由 Worker 进程运行。
  2. 分布式模式：多个 Worker 使用相同的 group.id 组成集群，通过三个内部主题协作：config.storage.topic（连接器配置）、offset.storage.topic（Source 读到外部系统的哪里）、status.storage.topic（运行状态）。Worker 增减或宕机时，Task 在 Worker 之间重新分配（增量协作再平衡）。管理通过 REST 接口（默认 8083 端口）。独立模式只有一个进程，偏移量存在本地文件，适合开发和边缘场景。
  3. Sink 连接器本质上是一个消费者组（connect-<连接器名>），偏移量存在 __consumer_offsets；Source 的“外部偏移量”（binlog 位置、文件行号、自增 ID）存在 offset 主题。
  4. 转换器（Converter，key.converter/value.converter）在 Connect 的内部数据格式与 Kafka 字节之间转换：JsonConverter（schemas.enable 决定是否附带 schema）、StringConverter、Avro/Protobuf 转换器（配合 Schema Registry）。
  5. 单消息转换（SMT）：在 Source 写入前或 Sink 写出前对每条记录做轻量修改，如 InsertField、ReplaceField、MaskField、TimestampRouter、RegexRouter、ExtractField；配合谓词只对部分记录生效。复杂的处理（关联、聚合）应该放到 Kafka Streams 或 Flink 中。
  6. 错误处理：errors.tolerance=all 跳过无法转换或处理的记录，errors.deadletterqueue.topic.name 把它们写入死信主题（只适用于 Sink），errors.deadletterqueue.context.headers.enable=true 在 header 中记录错误原因，errors.log.enable 记录日志；errors.retry.timeout 控制可重试错误的重试时长。
