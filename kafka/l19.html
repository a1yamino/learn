05
在你的电脑上练习
启动一个带 SCRAM 认证和 ACL 的单节点 Kafka。演示中 Broker 内部监听器使用 PLAINTEXT 且只在容器内可达，生产环境不要这样做。


01
写 Broker 配置。
cat > s.properties <<'X'
node.id=1
process.roles=broker,controller
listeners=INTERNAL://localhost:19092,CONTROLLER://localhost:9093,SASL://0.0.0.0:9192
advertised.listeners=INTERNAL://localhost:19092,SASL://localhost:9192
listener.security.protocol.map=INTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT,SASL:SASL_PLAINTEXT
inter.broker.listener.name=INTERNAL
controller.listener.names=CONTROLLER
controller.quorum.bootstrap.servers=localhost:9093
sasl.enabled.mechanisms=SCRAM-SHA-512
listener.name.sasl.scram-sha-512.sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required;
authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer
super.users=User:ANONYMOUS
log.dirs=/tmp/ks
offsets.topic.replication.factor=1
transaction.state.log.replication.factor=1
X

挑战
为多团队共享集群设计安全方案
一个 Kafka 集群给三个团队使用：订单团队（生产 orders.*，使用事务）、风控团队（消费 orders.*，组 risk-*）、数据平台（用 Connect 把所有主题导入数据湖，夜间批量重读）。公司已有 OIDC 身份平台。写出监听器与认证方案、每个团队的 ACL、配额，以及凭据如何轮换。
查看参考答案
  • 监听器：CLIENT 使用 SASL_SSL + OAUTHBEARER（对接公司 OIDC，服务账号获取短期令牌，自动刷新）；INTERNAL（Broker 间）和 CONTROLLER 使用双向 TLS，证书由内部 CA 签发；所有监听器都加密。allow.everyone.if.no.acl.found=false，super.users 只包含 Broker 和运维账号。
  • 订单团队（User:svc-orders）：--producer --topic orders. --resource-pattern-type prefixed，加上 --transactional-id orders- --resource-pattern-type prefixed 的 Write/Describe；不授予 Read。
  • 风控团队（User:svc-risk）：--consumer --topic orders. --group risk- --resource-pattern-type prefixed。
  • 数据平台（User:svc-connect）：所有业务主题的 Read 与 Describe、组 connect- 前缀的 Read；Connect 内部主题（connect-*）的读写与创建。
  • 配额：svc-connect 的 consumer_byte_rate 限制为如 100 MB/s，防止夜间重读挤占实时流量；对未知 client.id 设置默认配额。
  • 轮换：OAUTHBEARER 令牌本身短期有效，轮换客户端密钥在身份平台完成；TLS 证书提前在 truststore 中加入新 CA，滚动更新 keystore（Broker 支持动态更新 ssl.keystore.location）。SCRAM 同一用户、同一机制只能保留一套凭据；直接更新会替换旧密码。无中断轮换可创建临时新用户名，复制必要 ACL/配额，切换并确认全部客户端使用新身份后再删除旧用户凭据。

小结
记住这几点


  1. 监听器：一个 Broker 可以有多个监听器（listeners），每个映射到一种安全协议（listener.security.protocol.map）：PLAINTEXT、SSL、SASL_PLAINTEXT、SASL_SSL。常见布局：客户端用 SASL_SSL，Broker 间（inter.broker.listener.name）和控制器（controller.listener.names）用单独的监听器，同样加密和认证。
  2. TLS：Broker 配置 keystore（自己的证书和私钥）和 truststore（信任的 CA）。客户端设置 security.protocol=SSL 和 truststore，默认校验主机名（ssl.endpoint.identification.algorithm=https）。双向 TLS（ssl.client.auth=required）用客户端证书认证，主体名来自证书 DN（可用 ssl.principal.mapping.rules 映射）。
  3. SASL 机制：SCRAM-SHA-256/512（用户名密码，凭据以加盐哈希存在 KRaft 元数据中，用 kafka-configs.sh 管理）；OAUTHBEARER（对接 OIDC 身份提供方，令牌短期有效）；GSSAPI（Kerberos）；PLAIN（明文密码，只能配合 TLS，且需要自定义回调才不必把密码写在配置里）。SASL_PLAINTEXT 不加密，生产中应使用 SASL_SSL。
  4. 授权：KRaft 使用 authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer，ACL 存在元数据日志中。一条 ACL：主体（User:alice）、允许/拒绝、操作（Read、Write、Create、Describe、Alter…）、资源类型（Topic、Group、Cluster、TransactionalId）、资源名与匹配方式（LITERAL 或 PREFIXED）、来源主机。拒绝优先于允许；默认没有 ACL 就拒绝（allow.everyone.if.no.acl.found=false）；super.users 不受限制。
  5. 常用组合：生产者需要主题的 Write（和 Describe），非事务幂等生产者需要 Cluster 的 IdempotentWrite；事务生产者需要其 TransactionalId 的 Write。不能把普通幂等也写成必须配置事务 ID；消费者需要主题的 Read 和组的 Read。kafka-acls.sh --producer、--consumer 可以一次添加这些规则。按服务前缀授权（--resource-pattern-type prefixed --topic orders.）便于管理。
  6. 配额：按用户或 client.id 限制生产/消费字节速率（producer_byte_rate、consumer_byte_rate）和请求时间占比（request_percentage），超出时 Broker 延迟响应（限流）而不是报错。用于防止一个离线任务或失控的客户端拖垮整个集群。
