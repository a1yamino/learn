事务与精确一次

“读一条消息、处理、写出结果、提交偏移量”这四步如果不能原子完成，崩溃后就会重复或丢失。Kafka 事务让一个生产者对多个分区的写入和消费偏移量的提交要么全部可见、要么全部不可见。本课讲 transactional.id 与僵尸隔离、事务协调器的两阶段提交、控制标记与 LSO、read_committed 的读取方式，以及精确一次的适用边界。约 70 分钟。

02
用 Python 写一个中止的事务和一个提交的事务（宿主机，pip install confluent-kafka）。
python3 - <<'X'
from confluent_kafka import Producer
p=Producer({'bootstrap.servers':'localhost:9092','transactional.id':'demo-1'})
p.init_transactions()
p.begin_transaction(); p.produce('tx-out',b'aborted-1')
p.flush()  # 确保记录已送到 Broker；abort_transaction 会清理仍排在客户端的消息
p.abort_transaction()
p.begin_transaction(); p.produce('tx-out',b'committed-1'); p.commit_transaction()
X

挑战
判断哪些流程能做到精确一次
对下面四个流程，判断仅用 Kafka 事务能否做到精确一次，不能的话怎么办：① 从 clicks 读取，按用户计数，结果写入 click-counts；② 从 orders 读取，调用第三方支付接口扣款；③ 从 orders 读取，写入 Elasticsearch 索引；④ 订单服务在 MySQL 中创建订单，同时向 orders 发送事件。
查看参考答案
  1. 能。Kafka → Kafka，使用 Kafka Streams exactly_once_v2（状态存储的变更日志也在同一事务中），或手写事务：输出与输入偏移量一起提交。下游消费者使用 read_committed。
  2. 不能。扣款是外部副作用，事务中止后无法撤销。用支付接口的幂等键（如订单号）保证重复调用只扣一次，并以至少一次语义消费。
  3. 不能直接做到，但可以“效果上”精确一次：用事件中的唯一 ID 作为文档 ID，写入是覆盖（upsert），重复写入结果相同；按至少一次消费即可。Kafka Connect 的 Elasticsearch Sink 就是这样做的。
  4. 不能，因为 MySQL 事务和 Kafka 事务不是同一个。使用 Outbox 模式：在 MySQL 同一事务中写入 outbox 表，再由 Debezium 等 CDC 发送到 Kafka（第 21 课）；消费者按事件 ID 幂等。

小结
记住这几点


  1. 事务性生产者配置 transactional.id（每个逻辑实例固定、唯一，例如 order-enricher-3）。流程：initTransactions() → 循环 { beginTransaction() → send()… → sendOffsetsToTransaction(offsets, consumer.groupMetadata()) → commitTransaction() }，出错时 abortTransaction()。
  2. 事务协调器是某个 Broker（由 transactional.id 哈希到 __transaction_state 的分区决定）。生产者第一次向某分区写入前，先在协调器登记该分区；提交时协调器写入 PREPARE_COMMIT，再向每个涉及的分区写入提交标记（控制记录），最后写入 COMPLETE_COMMIT。偏移量提交也是写入 __consumer_offsets 的事务性消息。
  3. 僵尸隔离：initTransactions() 会让该 transactional.id 的生产者 epoch 加 1，并中止它未完成的事务。旧实例（例如网络分区后仍在运行的“僵尸”）用旧 epoch 写入会被拒绝（ProducerFenced）。Kafka 4.0 起的事务协议 v2（KIP-890）在每个事务都提升 epoch，并由 Broker 校验，堵住了更多的边界情况。
  4. 消费者 isolation.level=read_committed 只返回已提交事务的消息，跳过中止的；它最多读到 LSO（last stable offset，最早的未完成事务之前的位置）。所以一个长时间未完成的事务会阻塞 read_committed 消费者；transaction.timeout.ms（默认 60 秒）后协调器主动中止。默认的 read_uncommitted 能看到所有消息（包括后来被中止的）。
  5. 精确一次（EOS）的范围是 “从 Kafka 读 → 处理 → 写回 Kafka”：输入偏移量和输出消息在同一事务中提交。Kafka Streams 设置 processing.guarantee=exactly_once_v2 即可自动完成。处理中的外部副作用（调用 HTTP 接口、写数据库、发邮件）不在事务内，仍需要幂等或 Outbox 等手段。
  6. 代价：每个事务额外几次请求和标记写入，事务越小开销越明显，一般每 100 ms–1 s 或每几千条提交一次；读端延迟增加到一个事务周期。不需要跨分区原子性、只需要不重复写入时，幂等生产者就够了。
