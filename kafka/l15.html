Kafka Streams：拓扑与无状态处理

Kafka Streams 是一个 Java 库，用来编写“从 Kafka 读、处理、写回 Kafka”的应用，不需要单独的处理集群。本课讲流处理的基本模型：拓扑由源、处理器和汇组成；KStream 和 KTable 分别表示事件流和变更流；filter、map、flatMap、split 等无状态操作；改变 key 为什么会触发重分区；以及应用如何按分区拆成任务并行运行。约 60 分钟。

挑战
写一个订单分流应用
输入主题 orders（key 为订单号，value 为 JSON：{user_id, amount, country, status}）。要求：丢弃 status=test 的订单；给每条订单增加 amount_cny（按固定汇率）；金额 ≥ 10000 的写入 orders-large，海外订单写入 orders-intl，其余写入 orders-normal；另外输出一个以 user_id 为 key 的流 orders-by-user 供后续按用户统计。用 DSL 写出拓扑，并指出哪一步会产生重分区以及如何减少它的代价。
查看参考答案
KStream<String, Order> orders = builder.stream("orders", Consumed.with(Serdes.String(), orderSerde));
KStream<String, Order> clean = orders
    .filter((id, o) -> !"test".equals(o.status))
    .mapValues(o -> o.withAmountCny(o.amount * rate(o.currency)));   // 不改 key

clean.split(Named.as("route-"))
    .branch((id, o) -> o.amountCny >= 10000, Branched.withConsumer(s -> s.to("orders-large")))
    .branch((id, o) -> !"CN".equals(o.country), Branched.withConsumer(s -> s.to("orders-intl")))
    .defaultBranch(Branched.withConsumer(s -> s.to("orders-normal")));

clean.selectKey((id, o) -> o.userId).to("orders-by-user");
split 的分支按顺序匹配，一条订单只进入第一个满足条件的分支。selectKey 改变了 key，但这里直接 to() 写出，写出时按新 key 分区，不会产生内部重分区主题；只有在改 key 之后紧接 groupByKey/join 才会自动重分区。如果后续的按用户统计在同一个应用中进行，可以直接对 orders-by-user 做聚合（把它当作显式的重分区主题，便于控制分区数和保留时间），或使用 repartition(Repartitioned.numberOfPartitions(12))。

小结
记住这几点


  1. 一个 Streams 应用由 application.id 标识：它同时是消费者组 ID、内部主题的前缀和状态目录名。应用就是普通的 Java 进程，可以部署多个实例，实例之间通过消费者组协议分担工作。
  2. 拓扑（Topology）：源处理器从主题读取，中间处理器逐条处理，汇处理器写入主题。用 DSL 编写：builder.stream("orders").filter(...).mapValues(...).to("big-orders")；topology.describe() 打印结构。
  3. KStream 是事件流：每条记录都是独立的事实（“用户 42 下了一单”）。KTable 是变更流：每条记录是某个 key 的最新值（“用户 42 的等级是金卡”），同 key 的新记录覆盖旧值，通常来自压缩主题。GlobalKTable 在每个实例上都有完整副本。
  4. 无状态操作：filter、map/mapValues、flatMap/flatMapValues、split().branch()（按条件分流）、merge、peek、selectKey。尽量用 mapValues 而不是 map：不改变 key 就不需要重分区。
  5. 重分区：selectKey/map 改变了 key 后，接下来若有按 key 的有状态操作（groupByKey、join），Streams 会自动写入一个内部的 -repartition 主题，再按新 key 读回，以保证相同 key 进入同一个任务。这会增加一次网络往返和存储，应尽量在源头就用对的 key。
  6. 并行：输入主题的每个分区对应一个任务（task），任务是并行的最小单位，分配给实例上的流线程（num.stream.threads）。最大并行度等于输入分区数。处理语义由 processing.guarantee 决定：默认 at_least_once，或 exactly_once_v2（第 11 课）。
