生产者：发送流程、分区器与批处理

挑战
为两种数据选择生产者参数
① 应用访问日志：每秒 20 万条、每条约 1 KB JSON、能容忍秒级延迟；② 支付指令：每秒 200 条、每条约 2 KB，端到端延迟要求 P99 < 50 ms。分别给出 linger.ms、batch.size、compression.type、buffer.memory 的建议和理由，并说明 key 怎么选。
查看参考答案
  • 访问日志：linger.ms=50–100，batch.size=256KB–1MB，compression.type=zstd（或 lz4 节省 CPU），buffer.memory=128MB 以上，防止 Broker 短暂变慢时阻塞应用线程。无 key（粘性分区，批次大、分布均匀）；如果下游需要按用户聚合再用用户 ID 作 key。
  • 支付指令：流量小，批次本来就凑不满，linger.ms 保持默认 5 或设为 0–1，避免为等批次增加延迟；batch.size 默认即可；compression.type=lz4 或 none（数据量小，收益不大）；buffer.memory 默认。key 用账户 ID 或支付单号，保证同一账户的指令有序；可靠性配置见下一课（acks=all、幂等）。

小结
记住这几点


  1. send(record) 在调用线程中完成：拦截器 → key/value 序列化 → 分区器选分区 → 追加到记录累加器（RecordAccumulator）中该分区的当前批次，然后立即返回一个 Future；真正的网络发送由后台 Sender 线程完成。
  2. 分区规则：指定了分区就用它；有 key 时用 murmur2(keyBytes) % 分区数；没有 key 时使用粘性分区：一直往同一个分区追加，直到当前批次满或被发送，再换分区（Kafka 3.3 起还会避开响应慢的 Broker）。这样无 key 消息也能凑成大批次。
  3. 批次在满足任一条件时可以发送：达到 batch.size（默认 16384 字节）；等待超过 linger.ms（Kafka 4.0 起默认 5 ms，之前为 0）。Sender 把发往同一个 Broker 的多个分区的批次合并成一个 ProduceRequest，每个连接最多 max.in.flight.requests.per.connection（默认 5）个未完成请求。
  4. 压缩（compression.type：none、gzip、snappy、lz4、zstd）按批次进行，批次越大压缩率越高。CPU 花在生产者上，Broker 通常原样存储，网络和磁盘都受益。日志类数据常用 lz4 或 zstd。
  5. 累加器总大小由 buffer.memory（默认 32 MB）限制；满了以后 send() 阻塞，最多 max.block.ms（默认 60 秒）后抛异常。单条消息上限 max.request.size（默认 1 MB），还要与 Broker/主题的 message.max.bytes 一致。
  6. 回调（或 Future）在收到 Broker 响应后触发，在 Sender 线程（I/O 线程）中执行，所以回调里不要做慢操作。flush() 立即发送所有批次并等待完成；close() 前会 flush。生产者是线程安全的，一个进程通常共用一个实例。
