事件溯源与 CQRS

把“发生过什么”作为唯一的事实来源，而当前状态只是事件的折叠结果——这就是事件溯源。Kafka 的日志天然适合存放事件，CQRS 则把写模型与读模型分开，各自优化。本课讲事件溯源的建模、用 Kafka 做事件存储的长处与局限、用 Streams 或消费者构建读模型（物化视图），以及重放、快照和事件演进。约 60 分钟。

挑战
为银行账户设计事件溯源
需求：开户、存款、取款（余额不能为负）、查询余额、按月出对账单、风控需要“过去 1 小时取款总额”。请设计：① 事件类型；② 主题与 key；③ 写端如何保证“余额不能为负”；④ 需要哪些读模型，各用什么存储；⑤ 某个取款事件金额写错了怎么办。
查看参考答案
  1. 事件：AccountOpened、MoneyDeposited、MoneyWithdrawn、WithdrawalRejected（可选，用于审计）。
  2. 主题 account-events，key = 账户 ID（同账户有序），retention.ms=-1，开启分层存储；分区数按吞吐预留（以后不能改 key 分布）。
  3. 写端：命令主题 account-commands（同样以账户 ID 为 key）→ Streams 应用，在状态存储中按账户保存余额，校验通过才输出 MoneyWithdrawn，否则输出拒绝事件；配合 exactly_once_v2，状态与输出原子一致。同一账户的命令在同一分区串行处理，不会并发透支。
  4. 读模型：余额查询 → KTable 物化 / Redis；月度对账单 → 写入 PostgreSQL 按月分区的表；风控 1 小时取款总额 → Streams 跳跃窗口聚合（第 16 课）。各自一个消费者组，可独立重建。
  5. 不修改历史：追加补偿事件 WithdrawalCorrected（或冲正 + 重新入账），读模型据此更新；审计保留完整轨迹。

小结
记住这几点


  1. 事件溯源：不存“账户余额 = 70”，而存 Opened(100)、Withdrawn(50)、Deposited(20)。当前状态 = 对事件按顺序做 fold。好处：完整审计、可以重建任意时间点的状态、可以为新需求从头计算新视图。
  2. CQRS（命令查询职责分离）：写端接受命令、校验业务规则、产生事件；读端订阅事件，构建为查询优化的视图（数据库表、搜索索引、缓存）。读写可以独立扩展，读模型是最终一致的。
  3. 用 Kafka 存事件：按聚合 ID 做 key，同一聚合的事件在同一分区内有序；主题设置 retention.ms=-1 永久保留（或配合分层存储降低成本）。读模型就是一个消费者组，新视图只需新建一个组并 --reset-offsets --to-earliest 重放。
  4. 局限：Kafka 不能按 key 高效读取某一个聚合的全部事件，也不支持“期望版本”的乐观并发写入。所以写端校验通常依赖本地状态：Streams 的状态存储（按 key 分区、changelog 备份），或者把事件同时存入数据库事件表（再 Outbox 到 Kafka）。
  5. 快照：事件很多时，从头 fold 很慢。定期保存状态快照（例如压缩主题 account-snapshots，key 为账户 ID），恢复时从快照加后续事件开始。Streams 的 KTable + changelog 本质上就是这个机制。
  6. 事件演进：事件永久保存，所以结构只能兼容地演进（第 13 课的 Schema 兼容性）；事件命名用过去时、描述业务事实（OrderShipped 而不是 UpdateOrder）；不要删除或修改历史事件，用补偿事件纠正。
