序列化与 Schema Registry

Kafka 只存字节，消息的格式完全由生产者和消费者约定。约定写在代码里时，一次字段改名就可能让所有下游崩溃。本课比较 JSON、Avro、Protobuf 的取舍，讲 Schema Registry 如何为每条消息附加 schema ID、如何按兼容性规则检查新版本，以及安全地演进 schema 的方法。约 60 分钟。

在你的电脑上练习
让 Schema Registry 共享 kafka 容器的网络，这样它能用 localhost:9092 连接 Kafka。


01
启动 Schema Registry。
docker run -d --name sr --network container:kafka -e SCHEMA_REGISTRY_HOST_NAME=sr -e SCHEMA_REGISTRY_LISTENERS=http://0.0.0.0:8081 -e SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS=localhost:9092 confluentinc/cp-schema-registry:latest
docker exec sr curl -s localhost:8081/subjects
[]
02
注册 v1。
docker exec sr curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" localhost:8081/subjects/orders-value/versions -d '{"schema":"{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"id\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"double\"}]}"}'
{"id":1}
03
检查一个兼容的变更（新增带默认值的字段）。
docker exec sr curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" localhost:8081/compatibility/subjects/orders-value/versions/latest -d '{"schema":"{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"id\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"double\"},{\"name\":\"currency\",\"type\":\"string\",\"default\":\"CNY\"}]}"}'
{"is_compatible":true}
04
检查一个不兼容的变更（amount 改成 string）。
docker exec sr curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" localhost:8081/compatibility/subjects/orders-value/versions/latest?verbose=true -d '{"schema":"{\"type\":\"record\",\"name\":\"Order\",\"fields\":[{\"name\":\"id\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"string\"}]}"}'
{"is_compatible":false,"messages":["{errorType:'TYPE_MISMATCH', description:'The type (path '/fields/1/type') of a field in the new schema does not match with the old schema' …}"]}

挑战
规划一次 schema 演进
orders 主题使用 Avro，兼容性 BACKWARD，有 5 个消费者服务。需求：① 增加 coupon_code（可选）；② 把 amount（double，元）改为 amount_cents（long，分）；③ 删除不再使用的 legacy_flag（没有默认值）。给出每一步的 schema 变更、部署顺序（生产者和消费者谁先），以及需要多长时间的过渡。
查看参考答案
  1. coupon_code：新增 {"name":"coupon_code","type":["null","string"],"default":null}。BACKWARD 下先升级消费者（新 schema 能读旧数据，缺失字段用默认值），再升级生产者开始填写。实际上带默认值的新增在两个方向都兼容，部署顺序不敏感。
  2. amount → amount_cents：不能直接改类型或改名。步骤：新增 amount_cents（long，默认 0 或 null）；生产者同时写两个字段；消费者逐个改为读取 amount_cents（为空时回退到 amount×100）；确认所有消费者都迁移、且保留期内的旧消息已过期后，再进入删除步骤。
  3. 删除 legacy_flag：BACKWARD 允许删除字段（新 schema 读旧数据时忽略多出的字段）——先升级消费者使用不含该字段的 schema，再让生产者停止写。若有消费者仍使用旧 schema 读新数据，需要该字段有默认值：可以先给它加上默认值（一次兼容的变更），再删除。若要所有历史版本都兼容，使用 BACKWARD_TRANSITIVE。
  4. 过渡期至少覆盖主题保留期，以及最慢的消费者完成升级的时间；在 CI 中对每个变更运行兼容性检查。

小结
记住这几点


  1. Kafka 中的 key 和 value 都是字节数组，序列化由客户端的 key.serializer/value.serializer 完成。主题本身没有 schema，所以格式就是生产者与所有消费者之间的契约。
  2. JSON：可读、通用，但体积大（字段名重复出现）、没有强制的类型和必填约束，变更全靠约定。Avro：紧凑的二进制，写入方和读取方各有 schema，按字段名解析，支持默认值，Hadoop/数据湖生态常用。Protobuf：按字段编号编码，生成多语言代码，与 gRPC 一致，字段编号一旦使用不能复用。
  3. Schema Registry 是一个独立服务（Confluent Schema Registry 采用 Confluent Community License；Apicurio Registry 采用 Apache 2.0），按 subject（默认 <主题>-value）保存 schema 的各个版本。序列化器第一次使用某个 schema 时注册并得到全局 ID，之后每条消息的格式为：魔数 0x00 + 4 字节 schema ID + 二进制数据。反序列化器按 ID 拉取 schema 并缓存。
  4. 兼容性规则在注册新版本时检查：BACKWARD（默认）新 schema 能读旧数据——可以删除字段、添加带默认值的字段，先升级消费者；FORWARD 旧 schema 能读新数据——可以添加字段、删除有默认值的字段，先升级生产者；FULL 两者都要满足；*_TRANSITIVE 与所有历史版本比较而不只是上一个版本；NONE 不检查。
  5. 不兼容的变更（改字段类型、改名、删除没有默认值的必填字段）应该创建新字段并逐步迁移，或者使用新的主题（orders.v2），双写一段时间后切换消费者。
  6. 生产实践：在 CI 中检查兼容性；生产者设置 auto.register.schemas=false，schema 由流水线注册；在 key 中避免复杂类型（key 的字节决定分区，序列化方式变化会改变分区）；记录 schema 的所有者和文档。
