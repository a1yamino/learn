Outbox 模式与 CDC

一个服务既要写数据库、又要发事件时，两步之间的任何崩溃都会让两边不一致：订单存了但事件没发，或者事件发了但订单回滚了。本课讲为什么“双写”无解，Transactional Outbox 如何把事件和业务数据放进同一个数据库事务，以及用 CDC（Debezium 读取数据库日志）把 outbox 表可靠地转发到 Kafka 的完整做法与注意事项。约 65 分钟。

挑战
把一个双写服务改造为 Outbox
现有代码：orderRepo.save(order); kafka.send("orders", order.id, toJson(order));，在同一个方法里，标注了 @Transactional。线上偶尔出现“订单存在但下游从未收到事件”和“下游收到事件但订单不存在”的情况。① 分别解释这两种现象是怎么产生的；② 写出改造后的代码和表结构；③ 说明下游消费者需要做什么改变。
查看参考答案
  1. 订单存在但没有事件：send() 是异步的，事务提交后进程崩溃或发送最终失败（回调里没有处理），事件丢失。事件存在但订单不存在：send() 在事务内调用，消息很快发出，而后续某一步（或提交本身）失败导致事务回滚。
  2. 改造：
    @Transactional
void createOrder(Order o) {
  orderRepo.save(o);
  outboxRepo.save(new OutboxEvent(UUID.randomUUID(), "Order", o.id,
                                  "OrderCreated", toJson(o)));
}  // 只写数据库，不再直接调用 Kafka
    表：outbox(id uuid PK, aggregatetype text, aggregateid text, type text, payload jsonb, created_at timestamptz)。部署 Debezium 连接器 + EventRouter，路由到 outbox.event.Order，key 为订单号；定期删除已过 1 天的 outbox 行（或写入后立即删除）。
  3. 下游：主题名和格式可能变化（改为订阅新主题，或用 EventRouter 的 route.topic.replacement 保持原主题名 orders）；按 header 中的事件 ID 幂等处理，因为 CDC 是至少一次；同一订单的事件因 key 相同而有序。

小结
记住这几点


  1. 双写问题：db.commit(); kafka.send(event) —— 提交后、发送前崩溃，事件丢失；反过来先发送再提交，提交失败时下游收到了从未发生的事件。数据库事务与 Kafka 事务是两个系统，没有共同的原子提交（第 11 课）。
  2. Transactional Outbox：在同一个数据库事务中写业务表和一张 outbox 表（id、aggregate_type、aggregate_id、type、payload、created_at）。事务提交则两者都在，回滚则两者都不在。再由一个独立的中继把 outbox 中的行发送到 Kafka。
  3. 中继的两种实现：轮询（定时 SELECT … WHERE sent = false ORDER BY id，发送后标记）简单但有延迟和数据库压力，并发中继时要小心顺序；CDC（变更数据捕获）读取数据库的复制日志（MySQL binlog、PostgreSQL 逻辑复制），延迟低、不需要改应用、不额外查询数据库。Debezium 是最常用的开源 CDC，以 Kafka Connect Source 连接器的形式运行。
  4. Debezium 的 Outbox Event Router（SMT io.debezium.transforms.outbox.EventRouter）把 outbox 表的插入事件转成干净的业务事件：按 aggregate_type 路由到主题（如 outbox.event.Order），用 aggregate_id 作 key（保证同一订单的事件有序），payload 作 value，id 放入 header 作为事件 ID。
  5. 中继至少一次：Connect 重启时可能重发最后一批，所以消费者必须按事件 ID 幂等。outbox 表只增不改，可以在写入后立即删除（CDC 已经从日志中读到插入），或按时间定期清理。
  6. 也可以直接对业务表做 CDC（不建 outbox 表），但这样表结构就成了对外的事件契约，内部重构会破坏下游；outbox 把“内部数据模型”与“对外发布的事件”分开，是更稳妥的做法。PostgreSQL 注意：复制槽会保留 WAL 直到被消费，连接器长时间停止会让磁盘被 WAL 占满，需要监控复制槽延迟。
