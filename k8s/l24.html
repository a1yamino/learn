挑战
写一条告警
为 shop 命名空间的 api 写一条 PrometheusRule：过去 5 分钟内 5xx 错误率超过 5%，且持续 10 分钟，就发出 severity=page 的告警；请求量很小时（每秒少于 1 个）不要告警。指标为 http_requests_total{namespace, service, code}。说明为什么用 rate 而不是 increase 都可以，以及 for 的作用。
查看参考答案
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-errors
  namespace: shop
  labels: {release: mon}
spec:
  groups:
  - name: api
    rules:
    - alert: ApiHighErrorRate
      expr: |
        (
          sum(rate(http_requests_total{namespace="shop",service="api",code=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{namespace="shop",service="api"}[5m]))
        ) > 0.05
        and
        sum(rate(http_requests_total{namespace="shop",service="api"}[5m])) > 1
      for: 10m
      labels: {severity: page}
      annotations:
        summary: "api 5xx 错误率 {{ $value | humanizePercentage }}"
kubectl -n shop get prometheusrule
NAME         AGE
api-errors   5s
错误率是两个速率之比：rate 和 increase 在同一窗口上只差一个常数倍（窗口秒数），比值相同。先 sum 再相除，得到整个服务的比例；不要先算每个 Pod 的比例再平均。and … > 1 避免流量很小时一两个错误就触发。for: 10m 要求条件连续 10 分钟成立才从 pending 变为 firing，过滤短暂抖动。labels.release: mon 让 kube-prometheus-stack 的 Prometheus 选中这条规则。

小结
记住这几点


  1. 日志：容器写 stdout/stderr，运行时存到节点的 /var/log/pods/，kubelet 负责轮转。DaemonSet 形式的采集器（Fluent Bit、Vector、Alloy）读取这些文件，加上 Pod 元数据，发送到 Loki、Elasticsearch 等。Pod 删除后 kubectl logs 就看不到了。
  2. 指标：Prometheus 定期抓取各目标的 /metrics。在 Kubernetes 中通过服务发现找目标；Prometheus Operator 用 ServiceMonitor / PodMonitor 按标签选择。kube-state-metrics 把对象状态（副本数、重启次数）变成指标，node-exporter 提供节点指标。
  3. 计数器（counter）只增不减，进程重启时归零。要看速率用 rate(x[5m])，它会处理重置；不要直接对原始值求差。gauge（当前值，如内存）可以直接看。
  4. 延迟用直方图：histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))。先聚合 bucket 再算分位数，不能对各 Pod 的 p99 求平均。
  5. 标签基数：每个标签值组合是一条时间序列。把用户 ID、请求 ID、完整 URL 放进标签会让 Prometheus 内存爆炸。
  6. 追踪：OpenTelemetry SDK 在请求经过的每个服务里生成 span，通过 traceparent 头传递上下文，经 OTel Collector 发送到 Tempo、Jaeger。日志里带上 trace_id，三类信号就能互相跳转。告警基于症状（错误率、延迟、SLO 消耗），而不是基于原因（CPU 高）。
