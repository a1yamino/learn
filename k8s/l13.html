静态 Pod

在一个 worker 节点的 /etc/kubernetes/manifests/ 下放一个 nginx Pod 的 YAML（kind 的 worker 节点已配置该路径）。在 API Server 里能看到它吗？名字是什么？用 kubectl 删除它会发生什么？删除文件又会怎样？

查看参考答案
kubectl run static-web --image=nginx:alpine --dry-run=client -o yaml | docker exec -i learn-worker tee /etc/kubernetes/manifests/static-web.yaml >/dev/null
sleep 15; kubectl get pods -o wide | grep static
kubectl delete pod static-web-learn-worker; sleep 5; kubectl get pods | grep static
docker exec learn-worker rm /etc/kubernetes/manifests/static-web.yaml; sleep 15; kubectl get pods | grep static
static-web-learn-worker   1/1   Running   0   12s   learn-worker
static-web-learn-worker   1/1   Running   0   3s
（无输出）

kubelet 直接读取文件运行 Pod，不经过 API Server 和调度器。为了让人能看到，它在 API Server 里创建一个只读的“镜像 Pod”，名字加上节点名后缀。用 kubectl 删除的只是镜像，kubelet 马上重建；只有删除文件才能真正停掉它。控制平面组件就是这样自举的：API Server 自己也是一个静态 Pod。

小结

记住这几点

  1. kubelet 是节点代理：watch 分配给本节点的 Pod，不断让节点上的实际状态（容器、卷、网络）符合 Pod spec，并把状态写回。它也是一个控制循环。
  2. CRI（容器运行时接口）是 kubelet 和运行时之间的 gRPC 接口。Kubernetes 1.24 起移除了 dockershim，常用运行时是 containerd 和 CRI-O，底层仍是 runc（Docker 第 14 课）。
  3. 创建顺序：挂载卷 → RunPodSandbox（pause 容器 + 调用 CNI 分配 IP）→ 拉镜像 → init 容器依次运行 → 创建并启动应用容器 → 探针。
  4. 每一步失败都对应一种状态：卷挂不上 → ContainerCreating；镜像拉不下 → ErrImagePull / ImagePullBackOff；配置引用缺失 → CreateContainerConfigError；启动后退出 → CrashLoopBackOff。
  5. 终止：标记删除 → 从端点摘除 & preStop → SIGTERM → 等待 grace period → SIGKILL → 清理沙箱和网络。
  6. kubelet 还负责：节点资源压力时驱逐 Pod、镜像和容器的垃圾回收、运行静态 Pod、为容器配置 cgroup。
