挑战

写一份故障复盘

把上面“动手”中的故障写成一份简短的复盘（postmortem），包括时间线、影响、根因、为什么没有提前发现、以及至少三项改进措施，每项写出具体由什么机制保证。

查看参考答案
影响：14:02–14:19（17 分钟）shop.example.com 全部请求 503。
时间线：
  14:00  发布 api v1.4.3（新增启动时检查 /ready 依赖 Redis）
  14:02  api 使用 strategy: Recreate（早期为数据库迁移设置）：旧 Pod 全部先删除，新 Pod readiness 失败
  14:05  告警 ApiHighErrorRate 触发
  14:12  定位：EndpointSlice 为空，readiness 返回 503（REDIS_URL 未配置）
  14:14  kubectl rollout undo；14:19 恢复
根因：v1.4.3 依赖新环境变量 REDIS_URL，prod overlay 中漏配。
为何未提前发现：staging 有该变量；Recreate 策略在新 Pod 就绪前就删除了全部旧 Pod。
改进：
  1. 改为 RollingUpdate，maxUnavailable: 0 + progressDeadlineSeconds：新 Pod 未就绪时旧 Pod 不会被删除（Deployment 机制）；迁移改用独立的 Job
  2. Argo Rollouts 金丝雀 + 基于错误率的自动中止（分析模板）
  3. 应用启动时校验必需配置并以非零码退出，在 CI 的 prod 渲染上运行配置检查（kustomize build + 策略测试）
  4. 告警 for 由 5m 改为 2m，并针对 “EndpointSlice 端点数为 0” 单独告警

复盘的重点是机制而不是“下次注意”：每条改进都应该让同样的错误在流程中被自动拦截。注意第 1 条：用滚动更新时，这次事故根本不会造成中断：新 Pod 不就绪，旧 Pod 会一直保留，发布只会卡住并在超时后报告 ProgressDeadlineExceeded。

小结

记住这几点

  1. 先止血再根因：有最近的发布就先回滚（kubectl rollout undo 或 git revert），扩容、切流量，恢复服务后再查原因。
  2. 沿着对象层级往下看：Deployment → ReplicaSet → Pod → 容器；每一层看 status、conditions 和 events。kubectl describe 最后的 Events 往往直接给出原因。
  3. 沿着请求路径排查网络：DNS → Service（有没有端点）→ Pod 端口 → 应用；Ingress / Gateway 在最前面。kubectl get endpointslices 为空几乎总是 selector 或 readiness 的问题。
  4. Pod 状态速查：Pending（调度：资源、污点、亲和、PVC）、ContainerCreating（卷、CNI）、ImagePullBackOff（镜像名、凭证）、CrashLoopBackOff（看 logs --previous 和退出码）、OOMKilled（退出码 137，内存 limits）、Running 但不 Ready（readiness 探针）。
  5. 节点问题：NotReady（kubelet、容器运行时、网络）、DiskPressure / MemoryPressure 导致驱逐。kubectl debug node/… 可以在节点上开一个调试 Pod。
  6. 没有 shell 的镜像用 kubectl debug -it pod --image=busybox --target=容器 附加临时容器。性能问题先看饱和度：CPU 节流（throttling）、内存接近 limits、连接池、下游延迟。
