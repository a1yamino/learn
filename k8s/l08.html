在你的电脑上练习

用 Traefik 作为控制器，同时体验 Ingress 和 Gateway API。需要 Helm（brew install helm 或见 helm.sh）。
01

重建集群，把宿主机 8080 映射到节点的 30080。

cat > kind-ing.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  extraPortMappings:
  - { containerPort: 30080, hostPort: 8080 }
- role: worker
- role: worker
EOF
kind delete cluster --name learn; kind create cluster --name learn --config kind-ing.yaml
Set kubectl context to "kind-learn"
02

安装 Gateway API CRD 和 Traefik。

kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/standard-install.yaml
helm repo add traefik https://traefik.github.io/charts && helm repo update
helm install traefik traefik/traefik -n traefik --create-namespace \
  --set service.type=NodePort --set ports.web.nodePort=30080 \
  --set providers.kubernetesGateway.enabled=true
kubectl -n traefik rollout status deploy traefik
deployment "traefik" successfully rolled out

两个后端服务。serve-hostname 对任意路径返回主机名，便于验证路由选择；Ingress 的 Prefix 匹配不会自动去掉 /api。

for s in web api; do kubectl create deployment $s --image=registry.k8s.io/e2e-test-images/agnhost:2.52 -- /agnhost serve-hostname --port 8080; kubectl expose deployment $s --port 80 --target-port 8080; done

04

Ingress：/api 给 api，其余给 web。

kubectl create ingress shop --class=traefik --rule="shop.localhost/api*=api:80" --rule="shop.localhost/*=web:80"
curl -s -H "Host: shop.localhost" localhost:8080/hostname; echo
curl -s -H "Host: shop.localhost" localhost:8080/api/hostname; echo
web-6d8f7c9b5-2kq8x
api-7b9c6d5f4-x7k2p
05

改用 Gateway API。先删除 Ingress，再创建 Gateway 和 HTTPRoute。

kubectl delete ingress shop
kubectl apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: shop }
spec:
  gatewayClassName: traefik
  listeners: [{ name: web, port: 8000, protocol: HTTP }]
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop }
spec:
  parentRefs: [{ name: shop }]
  hostnames: [shop.localhost]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs: [{ name: api, port: 80 }]
  - backendRefs: [{ name: web, port: 80 }]
EOF
kubectl get gateway shop; curl -s -H "Host: shop.localhost" localhost:8080/api/hostname; echo
NAME   CLASS     ADDRESS   PROGRAMMED   AGE
shop   traefik             True         5s
api-7b9c6d5f4-x7k2p

挑战

金丝雀发布

部署 web-v2（同样的镜像即可，用于区分主机名）。修改 HTTPRoute，让 90% 的默认流量到 web、10% 到 web-v2；带请求头 x-canary: 1 的请求 100% 到 web-v2。用 100 次 curl 统计分布。

查看参考答案
kubectl create deployment web-v2 --image=registry.k8s.io/e2e-test-images/agnhost:2.52 -- /agnhost serve-hostname --port 8080
kubectl expose deployment web-v2 --port 80 --target-port 8080
kubectl apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop }
spec:
  parentRefs: [{ name: shop }]
  hostnames: [shop.localhost]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs: [{ name: api, port: 80 }]
  - matches: [{ headers: [{ name: x-canary, value: "1" }] }]
    backendRefs: [{ name: web-v2, port: 80 }]
  - backendRefs:
    - { name: web, port: 80, weight: 90 }
    - { name: web-v2, port: 80, weight: 10 }
EOF
for i in $(seq 100); do curl -s -H "Host: shop.localhost" localhost:8080/hostname; echo; done | sed 's/-[^-]*$//' | sort | uniq -c
curl -s -H "Host: shop.localhost" -H "x-canary: 1" localhost:8080/hostname
     91 web-6d8f7c9b5
      9 web-v2-5f7d8c6b4
web-v2-5f7d8c6b4-q2w8z

权重和请求头匹配是 Gateway API 的标准字段，换一个实现（Envoy Gateway、Istio、云厂商）配置不变。用 Ingress 实现同样的效果，要靠各控制器不同的注解。逐步调大 v2 的权重即可完成发布，出问题时把权重调回 0。

小结

记住这几点

  1. Ingress / Gateway 本身只是规则，需要一个控制器（Envoy Gateway、Traefik、云厂商的负载均衡器等）来真正处理流量。没有控制器，规则不生效。
  2. 一个入口（一个 LoadBalancer）按 host 和 path 把请求分给多个 Service，省去每个服务一个负载均衡器。
  3. pathType：Prefix 按路径段前缀匹配（/api 匹配 /api/x，不匹配 /apix），Exact 精确匹配。多条规则时最长匹配优先。
  4. TLS：证书放在 kubernetes.io/tls 类型的 Secret 中，入口负责解密。cert-manager 可以自动申请和续期 Let's Encrypt 证书。
  5. Gateway API：按角色拆分为 GatewayClass（基础设施提供方）、Gateway（集群运维：监听端口、证书）、HTTPRoute（应用团队：路由规则）。原生支持按权重分流、请求头匹配、改写等，不再依赖各控制器的私有注解。新项目优先选它。
  6. 社区的 ingress-nginx 已于 2026 年 3 月停止维护。已有的 Ingress 资源仍可由其他控制器处理，迁移目标通常是 Gateway API。
