为什么需要 Kubernetes

Docker 管好了一台机器上的容器。当服务要跑在几十台机器上、要自动恢复、要不停机更新时，就需要一个集群级别的系统。本课讲 Kubernetes 解决什么问题、核心思想“声明期望状态”，以及集群由哪些部分组成。约 35 分钟。

在你的电脑上练习

用 kind（Kubernetes in Docker）在本机起一个集群。第 2 课会详细讲 kind 和 kubectl，这里先体验。
01

安装 kind 和 kubectl（需要 Docker 已运行）。macOS：brew install kind kubectl。Linux 见右侧命令：为匹配示例中的 kind v0.24.0 / Kubernetes v1.31，kubectl 固定为 v1.31.1；升级集群时需一起选择版本差不超过一个小版本的 kubectl。Windows：winget install Kubernetes.kind Kubernetes.kubectl。

curl -Lo kind https://kind.sigs.k8s.io/dl/v0.24.0/kind-linux-amd64 && chmod +x kind && sudo mv kind /usr/local/bin/
curl -LO "https://dl.k8s.io/release/v1.31.1/bin/linux/amd64/kubectl" && chmod +x kubectl && sudo mv kubectl /usr/local/bin/
kind version && kubectl version --client

挑战

和 docker 对比

在 kind 节点容器里直接用 docker exec 或 crictl 删除一个 web 的容器（不是通过 kubectl 删 Pod）。会发生什么？再对比：用 docker rm -f 删除一个普通 Docker 容器（没有 restart 策略）会发生什么？用你的观察说明“声明式”的含义。

查看参考答案
docker exec learn-control-plane crictl ps --name nginx -q | head -1 | xargs -I{} docker exec learn-control-plane crictl rm -f {}
kubectl get pods
NAME                   READY   STATUS    RESTARTS     AGE
web-7c5b8d6f9b-h8zmw   1/1     Running   1 (3s ago)   5m
…

容器没了，但 Pod 对象还在。节点上的 kubelet 发现“这个 Pod 应该有一个运行中的 nginx 容器，但实际没有”，于是重新创建，RESTARTS 加 1。而普通的 docker rm -f 之后，容器就永远不在了，因为 Docker 只执行你的命令，不记得你“想要”什么。声明式：系统保存的是期望状态，并持续让现实符合它。

小结

记住这几点

  1. 单机 Docker / Compose 的边界：一台机器宕机，服务就停；扩容、分布、更新都要人工完成。
  2. Kubernetes 的核心是声明式：你提交“要什么”（3 个副本、这个镜像），系统持续把实际状态调整为期望状态。
  3. 这个调整由许多控制器完成，每个都在循环：观察 → 比较 → 修正。Docker 第 24 课的 Swarm 也是这个思想。
  4. 集群 = 控制平面（API Server、etcd、调度器、控制器管理器）+ 工作节点（kubelet、容器运行时、kube-proxy）。
  5. 所有操作都通过 API Server。kubectl 只是一个 API 客户端。
  6. Kubernetes 不构建镜像，镜像仍然用 Docker / BuildKit 构建并推送到仓库。
