阶段 1：集群与命名空间。创建 shop 命名空间，开启 restricted、配额和默认拒绝。

kubectl create ns shop
kubectl label ns shop pod-security.kubernetes.io/enforce=restricted
kubectl -n shop create quota shop --hard=requests.cpu=4,requests.memory=8Gi,limits.memory=16Gi,pods=40
kubectl -n shop apply -f - <<EOT
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny}
spec: {podSelector: {}, policyTypes: [Ingress, Egress]}
EOT
kubectl get ns shop --show-labels; kubectl -n shop get quota,netpol

02

阶段 2：数据库。安装 CloudNativePG Operator，创建 3 实例集群（第 19、17 课）。

kubectl apply --server-side -f https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.27/releases/cnpg-1.27.0.yaml
kubectl -n cnpg-system rollout status deploy/cnpg-controller-manager
kubectl -n shop apply -f - <<EOT
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: {name: db}
spec:
  instances: 3
  resources:
    requests: {cpu: 200m, memory: 256Mi}
    limits: {memory: 512Mi}
  storage: {size: 1Gi}
EOT
kubectl -n shop get cluster db
cluster 已创建；默认拒绝策略下暂不要求 Ready，先完成下一步网络放行。

先编写并应用网络策略（第 21 课）：DNS、数据库副本互通、Operator → db 的管理端口、db → API Server，以及 web → api → db 的双向规则。默认拒绝同时限制入站和出站，两端都须放行。策略生效后再等待数据库就绪。

挑战

故障演练

对完成的系统依次执行下面五个演练，每个演练前写下你预期会发生什么，再执行并对比：① 删除数据库 primary Pod；② drain 运行着 2 个 api 副本的节点；③ 发布一个 readiness 永远失败的 api 版本；④ 手动 kubectl scale deploy/web --replicas=1；⑤ 删除 allow-dns 网络策略。每项写出你观察到的现象、恢复由谁完成、用户是否感知。

查看参考答案
① kubectl -n shop delete pod db-1
   → CNPG 在数秒内把一个 replica 提升为 primary，Service db-rw 指向新 primary；api 的连接断开一次后重连
   → 恢复者：Operator；用户：可能有几秒写入错误（应用需要重试）
② kubectl drain learn-worker --ignore-daemonsets --delete-emptydir-data
   → PDB 限制一次只驱逐 1 个 api；拓扑分布让新副本落到其他节点；db 的 PDB 同样生效
   → 恢复者：Deployment + 调度器；用户：无感知
③ git commit（镜像 api:broken）→ Argo CD 同步
   → maxUnavailable: 0，新 Pod 不就绪，旧 Pod 保留；rollout 停止，ProgressDeadlineExceeded；Argo CD Health: Degraded
   → 恢复者：人（git revert）；用户：无感知
④ kubectl -n shop scale deploy/web --replicas=1
   → Argo CD selfHeal 改回 Git 中的值（如果 Git 中省略了 replicas、由 HPA 管理，则 HPA 会把副本恢复到 minReplicas）
   → 用户：短时间容量下降
⑤ kubectl -n shop delete netpol allow-dns
   → 新建立的连接全部因 DNS 失败而报错；已建立的连接还在
   → Argo CD 检测到缺失并重新创建（selfHeal）；告警 ApiHighErrorRate 可能触发
   → 用户：几十秒内部分请求失败

演练的价值在于“预期”和“实际”的差异：每一个出乎意料的现象都是一个尚未被处理的风险。把结论写进运维手册（runbook），并把能自动化的检查加入 CI 或策略引擎。到这里，你已经亲手搭出了一个接近生产标准的 Kubernetes 应用，并验证了它在常见故障下的表现。

自测

综合前面各课的知识。
小结

记住这几点

  1. 生产就绪不是某个功能，而是一组检查项：每个工作负载都有 requests/limits、探针、多副本与分布、PDB；每个命名空间都有 Pod 安全级别、默认拒绝的网络策略和配额。
  2. 所有内容都在 Git 中声明（Kustomize base + overlay），由 GitOps 控制器同步；集群里的手动修改应当被视为故障。
  3. 有状态部分（数据库）要么交给成熟的 Operator（如 CloudNativePG），要么接受它的运维成本：复制、备份、升级、故障切换都要有人负责。
  4. 可观测性先于上线：至少有错误率、延迟、饱和度的仪表板，以及基于症状的告警。
  5. 备份必须恢复演练过；升级必须在类似生产的环境里先做一遍。
  6. 最后一步永远是故障演练：删 Pod、drain 节点、断开数据库、发布坏版本，确认系统和人都按预期反应。
