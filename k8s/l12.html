挑战

写一个最小的控制器

用 shell 写一个控制循环：确保每个带 replicas-of 注解（值为一个数字 N）的 ConfigMap，都有 N 个名为 <名字>-0..N-1、带 owner=<名字> 标签的 ConfigMap。多余的删除，缺的补上。要求水平触发：每轮都从当前完整状态计算。

查看参考答案
while true; do
  for src in $(kubectl get cm -o jsonpath='{range .items[?(@.metadata.annotations.replicas-of)]}{.metadata.name}{"\n"}{end}'); do
    want=$(kubectl get cm $src -o jsonpath='{.metadata.annotations.replicas-of}')
    have=$(kubectl get cm -l owner=$src -o name | sed 's#.*/##' | sort)
    for i in $(seq 0 $((want-1))); do
      echo "$have" | grep -qx "$src-$i" || kubectl create cm $src-$i && kubectl label cm $src-$i owner=$src --overwrite >/dev/null
    done
    for n in $have; do
      idx=${n##*-}; [ "$idx" -ge "$want" ] && kubectl delete cm $n
    done
  done
  sleep 3
done
# 另一个终端
kubectl create cm demo && kubectl annotate cm demo replicas-of=3
kubectl get cm -l owner=demo        # demo-0 demo-1 demo-2
kubectl delete cm demo-1            # 下一轮被补回
kubectl annotate cm demo replicas-of=1 --overwrite   # demo-1、demo-2 被删除

它不关心“发生了什么事件”，每轮只比较期望（注解）和实际（列表）。即使循环停了一阵子、期间改了好几次，恢复后第一轮就能收敛。真实控制器用 watch + 本地缓存（informer）代替轮询以减少负载，再加上 ownerReferences 让删除 demo 时级联清理，但核心就是这个循环（第 19 课用 Operator 框架实现）。

小结

记住这几点

  1. 控制循环：读取期望状态（spec）和实际状态 → 计算差异 → 执行一步 → 写回 status → 重复。每次都从当前完整状态出发，而不是依赖“发生了什么事件”。
  2. 水平触发（level-triggered）：错过事件也没关系，下次调和看到的仍是正确的差异。控制器重启、网络中断后能自动恢复。
  3. 每个对象有 resourceVersion。更新时带上读到的版本，如果期间有人改过，API Server 返回 409 Conflict，客户端重新读取再试（乐观并发）。
  4. Server-side apply（kubectl apply --server-side）：API Server 记录每个字段由谁管理（managedFields）。两个管理者改同一字段会报冲突，避免互相覆盖（如 HPA 管 replicas、你管镜像）。
  5. metadata.generation 在 spec 变化时增加；控制器处理后写 status.observedGeneration。两者相等才说明“最新的期望已被处理”。
  6. 删除：带 finalizer 的对象先被标记 deletionTimestamp，等负责的控制器完成清理并移除 finalizer 后才真正删除。所属对象由垃圾回收器按 ownerReferences 级联删除。
