集群网络：CNI、kube-proxy 与 DNS

Kubernetes 只规定网络模型，具体由插件实现。本课讲每个 Pod 一个 IP 的模型、CNI 插件如何连接 Pod 和跨节点路由、kube-proxy 如何把 ClusterIP 变成真实的 Pod 地址，以及集群 DNS 的解析过程和 ndots 的坑。约 55 分钟。

挑战

多副本时的负载均衡规则

把 Service a 背后的 Pod 变成 3 个（创建一个 app=a 的 Deployment 并让 Service 选择它）。查看 iptables 的 KUBE-SVC 链：kube-proxy 用什么规则在 3 个端点间分配？概率分别是多少，为什么最终是均匀的？

查看参考答案
kubectl create deployment a3 --image=nginx:alpine --replicas=3
kubectl expose deployment a3 --port 80
IP=$(kubectl get svc a3 -o jsonpath="{.spec.clusterIP}")
C=$(docker exec learn-worker iptables -t nat -S KUBE-SERVICES | grep $IP | grep -o "KUBE-SVC-[A-Z0-9]*")
docker exec learn-worker iptables -t nat -S $C | grep KUBE-SEP
-A KUBE-SVC-… -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-AAA
-A KUBE-SVC-… -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-BBB
-A KUBE-SVC-… -j KUBE-SEP-CCC

规则从上到下匹配：第一条以 1/3 概率命中；没命中的（2/3）进入第二条，以 1/2 命中，即总体 2/3 × 1/2 = 1/3；剩下的 1/3 落到最后一条。每个端点各 1/3。这是按连接随机，不是按请求：HTTP/2、gRPC 的长连接会一直粘在同一个 Pod 上，需要客户端负载均衡或服务网格。端点很多时 iptables 规则线性增长，大集群改用 IPVS、nftables 模式或 eBPF。

小结

记住这几点

  1. 网络模型：每个 Pod 一个集群内唯一的 IP；所有 Pod 之间不经 NAT 直接互通；节点和 Pod 之间也互通。
  2. CNI 插件（kindnet、Calico、Cilium、Flannel、云厂商插件）在 Pod 创建时被调用：建 veth 对、分配 IP、设置路由。跨节点用路由（BGP、云路由表）或封装（VXLAN、Geneve）。
  3. ClusterIP 不在任何网卡上。kube-proxy 在每个节点写入 iptables / nftables（或 IPVS）规则：发往 ClusterIP:port 的包被 DNAT 到某个端点 Pod。Cilium 等可用 eBPF 完全替代 kube-proxy。
  4. CoreDNS 是集群 DNS，本身也是一个 Deployment + Service（10.96.0.10）。Pod 的 resolv.conf 指向它。
  5. ndots:5：名字里少于 5 个点就先依次尝试 search 域。查 api.example.com 会先产生 3 次无用查询。高频访问外部域名时用完整域名加尾点（api.example.com.）或调低 ndots。
  6. NetworkPolicy 也由 CNI 插件执行；不支持它的插件（如 Flannel）会静默忽略策略（第 21 课）。
