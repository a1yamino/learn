挑战

PDB 让 drain 卡住了

一个 Deployment 只有 1 个副本，PDB 设置 minAvailable: 1。运维 drain 这个节点时会怎样？列出至少两种正确的处理方式，并说明 maxUnavailable 和 minAvailable 在副本数变化时的区别。

查看参考答案
kubectl drain learn-worker --ignore-daemonsets --timeout=60s
error when evicting pods/"api-5f7d8-x2k9l" -n "shop" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
…
error: unable to drain node "learn-worker" due to error: … global timeout reached: 1m0s

ALLOWED DISRUPTIONS 为 0，驱逐永远不被允许，drain 会一直重试直到超时；节点自动扩缩和托管集群的升级也会被卡住。处理方式：① 把副本数提高到 2 以上（这才是 PDB 的前提）；② 单副本应用如果能接受短暂中断，就不要设置 PDB，或设置 maxUnavailable: 1；③ 临时情况下先扩容 kubectl scale --replicas=2，新 Pod 就绪后再 drain。不要用 --disable-eviction 绕过，那会直接删除 Pod。

minAvailable: 2 是绝对下限，副本从 3 扩到 10 时仍只要求 2 个，等于允许同时驱逐 8 个；maxUnavailable: 1 随副本数自动适应，始终一次只驱逐一个，通常更合适。也可以写百分比。

小结

记住这几点

  1. etcd 使用 Raft，需要多数派（quorum）才能写入：3 个成员容忍 1 个故障，5 个容忍 2 个。偶数成员不增加容错。成员分布在不同可用区。
  2. 控制平面高可用：多个 API Server 放在负载均衡后面（无状态）；scheduler 和 controller-manager 多副本但通过 Lease 选主，同一时间只有一个工作。托管集群（EKS、GKE、AKS）由云厂商负责。
  3. 应用高可用：至少 2–3 个副本，用 topologySpreadConstraints 分散到不同节点和可用区，配置 readiness 探针，并用 PodDisruptionBudget 限制自愿中断（drain、节点缩容、升级）时同时被驱逐的数量。
  4. 升级顺序：先控制平面（一次只升一个小版本，如 1.33 → 1.34），再逐个节点 drain、升级 kubelet、uncordon。版本偏差：kubelet 不能比 API Server 新，最多旧 3 个小版本；kubectl 与 API Server 相差不超过 1。升级前检查已弃用的 API。
  5. 备份：etcd 快照（etcdctl snapshot save）保存整个集群状态；Velero 按命名空间备份 API 对象并配合卷快照备份数据，可恢复到另一个集群。GitOps 仓库本身也是配置的备份，但不包括 PV 中的数据和运行时生成的对象。
  6. 没有演练过的备份不算备份：定期在独立环境中恢复并验证，记录恢复所需时间（RTO）和可能丢失的数据量（RPO）。
