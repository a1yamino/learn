- role: worker
- role: worker

04

生成 YAML 模板，而不是直接创建。

kubectl create deployment web --image=nginx:alpine --replicas=2 --dry-run=client -o yaml > web.yaml
grep -E "^kind|replicas|image:" web.yaml
kind: Deployment
  replicas: 2
      - image: nginx:alpine
05

应用，修改，看差异，再应用。

kubectl apply -f web.yaml
sed -i.bak "s/replicas: 2/replicas: 4/" web.yaml
kubectl diff -f web.yaml | grep replicas
kubectl apply -f web.yaml
deployment.apps/web created
-  replicas: 2
+  replicas: 4
deployment.apps/web configured

挑战

不用 kubectl 访问 API

用 kubectl proxy 在本地开一个已认证的代理，然后只用 curl 列出 default 命名空间里所有 Pod 的名字，并把 web 的副本数改成 1。说明为什么“kubectl 只是一个 API 客户端”。

查看参考答案
kubectl proxy --port 8001 &
curl -s localhost:8001/api/v1/namespaces/default/pods | python3 -c "import json,sys;[print(i['metadata']['name']) for i in json.load(sys.stdin)['items']]"
curl -s -X PATCH -H "Content-Type: application/merge-patch+json" \
  -d '{"spec":{"replicas":1}}' \
  localhost:8001/apis/apps/v1/namespaces/default/deployments/web/scale | grep '"replicas"'
kubectl get deploy web
kill %1
web-5d9c7f6b8-2bxkq
…
    "replicas": 1
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    1/1     1            1           6m

Pod 在 /api/v1（核心组），Deployment 在 /apis/apps/v1。proxy 用 kubeconfig 里的证书完成认证，所以 curl 不需要凭证。kubectl、Dashboard、CI 工具、控制器，全都是在调用同一组 REST API。

小结

记住这几点

  1. kind 用 Docker 容器模拟节点，适合学习和 CI。其他选择：minikube、k3d、Docker Desktop 自带的 Kubernetes。
  2. kubeconfig（~/.kube/config）包含 clusters、users、contexts。context = 集群 + 用户 + 默认命名空间。执行命令前确认当前 context。
  3. kubectl 的每条命令都是对 API Server 的 HTTP 请求。-v=6 可以看到请求的 URL。
  4. 每个资源都有 apiVersion、kind、metadata、spec，系统写回 status。kubectl explain 查字段含义。
  5. 命令式（create、scale）适合试验；声明式（YAML + apply）适合正式使用，文件放进 git。
  6. --dry-run=client -o yaml 生成 YAML 模板；kubectl diff 在 apply 前看差异。
