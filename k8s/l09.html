01

readiness 失败：Pod 不重启，但从端点消失。

kubectl create deployment rd --image=nginx:alpine --replicas=2
kubectl patch deployment rd --type=json -p='[{"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{"httpGet":{"path":"/ready","port":80},"periodSeconds":2}}]'
kubectl expose deployment rd --port 80
sleep 15; kubectl get pods -l app=rd; kubectl get endpointslices -l kubernetes.io/service-name=rd -o jsonpath="{.items[0].endpoints[*].conditions.ready}"

03

liveness 失败：容器被重启。

kubectl run lv --image=busybox --overrides='{"spec":{"containers":[{"name":"lv","image":"busybox","command":["sh","-c","touch /tmp/ok; sleep 20; rm /tmp/ok; sleep 600"],"livenessProbe":{"exec":{"command":["cat","/tmp/ok"]},"periodSeconds":3,"failureThreshold":2}}]}}'
sleep 40; kubectl get pod lv; kubectl describe pod lv | grep -m1 Unhealthy
lv   1/1   Running   1 (8s ago)   40s
Warning  Unhealthy  … Liveness probe failed: cat: can't open '/tmp/ok': No such file or directory

QoS 等级。

kubectl run g --image=nginx:alpine --overrides='{"spec":{"containers":[{"name":"g","image":"nginx:alpine","resources":{"requests":{"cpu":"100m","memory":"64Mi"},"limits":{"cpu":"100m","memory":"64Mi"}}}]}}'
kubectl get pod g lv -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
NAME   QOS
g      Guaranteed

挑战

优雅终止

部署 3 副本的 nginx + Service，用第 4 课挑战里的 probe Pod 持续请求。分别在没有和有 preStop: sleep 5 的情况下执行 kubectl rollout restart，比较失败请求数，并解释原因。

查看参考答案
        lifecycle:
          preStop:
            exec: { command: ["sleep", "5"] }
      terminationGracePeriodSeconds: 30
没有 preStop：ok=503 bad=4
有 preStop：  ok=511 bad=0

删除 Pod 时，两件事并行开始：(1) 端点控制器把 Pod 从 EndpointSlice 删除，各节点 kube-proxy 再更新规则；(2) kubelet 向容器发送 SIGTERM。nginx 收到 SIGTERM 很快就退出了，而有些节点的转发规则还没更新，仍在把请求发给它 → 失败。preStop 先睡 5 秒，等规则传播完毕再让进程开始退出。preStop 的时间计入 terminationGracePeriodSeconds。（新版本 Kubernetes 也可以用 sleep 动作代替 exec。）

小结

记住这几点

  1. readinessProbe：失败就从 Service 端点中摘除，不重启。livenessProbe：失败就重启容器。startupProbe：启动完成前暂停另外两个探针，保护慢启动的应用。
  2. liveness 只检查进程自身是否卡死，不要检查数据库等外部依赖：依赖出问题时重启所有 Pod 只会让情况更糟。
  3. 优雅终止：Pod 删除时同时开始“从端点摘除”和“发 SIGTERM”。用 preStop 短暂等待，应用收到 SIGTERM 后处理完已有请求再退出，在 terminationGracePeriodSeconds（默认 30 秒）内完成。
  4. requests 用于调度：节点上 requests 之和不能超过可分配资源。limits 是运行时上限：CPU 超了被节流，内存超了被 OOMKill（Docker 第 21 课）。
  5. QoS：requests = limits → Guaranteed；只设了部分 → Burstable；都没设 → BestEffort。节点内存紧张时，BestEffort 最先被驱逐。
  6. 常见做法：内存 requests = limits；CPU 设 requests，不设或放宽 limits，避免节流。
