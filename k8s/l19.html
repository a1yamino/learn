CRD 与 Operator：扩展 Kubernetes API

Kubernetes 的 API 可以扩展：用 CRD 定义新的资源类型，再写一个控制器持续把它变成现实，就是 Operator。本课讲 CRD 的结构、spec 与 status 的分工、finalizer 和 ownerReference，以及用 kubebuilder / controller-runtime 写 Operator 的基本套路。约 55 分钟。

在你的电脑上练习

先定义 CRD，看没有控制器时的效果；再用一个 shell 脚本当作最简单的控制器。
01

创建 CRD。

kubectl apply -f - <<EOT
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: {name: websites.example.com}
spec:
  group: example.com
  names: {kind: Website, plural: websites, singular: website, shortNames: [ws]}
  scope: Namespaced
  versions:
  - name: v1
    served: true
    storage: true
    subresources: {status: {}}
    additionalPrinterColumns:
    - {name: Replicas, type: integer, jsonPath: .spec.replicas}
    - {name: Ready, type: string, jsonPath: .status.ready}
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [image]
            properties:
              image: {type: string}
              replicas: {type: integer, minimum: 1, maximum: 5, default: 1}
          status:
            type: object
            properties: {ready: {type: string}}
EOT
kubectl api-resources | grep websites
websites    ws    example.com/v1    true    Website

创建一个合法的对象：存起来了，但什么也没发生。

kubectl apply -f - <<EOT
apiVersion: example.com/v1
kind: Website
metadata: {name: blog}

EOT
kubectl get ws; kubectl get deploy

blog   2

04

最简控制器：watch Website，生成 Deployment 并设置 ownerReference，再写回 status。

cat > ctl.sh <<'EOT'
kubectl get ws -w -o jsonpath='{.metadata.name} {.metadata.uid} {.spec.image} {.spec.replicas}{"\n"}' |
while read n uid img rep; do
  kubectl create deploy $n --image=$img --replicas=$rep --dry-run=client -o json |
  jq --arg uid $uid --arg n $n '.metadata.ownerReferences=[{apiVersion:"example.com/v1",kind:"Website",name:$n,uid:$uid,controller:true}]' |
  kubectl apply -f -
  kubectl patch ws $n --subresource=status --type=merge -p "{\"status\":{\"ready\":\"$rep\"}}"
done
EOT
bash ctl.sh &
sleep 5; kubectl get ws,deploy
NAME                       REPLICAS   READY
website.example.com/blog   2          2

NAME                   READY   UP-TO-DATE   AVAILABLE
deployment.apps/blog   2/2     2            2
05

删除 CR，Deployment 被垃圾回收器级联删除。

kubectl delete ws blog; sleep 3; kubectl get deploy
No resources found in default namespace.
挑战

为什么 Deployment 被删了也没恢复

用上面的 ctl.sh：重新创建 blog，然后手动 kubectl delete deploy blog。Deployment 会被重建吗？说明原因，以及真正的 Operator（controller-runtime）怎样避免这个问题。

查看参考答案
kubectl apply -f blog.yaml; sleep 3
kubectl delete deploy blog; sleep 5; kubectl get deploy
No resources found in default namespace.

不会。脚本只 watch Website；删除 Deployment 不改变 Website，所以没有触发。这就是只对“自己关心的那类事件”反应的边沿触发问题。

controller-runtime 里用 Owns(&appsv1.Deployment{}) 同时 watch 子资源：子资源任何变化都按 ownerReference 找到所属 CR，把它放入工作队列再 Reconcile 一次。再加上定期全量重新同步（resync），即使丢事件也能最终收敛。Reconcile 本身每次都从头比对“应有的”和“现有的”，所以多触发几次也没关系。

小结

记住这几点

  1. CRD（CustomResourceDefinition）向 API Server 注册新的类型，例如 databases.example.com。之后可以像内置资源一样 kubectl get databases，存在 etcd 中，支持 watch、RBAC。
  2. CRD 用 OpenAPI v3 schema 校验字段；subresources.status 让 status 只能通过 /status 子资源修改；additionalPrinterColumns 控制 kubectl get 的列；可以有多个版本，用转换 webhook 互转。
  3. 只有 CRD 没有控制器，对象只是存起来的数据。Operator = CRD + 控制器，把领域运维知识（创建、备份、升级、故障切换）写成代码。
  4. 控制器的 Reconcile 函数应该是幂等的、水平触发的（第 12 课）：读取当前对象，对比实际状态，做下一步，更新 status，必要时要求稍后再次调用。
  5. ownerReference：Operator 创建的子资源指向 CR，删除 CR 时垃圾回收器级联删除它们。finalizer：删除前需要清理外部资源（如云数据库）时，控制器完成清理后移除 finalizer，对象才真正消失。
  6. 常用框架：kubebuilder / Operator SDK（Go，基于 controller-runtime）、kopf（Python）。成熟的 Operator：CloudNativePG、Strimzi（Kafka）、cert-manager、Prometheus Operator。
