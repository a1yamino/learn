挑战
给 CI 部署账号授权
CI 需要一个 ServiceAccount deployer，能在 staging 和 prod 两个命名空间里更新 Deployment 的镜像、查看 Pod 和日志，但不能读 Secret、不能 exec，也不能在其他命名空间做任何事。规则只写一份。写出命令并用 can-i 验证。
查看参考答案
kubectl create clusterrole deployer --verb=get,list,watch,patch,update --resource=deployments.apps
kubectl patch clusterrole deployer --type=json -p '[{"op":"add","path":"/rules/-","value":{"apiGroups":[""],"resources":["pods","pods/log"],"verbs":["get","list","watch"]}}]'
kubectl create sa deployer -n ci
for ns in staging prod; do
  kubectl -n $ns create rolebinding deployer --clusterrole=deployer --serviceaccount=ci:deployer
done
SA=system:serviceaccount:ci:deployer
kubectl auth can-i patch deploy -n prod --as=$SA
kubectl auth can-i get pods --subresource=log -n staging --as=$SA
kubectl auth can-i get secrets -n prod --as=$SA
kubectl auth can-i create pods/exec -n prod --as=$SA
kubectl auth can-i patch deploy -n default --as=$SA
yes
yes
no
no
no
ClusterRole 只定义一次规则，用两个 RoleBinding 引用：权限只在这两个命名空间生效。如果用 ClusterRoleBinding 就会扩大到所有命名空间。注意：能 patch Deployment 就能修改 Pod 模板（换镜像、挂载 Secret、改 serviceAccountName），实际上可以间接读到该命名空间的 Secret。所以生产命名空间的写权限要配合准入策略（第 21 课）或 GitOps（第 23 课），只让流水线提交变更。

小结
记住这几点


  1. 请求流程：认证（客户端证书、OIDC 令牌、ServiceAccount 令牌）→ 授权（RBAC）→ 准入（第 21 课）→ 写入 etcd。Kubernetes 没有“用户”对象，人的身份来自外部（证书 CN、OIDC）。
  2. RBAC 只有“允许”，没有“拒绝”；默认什么都不允许。规则由 apiGroups、resources、verbs（get、list、watch、create、update、patch、delete）组成。
  3. Role（命名空间内）和 ClusterRole（集群范围或可复用）定义权限；RoleBinding 和 ClusterRoleBinding 把权限授予用户、组或 ServiceAccount。RoleBinding 也可以引用 ClusterRole，只在本命名空间生效。
  4. ServiceAccount 是给 Pod 用的身份。kubelet 给 Pod 挂载一个有时效、绑定 Pod 的投射令牌（默认约 1 小时自动轮换）到 /var/run/secrets/kubernetes.io/serviceaccount/。不需要访问 API 的 Pod 设 automountServiceAccountToken: false。
  5. 危险权限：secrets 的 get/list、pods/exec、创建 Pod（可以挂载任意 SA 和 hostPath）、escalate/bind/impersonate、通配符 *。cluster-admin 只给少数人。
  6. 检查工具：kubectl auth can-i（可加 --as 模拟他人）、kubectl auth whoami。
