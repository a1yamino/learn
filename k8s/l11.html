挑战

停掉调度器

把调度器的静态 Pod 文件移出 manifests 目录（kubelet 会停止它），然后创建一个 Deployment。观察 Pod 的状态，再把文件移回去。解释你看到的现象说明了什么。

查看参考答案
docker exec learn-control-plane mv /etc/kubernetes/manifests/kube-scheduler.yaml /tmp/
sleep 20; kubectl get pods -n kube-system | grep scheduler   # 消失
kubectl create deployment nosched --image=nginx:alpine --replicas=2
kubectl get pods -l app=nosched -o wide
docker exec learn-control-plane mv /tmp/kube-scheduler.yaml /etc/kubernetes/manifests/
sleep 30; kubectl get pods -l app=nosched -o wide
NAME                       READY   STATUS    NODE
nosched-7d8f9c6b5-2kq8x    0/1     Pending   <none>
nosched-7d8f9c6b5-x7k2p    0/1     Pending   <none>
…（调度器恢复后）
nosched-7d8f9c6b5-2kq8x    1/1     Running   learn-worker
nosched-7d8f9c6b5-x7k2p    1/1     Running   learn-worker2

API Server 和控制器都正常：Deployment、ReplicaSet、Pod 对象都被创建了。只是没有人给 Pod 填写 nodeName，所以停在 Pending，kubelet 也不会认领。调度器回来后，它 watch 到这些未调度的 Pod，立刻处理。这说明每个组件独立工作，通过 API Server 里的对象状态衔接；任何一个暂时缺席，其余部分照常运行，恢复后自动补上。

小结

记住这几点

  1. API Server 处理请求：认证（你是谁）→ 授权（RBAC）→ 准入（变更型，然后校验型 webhook）→ 结构校验 → 写入 etcd。它是唯一直接访问 etcd 的组件。
  2. etcd 是基于 Raft 的强一致键值存储。写入需要多数成员确认：3 个成员容忍 1 个故障，5 个容忍 2 个。etcd 是集群唯一的状态来源，必须备份（第 26 课）。
  3. 组件之间不直接调用，而是通过 API Server 的 watch：订阅某类对象的变化，收到事件后各自行动。
  4. 调度器：为每个未调度的 Pod，先过滤（资源够吗、污点、亲和性），再打分（均衡、镜像已存在…），选最高分节点，写入 spec.nodeName（绑定）。
  5. kube-controller-manager 里运行着几十个控制器：Deployment、ReplicaSet、Node、Endpoint、Job、ServiceAccount、垃圾回收……每个只负责一件事。
  6. kubeadm 集群里，控制平面组件本身是 静态 Pod：kubelet 直接读取 /etc/kubernetes/manifests/ 里的 YAML 运行它们。
